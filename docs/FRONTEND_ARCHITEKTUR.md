## 1. Überblick

Das Team4s-Frontend ist eine Next.js-Anwendung im App Router, die als eigener Container im Docker-Compose-Stack läuft und ausschließlich über eine zentrale API-Schicht mit dem Go-Backend spricht. Die Oberfläche ist komplett deutschsprachig (kein i18n-/Locale-System), es gibt keinen globalen State-Container, keine Server-Komponenten-Emulation und keinen Konsolenmodus — die Anwendung ist eine klassische Browser-/SSR-Hybrid-App für den produktiven Admin- und Mitgliederbetrieb.

| Bereich | Aktuelle Umsetzung |
|---|---|
| Build | Next.js 16 (App Router), TypeScript, ESLint 9 |
| UI-Runtime | React 18.3.1 / react-dom 18.3.1 |
| State | Kein globaler Store; Component-State + fetch, wenige schmale React-Contexts |
| Routing | Next.js App Router, Dateisystem-Routen unter `src/app/` |
| HTTP-Client | Zentraler Client in `src/lib/api/client.ts`, Barrel-Export über `src/lib/api.ts` |
| Auth | Cookie-basierte Browser-Session, Keycloak-Refresh-Orchestrierung zentral im API-Client |
| Styling | CSS-Module pro Komponente + globale Design-Tokens in `src/styles/globals.css` |
| Komponenten-System | Verbindliche globale Primitives unter `src/components/ui` |
| Bilder | `next/image` mit expliziter Pattern-Allowlist, Fallback über `ResponsiveImage` |
| Tests | Vitest 3, Tests laufen im Docker-Container |
| Dev-Port | `3000` (Docker-Compose-Mapping `3000:3000`) |

## 2. Gesamtarchitektur und Datenfluss

```
┌─────────────┐        HTTPS/HTTP        ┌──────────────────────────────┐
│   Browser   │ ───────────────────────▶ │  Next.js App Router (SSR +   │
│  (Client)   │ ◀─────────────────────── │  Client-Komponenten)         │
└─────────────┘                          └──────────────────────────────┘
       │  fetch über src/lib/api.ts                      │
       │  (Cookie-Session, kein Bearer in Komponenten)    │  Proxy-/Stream-Routen
       ▼                                                  │  unter src/app/api/*,
┌──────────────────────────────┐                          │  src/app/covers/*,
│  src/lib/api/client.ts       │                          │  src/app/media/*
│  getApiBaseUrl():            │ ◀────────────────────────┘
│  - Browser → NEXT_PUBLIC_    │
│    API_URL (127.0.0.1:8092)  │
│  - SSR     → API_INTERNAL_   │
│    URL (team4sv30-backend:   │
│    8092)                     │
└──────────────────────────────┘
       │
       ▼
┌──────────────────────────────┐
│  Go-Backend (Gin)             │
│  /api/v1/*, /health, /media   │
└──────────────────────────────┘
```

Typischer Datenfluss für eine Admin-Seite:

1. Der Browser ruft eine App-Router-Route auf (z. B. `/admin/anime/[id]/edit`).
2. Next.js rendert die Server-Komponente zuerst; falls die Seite SSR-Daten benötigt (z. B. `/anime/[id]`, `/watchlist`), liest sie Cookies serverseitig und ruft das Backend über `API_INTERNAL_URL` auf.
3. Im Browser übernehmen Client-Komponenten (`'use client'`) die interaktive Logik und rufen Hilfsfunktionen aus `src/lib/api.ts` auf.
4. `src/lib/api/client.ts` bestimmt die Basis-URL kontextabhängig (`getApiBaseUrl()`), hängt die Session-Cookies/Bearer-Header zentral an und sendet den Request.
5. Für normale JSON-Requests geht der Call entweder direkt an das Backend (Browser → `NEXT_PUBLIC_API_URL`) oder über eine Next.js-Proxy-/Stream-Route (z. B. Episoden-Playback, Segment-Streaming, Cover-Varianten), wenn serverseitige Umformung, Byte-Range-Handling oder Dateisystemzugriff nötig ist.
6. Das Backend antwortet mit JSON oder Binärdaten; der zentrale Client parst Fehlerantworten einheitlich (`parseApiErrorPayload`, `ApiError`) und löst bei Bedarf einen einmaligen Token-Refresh plus Retry aus.
7. UI-Komponenten erhalten nur fertige Daten oder typisierte Fehler und aktualisieren ausschließlich lokalen Komponenten-State oder die wenigen schmalen Contexts.

## 4. Anwendungs-Lebenszyklus

**Start:** `src/app/layout.tsx` ist eine asynchrone Server-Komponente. Sie setzt `lang="de"`, importiert `@/styles/globals.css` genau einmal, lädt serverseitig den Rollenkatalog (`listRoleDefinitions()` für die Kontexte `fansub_group`, `anime_contribution`, `group_history`) und reicht das Ergebnis an `RoleCatalogProvider` weiter. Zusätzlich werden `LocalhostCanonicalRedirect` (Canonical-Host-Redirect) und `AuthSessionSwitchGuard` (Erkennung von Session-/Nutzerwechsel) vor dem eigentlichen Inhalt gerendert, bevor `AppShellClientWrapper` die Client-Navigation und Seiteninhalte übernimmt.

**Request-Ablauf (SSR vs. Browser):** Jede Route entscheidet implizit über `getApiBaseUrl()` in `src/lib/api/client.ts`, welche Backend-Adresse verwendet wird:

- Serverseitig (SSR-Seiten wie `/watchlist`, `/anime/[id]`, Root-Layout) wird `API_INTERNAL_URL` verwendet und über `normalizeInternalApiBaseUrl()` normalisiert — ein veralteter Hostname `backend` wird dabei auf `team4sv30-backend` umgeschrieben, damit Container-interne Aufrufe im Compose-Netzwerk zuverlässig auflösen.
- Im Browser wird `NEXT_PUBLIC_API_URL` (`http://127.0.0.1:8092`) über `getBrowserApiBaseUrl()` aus `src/lib/publicApiUrl.ts` verwendet.

Diese Trennung verhindert, dass Server- und Client-Code denselben internen Docker-Hostnamen verwenden müssen, der im Browser nicht aufgelöst werden könnte.

## 5. Routing & Navigation

Routing folgt vollständig dem Next.js-App-Router-Dateisystem unter `src/app/`. `src/app/admin/layout.tsx` ist bewusst **kein** Permission-Gate — es ergänzt nur die Admin-Hauptnavigation (`AdminMainNav`). Jede Admin-Seite bindet ihr eigenes `PlatformAdminGate` individuell ein.

**Wichtige Hauptrouten:**

| Route | Zweck |
|---|---|
| `/` | Startseite |
| `/anime`, `/anime/[id]` | öffentliche Anime-Übersicht/-Detail |
| `/episodes` | öffentliche Episodenansicht |
| `/fansubs`, `/fansubs/[id]` | öffentliche Fansub-/Gruppenseiten |
| `/members` | öffentliche Mitgliederliste |
| `/suche` | Suche |
| `/watchlist` | Watchlist (SSR-Seitenrenderung mit Cookie-Lesung) |
| `/login` | Keycloak-Login-Einstieg |
| `/invitations`, `/claim-invitations` | Einladungs-Workflow |
| `/me/dashboard` | Mitglieder-Dashboard |
| `/me/profile` | eigenes Profil |
| `/me/contributions` | eigene Beiträge |
| `/me/projects/[animeId]/group/[fansubGroupId]` | Projektarbeitsfläche je Anime/Gruppe |
| `/admin/anime`, `/admin/anime/create`, `/admin/anime/[id]/edit` | Anime-Verwaltung (manuell + Jellyfin-Import) |
| `/admin/anime/[id]/episodes/[episodeId]/edit`, `.../versions`, `.../import` | Episodenverwaltung je Anime |
| `/admin/episode-versions/[versionId]/edit` | zentraler Release-/Episoden-Versions-Editor |
| `/admin/episodes` | Episodenübersicht |
| `/admin/fansubs`, `/admin/fansubs/create`, `/admin/fansubs/[id]/edit`, `/admin/fansubs/[id]/reviews/[reviewId]`, `/admin/fansubs/merge` | Fansub-Verwaltung |
| `/admin/groups` | Gruppenverwaltung |
| `/admin/changes`, `/admin/claims` | Änderungs-/Claim-Verwaltung |
| `/admin/users/[id]` | Nutzerverwaltung |
| `/admin/roles`, `/admin/role-capabilities` | Rollen-/Rechte-Verwaltung |
| `/admin/tags-genres` | Taxonomie-Verwaltung |
| `/admin/profile` | Admin-Eigenprofil |

**Guards/Rechte:** `PlatformAdminGate` (`src/components/auth/PlatformAdminGate.tsx`) ist eine Client-Komponente. Sie liest `useAuthSession()` (`hasAccessToken`, `hasRefreshToken`, `isClientInitialized`) aus `src/lib/useAuthSession.ts`, ruft bei vorhandener Session `getCurrentUser()` auf und zeigt inline einen "Anmeldung erforderlich"- oder Fehlerzustand, solange kein berechtigter Nutzer ermittelt ist. Da jede Admin-Seite ihr eigenes Gate einbindet, gibt es keinen zentralen Middleware-Schutz auf Routenebene — die Autorisierung entsteht konsequent pro Seite plus serverseitiger Backend-Durchsetzung.

**Retired Route:** `/me/releases/[versionId]/workspace` existiert nicht mehr als eigene Arbeitsfläche. `frontend/next.config.mjs` baut über `buildReleaseEditorRedirects()` aus `src/lib/releaseEditorRedirects.mjs` einen permanenten Redirect auf `/admin/episode-versions/:versionId/edit`. Der restliche Mitgliederbereich (`/me/dashboard`, `/me/profile`, `/me/contributions`, `/me/projects/[animeId]/group/[fansubGroupId]`) bleibt vollständig bestehen.

## 6. Zustandsverwaltung

Es gibt keinen globalen Store (kein Redux, kein Zustand, keine vergleichbare Bibliothek). Der Normalfall ist lokaler Komponenten-State kombiniert mit direkten Aufrufen der API-Helfer aus `src/lib/api.ts`. Darüber hinaus existieren einige wenige, bewusst schmal gehaltene React-Contexts:

- `src/providers/RoleCatalogProvider.tsx` — app-weiter Context, wird im Root-Layout um den gesamten Baum gelegt. Er wird serverseitig durch `listRoleDefinitions()` für die Kontexte `fansub_group`, `anime_contribution`, `group_history` vorbefüllt und stellt zusammengeführte Rollenoptionen bereit, ohne dass jede Seite den Katalog erneut laden muss.
- `src/app/admin/anime/hooks/useAnimeContext.ts` plus `components/AnimeContext/` — ein Context, der ausschließlich auf das Anime-Edit-Studio begrenzt ist.
- `src/lib/animeGridContext.ts`, `src/lib/useMemberViewer.ts` — seitengebundene Helfer-Hooks, keine Provider im React-Sinn.

Diese Zurückhaltung ist bewusst: generische UI-States (Lade-/Fehlerzustände) bleiben lokal in der jeweiligen Komponente, fachlicher Cross-Cutting-State bleibt auf die wenigen Fälle begrenzt, in denen mehrere Geschwisterkomponenten denselben Katalog brauchen.

## 7. API- und Datenschicht

`src/lib/api.ts` ist ein schlanker Barrel (34 Zeilen), der ausschließlich re-exportiert — aus `./api/client` sowie aus feature-spezifischen Modulen wie `./api/admin/anime-core`, `./api/admin/anime-jellyfin`, `./api/fansubs-core`, `./api/episodes`, `./api/members`, `./api/releases`, `./api/media`, `./api/auth`, `./api/permissions`, `./api/reviews`, `./api/history`, `./api/search`, `./api/watchlist`, `./api/comments` usw. Die eigentliche Logik liegt in `src/lib/api/client.ts`.

**Zentrale Verantwortung des Clients:** Seit Phase 49 ist `src/lib/api.ts`/`client.ts` der alleinige Eigentümer der normalen Browser-API-Authentifizierung. Fach-Code (Seiten, Komponenten, Hooks) konsumiert ausschließlich tokenfreien Auth-State und zentrale Helfer — er liest, speichert, übergibt oder konstruiert keine Bearer-Token selbst. Konkret verantwortet der Client:

- Auth-Cookies und Laufzeit-Metadaten (Zugriffstoken, Refresh-Token, Anzeigename) über den einzigen Schreib-/Löschpfad `writeBrowserCookie`, der die `Secure`-Eigenschaft protokollabhängig setzt (`https:` → `Secure` auch bei Löschung, lokales `http:` → ohne `Secure`, damit lokale Entwicklung unter `127.0.0.1` funktioniert).
- Keycloak-Refresh-Orchestrierung über `refreshKeycloakToken`, mit genau einem In-Flight-Refresh-Promise, das parallele Requests teilen.
- proaktive Prüfung der Token-Frische vor geschützten Requests sowie zentrale Bearer-Header-Anheftung.
- genau einen Retry für auth-bezogene `401`-Antworten, wenn Retry aktiviert ist.
- Upload-Preflight-Refresh und Bearer-Anheftung für XHR-Uploads (für Fortschritts-Events), z. B. `uploadFansubMedia`, `uploadAdminAnimeMedia`, `uploadAdminReleaseThemeAsset(ForRelease)`, `uploadReleaseVersionMedia`, `uploadSegmentAsset`, `uploadOwnProfileAvatar` — diese nutzen aktuell nur Preflight-Refresh ohne automatischen Replay nach einem Upload-`401`.
- Auth-State-Broadcasts und lokale Session-Bereinigung bei Logout.

UI-Code gated stattdessen nur über `useAuthSession()` (`hasAccessToken`, `hasRefreshToken`, `isClientInitialized`) und behandelt lokale Lade-/Fehler-/Disabled-Zustände selbst. Ein gültiger Refresh-Token allein gilt bereits als aktive Session, da Keycloak-Zugriffstoken kurzlebig sind — der zentrale Client refresht transparent vor dem eigentlichen Request. Verbotene Muster in normalem App-Code sind unter anderem `getRuntimeAuthToken`/`getRuntimeRefreshToken`, direkte Cookie-Namen-Konstanten, `document.cookie`-Zugriffe, `localStorage`/`sessionStorage`-Token-Reads, manuelle `Authorization: Bearer`-Konstruktion und doppelte XHR-Header-Logik; `src/lib/api.no-token-boundary.test.ts` setzt diese Grenze automatisiert durch, mit separaten Allowlists für den zentralen Client selbst, Keycloak-PKCE-Helfer, `/login`, SSR-Seiten und Streaming-Routen.

Keycloak ist ausschließlich für Identität und Token-Lifecycle verantwortlich (Login, OIDC-Token, Session-Ende). Team4s-eigene Domänen-Autorisierung (App-User, globale Rollen, Fansub-Mitgliedschaft, Release-/Medien-Capabilities) kommt ausschließlich vom Backend; das Frontend darf Domänen-Rechte nicht aus Keycloak-Rollen oder JWT-Claims ableiten.

**Basis-URL-Auflösung:** `getApiBaseUrl()` unterscheidet Browser (`NEXT_PUBLIC_API_URL` → `http://127.0.0.1:8092`) und Server (`API_INTERNAL_URL` → `http://team4sv30-backend:8092`, normalisiert über `normalizeInternalApiBaseUrl()`, die den veralteten Hostnamen `backend` korrigiert).

**Proxy- und Stream-Routen unter `src/app/api/`, `src/app/covers/`, `src/app/media/`:**

| Route | Zweck |
|---|---|
| `src/app/api/v1/[...path]/route.ts` | generischer Catch-All-Proxy (`proxyBackendApiRequest`), mit Sonderzweig für `media/files/:filename`-Anzeigevarianten via `serveImageDisplay` |
| `src/app/api/admin/asset-proxy/route.ts` | Admin-Asset-Proxy |
| `src/app/api/admin/upload-cover/route.ts` | Cover-Upload-Proxy |
| `src/app/api/auth/keycloak/logout/route.ts`, `.../token/route.ts` | Keycloak-Auth-Grenzen |
| `src/app/api/episodes/[id]/play/route.ts` | Episoden-Playback-Relay |
| `src/app/api/releases/[id]/stream/route.ts` | Release-Streaming-Relay |
| `src/app/api/segments/[id]/stream/route.ts` | Segment-Streaming-Relay |
| `src/app/covers/[file]/route.ts` | Rohe Cover-Datei (`resolveCoverFilePath`) |
| `src/app/covers/display/[file]/route.ts` | größenangepasste Anzeigevariante über `serveImageDisplay` |
| `src/app/media/[...path]/route.ts` | direkter Dateisystem-Mediaserver (`MEDIA_BASE_PATH`), mit Byte-Range-Unterstützung für Video-Streaming |

Jellyfin- und andere Streaming-Routen gelten explizit als serverseitige Stream-Relay-Grenzen und als öffentliche, auth-freie Fetches klassifiziert, wenn sie keine Auth-Informationen senden — beides bewusst getrennt von der zentralen Browser-Session-Logik.

## 8. Komponenten-Architektur

Die globale UI-Schicht liegt vollständig unter `src/components/ui` und ist laut Projektregel verbindlich: Jede neutextliche, fachlogikfreie UI muss diese Primitives verwenden — ein handgebautes natives `<select>`, `<input>`, `<textarea>` oder `<button>` für einen Fall, den `@/components/ui` bereits abdeckt, ist verboten. Die Primitiv-Definitionen selbst dürfen native Elemente kapseln; das ist die einzige Ausnahme. ESLint (`frontend/eslint.config.mjs`, Regel `no-restricted-syntax`) warnt aktuell bei nativen Ersatzformen und wird nach Migration der Altfälle auf `error` angehoben.

**Grundregel des UI-Systems:** Generische UI wird zentral gebaut, Fachlogik bleibt in Domain-Komponenten. Globale Komponenten dürfen keine Anime-/Fansub-/Release-spezifischen Regeln, keine API-Aufrufe, keine Permission-Checks, keine Keycloak-Logik und keine domänenspezifische Query-/Routing-Logik enthalten. Vor jedem neuen generischen Style gilt die verbindliche Prüfreihenfolge: (1) Gibt es bereits eine globale Komponente? (2) Gibt es eine passende Variante? (3) Reicht eine kleine Erweiterung? (4) Ist der Fall wirklich domänenspezifisch? Nur wenn 1–3 "nein" und 4 "ja" ergeben, darf neuer lokaler Stil für generische Darstellung entstehen.

**Verfügbare Primitives** (`src/components/ui/index.ts`): `Accordion`, `AvatarStack`, `ActionBar`, `AccentRule`, `AdjacentNavigation`, `ActivationStatusIndicator`, `Badge`, `Button`, `Card`, `Cluster`, `ConfirmDialog`, `DatePicker`, `Drawer`, `DisclosureIndicator`, `DisclosureTrigger`, `Divider`, `EmptyState`, `ErrorState`, `FormField`, `FocalCarousel`, `HeroMetrics`, `ArtworkHero`, `Input`, `Label`, `LinkChip`, `LoadingState`, `MediaSlot`, `Modal`, `NavArrow`, `PageHeader`, `Pagination`, `SectionHeader`, `Select`, `SplitLayout`, `Stack`, `Switch`, `Table`, `Tabs`, `Text`, `Textarea`, `ThumbnailStrip`, `Toolbar`, `UploadDropzone`, `UploadFileRow`, `YearPicker`, `SortableList`, `BannerSection`, ergänzt um `ResponsiveImage` (jetzt auch im Barrel exportiert) und das gemeinsame Hilfsmodul `classNames.ts`.

Wichtige Varianten-Entscheidungen: `Button` kennt `primary` (Cobalt-Farbfamilie), `secondary` (Slate), `danger` (Wine), `success` (Petrol), `warning`, `info` sowie die tokenbasierten Merkliste-Zustände `watchlist`/`watchlistActive`, zusätzlich `ghost`/`subtle`/`text`/`floating`, `chipGlass` (durchscheinender Umschalt-Chip auf dunklem Glasgrund, reagiert wie jeder Button auf `aria-pressed` -- globale Form des vormals feature-lokalen FansubGroupPicker-Chips), Größen `sm`/`md`/`lg`, `loading` und `responsiveFullWidth`. `Card` kennt `default`, `elevated`, `interactive`, `compact`, `section`, `flat`, `nested`, `nestedFlat`, die öffentlichen Glas-Varianten `glass`/`glassStrong` sowie `publicSection`, `publicHero`, `publicPoster` und `publicHeroInfo`; diese Varianten halten die öffentliche Anime-Detailoptik samt Glasflächen, asymmetrischen Radien und Unschärfe global. `publicHeroInfo` ist dabei eine EIGENE, zu `glass`/`glassStrong` gegensätzliche Tonalität (oben nahezu opak hell mit dunkler Standard-Textfarbe, nach unten durchscheinend werdend, unterhalb 767px auf eine einheitlich dunkle Fläche kippend) statt einer Komposition mit `cardGlass`. Card bietet zusätzlich eine `padding`-Prop als generischen Override-Hook nach demselben Muster wie `tintHue`/`--card-radius-override`: gesetzt auf `--card-padding-override` und von jeder padding-tragenden Varianten-Regel per `var(--card-padding-override, <bisheriger Wert>)` gelesen, sodass ein Aufrufer die Innenpolsterung EINER Card-Instanz anfordern kann, ohne selbst eine `padding:`-Regel zu schreiben -- ohne Angabe bleibt jede Variante bei ihrer bisherigen Standardpolsterung. Seit Review-Befund 2 nimmt `padding` ausschließlich benannte Zweck-Werte entgegen (`'content'`/`'nestedBlock'`/`'dividedSection'`/`'none'`, über eine eigene `PADDING_PURPOSE_TOKENS`-Tabelle auf gleichnamige `layout.css`-Zweck-Token aufgelöst), nie mehr eine rohe Space-Skalenstufe -- `'content'` deckt eine Card-Instanz ab, deren Variante selbst kaum/kein Padding mitbringt, `'nestedBlock'` einen verschachtelten Inhaltsblock innerhalb einer äußeren Karte, `'dividedSection'` ein neues asymmetrisches (oben/seitlich/unten) Rezept für einen durch eine Trennlinie statt einen Rahmen abgesetzten verschachtelten Abschnitt. Zusätzlich kennt `Card` seither `bleedBelowMd?: boolean` (Rand-bis-Rand-Modus): unterhalb von 767px kollabiert die horizontale Innenabstand-Komponente auf 0 (vertikal unverändert) und `justify-items` wechselt von Cards implizitem Standard `stretch` auf `center`, über eine eigene Modifikatorklasse innerhalb von Cards bestehendem `@media (max-width: 767px)`-Block -- ohne die Prop bleibt jede Variante byte-identisch zum bisherigen Render. Seit der fünften Gap-Closure-Runde (Phase 192, unabhängiger Review Runde 2) kennt `padding` zwei weitere Zweck-Werte: `'section'` (32px, volle Innenabstand-Polsterung eines EIGENSTÄNDIGEN Seitenabschnitts wie des Episoden-Bereich-Rahmens -- größer als `'nestedBlock'`, dessen 16px einen Block INNERHALB einer äußeren Karte polstert) und `'contextCard'` (24px, Innenabstand einer eigenständigen Kontext-/Hinweiskarte wie der Fansub-Gruppenkontext-Karte). `Card` kennt außerdem `widthPurpose?: 'compactPreview'` (setzt `--card-width-override`, gelesen von Cards Basisregel über `var(--card-width-override, auto)`, exakt derselbe Override-Hook-Mechanismus wie `padding` -- `'compactPreview'` begrenzt eine Instanz auf `min(260px, 90vw)` für eine schmale, schwebende Vorschaukarte, benannt nach Funktion statt Aufrufstelle) und `seamless?: boolean` (Modifikatorklasse nach demselben Muster wie `bleedBelowMd`, zeroed Rahmenbreite/Eckenrundung/Hintergrund einer Instanz, die flächenlos/bündig innerhalb einer bereits eigenständig gerahmten äußeren Fläche sitzen soll -- die gewählte Auflösung für eine verschachtelte, randlose Card ohne dass die Aufrufstelle selbst eine `border-radius`-Regel deklarieren muss). Alle vier Fähigkeiten sind rein additiv/opt-in (Zero-Pixel-Diff ohne Angabe) und in dieser Runde bewusst an keiner Aufrufstelle verdrahtet. `MediaFrame variant="posterFade"` ist die gemeinsame Poster-Option mit transparenter Bildmaske und farbiger, unscharfer Fortsetzung, die unterhalb 767px (zu wenig Platz für die seitliche Verlängerung) vollständig abschaltet statt nur zu clippen. `BannerSection variant="anime"` reproduziert die frühere, schwächer kontrastierte Backdrop-Rezeptur der Anime-Detailseite (blur(20px), scale(1.1), ohne brightness/saturate-Abweichung, vertikale Ausblendmaske zum Seitenhintergrund) über eigene Tokens, statt die Standardvariante (stärker abgedunkelt/entsättigt, FansubHeroSection-Rezeptur) zu überschreiben oder zu nutzen. `Breadcrumbs variant="scrim"` stellt dieselbe helle Scrim-Tonalität (meist mit der bestehenden `textHalo`-Prop kombiniert) für Breadcrumbs auf einem Foto-/Bannerhintergrund bereit -- ein Aufrufer setzt dafür nur die Prop, keine eigenen `--breadcrumb-*`-CSS-Variablen von außen. Die Anime-Detailseite (`page.module.css`) spannt Breadcrumbs/Hero/Inhalt über einen eigenständigen `--public-page-detail-max-width`/`-gutter`/`-hero-offset-top`-Breitenvertrag (1200px/48px/120px, styles/tokens/layout.css) auf -- bewusst GETRENNT vom gemeinsamen `--public-page-max-width`/`-gutter` der übrigen öffentlichen Fansub-Flächen (Mitglieder, Fansub-Gruppen, Suche), damit beide unabhängig voneinander angepasst werden können, ohne die jeweils andere Seite zu verschieben. Grundsatz: öffentliche, durchscheinende/dunkle Flächen sind KEIN Admin-Abweichler, der angeglichen werden muss, sondern eine zweite, gleichberechtigte, tokenbasierte Erscheinung derselben Bausteine. `Text` setzt keinen Browser-Absatzabstand; vertikale Abstände gehören in das Layout über Tokens. `AdjacentNavigation` ist der globale Standard für fachliche Vorher/Nachher-Navigation einschließlich der Anime-Randnavigation; deren Vorschau bleibt ein zusammengesetzter Fachbaustein. Aus der sechsten Gap-Closure-Runde (Phase 192, unabhängiger Review Runde 2) stammen drei weitere, bewusst unverdrahtete Grundbaustein-Fähigkeiten: `Avatar` kennt neben den drei bisherigen Größenstufen zusätzlich `size="xs"` (20px, `--avatar-size-xs`) sowie einen optionalen `bordered`-Modifikator (Rand "auf dunkler Fläche", derselbe `--border-on-media`-Ton wie `Divider`/Cards Glas-Varianten) -- beide decken das wiederkehrende Muster eines kleinen, runden/eingerahmten Gruppen- oder Identitätsbilds ab. `chipGlass` setzt seither einen eigenen `--button-gap: var(--space-1)` (4px statt der 10px-Standardlücke) -- ein kleines Inline-Logo neben einer kurzen Chip-Beschriftung braucht einen engeren Abstand als eine gepolsterte primäre Aktion; der Wert entspricht exakt dem bisher lokal in `FansubGroupPicker.module.css` gesetzten Chip-Abstand.

`Stack`, `Cluster` und `SplitLayout` sind drei token-only Layout-Grundbausteine (Befund 23): `Stack` ordnet Kinder vertikal, `Cluster` horizontal mit Umbruch, beide ausschließlich über einen `gap`-Prop, der auf `var(--space-N)` abbildet — keiner der beiden setzt Fläche, Farbe oder Rundung. `SplitLayout` ist der generische Zwei-Spalten-Grundbaustein (feste/automatische erste Spalte + flexible Restspalte) mit einem eigenen, container-basierten Haltepunkt-Kollaps (`container: split-layout` / `inline-size`, Breakpoint `md`/`lg`), der demselben Muster folgt wie `ArtworkHero`s bestehender Container-Query-Kollaps — bewusst KEINE Viewport-Medienabfrage, damit der Baustein unabhängig von seiner Platzierung auf der Seite funktioniert. Daraus ergibt sich die verbindliche "Seiten vs. Bausteine"-Regel (Befund 22): Eine Seiten-Datei (`page.module.css` und ihre Geschwister wie `page.episodes.module.css`) darf ausschließlich die Seiten-Breite, den Außenabstand (Gutter) und den Abstand zwischen Abschnitten deklarieren. Jedes `grid-template-columns`/`grid-template-rows`, jeder Farbwert, jeder `border-radius`/Schatten und jedes innere Komponenten-Padding/-Gap gehört stattdessen in das eigene `.module.css` des besitzenden zusammengesetzten Bausteins (z. B. `AnimeDetailHero.module.css`) — eine Seite ordnet Bausteine nur an, sie kennt deren inneres Raster oder deren Optik nicht. Für `/anime/[id]` erzwingt `detailStyleSystem.guard.test.ts` diese Grenze dauerhaft per Musterabgleich über die Seiten-CSS-Dateien. Dieselbe Grenze gilt seit Befund B (Phase 192, Runde 3) auch INNERHALB eines zusammengesetzten Bausteins selbst: dessen eigenes `.module.css` darf Positionierung/Größe/Sichtbarkeit und inhaltsspezifisches CSS deklarieren, aber kein eigenes `display:flex`/`grid-template`/rohes `gap`/`padding`/`margin`, wo bereits ein Grundbaustein (`Stack`/`Cluster`/`Card`s `padding`-Prop/`Divider`) genau diesen Zweck abdeckt — ein zusammengesetzter Baustein ordnet seine eigenen Kind-Elemente über dieselben Grundbausteine an, die auch einer Seite zur Verfügung stehen, statt das Raster lokal nachzubauen. `compositeLayoutPurity.guard.test.ts` erzwingt dies dauerhaft für die vier Pilot-Dateien dieser Phase (`AnimeDetailHero.module.css`, `ReleasePreviewRow.module.css`, `EpisodeGlassCard.module.css`, `AnimeEdgeNavigation.module.css`) über einen zeilenweisen Selektor-Scan mit explizit benannter, pro Selektor begründeter Ausnahmeliste — eng begrenzte, nicht generalisierbare Einzelfälle bleiben dokumentiert lokal (z. B. eine haltepunktabhängige Zeile-zu-Spalte-Umkehr, die weder `Cluster` noch `SplitLayout` ausdrücken können, oder ein bewusst uneinheitlicher vertikaler Abstands-Rhythmus zwischen Geschwister-Elementen, dessen Zero-Pixel-Diff-Erhalt eine einzige neue Stack-Zweck-Variante pro Lücke erfordert hätte), statt stillschweigend als "Sonderfall" unentdeckt zu bleiben. "Zweck statt Größe" (Befund 24): `Stack`/`Cluster`s `gap`-Prop und `SplitLayout`s `firstColumnWidth`-Prop nehmen seit dieser Phase ausschließlich benannte Zweck-Werte entgegen (z. B. `gap="section"`/`gap="badgeRow"`, `firstColumnWidth="poster"`), niemals eine rohe Space-Skalenstufe ("gap=2") oder einen freien CSS-Längen-String ("firstColumnWidth='200px'") — jeder Zweck-Wert verweist über ein eigenes, dokumentiertes Zweck-Token in `styles/tokens/layout.css` auf die unveränderte `--space-N`-/`--media-frame-poster-width*`-Grundskala, exakt wie jeder andere Design-Token dieses Projekts purpose- statt größenbenannt ist. `gapPurposeNaming.guard.test.ts` erzwingt dies dauerhaft für die bereits umgestellten Aufrufstellen. `Stack`s `gap`-Prop akzeptiert seit Review-Befund 1 (Phase 192, vierte Gap-Closure-Runde) zusätzlich ein Array von Zweck-Werten für einen bewusst nicht-einheitlichen Kind-zu-Kind-Abstandsrhythmus (ein Eintrag pro Lücke zwischen zwei aufeinanderfolgenden Kindern -- bei einem einzelnen Zweck-Wert, dem überwiegenden Regelfall, bleibt das bisherige, einheitliche `gap`-Verhalten über das native CSS unverändert); dazu kommt der neue Zweck `'captionLines'` (`--space-caption-lines`, 4px) für eine enge Zwei-Zeilen-Bildunterschrift wie Titel+Typ der Randnavigations-Vorschaukarte. Ebenfalls seit Review-Befund 1 kennt `Cluster` zwei weitere, rein additive Zusatzfähigkeiten nach demselben container-query-basierten Zweistufen-Muster wie `SplitLayout`: `collapseBelow="md"`/`gapCollapsed` kippt `Cluster` unterhalb von 48rem/768px von einer horizontalen Zeile auf eine gestapelte Spalte mit einem eigenen Lücken-Zweck für den gestapelten Zustand (Fallback auf `gap`, falls `gapCollapsed` fehlt) -- löst die bisherige lokale Zeile-zu-Spalte-Umkehr in `AnimeDetailHero.module.css`s `.titleRow` und `ReleasePreviewRow.module.css`s `.row` ab. `float="controlBand"` macht `Cluster` oberhalb von 768px zu einem präzise auf dem Rand seines positionierten Vorfahren schwebenden `position:absolute`-Band (`pointer-events:none` auf dem Wurzelelement, `pointer-events:auto` auf dessen direktem Kind, von dort per CSS-Vererbung an jeden tatsächlichen Inhalts-Nachfahren weitergereicht) und unterhalb davon zu einer normalen, im Textfluss liegenden Zeile -- löst die vormalige lokale `.edgeNavigationOverlay`-Regel in `AnimeDetailHero.module.css` vollständig ab (Plan 192-25). WICHTIG: anders als `collapseBelow` triggert `float`s Positionierung bewusst über eine normale `@media`-Abfrage statt `@container` -- eine Container-Abfrage darf laut Spezifikation nie das eigene Container-Wurzelelement selbst umordnen, nur dessen Nachfahren; ein `position:absolute` nur auf dem inneren, nachfahren-gebundenen Flex-Kind würde das äußere Wurzelelement selbst aber als normales, nur 0px hohes Element im Textfluss zurücklassen, das in einem umgebenden Flex-/Grid-Kontext mit eigenem `gap` (z. B. ein `Stack`, der diesen `Cluster` neben weiterem Inhalt rendert) trotzdem einen vollen `gap`-Abstand erzeugen würde (CSS-Gap wirkt unabhängig von der tatsächlichen Höhe eines teilnehmenden Elements) -- erst wenn das Wurzelelement selbst `position:absolute` trägt, fällt es vollständig aus dem Flex-/Grid-Layout des Elternelements heraus. Beide Fähigkeiten sind ohne die jeweilige Prop byte-identisch zum bisherigen, einzelnen `Cluster`-Element (Zero-Pixel-Diff für jeden bestehenden Aufrufer). `AnimeDetailHero.tsx` wrappt seit Plan 192-25 `SplitLayout` und den optionalen `edgeNavigation`-Slot (`<Cluster float="controlBand">`) gemeinsam in einen äußeren `<Stack gap="contentToControlBand">` (16px) -- dieser Abstand wirkt NUR sichtbar, solange die Steuerelement-Reihe unterhalb ihres Haltepunkts normal im Textfluss liegt (oberhalb davon nimmt das schwebende Wurzelelement am Stack-Abstand gar nicht erst teil, siehe oben). `AnimeDetailHero.module.css`s vormals bespoker Info-Karten-Rhythmus (`.infoCardBody`/`.titleRow`/`.badges`/`.description`/`.tagsSection`/`.statsRow`/`.relatedSection`) ist seither vollständig über `Stack`s Rhythmus-Array-Modus und fünf live gegen die vormalige CSS vermessene Zweck-Werte abgebildet: `'headingToBadges'` (16px, Titelzeile vor Badges), `'primaryContentBlocks'` (24px, deutlicher Blockwechsel zwischen Badges/Beschreibung/Tags), `'dividedSectionLeadIn'` (24px Desktop/16px Mobil, responsiv über eine `@media`-Überschreibung des zugrunde liegenden Zweck-Tokens in `layout.css`, Vorlauf vor dem "Verwandte Anime"-Abschnitt), `'dividerToContent'` (16px, Abstand nach einer eingefügten Trennlinie bis zum folgenden Inhalt) und `'none'` (Literalwert 0, für den Fall, dass das nächste Kind seinen Abstand bereits selbst mitbringt, z. B. `AnimeInfoBanner`s eigene führende Trennlinie). Die vormaligen `border-top`-Trennlinien von `.statsRow`/`.relatedSection` sind dabei durch echte `Divider`-Elemente ersetzt (`spacing="none"`, siehe unten), deren Vorlauf/Nachlauf je ein eigener Lücken-Eintrag im Array ist.

Globale Komponenten bleiben varianten-begrenzt: Ist ein neuer Fall mit einer vorhandenen Variante lösbar, wird keine neue Variante ergänzt; ergibt ein Fall nur für ein einzelnes Fachfeature Sinn, gehört er nicht unter `src/components/ui`. Lokale Styles bleiben erlaubt für fachliche Speziallayouts, komplexe Domain-Grids, einmalige Sonderfälle und hochspezifische Editor-/Media-/Story-Kompositionen — sie sind aber nicht mehr die erste Wahl für Standard-Buttons, -Cards, -Badges, -FormFields, -Header oder -EmptyStates.

**Showcase/Referenz:** Storybook (`frontend/.storybook/main.ts`, Start über den `team4sv30-storybook`-Compose-Service, Port 6006) ist die verbindliche visuelle Referenz, gegliedert in vier Kategorien: `Grundlagen/*` zeigt die Rohdaten des Design-Systems selbst (2 Stories: `Design-Tokens`, liest alle CSS-Custom-Properties automatisch aus `globals.css` aus; `Effekte`, ein hand-kuratierter Katalog der fünf Blur-/Glas-/Scrim-Rezepturen aus `styles/tokens/effects.css`, siehe "Effekte" in Abschnitt 10). `Grundbausteine/*` zeigt jedes eigenständige Primitiv (29 Stories) mit voller Zustandsabdeckung (Standard/disabled/Fehler/Laden/leer/lange Inhalte/Fokus, soweit zutreffend) — ein Grundbaustein importiert intern keine andere `components/ui`-Komponente. Dazu gehören seit der UAT-Nachbesserungsrunde zwei neue Typografie-Grundbausteine: `Heading` (Props `level`/`size` als zwei getrennte, optionale Werte — `level` bestimmt das semantische Tag h1-h4, `size` die davon unabhängige visuelle Größenstufe, Standard = `level`) und `Text` (Prop `variant`: `body`/`soft`/`meta`/`small`, jeweils per `var(--text-*-size/-color, Fallback)` vom Aufrufer überschreibbar, zusätzlich `tone="error"` für kontrastgeprüften Fehlertext). `Label` (neuer Grundbaustein) ist die gemeinsame Feldbeschriftung mit optionaler Pflicht-Markierung (sichtbares `*` plus separater, nur für Screenreader vorhandener Hinweistext) -- von `FormField` intern genutzt, zusätzlich eigenständig für Fälle ohne `FormField` verfügbar. `DisclosureTrigger` (vollbreite aufklappbare Kopfzeile, Grundlage für `Accordion`) ist seit dieser Runde ebenfalls hier katalogisiert statt unter „Zusammengesetzte Bausteine" -- sein Import von `DisclosureIndicator` ist nur das interne Öffner-Symbol, kein sichtbar komponierter Baustein-Verbund. `LinkChip` (neuer Grundbaustein) ist ein Link in Chip-Form (`href`/`children`/optional `icon`/`count`) mit zwei Tönen (`tone="glass"`/`"scrim"`) für unterschiedlich durchscheinende Hintergründe, ohne Import einer anderen katalogisierten `components/ui`-Komponente. `Divider` (neuer Grundbaustein) ist eine neutrale, themenfarbene horizontale Trennlinie für Inhalte auf einer bereits dunklen/durchscheinenden Fläche -- Props `tone` (`'onMedia'`/`'onMediaStrong'`, liest die bestehenden `--border-on-media(-strong)`-Tokens) und `spacing` (`'withinMetaBlock'`/`'betweenSections'`/`'none'`, benannte Zweck-Abstände statt roher Space-Stufen -- `'none'` setzt keinen Eigen-Abstand, für den Fall, dass ein umgebender Rhythmus-Mechanismus wie `Stack`s Rhythmus-Array-Modus den vollständigen Vorlauf/Nachlauf bereits selbst trägt) decken beide Eigenschaften vollständig ab, sodass ein Aufrufer keine eigene `<hr>`+`background`/`margin`-CSS mehr braucht. Bewusst KEINE `AccentRule`-Variante: `AccentRule` ist fest auf die Wein-/Markenakzentfarbe (`--ui-line`) gebunden (andere Zweck-/Farbfamilie), `Divider` trennt neutral auf Medienflächen. Eine automatische Katalogprüfung (`frontend/src/components/ui/catalogTaxonomy.test.ts`) liest alle `Grundbausteine/*`-Stories per `fs` und lässt den zugehörigen Testfall fehlschlagen, sobald eine Komponente stillschweigend eine andere, selbst katalogisierte Komponente importiert — Ausnahmen (aktuell `Button`/`IconButton` → `Spinner`, `Avatar`/`Label` → `VisuallyHidden`, `DisclosureTrigger` → `DisclosureIndicator`, jeweils als reines internes Implementierungsdetail) müssen in der Testdatei begründet dokumentiert sein. `Zusammengesetzte Bausteine/*` (26 Stories, u. a. FormField, Modal, Drawer, EmptyState, ErrorState, LoadingState, ConfirmDialog, NavArrow, Accordion, FocalCarousel, ThumbnailStrip, UploadFileRow, UploadDropzone, MediaSlot, Pagination, HeroMetrics, ActivationStatusIndicator, ArtworkHero, AvatarStack, DatePicker, YearPicker, SectionHeader/PageHeader, `BannerSection` (Bannerbild-Hintergrund + WCAG-AA-Scrim + Komposition-Slot, z. Drei weitere Zusammengesetzte-Bausteine-Stories leben unter `frontend/src/components/fansubs/` statt `components/ui/` (domänennahe, aber dennoch sichtbar komponierte Bausteine): `Fansub-Kopfzeile` (`FansubHeroSection`, besteht aus Badge, ResponsiveImage, MetricList), `EpisodenKarte` (`EpisodeGlassCard`, besteht aus Card variant="glass" + Tönungs-Hook, DisclosureTrigger, Text) und `Release-Versionszeile` (`ReleasePreviewRow`, besteht aus Card variant="glassStrong", Avatar, Text, Button).

`npm run build-storybook` UND `npm run test-storybook` (Render-Smoke-Test über `@storybook/test-runner`, prüft jede Story auf tatsächliche Render-Fehler im Browser, nicht nur auf Compile-Erfolg) sind beide Teil der Quality-Gate-Prüfung.

Wiederverwendbare interne Bausteine (nicht aus `index.ts` exportiert, da kein eigenständiges Primitiv): `DialogHeader` (`frontend/src/components/ui/DialogHeader.tsx`) ist die gemeinsame Titelzeile für `Modal` und `Drawer` (Titel/Beschreibung links, Schließen-`IconButton` rechts) — vor einem neuen, eigenen Dialog-Header-Markup prüfen, ob `DialogHeader` wiederverwendbar ist. `useOverlaySurface` (`frontend/src/components/ui/useOverlaySurface.ts`) ist der gemeinsame Fokus-/Escape-/Tab-Zyklus-/Portal-Kern für modale Overlay-Flächen (genutzt von `Modal` und `Drawer`) — vor einem neuen, eigenen Dialog-/Overlay-Verhalten (Fokusführung, Escape-Handling, Body-Portal) immer zuerst prüfen, ob dieser Hook wiederverwendbar ist. `Spinner` (rotierender Lade-Kreisel, sm/md/lg) und `StatusIcon` (tonaler Icon-Kreis, neutral/info/success/warning/danger) sind Grundbausteine für Lade- und Status-Zustände — vor einer neuen, lokalen Lade-Animation oder Icon-Tönung immer zuerst `Spinner`/`StatusIcon` prüfen. `IconButton` (Icon-only-Button mit Pflicht-`aria-label`, eigene `forwardRef`-Implementierung) ist der globale Standard für Icon-only-Schaltflächen wie Schließen-Kreuze.

## 10. Theming & Styling

Design-Tokens sind als CSS Custom Properties definiert und werden genau einmal im Root-Layout über `src/styles/globals.css` importiert. `globals.css` selbst enthält (wegen der 450-Zeilen-Regel) nur noch `@import`-Anweisungen auf fachlich aufgeteilte Token-Dateien unter `src/styles/tokens/` (`palette.css` Grundfarben/Markenpaletten, `layout.css` Radien/Abstände/Steuerelement-Höhen/Breiten, `typography.css` Schriftgrößen/-gewichte, `colors.css` semantische Oberflächen-/Text-/Schatten-/Fokus-Tokens, `fields.css` Feld-/Dialog-/Picker-Stil, `components.css` komponentenspezifische Tokens wie `--card-*`/`--icon-button-*`/`--button-*`, `effects.css` Blur-/backdrop-filter-/color-mix-/Scrim-Transparenz-Rezepturen (siehe "Effekte" weiter unten), `roleCatalog.css` die Rollen-Katalog-Farbnaht) plus `src/styles/base.css` für den Element-Reset — `@import` fügt alle Deklarationen weiterhin in DIESELBE `:root`-Kaskade ein, an der Auflösung von `var(...)` über Dateigrenzen hinweg ändert sich nichts. `src/lib/cssCustomProperties.ts` (mit begleitendem `.guard.test.ts`) bindet JavaScript-Zugriffe an dieselben CSS-Variablen, um Drift zwischen Token-Quelle und Code zu verhindern. `src/components/ui/foreignVariableOverrides.regression.test.ts` prüft zusätzlich generisch über alle `components/ui/*.module.css`-Dateien, dass keine Datei die private Override-Variable eines anderen Bausteins setzt und dass keine Datei feste px-/rem-Größen, Hex-Farben oder rgba-Literale statt eines globalen Tokens enthält (Ausnahmen: `0`, `1px`-Haarlinien, Prozentwerte, `@media`/`@container`-Bedingungen).

Komponentenspezifisches Styling liegt pervasiv in colokierten `*.module.css`-Dateien neben der jeweiligen Komponente — dies ist der Normalfall für fachliche Speziallayouts, während Standardelemente (Buttons, Cards, Badges, FormFields, Header, EmptyStates) über die globalen Primitives aus Abschnitt 8 abgedeckt werden, statt erneut lokal gebaut zu werden.

Responsive Layout folgt einem Container-first-Ansatz: Wiederverwendbare/eingebettete Komponenten (Cards, Stages, Carousels) reagieren über `container-type: inline-size` auf ihren verfügbaren Inline-Raum statt auf Viewport-Breakpoints; nur ganze Seiten/App-Shells nutzen Viewport-Media-Queries. Breakpoints werden nach Layoutzweck benannt, nicht nach Geräteklassen (`phone`/`tablet`/`desktop` sind zu vermeiden).

**Effekte:** Blur-/`backdrop-filter`-/`color-mix()`-/Scrim-Transparenz-Rezepturen sind Zweck-Tokens wie Abstand/Radius (Befund 26) und leben in `src/styles/tokens/effects.css`, eingesetzt ausschließlich innerhalb von `components/ui/*.module.css` als benannte Variante -- ein zusammengesetzter Baustein oder eine Seite schreibt niemals selbst ein rohes `filter`/`backdrop-filter`/`color-mix`/`rgba` direkt. Aktuell fünf Rezepturen: `--banner-backdrop-*` (unscharfer Bannerbild-Hintergrund, `BannerSection`), `--linkchip-glass-*` (Glas-Fläche auf hellem Bildhintergrund, `LinkChip` tone="glass"), `--linkchip-scrim-*` (Abdunklung unter Chip-Text auf Bild, `LinkChip` tone="scrim"), `--button-chip-glass-*` (Glas-Knopf auf Bildfläche, `Button` variant="chipGlass") und `--badge-onmedia-*` (Abzeichen auf Bildfläche, `Badge` variant="onMedia"). Die Storybook-Seite "Grundlagen/Effekte" (`EffectsShowcase`) zeigt jede Rezeptur live über einem echten Bild anhand des tatsächlich konsumierenden Grundbausteins; `effectTokenPurity.guard.test.ts` erzwingt das automatisiert -- bewusst nur für die acht von dieser Phase bereits umgestellten zusammengesetzten Baustein-Dateien (`AnimeDetailHero.module.css`, `ReleasePreviewRow.module.css`, `FansubGroupPicker.module.css`, `FansubVersionBrowser.module.css`, `AnimeEdgeNavigation.module.css`, `Stack.module.css`, `Cluster.module.css`, `SplitLayout.module.css`), nicht repo-weit -- die ca. 941 bestehenden, von dieser Phase unberührten Rohliterale im übrigen Frontend sind explizit künftige Arbeit.

## 11. Bilder

`next.config.mjs` konfiguriert `images.formats: ['image/webp']` sowie explizite `deviceSizes`/`imageSizes`/`qualities: [75, 85]`. Die erlaubten `localPatterns`/`remotePatterns` stammen aus dem gemeinsamen Datenmodul `src/lib/images/publicImagePatterns.mjs` — der Single Source of Truth für erlaubte Bild-Pfade (u. a. `/covers/**`, `/media/anime/**`, `/media/profile/**`, `/media/release-version/**`, `/media/fansub/**`; bewusst **kein** blanker `/media/**`-Wildcard, damit z. B. `/media/admin/**` niemals über den öffentlichen Bild-Endpunkt optimiert/ausgeliefert werden kann). Das Modul ist deliberately framework-/runtime-neutral (keine Node-Builtins), damit es sowohl von `next.config.mjs` (direkt durch Node geladen) als auch von Client-Komponenten importiert werden kann.

`src/components/ui/ResponsiveImage.tsx` kapselt `next/image` und validiert `src` vorab gegen dasselbe Pattern-Modul (`isConfiguredForImageOptimization`), um den SSR-Crash von Next bei nicht migrierten Pfaden zu vermeiden — bei Nichtübereinstimmung fällt die Komponente auf unoptimiertes Rendering zurück, statt die ganze Seite abstürzen zu lassen. Seit der sechsten Gap-Closure-Runde (Phase 192, unabhängiger Review Runde 2) kennt `ResponsiveImage` zusätzlich eine optionale `roundedThumbnail`-Prop, die das Bild wie ein kleines, randloses Vorschau-/Miniaturbild rundet und zuschneidet (`border-radius: var(--radius-sm); object-fit: cover;`) -- ein Aufrufer muss dafür keine eigene `border-radius`-Regel mehr deklarieren; ohne Angabe bleibt das Bild Zero-Pixel-Diff unverändert.

**Upload:** `src/components/ui/MediaSlot.tsx` ist der gemeinsame Upload-Slot für ein einzelnes Bild/Video, gesteuert über Seitenverhältnis und Form, aufgebaut auf `UploadDropzone.tsx`. Die Medienvorschau wird über die `media`-Prop (`{ kind: 'image' | 'video', src, ... }`) beschrieben und von MediaSlot selbst über `ResponsiveImage`/`<video>` gerendert -- kein Aufrufer baut mehr seine eigene img-/next-image-/video-Vorschau. `UploadDropzone.tsx` selbst nutzt mit gesetztem `aspectRatio`-Prop den `MediaFrame`-Grundbaustein als eigenes Fundament (statt MediaSlot diese Fläche separat außen herum zu wrappen) und komponiert den Leer-Zustand aus `StatusIcon`/`Heading`/`Text`. Beide werden für Fansub-Logo/-Banner, das Anime-Asset-Board und Profil-Avatar/-Hintergrund wiederverwendet. `src/hooks/useUploadQueue.ts` kapselt die Warteschlangen-Logik für Multi-File-Upload-Flows, etwa in Media-Review-/Upload-Panels.

**Galerie-/Viewer-Hilfslogik** liegt als reine Helfer-Module vor (keine eigenständigen Komponenten): `src/lib/mediaViewerZoom.ts`, `mediaViewerNavigation.ts`, `mediaViewerMetadata.ts`, `mediaViewerCaptionPanel.ts`.

## Anhang: zentrale Entwurfsmuster

1. **Kein globaler Store:** Fachlicher State lebt in Komponenten oder in wenigen schmalen Contexts (`RoleCatalogProvider`, `useAnimeContext`); es gibt bewusst kein Redux/Zustand-Äquivalent.
2. **Zentraler API-Client als Auth-Grenze:** Nur `src/lib/api/client.ts` darf Token lesen, refreshen oder anhängen; UI-Code gated ausschließlich über `useAuthSession()`.
3. **Kontextabhängige Basis-URL:** `getApiBaseUrl()` unterscheidet SSR (`API_INTERNAL_URL`) und Browser (`NEXT_PUBLIC_API_URL`), inklusive Hostnamen-Normalisierung für das Docker-Compose-Netzwerk.
4. **Manuelle Kontrolle vor Automatik:** Jeder Jellyfin-Import mündet in ein editierbares Formular, nie in eine automatische, ungeprüfte Übernahme in die Datenbank.
5. **Globales UI-System vor lokalem Stil:** Neue generische UI muss zuerst gegen vorhandene `@/components/ui`-Primitives und deren Varianten geprüft werden, bevor lokaler Stil entsteht.
6. **Fachlogikfreie Primitives:** Komponenten unter `src/components/ui` kennen keine Anime-/Fansub-/Release-Regeln, keine API-Calls und keine Permission-Checks — diese Verantwortung bleibt in Domain-Komponenten.
7. **Pro-Seite-Gates statt zentraler Middleware:** `PlatformAdminGate` wird individuell in jede Admin-Seite eingebettet; `admin/layout.tsx` liefert nur Navigation, keinen Schutz.
8. **Single Source of Truth für Bild-Pfade:** `publicImagePatterns.mjs` wird sowohl von `next.config.mjs` als auch von `ResponsiveImage` konsumiert, damit Konfiguration und Laufzeitprüfung nie auseinanderlaufen.
9. **Modularität durch Colocation:** Komplexe Editor-Flächen (z. B. der Episoden-Versions-Editor) werden in viele kleine, eng benannte Dateien mit colokierten Hooks/Tests/Styles aufgeteilt, statt in einer monolithischen Datei zu wachsen.
10. **Permanente Redirects statt Codeverzweigung bei Routen-Rückzug:** Der Rückzug von `/me/releases/[versionId]/workspace` erfolgt als deklarativer `next.config.mjs`-Redirect in einem eigenen, framework-neutralen Modul — nicht als bedingte Logik in der Zielseite.
