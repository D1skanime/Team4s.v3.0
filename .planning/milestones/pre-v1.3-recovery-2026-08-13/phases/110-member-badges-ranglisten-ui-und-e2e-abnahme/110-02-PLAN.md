<objective>
Thread `total_points` end-to-end through the public member profile projection (D-02's data
layer) and extend the existing `loadPublicBadges` read to append live-computed,
never-persisted role-entry badges (D-03's data layer). This is the one part of Phase 110 with
real architectural risk (per 110-RESEARCH.md): the existing `member_badges` table is a
persisted-upsert store (Phase 68's badge engine), and D-03's "disappears the instant the point
is reversed" requirement is incompatible with that pattern — so this plan deliberately adds a
computed UNION at read time and never calls the persisted-write path for these 8 badges.

Purpose: give Plan 110-03 (frontend display) a stable, already-correct backend contract to
render against — no frontend logic should ever need to compute eligibility itself.
Output: `total_points` on `PublicMemberProfileData` (OpenAPI + Go), and role-entry badges
appearing/disappearing live in `PublicBadges`, both proven by a new Postgres-backed test file.
</objective>
