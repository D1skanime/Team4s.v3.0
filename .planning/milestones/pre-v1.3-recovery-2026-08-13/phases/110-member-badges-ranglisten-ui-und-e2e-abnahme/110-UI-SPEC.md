> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — this project does **not** use shadcn. `components.json` is absent by design. |
| Preset | not applicable |
| Component library | In-house global UI primitive library `@/components/ui` (Button, Card, Table, Pagination, Badge, PageHeader, SectionHeader, HeroMetrics, EmptyState, ErrorState, Modal, …) — see `/dev/ui-system` showcase route |
| Icon library | `lucide-react` |
| Font | `Inter` via `var(--font-sans)` (globals.css) |

**Locked project constraint (CLAUDE.md, non-negotiable):** every user-facing surface built in Phase 110 MUST use `@/components/ui` primitives. No hand-built `<select>`/`<input>`/`<textarea>`/`<button>` or bespoke markup for a type the library already provides. Local-file-consistency ("the file next to it does X") never overrides this rule. The gsd-ui-checker gates on this.

Since no shadcn preset exists and the CLAUDE.md-mandated design system is the existing in-house library, the shadcn initialization gate is intentionally skipped for this phase — introducing shadcn now would contradict the locked project convention. Registry safety gate: **not applicable**.

## Component Inventory & Reuse Contract (binding for planner/executor)

This phase adds **zero** new primitive components. Everything is composed from existing `@/components/ui` + existing profile/fansub components:

### 1. `/members/ranking` (new public route)
- Page shell: same `page.module.css` pattern as `/fansubs/[slug]` and `/members/[slug]` — `width: min(var(--public-page-max-width), calc(100% - var(--public-page-gutter)))`.
- Header: `PageHeader` (eyebrow "Community", title "Rangliste").
- List: `Table` / `TableHead` / `TableBody` / `TableRow` / `TableHeaderCell` / `TableCell` from `@/components/ui`. Columns: **Rang** (#, 1-based row position), **Name** (linked or plain per rule above), **Punkte** (right-aligned, bold).
- Pagination: reuse `@/components/ui` `Pagination` (NOT the domain-specific `@/components/anime/Pagination` variant) — page-number navigation matching `getMemberPointRanking(page)` contract.
- Empty state: `EmptyState` component with copy above, when `data.length === 0` on page 1.
- Error state: `ErrorState` component (optionally via `getErrorStateCopy`) when the fetch fails.
- Data source: existing `getMemberPointRanking(page?)` / `MemberPointRankingRow` from `frontend/src/lib/api.ts` (Phase 109) — no new endpoint, no new DTO.
- Row link rule ties directly to `MemberPointRankingRow.slug`: `slug !== null` → `<Link href={`/members/${slug}`}>`; `slug === null` → plain `<span>`.

### 2. Member-Profil-Hero — Punktzahl (D-02)
- Extend `MemberProfileHero.tsx` (public-view branch only) with `HeroMetrics` from `@/components/ui`, reusing the exact pattern already established in `FansubHeroSection.tsx` / `ReleaseDetailHero.tsx`:
  `<HeroMetrics items={[{ label: 'Punkte', value: totalPoints }]} ariaLabel="Mitglied-Punktzahl" />`
- Placement: inside `styles.heroCopy`, directly below the name/status row (`heroTitleRow`), above the bio paragraph — a single metric, no rank, no breakdown (per D-02, ranking placement deferred).
- No display for `isPublicView === false` (own-profile edit view) unless later explicitly requested — this phase only adds the number to the **public** profile hero (`isPublicView` branch), consistent with D-02 discussing the public-facing profile.

### 3. Rollen-Einstiegs-Badges (D-03) — extend the existing catalog, do not invent new UI
Add exactly these 8 entries to `MEMBER_BADGE_PRESENTATIONS` and `PUBLIC_MEMBER_BADGE_CATALOG` in `frontend/src/components/profile/memberBadgeLabels.ts`. Display remains 100% inside the existing `MemberBadgeChain` component/section ("Auszeichnungen") — no new section, no `MemberBadgeHighlights` row (explicitly declined by user).

| Role code | `badge_code` | Label | Icon (`lucide-react`) | `variant` | `palette` | `badge_category` |
|---|---|---|---|---|---|---|
| `translator` | `role_entry_translator` | Erste Übersetzung | `Languages` | `info` | `indigo` | `role_entry` |
| `timer` | `role_entry_timer` | Erstes Timing | `Clock3` | `info` | `indigo` | `role_entry` |
| `encoder` | `role_entry_encoder` | Erster Encode | `Cpu` | `info` | `indigo` | `role_entry` |
| `typesetter` | `role_entry_typesetter` | Erstes Typesetting | `Type` | `info` | `indigo` | `role_entry` |
| `quality_checker` | `role_entry_quality_checker` | Erste Qualitätsprüfung | `ShieldCheck` | `info` | `indigo` | `role_entry` |
| `project_lead` | `role_entry_project_lead` | Erste Dokumentation als Projektleitung | `ClipboardList` | `info` | `indigo` | `role_entry` |
| `editor` | `role_entry_editor` | Erstes Editing | `Scissors` | `info` | `indigo` | `role_entry` |
| `raw_provider` | `role_entry_raw_provider` | Erste Raw-Bereitstellung | `HardDrive` | `info` | `indigo` | `role_entry` |

- **Icons are placeholders** per D-03 ("Badge-Bilder/Artwork liefert der Nutzer später") — Lucide icons only, no custom artwork/image assets in this phase. Swapping icons for real artwork later must not require logic changes (the catalog/presentation map is already the single swap point).
- **No hardcoded role list at the derivation layer**: any role not covered by the static catalog above automatically renders through the *existing* generic fallback in `getMemberBadgePresentation()` (Sparkles icon, `mint` palette, raw `badge_code` as label) — this fallback already exists in `memberBadgeLabels.ts` and needs no new code. This satisfies D-03's "gilt automatisch für jede punktfähige Rolle" without the frontend needing a dynamic role registry.
- **Live-Projektion (badge can disappear)**: the badge presence is fully derived from backend state (`≥1 netto Punkt` in that role) each time the profile is fetched — the frontend must not cache/memoize earned-badge membership beyond the current page load. No new frontend logic needed; `earnedBadges` is passed in fresh from the profile API response exactly like today.
- Ordering in the chain: role-entry badges append after the existing catalog array order (`founding_member` → … → `verified` → the 8 new entries), matching the existing `catalogWithEarnedBadges()` append behavior — no manual reordering required.

## Interaction / State Contract

| Surface | Loading | Empty | Error | Success |
|---------|---------|-------|-------|---------|
| `/members/ranking` | Standard SSR fetch (like `/fansubs/[slug]`, `/members/[slug]`) — no client spinner needed if server-rendered; if a client-paginated variant is chosen, use `LoadingState` from `@/components/ui` | `EmptyState` (copy above) | `ErrorState` (copy above) | `Table` with rows, `Pagination` below |
| Hero point count | N/A (rendered synchronously with the rest of the hero) | If `total_points === 0`, still render `HeroMetrics` with value `0` — do not hide the metric (a member legitimately having 0 points is a valid, honest state) | N/A (fails silently with the rest of the profile fetch — no separate error UI for this one field) | Number rendered as-is, no `+`/`-` sign, no thousands separator needed at current scale (values are small integers) |
