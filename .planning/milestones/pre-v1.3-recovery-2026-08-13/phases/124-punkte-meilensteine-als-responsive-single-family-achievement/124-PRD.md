# GSD Phase 124 – Punkte-Meilensteine als responsive Single-Family Achievement Stage

## Ausgangslage

Phase 121 hat die Rollen-Badge-Sektion abgeschlossen und ein stabiles responsives Badge-Layout etabliert.

Phase 123 hat anschließend die Sektion **Anime-Projekte** erfolgreich aus dem künstlichen Ein-Karten-Carousel herausgelöst und als responsive Single-Family Achievement Stage umgesetzt.

Die Sektion **Punkte-Meilensteine** besitzt dieselbe grundsätzliche fachliche Struktur wie Anime-Projekte:

- genau eine Achievement-Familie
- mehrere lineare Stufen
- aktueller Wert
- aktuelle Stufe
- nächste Stufe
- Fortschritt
- bereits verdiente frühere Stufen
- gesperrte zukünftige Stufen

Der entscheidende Unterschied:

Die Punkte-Meilensteine sind **visueller Typ B**.

Die sechs Stufen besitzen eine verwandte medaillenartige Grundform, aber deutlich unterschiedliche Motive, Figuren und Kompositionen.

Deshalb soll Phase 124 die in Phase 123 etablierte Stage-Grundlage wiederverwenden, aber für eine **visuell stärkere sechs-stufige Thumbnail-/Meilenstein-Navigation** erweitern.

---

# 1. Ziel von Phase 124

Die Punkte-Meilenstein-Sektion soll künftig:

- kein äußeres `FocalCarousel` mehr verwenden
- als eigenständige responsive Achievement Stage dargestellt werden
- auf Desktop die vorhandene Wide-/Visual-Breite sinnvoll nutzen
- auf Mobile vertikal gestapelt funktionieren
- das aktuelle beziehungsweise ausgewählte Punkte-Badge groß als Hero zeigen
- den tatsächlichen Punktewert prominent darstellen
- Fortschritt bis zur nächsten Stufe visualisieren
- alle sechs Punkte-Stufen sichtbar und verständlich darstellen
- frühere verdiente Stufen als Vorschau auswählbar lassen
- zukünftige gesperrte Stufen weiterhin nicht auswählbar machen
- bestehende Punkteberechnung und Schwellen unverändert übernehmen

Diese Phase betrifft ausschließlich **Punkte-Meilensteine**.

# 3. Besonderheit der Punkte-Familie

Die Punkte-Meilensteine werden aktuell nicht als sechs persistierte `member_badges` geliefert.

Die Profilseite leitet aus:

```text
total_points
```

die höchste erreichte Punkte-Stufe ab.

Die Collection-/Familienlogik rekonstruiert daraus anschließend die vollständige sechsstufige Familie.

Diese bestehende zentrale Ableitung muss erhalten bleiben.

Nicht:

* dieselbe Punkte-Threshold-Logik nochmals in einer neuen Stage duplizieren
* SSR und Client unterschiedlich berechnen
* neue persistierte Punkte-Badges erzeugen

Die Stage ist eine reine Präsentationsschicht auf der bestehenden Punkteableitung.

---

# 4. Kein äußeres Carousel mehr

Die Punkte-Meilenstein-Sektion soll künftig nicht mehr durch `FocalCarousel` laufen.

Entfernen aus diesem Badge-Pfad:

* äußeren Carousel-Wrapper
* Quiet-Carousel-Konfiguration
* Ein-Karten-Carousel-Semantik
* äußere Carousel-Pfeile
* Carousel-Zähler
* äußeres Swipe/Drag
* Carousel-Skeleton für diesen Single-Family-Pfad

`FocalCarousel` selbst bleibt unverändert.

Weiterhin relevante Consumer:

* Rollen
* Beiträge
* `FansubProjectsGrid`

# 5. Phase-123-Stage als Grundlage verwenden

Die in Phase 123 etablierte Achievement-Stage für Anime-Projekte soll als technische und visuelle Grundlage dienen.

Nicht eine zweite komplett unabhängige Stage bauen, wenn die bestehende Stage sinnvoll wiederverwendet werden kann.

Wiederverwendbare Prinzipien:

* Wide-Desktop-Komposition
* Hero links / Informationen rechts
* Track über die Breite darunter
* gestapelte Mobile-Darstellung
* stabiler Artwork-Slot
* sichtbare Progressbar
* Prozentwert
* separates nächstes Ziel
* Status „Aktuell“ / „Vorschau“
* keine äußere Carousel-Engine
* gleiche DOM-/Datenstruktur für Desktop und Mobile

Aber:

Die Punktefamilie benötigt einen stärker visuellen Track als Anime-Projekte.

# 8. Visueller Typ B berücksichtigen

Die sechs Punkte-Artworks besitzen verwandte Medaillenformen, aber unterschiedliche Motive.

Das bedeutet:

Ein rein textlicher Rank-Track wie bei Rollen wäre nicht ausreichend.

Die Benutzer sollen die unterschiedlichen Auszeichnungen visuell erkennen können.

Daher:

* echte kleine Artwork-Thumbnails
* Hero zeigt aktuelle oder ausgewählte Stufe
* Thumbnail-Track zeigt alle sechs Stufen
* Unterschiede zwischen den Motiven bleiben sichtbar

Keine sechs großen Karten.

Keine zweite Hero-Galerie.

# 10. Artwork-Geometrie

Aus Phase 121 und 123 wurde gelernt, dass Badge-Geometrie ausdrücklich geprüft werden muss.

Für alle sechs Punkte-Artworks:

* stabiler quadratischer Hero-Slot
* korrektes Seitenverhältnis
* `object-fit: contain`
* keine Verzerrung
* keine unkontrollierte Ovalisierung
* keine Hintergrundflächen, die außerhalb einer vorgesehenen Badge-Silhouette sichtbar werden
* keine unterschiedlich gestreckten Hero-Slots

Die Punkte-Artworks sind eigenständige vollständige PNGs.

Keine Layer-Komposition erfinden, wenn sie nicht bereits existiert.

# 11. Hero-Darstellung

Hero zeigt standardmäßig die tatsächliche aktuelle Punkte-Stufe.

Beispiel:

```text
Stark engagiert
734 Punkte
```

Wenn eine frühere verdiente Stufe gewählt wird:

```text
Erfahrungsstufe
Vorschau

734 Punkte aktuell
```

Wichtig:

Der tatsächliche Punktewert darf durch eine Vorschau nicht verändert erscheinen.

Die Vorschau betrifft ausschließlich:

* Hero-Artwork
* Stufenname
* Präsentationsstatus

Nicht:

* echten Punktewert
* echten Progress
* nächste tatsächliche Schwelle

---

# 12. Vorschau-Semantik

Bestehendes Verhalten beibehalten:

* aktuelle Stufe aktiv
* frühere verdiente Stufen auswählbar
* zukünftige gesperrte Stufen sichtbar, aber nicht auswählbar
* lokale Auswahl wird nicht persistiert
* Datenänderung setzt Vorschau sinnvoll zurück

Status klar unterscheiden:

```text
Aktuell
```

vs.

```text
Vorschau
```

Keine zukünftige Vorschau gesperrter Stufen in Phase 124 neu einführen.

---

# 13. Thumbnail-Track

Der Punkte-Track enthält genau sechs Stationen.

Jede Station zeigt:

* kleines Badge-Artwork
* kurze Stufenbezeichnung oder sinnvolle Kurzform
* Schwellenwert
* Status

Zustände:

* erreicht
* aktuell
* ausgewählt
* gesperrt

Die visuelle Sprache muss diese Zustände klar unterscheiden.

Nicht nur Farbe verwenden.

Beispielsweise:

* Current-Ring
* Check/Statusmarker
* reduzierte Opazität bei locked
* `aria-current`
* Vorschau-Markierung

---

# 14. Desktop-Track

Auf breiten Displays sollen alle sechs Stufen möglichst vollständig sichtbar sein.

Beispiel:

```text
[Erste] [Aktiv] [Erfahrung] [Engagiert] [Veteran] [Legende]
   1       50       200         500        1000       2500
```

Die Thumbnails dürfen nicht so groß werden, dass sie mit dem Hero konkurrieren.

Der Track bleibt visuell eine sekundäre Navigation.

# 15. Mobile-Track

Bei 390 px ist eine horizontale Scrollfläche für sechs Stufen akzeptabel.

Aber:

Nicht die alte `FamilyCollectionCard`-Scrollkomplexität 1:1 zurückbringen.

Bevorzugt:

* native horizontale Overflow-Leiste
* CSS Snap nur wenn tatsächlich hilfreich
* semantische Buttons für verdiente auswählbare Stufen
* locked Elemente nicht interaktiv
* kein Momentum-Code
* kein eigener 140/160-ms-Settle
* keine Wheel-Sonderlogik auf Mobile
* kein ResizeObserver nur zum künstlichen Zentrieren, sofern CSS reicht

Wenn die aktuelle Stufe bei Initialrender sinnvoll ins Sichtfeld gebracht werden muss, dies möglichst einfach und robust lösen.

# Leitprinzip Phase 124

Die Punkte-Meilensteine sollen nicht wie sechs separate Hauptkarten wirken.

Sie sind eine gemeinsame Achievement-Reise:

**ein aktueller Hero, echter Punktefortschritt und sechs visuell erkennbare Meilensteine innerhalb einer einzigen responsiven Stage.**

```
```
