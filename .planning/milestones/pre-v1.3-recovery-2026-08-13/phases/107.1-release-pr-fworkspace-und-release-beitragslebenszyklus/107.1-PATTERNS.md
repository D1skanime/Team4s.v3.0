## Pattern Assignments

### Lifecycle migration and repositories

**Analogs:** `database/migrations/0064_release_version_notes.up.sql`, `0059_release_version_media_schema.up.sql`, `0132_member_point_foundation_review_hardening.up.sql`; `backend/internal/repository/release_version_notes_repository.go`; `backend/internal/repository/release_version_media_repository.go`.

Preserve source ownership. Lifecycle rows are one-to-one metadata keyed to `release_version_notes.id` or `release_version_media.id`; they must not copy note bodies, media paths, or binaries. Media identity is the relation ID, not `media_assets.id`.

**Repository model convention** (`release_version_notes_repository.go:13-35`):

```go

    ID               int64
    ReleaseVersionID int64
    FansubGroupID    *int64
    MemberID         int64
    BodyHTML         string
    BodyJSON         []byte
    Visibility       string
    Status           string
    CreatedByUserID  *int64
    CreatedAt        time.Time
    UpdatedAt        *time.Time
}
```

**Canonical release-version media write inside caller transaction** (`release_version_media_repository.go:97-122`):

```go
func (r *MediaRepository) CreateReleaseVersionMediaAsset(
    ctx context.Context,
    tx pgx.Tx,
    input ReleaseVersionMediaCreateInput,
) (int64, error) {
    var id int64
    err := tx.QueryRow(ctx, `
        INSERT INTO release_version_media
            (release_version_id, fansub_group_id, media_asset_id, category, caption, sort_order,
             is_preview_candidate, uploaded_by_user_id, created_at)
        VALUES ($1, $2, $3, $4, $5, $6, $7, (SELECT id FROM users WHERE id = $8), NOW())
        RETURNING id
    `, input.ReleaseVersionID, input.FansubGroupID, input.MediaAssetID, input.Category,
       input.Caption, input.SortOrder, input.IsPreviewCandidate, uploadedByUserID).Scan(&id)
    if err != nil {
        return 0, fmt.Errorf("create release_version_media: %w", err)
    }
    return id, nil
}
```

Apply the caller-owned transaction pattern to lifecycle creation/update. Submission must set private/pending server-side, increment the same source’s revision on edit/resubmit, and update explicit `last_activity_at`. Do not accept visibility/review status from submitter DTOs.

The queue repository should use a read-only `UNION ALL` projection over the two source-specific lifecycle tables, with full-tuple seek order:

```sql
WHERE fansub_group_id = $1
  AND review_state = $2
  AND ($3::timestamptz IS NULL OR
       (submitted_at, source_type, source_id) > ($3, $4, $5))
ORDER BY submitted_at ASC, source_type ASC, source_id ASC
LIMIT $6 + 1
```

Use the same capability/group predicates for rows, counters, detail, history, and next-item. Cap the requested page size at 50.

### Source adapters and atomic decision service

**Analog:** the actual Phase-107 adapter/ReviewService interfaces after the dependency gate. Existing repositories supply source persistence only.

The adapter must expose stable source key, revision, fansub group, release version, submitter App-User, canonical beneficiary Member, type/category, and conditional mutation through the caller’s `DBTX`. Confirmation/rejection must be conditional on source ID + expected revision + pending state.

Do not copy the current `contribution_review_handler.go:132-151` split transaction/audit behavior: it mutates through the repository and writes audit afterward. Phase 107.1 instead calls one Phase-107 application service transaction containing first-decision arbitration, source mutation/publication, contribution point, optional reviewer credit, audit/reason, and commit. All failures roll back; the losing concurrent decision maps to the stable Phase-107 conflict.

           COALESCE(mf_orig.path, ''), COALESCE(mf_thumb.path, ''), rvm.deleted_at
    FROM release_version_media rvm
    LEFT JOIN media_files mf_orig

## Shared Patterns

### Domain ownership

- Notes remain in `release_version_notes`.
- Process images remain in `release_version_media` → `media_assets` → `media_files`, addressed through a real `release_version_id`.
- Lifecycle metadata may be additive one-to-one rows; it must not become a parallel content/media table.
- Never substitute `release_media`, attach process media to episodes, or mutate a shared asset merely because one relation is approved/rejected.

### Transaction and concurrency

- Phase-107 `ReviewService` is the only decision arbiter.
- One caller-owned transaction contains decision uniqueness, expected-revision source mutation, publication/rejection, points, audit/reason.
- Stable conflict is returned for zero affected rows/duplicate first decision.
- UI never optimistically publishes, removes a row before server success, or retries a conflict.

### Authorization and privacy

- Use Phase-107 typed image/text capabilities, group equality, target context, and App-User plus Member self-review checks.
- Apply the same scope to list, counts, detail, next-item, history, and error behavior.
- Review permission does not grant release-edit permission.
- Views are not audited; mutations are.

### Validation and German copy

- Validate typed filters, bounded search/cursor/limit, exact media categories, rejection category, and 10–1000 non-whitespace reasons.
- All user-facing German strings use correct umlauts.
- Use semantic controls and global UI primitives; no new UI library or local generic controls.
