## User Constraints (from CONTEXT.md)

### Locked Decisions

### Einreichung und Eigentum
- **D-01:** Beim Speichern eines Release-Texts beziehungsweise Hochladen/Speichern eines Release-Bilds setzt der Server den Beitrag automatisch privat auf `in_pruefung`. Der Einreicher wählt weder Review- noch Veröffentlichungsstatus.
- **D-02:** Release-Medien bleiben ausschließlich über einen realen `release_version_id` an `release_version_media`, `media_assets` und `media_files` gebunden. `release_media` ist kein Ersatz; es entsteht kein paralleler Upload- oder Medienpfad.
- **D-03:** Die vier bestehenden Bildkategorien bleiben erhalten: `screenshot`, `typesetting_karaoke`, `fun_outtake`, `other`. Eine gemeinsame Capability „Bilder prüfen“ deckt alle vier ab; Kategorie ist Filter- und Punkteaufschlüsselungsmerkmal.
- **D-04:** Einreicher sehen Status und Ablehnungsinformationen ihrer eigenen Einreichungen auf der kanonischen Release-Version-Editseite. Fremde offene Einreichungen sehen nur passende Reviewer.

### Gruppen-Prüfqueue
- **D-05:** Die Queue liegt im kanonischen Gruppen-Workspace unter `/admin/fansubs/[groupId]/edit?tab=pruefungen`. Der alte Query-Wert `vorschlaege` wird kompatibel auf `pruefungen` weitergeleitet.
- **D-06:** Die Queue ist eine kompakte, abarbeitbare Liste statt Karten oder Drawer. Filter: Projekt/Anime, Episode/Release, Typ, Bildkategorie, Suche sowie Offen/Verlauf. Standard ist gruppenweit chronologisch „älteste zuerst“.
- **D-07:** Texte, Bilder und Mitwirkungen erhalten getrennte Typzähler. Bilder besitzen zusätzlich Kategorie-Filter und -Zähler. Es gibt keine Bulk-Bestätigung.
- **D-08:** Die Liste lädt cursorbasiert/incrementell und hält nicht tausende Einträge gleichzeitig im DOM. Sticky Tabellenkopf und klar begrenzte Lade-/Fehlerzustände verwenden vorhandene globale UI-Primitives.
- **D-09:** Die Prüfoberfläche ist bewusst nur für Tablet und Desktop. Auf Smartphones erscheint eine verständliche Meldung, dass Prüfungen eine größere Arbeitsfläche benötigen.

### Read-only Prüfdetail
- **D-10:** „Öffnen“ führt zu `/admin/fansubs/[groupId]/reviews/[reviewId]`. Die Seite zeigt exakt den gewählten Beitrag samt Release-, Einreicher-, Typ-/Kategorie- und Zeitkontext.
- **D-11:** Texte verwenden den bestehenden `RichTextRenderer`; Bilder verwenden vorhandene Media-URLs und die vorhandene Originalansicht. Es gibt dort keinen Editor, keinen Status-/Visibility-Selector und keinen zweiten Upload-Flow.
- **D-12:** Reviewer erhalten durch die Review-Route nur Zugriff auf das konkrete Prüfobjekt, nicht automatisch breite Leserechte für alle Release-Editdaten. Ein Link zur Release-Editseite erscheint nur bei bereits vorhandener echter Edit-Berechtigung.
- **D-13:** Nach erfolgreicher Entscheidung bietet die Seite „Nächste offene Prüfung“ und „Zurück zur Prüfliste“. Die UI zeigt keinen sichtbaren „Punkteempfänger“; das ist eine serverseitige Zuordnung.

### Entscheidung und Lebenszyklus
- **D-14:** Bestätigung, Veröffentlichung, Beitragspunkt, optional zulässiger Review-Credit, Audit und Entfernen aus der offenen Queue committen atomar. Bei Fehler bleibt der Beitrag privat/offen und es entsteht kein Teilzustand.
- **D-15:** Ablehnung verlangt strukturierte Kategorie plus Pflichtfreitext. Der Beitrag bleibt privat und für seinen Einreicher bearbeitbar; Bearbeitung und Neueinreichung verwenden dieselbe Beitrags-ID.
- **D-16:** Eine erfolgreiche Entscheidung verschwindet sofort aus „Offen“, senkt den Typzähler und erscheint nur noch im Verlauf. Parallel entscheidende Verlierer sehen den stabilen Phase-107-Konflikt.
- **D-17:** Jede zustandsändernde Aktion wird auditiert; reine Ansichten/Öffnen werden nicht protokolliert. Plattform-Admin-Override zeigt Pflichtwarnung und -grund, erzeugt aber keinen Admin-Review-Credit.

### Cleanup
- **D-18:** Die Retention beginnt bei der letzten Aktivität; Bearbeitung oder Neueinreichung setzt sie zurück. Produktion: 90 Tage. Lokale Testumgebung: 5 Stunden. Automatisierte Tests verwenden kontrollierte Zeit.
- **D-19:** Der Tombstone behält nur strukturierte IDs, Typ/Kategorie, Beteiligte, Zeitpunkte und Statusfolge. Textinhalt, freier Ablehnungs-/Override-Grund und Mediendatei werden entfernt.
- **D-20:** Physische Mediendateien werden erst gelöscht, wenn keine andere Referenz mehr existiert, und nur über kontrollierte Storage-/Pfad-Seams. Fehler erzeugen einen persistenten, idempotent wiederholbaren Nachlauf; Tombstone und logischer Cleanup dürfen trotzdem abgeschlossen werden.

### the agent's Discretion

## Summary

Phase 107.1 sollte als **zwei konkrete Source-Adapter plus eine gemeinsame Release-Review-Read-Projection** geplant werden. `release_version_notes` und `release_version_media` bleiben die Content-Autoritäten; Phase 107 bleibt alleiniger Arbiter für Capability, erste Entscheidung, Audit und Review-Credit. Ein Adapter muss Source-Key, Revision, Gruppe, Einreicher-App-User, Punkteempfänger-Member und die transaktionale Domainmutation liefern. Es darf keine universelle Beitragstabelle geben, welche Text oder Media dupliziert. [VERIFIED: CONTEXT D-01..D-20; Phase-107 `107-RESEARCH.md`/`107-SOURCE-AUDIT.md`]

Das aktuelle Modell benötigt dennoch neue **Lifecycle-Metadaten**: Notes haben heute nur `visibility/status`; Media-Reviewstatus liegt auf dem geteilten `media_assets`-Datensatz. Für Same-ID-Resubmit, Revision, Ablehnungszustand, Last-Activity und Tombstone darf der Plan diese Metadaten nicht in freie JSON-Payloads oder auf möglicherweise mehrfach referenzierte Assets pressen. Verwende source-spezifische, FK-gebundene Lifecycle-Zeilen (eine pro `release_version_notes.id` beziehungsweise `release_version_media.id`) und eine polymorphe read-only Queue-Projektion darüber. Content und Ownership verbleiben in den bestehenden Tabellen. [VERIFIED: migrations 0059/0064/0097/0130 and repositories; locked D-02/D-15/D-19]

Die größte Planabhängigkeit ist Phase 107: Im aktuellen Worktree existieren dessen Implementierungsdateien noch nicht, sondern nur Pläne/Research. Phase 107.1 darf deshalb erst nach grünem Phase-107-Fundament implementiert werden; jeder Plan muss die tatsächlich entstandenen `review_service`, Decision-/Audit-/Credit-Repositories, Capability-Actions und Migration lesen, statt Dateinamen blind aus dem Research zu übernehmen. [VERIFIED: code grep 2026-07-23]

**Primary recommendation:** Erst Phase-107-Foundation-Gate, dann additive Lifecycle-Migration + Adapter-/Transaktionstests, anschließend Contracts/Handler/Queue/Detail, danach bestehende Submitter-Seams und Cleanup verdrahten. [VERIFIED: dependency and atomicity boundary]

## Architecture Patterns

### System Architecture Diagram

```text
Existing release-version editor
  ├─ save note ───────┐
  └─ existing upload ─┴─> Source-specific submit adapter (server-owned private/in_pruefung)
                               │ same stable source ID + incremented revision
                               v
                       Lifecycle metadata + existing content tables
                               │
        group-scoped filters -> Queue projection -> cursor page -> Tablet/Desktop table
                               │ selected review ID
                               v
                   Narrow authorized detail projection
                       ├─ note -> RichTextRenderer
                       └─ media -> existing URLs/original view
                               │ confirm/reject
                               v
                     Phase-107 ReviewService (one DB Tx)
                       ├─ first-decision arbiter
                       ├─ adapter conditional publish/reject
                       ├─ PointService contribution/review credits
                       ├─ immutable structured audit + scrub-capable reason
                       └─ commit -> open queue/history projection changes

Rejected + inactive past retention
  -> logical scrub/tombstone committed
  -> if media unreferenced: persistent physical-delete job
  -> controlled storage seam -> success OR idempotent retry
```

### Pattern 1: Thin source adapters, content stays canonical

Use distinct `release_note` and `release_media` adapters registered with Phase-107 core. Their source keys should be deterministic from the stable row ID, and their revision comes from lifecycle metadata. Submission/update/resubmit mutates the same source row and increments revision/last activity. [VERIFIED: D-02/D-15 and Phase-107 adapter contract]

### Pattern 2: Lifecycle metadata beside, not instead of, content

Add source-specific 1:1 lifecycle records keyed by the existing note/relation ID. Store review revision/state, submitter snapshot/beneficiary anchor, submitted/last-activity/decided timestamps, structured rejection category, and links needed for Phase-107 decisions. Do not copy body HTML/JSON, captions, paths, or binaries into them. [VERIFIED: D-15/D-19; current schemas]

This is especially important for media: `media_assets.review_status_id` belongs to an asset that may have other references, whereas this phase reviews the `release_version_media` relation in one release-version/group context. Publication may synchronize asset visibility/status only after a reference-scope audit proves it safe; otherwise lifecycle authority stays relation-scoped and the public projection must require the approved relation state. [VERIFIED: current schema and D-02; this is a planner gate, not permission to guess]

### Pattern 3: Stable seek pagination

Use `ORDER BY submitted_at ASC, source_type ASC, source_id ASC`, overfetch `limit+1`, encode the complete tuple in an opaque cursor, and apply a matching tuple seek predicate. All group/filter/search predicates must precede the cursor; counters come from the same visibility/capability scope. Filter changes reset pages; client request identity includes group/view/filters/search/cursor, aborts/ignores stale responses, and deduplicates by review ID. [VERIFIED: UI-SPEC and existing cursor helpers]

### Pattern 4: Atomic decision through the Phase-107 transaction

The HTTP handler must not patch content and then call review logic. It resolves actor/request, validates typed input, and calls one application service. That service opens one Tx, loads the adapter source, authorizes the matching capability/group, inserts the first-decision arbiter, conditionally changes lifecycle/content at expected revision, awards contribution/review points through `PointService.*InTx`, writes audit/reason, and commits. Any error rolls everything back. [VERIFIED: D-14/D-16; Phase-107 research]

### Pattern 5: Logical cleanup and physical cleanup are separate state machines

At controlled `now`, select rejected sources with `last_activity_at < cutoff` using a claimable/locked batch. In Tx, scrub note content or detach the media relation, delete free reason text through the Phase-107 scrub seam, and retain only structured tombstone fields. For media, enqueue a unique persistent physical-delete job only after reference counting. Job processing rechecks references and canonical path, records attempts/errors, and is idempotent. [VERIFIED: D-18..D-20; existing cleanup/storage seams]

## Common Pitfalls

### Pitfall 1: Building atop planned, not implemented, Phase 107
**What goes wrong:** adapters invent signatures/errors/actions that diverge from the final core.  
**How to avoid:** make Phase-107 green artifacts an explicit plan prerequisite and update `read_first` to actual files. [VERIFIED: current code grep]

### Pitfall 2: Reviewing shared asset state instead of release relation state
**What goes wrong:** publishing/rejecting one relation changes another reference unexpectedly.  
**How to avoid:** lifecycle identity is `release_version_media.id`; audit `media_asset` sharing before status synchronization and always reference-check cleanup. [VERIFIED: schema/D-02/D-20]

### Pitfall 3: Revision changes without new Phase-107 target revision
**What goes wrong:** old decisions conflict with valid resubmission or a stale review decides edited content.  
**How to avoid:** increment revision atomically on edit/resubmit, create the next open source revision, and detail/decision requests carry expected revision. [VERIFIED: D-15/D-16 and Phase-107 key]

### Pitfall 4: Queue leakage through counts, search, next-item, or errors
**What goes wrong:** unauthorized reviewers infer foreign submissions.  
**How to avoid:** apply identical typed capability/group predicates to list, counters, detail, history and next-item; wrong-group IDs return the established scoped not-found/forbidden shape without context. [VERIFIED: D-04/D-12/UI-SPEC]

### Pitfall 5: Cleanup clock tied to `updated_at` or wall-clock sleeps
**What goes wrong:** unrelated edits reset retention or tests flake for five hours.  
**How to avoid:** explicit lifecycle `last_activity_at`; injectable clock/cutoff and controlled PostgreSQL timestamps. [VERIFIED: D-18]

### Pitfall 6: Logical cleanup blocks forever on storage failure
**What goes wrong:** rejected personal content/reason survives because disk is unavailable.  
**How to avoid:** commit scrub/tombstone and persistent retry job separately; never put a filesystem operation inside the DB Tx. [VERIFIED: D-20]

### Pitfall 7: Stale client requests resurrect decided rows
**What goes wrong:** a slow filter/page response appends an already decided item or wrong working set.  
**How to avoid:** full request key, abort/sequence guard, stable-ID dedupe, authoritative response/refetch and non-negative counters. [VERIFIED: UI-SPEC]

### Pitfall 8: Access-token-only UI gate
**What goes wrong:** valid refresh-session user flashes logged out/forbidden and review fails before central refresh.  
**How to avoid:** explicitly test absent/expired access token + valid refresh token for list, detail, decision and upload/save. [VERIFIED: AGENTS/auth contract]

```go
    tag, err := tx.Exec(ctx, `
        UPDATE release_note_review_lifecycle
        SET review_state = 'confirmed', decided_at = $4
        WHERE release_version_note_id = $1
          AND revision = $2
          AND review_state = 'pending'
          AND fansub_group_id = $3`,
        source.ID, source.Revision, source.FansubGroupID, a.clock.Now())
    if err != nil { return err }
    if tag.RowsAffected() != 1 { return services.ErrReviewConflict }

    _, err = tx.Exec(ctx, `
        UPDATE release_version_notes
        SET visibility='public', status='published', updated_at=$2
        WHERE id=$1`, source.ID, a.clock.Now())
    return err
}
```

   - Inspection found `ReleaseVersionMediaGallery.tsx` and `ReleaseVersionMediaDetailPanel.tsx`, but both carry edit-page interaction/mutation concerns (`onPatch`, preview selection, hover/edit state) and are unsafe to import into the narrow review route. It renders the existing responsive image/original-anchor behavior (`target="_blank"` plus safe `rel`) and no upload, patch, editor, review-state, or release-edit capability. This is the smallest domain-owned read-only seam permitted by D-11/D-12.
