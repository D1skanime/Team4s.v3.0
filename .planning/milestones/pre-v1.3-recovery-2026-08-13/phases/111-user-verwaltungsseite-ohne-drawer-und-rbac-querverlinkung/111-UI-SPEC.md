# Phase 111 — UI Design Contract

> Visual and interaction contract for `/admin/users` (drawer removal + progressive detail page) and the RBAC cross-links to `/admin/role-capabilities`. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase is a **structural rework of an existing admin surface**, not a new visual identity. No new colors, type sizes, or spacing tokens are introduced. Every value below is pulled from the already-established design system (`frontend/src/styles/globals.css`, `frontend/src/components/ui/`) and is repeated here so the contract is self-contained and prescriptive for planner/executor.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — project-owned custom design system (no shadcn/`components.json`) |
| Preset | not applicable |
| Component library | Custom internal primitives at `@/components/ui` (mandatory per `CLAUDE.md`) — not Radix/Base UI |

| Font | `Inter` (`--font-sans`, `frontend/src/styles/globals.css:2`) |

No handgebautes `<select>/<input>/<textarea>/<button>` and — specific to this phase — **no handgebaute `role="tablist"`/`role="tab"` markup** (this is exactly the violation D-02 removes from `UserDetailContent.tsx:60-85`).

## Primary Visual Anchor (per screen)

Each screen needs one unambiguous focal point the eye lands on first. This is prescriptive, not optional — the executor must not invent a competing anchor (e.g. a large hero image or an oversized action button).

| Screen | Primary visual anchor |
|--------|------------------------|
| `/admin/users` (list) | Der Fokuspunkt ist die erste Tabellenspalte „Benutzer" (Avatar-Initialen-Kreis + fettes `display_name`) der jeweils obersten sichtbaren Zeile — die Filterleiste bleibt bewusst zurückhaltend, damit die Nutzerliste selbst der erste Blickfang ist. |
| `/admin/users/[id]` (detail page) | Der Fokuspunkt ist die `PageHeader`-Titelzeile mit `display_name` direkt neben dem Status-`Badge` (aktiv/ausstehend/deaktiviert) aus der stets offenen „Übersicht"-Sektion — Name und Kontostatus sind zusammen das Erste, was der Blick erfasst, noch vor den darunterliegenden Accordion-Sektionen. |
| `/admin/role-capabilities` | Der Fokuspunkt ist der neue „N-mal vergeben"-Impact-Count-`Badge` der aktuell ausgewählten Rolle in der `RoleMasterList` bzw. im `RoleCapabilityDetail`-Panel — er verankert visuell die neue RBAC-Querverlinkung und sticht farblich (Akzentfarbe) gegenüber der neutralen Rollen- und Aktionsliste hervor. |

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.5 |
| Label / meta | 13px | 700 | 1.4 |
| Heading (Section/Card/Accordion title) | 16px | 700 | 1.3 |
| Display (page title via `PageHeader`) | clamp(32px, 3vw, 44px) — existing `.pageTitle` token, unchanged | 700 | 1.15 |

Rule for this phase's new markup: only `400` and `700` weights are used. Do not introduce `600`/`800`/`900` in newly authored JSX for this phase, even though older tab files use them — those files are reused as-is (out of scope to restyle), but any *new* section/link/badge label this phase adds uses 400/700 only.

## RBAC Cross-Link Contract (D-04, D-05)

### User → Rolle ("Was darf diese Rolle?")

- Applies wherever a role is rendered as a `Badge` on the user detail page: `UserGlobalRolesTab` (global roles) and `UserGroupRightsTab` (`granted_roles` per group).
- A role is linkable **only if it resolves in `listRoleCapabilities()`'s `RoleEntry[]`** (matched by `role_code`). Resolve this client-side against the matrix, or — if the planner chooses a leaner data path — the backend may inline a `capability_editable`/resolvable flag onto the user's role payload. Either way, unresolvable roles (pure historical roles) render as **plain `Badge`, no link, no hover affordance**.
- Link target: `/admin/role-capabilities?role={role_code}` — reuses the URL pre-selection contract defined below. Do not invent a second deep-link format (e.g. hash anchors); stay consistent with the D-06 URL-filter pattern already established for `/admin/users`.
- Rendering: a small secondary action next to the `Badge`, not a full row link (the row/badge itself stays static so it doesn't visually compete with the "Rolle entziehen" destructive action already in that row).

### Rolle → User ("N-mal vergeben")

- Applies to `RoleMasterList.tsx` (and/or `RoleCapabilityDetail.tsx`, if the planner surfaces it in both places — minimum bar is `RoleMasterList` since that's the always-visible master row).
- Count = **global role assignment count only** (D-05) — same semantic scope as the existing `global_role` list filter, so the number a user sees always matches what they'll find after the jump.
- Render as a `Badge` (accent-tinted / `variant="info"` when count > 0, `variant="muted"` when count = 0) positioned in the same row as the existing `badgeLabel` context badge (`Aktive App-Rolle` / `Projekt-/Release-Rolle` / `Historische Rolle`) — do not add a second row.
- Only roles with `assignable === true` (the actual global/app roles) get a live count; group-/project-scoped (contribution) roles show the muted `–` non-link state (see Copywriting Contract) — this is the explicit D-05 scope boundary, not a bug to fix in this phase.
- Clicking navigates to `/admin/users?role={role_code}` (clears any pre-existing `role` param, preserves nothing else — a fresh filtered view, matching the "N-mal vergeben" promise literally).

### URL pre-selection on `/admin/role-capabilities?role={code}`

- `RoleCapabilityClient.tsx` reads `role` via `useSearchParams` on mount (new — today `selectedRoleCode` is purely local state) and, if the code exists in the loaded matrix, calls the same `handleSelectRole` path used for a manual click (desktop → inline panel; mobile → opens the `Drawer variant="responsiveSheet"`, matching `isMobile` branch exactly).
- If the `role` param doesn't match any loaded role (stale/typo), fail silently to the current no-selection state — do not show an error state for this cosmetic mismatch.

## Filter → URL Query Contract (D-06)

`AdminUsersClient.tsx` moves `q`, `status`, and `role` from local `useState` to `useSearchParams`/`router.replace` (shallow, no full navigation). Keep the existing 300ms debounce on `q`.

| URL param | Maps to API param | Existing UI control | Notes |
|-----------|--------------------|----------------------|-------|
| `q` | `q` | `Input type="search"` (unchanged) | Debounced 300ms before writing to the URL, same as today's debounce before writing to local `params` |
| `status` | `status` | `Select` (unchanged options) | Written immediately on change |
| `role` | `global_role` | `Select` (unchanged options) — **plus** now also settable by the two new RBAC jump-links | Written immediately on change; URL key is `role` (short, matches the CONTEXT.md-locked example `/admin/users?role=content_admin&status=active&q=…`), backend/API param stays `global_role` — translate at the `listAdminUsersPage(params)` call site, not in the URL |
| `page`/`offset` | `offset` (derived) | `Pagination` (unchanged) | Optional — include only if the planner wants page position preserved through the back-link too; not required by D-06's wording, but recommended for a fully faithful "exact previous list" restore |

The existing hardcoded `<option>` lists (`platform_admin`, `content_admin`, `user` for role; `active`/`pending`/`disabled` for status) stay as-is — D-06 explicitly keeps them functional, no dynamic role list needed here.

`has_conflicts` (the "Nur mit Konflikten" toggle) is **not** in D-06's locked URL-param list — leave it as local state unless the planner decides otherwise; it's not part of this phase's explicit scope.

The back-link on `/admin/users/[id]` (`Zurück zur Liste`) must construct its `href` from the exact incoming query string (pass it through as a prop/searchParam from the list → detail navigation, e.g. `/admin/users/[id]?from=q%3D...%26status%3D...%26role%3D...` or simply forward `router.push('/admin/users/' + id)` while the list itself already reflects its own state in the URL — the simplest correct implementation is: **row navigation from the list appends nothing extra**, and the back-link on the detail page uses `document.referrer`-independent logic by reading the list's own current URL via `router.back()` is NOT reliable for deep-linked/shared detail URLs, so use an explicit forwarded query string.) Concretely: **the list row link's `href` is `/admin/users/[id]`, and the back-link's `href` is built from the list's *current* URL query string, forwarded as a `from` search param on navigation** (`/admin/users/[id]?from=<encoded list query string>`), so a directly-shared/bookmarked `/admin/users/[id]` link still has a safe fallback back-link target of plain `/admin/users` (no `from` param).

Minor pre-existing violation to fix while this file is touched anyway (CLAUDE.md mandate, not scope creep — same file, same edit pass): the raw `<label htmlFor="role-filter" className={styles.roleFilterLabel}>` in `AdminUsersClient.tsx:170-172` should become a `FormField label="Globale Rolle" htmlFor="role-filter"` wrapper around the existing `Select`, matching how `FormField` is meant to pair with form controls elsewhere in the design system.
