**Der entscheidende, bereits im Code vorhandene Präzedenzfall (muss 1:1 gespiegelt werden):**
`backend/internal/handlers/jellyfin_source_folder_management.go` (`connectJellyfinFolderAdditively`,
Phase 165-07, Kommentar "RESEARCH.md Pitfall 3") löst EXAKT das symmetrische Problem für
Jellyfin: "ein 'Verbinden' darf eine bestehende anime.source (z. B. anisearch:<id>) NIEMALS
force-überschreiben — additiv in `anime_source_links` schreiben." Für AniSearch gilt dasselbe
umgekehrt: Verknüpfen darf eine bestehende `anime.source` (z. B. `jellyfin:<id>`, der Fall bei
Anime 12/13) NIEMALS überschreiben. `LinkAdditionalJellyfinSource`
(`backend/internal/repository/anime_source_links.go:95-129`) ist das Muster für den additiven,
konflikt-sicheren Insert (ON CONFLICT (source) DO NOTHING + Eigentümer-Nachprüfung ->
`repository.ErrConflict` bei Fremdbesitz, stiller Erfolg bei Re-Link auf denselben Anime). Baue
eine analoge Funktion für AniSearch, die ZUSÄTZLICH die eigene `anime.anisearch_id`-Spalte
schema-bewusst setzt (`animeV2SchemaInfo.HasAniSearchID`/`AniSearchIDIsNumber`,
`backend/internal/repository/anime_schema.go`) — diese Spalte trägt den eindeutigen Index
`uq_anime_anisearch_id` (`database/migrations/0045_reconcile_db_schema_v2_columns.up.sql`).
`anime.source` (die skalare Primärquellen-Spalte) wird von der neuen Funktion NIE verändert —
das ist bewusst so, nicht vergessen/unvollständig: ein Anime mit bestehender
Jellyfin-Primärquelle bleibt Jellyfin-primär, AniSearch kommt additiv in
`anime_source_links` + die eigene Spalte hinzu. Der Episoden-Import
(`backend/internal/handlers/admin_episode_import_series_resolution.go`,
`extractAniSearchIDFromSourceLinks`) liest ohnehin zuerst `anime.source`, DANN
`anime_source_links` — additiv reicht vollständig aus, um den Episoden-Import-Bug zu fixen.

**Konflikt-Antwort wiederverwenden, nicht neu erfinden:** `models.AdminAnimeAniSearchEditConflictResult`

**Warum das keine rein technische Entscheidung ist:** Die Aufgabenbeschreibung sagt explizit:
„Beim Verknüpfen KEINE bestehenden, manuell gepflegten Daten überschreiben“ (unstrittig, Task 1-3
setzen das um) UND „Ob zusätzlich AniSearch-Daten übernommen werden sollen, nur über die
bestehende Übernahme-Logik/Bestätigung — falls dafür eine Produktentscheidung nötig ist:
anhalten und fragen.“ Es gibt zwei gleichermaßen plausible, aber unterschiedliche UX-Formen:

1. **Getrennt (von diesem Plan empfohlener Default, siehe Task 4 Option
   `defer-separate-quick-task`):** „Verknüpfen“ ist ein eigenständiger, sofort persistierender
   Mini-Workflow (Task 1-3) — exakt symmetrisch zum bereits produktiv gehärteten Jellyfin-
   „additiv verbinden“-Muster (`connectJellyfinFolderAdditively`, 165-07). „Daten übernehmen“
   wäre ein zweiter, unabhängiger Button/Abschnitt, der weiterhin NUR einen Entwurf im
   Bearbeitungsformular befüllt (keine eigene Persistenz), den der Admin wie bisher über den
   normalen „Änderungen speichern“-Klick bestätigt. Vorteil: kleinere, klar abgegrenzte
   Änderungseinheiten; kein Risiko, dass ein einzelner Klick sowohl verknüpft als auch
   unerwartet Felder überschreibt.

2. **Kombiniert:** Die Suchergebnis-Auswahl in der neuen „Verknüpfen“-Karte böte direkt eine
   Checkbox/einen zweiten Button „auch Daten übernehmen“ an, der im selben Dialog sowohl den
   Link-Endpunkt als auch den Draft-Merge-Endpunkt anstößt. Vorteil: ein Workflow statt zwei;
   Nachteil: vermischt eine IMMER sichere, additive Aktion mit einer POTENZIELL
   feldüberschreibenden Aktion in einem UI-Element — höheres Risiko für Fehlbedienung
   („ich wollte nur verknüpfen, jetzt wurden auch Felder überschrieben“).
