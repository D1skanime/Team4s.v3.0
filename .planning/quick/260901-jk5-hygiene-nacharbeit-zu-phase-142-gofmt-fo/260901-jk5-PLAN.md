Task 2/3 exact ESLint rule (confirmed via `npx eslint src` inside the frontend container, and cross-checked against `node_modules/eslint-plugin-react-hooks` v7.0.1 source): the diagnostic is React Compiler's `set-state-in-effect` check, surfaced through `eslint-config-next`'s `core-web-vitals` config (not a rule ID like `react-hooks/exhaustive-deps` — it reports as `error  Error: Calling setState synchronously within an effect can trigger cascading renders`, no ESLint rule suffix, `suggestions: null`, no `--fix` available). It flags only a setState call written as a direct, synchronous top-level statement inside a `useEffect` body. It does NOT flag setState calls inside a nested callback (e.g., inside `.then()`/`.catch()`) — this codebase already relies on that distinction: in both target files, the async-branch `.then()/.catch()` setState calls in the SAME effect are not flagged, only the synchronous early-return-guard call is.

Fix pattern (verified zero-import, same-effect-still-runs, same dependency array): wrap only the flagged synchronous call in `queueMicrotask(() => setter(value))`. This defers the call by one microtask (flushes before the next paint, same as the codebase's existing `.then()`-based resets in the very same effects) and removes it from the compiler's synchronous-call check without altering the effect's dependency array, its cleanup, or any other statement. Do not restructure the surrounding guard clause beyond this one wrap.
