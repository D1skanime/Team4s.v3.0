# Phase 261101-q79: Code Review Report

**Reviewed:** 2026-11-01T21:13:14Z

**Files Reviewed:** 97

## Summary

This is a frontend-only design-system refactor: extraction of a shared `useOverlaySurface` hook (focus trap/restore, Escape, portal) from `Modal` into `Drawer`, new Button/Badge/IconButton status-tone variants built on `color-mix()`, removal of `Button`'s `iconOnly` in favour of `IconButton` across ~18 call sites, a new `Label` primitive wired into `FormField`, and a `Picker` `aria-label`/`aria-labelledby` fix. The `iconOnly → IconButton` migration itself is clean: `aria-label` is a mandatory TypeScript prop on `IconButton`, so the compiler already guards against the "aria-label silently dropped" failure mode, and the spot-checked call sites (`SegmentsListSection.tsx`, `AnimeContributionModal.tsx`, `ReleaseContributionDrawer.tsx`, `AnimeGroupCard.tsx`, `RichTextEditor.tsx`) all carry correct variant/tone mappings and in one case (`SegmentsListSection.tsx` "Bearbeiten" button) actually *add* a previously-missing `aria-label`.

The one concrete, reachable **Critical** issue is in the newly shared focus-trap logic: `useOverlaySurface`'s Tab-cycle computes focusable elements via `panelRef.current.querySelectorAll(...)`, a real DOM query — but `YearPicker`'s calendar popover is rendered through `createPortal(..., document.body)`, i.e. **outside** that DOM subtree, even though the portaled content is still a React-tree descendant and so its keydown events still bubble into the trap handler. Opening `YearPicker` inside a `Drawer` (a reachable, real flow: the mobile search-filter `Drawer` at `frontend/src/app/suche/SearchFilterDrawer.tsx` embeds `YearPicker` for "Von/Bis Jahr") now forcibly yanks focus back into the Drawer panel on every Tab press inside the calendar grid, because `Drawer` previously had **no** focus trap at all and only gained one through this refactor. This specific regression is net-new for `Drawer` (Modal already had the same latent interaction, but no current Modal call site combines `Modal` + `YearPicker`, so `Drawer` is where it first becomes user-visible).

Three further Warnings and one Info-level item round out the findings — none of them block the generally sound `iconOnly` migration or the status-tone work, but they are real defects worth fixing before this ships.

## Critical Issues

### CR-01: Tab-trap in `useOverlaySurface` breaks keyboard navigation inside `YearPicker`'s portaled calendar when nested in `Drawer`

**File:** `frontend/src/components/ui/useOverlaySurface.ts:84-101` (trap logic) interacting with `frontend/src/components/ui/YearPicker.tsx:242` (`createPortal(pickerPanel, document.body)`), reachable via `frontend/src/app/suche/SearchFilterDrawer.tsx:57-76` and `frontend/src/app/suche/SearchFilters.tsx:147,158` (`YearPicker` "Von Jahr"/"Bis Jahr").

**Issue:** `handleKeyDown`'s Tab-cycle builds its focusable-elements list via `getFocusableElements(panelRef.current)`, which calls `panelRef.current.querySelectorAll(...)` — a query over the *actual DOM subtree* rooted at the Drawer/Modal panel. `YearPicker` renders its open calendar popover (`pickerPanel`) through `createPortal(pickerPanel, document.body)`, so the popover's day/month/year tiles live **outside** `panelRef`'s DOM subtree, in a sibling of `document.body`. React preserves React-tree (not DOM-tree) event bubbling for portals, so a Tab keydown fired from inside the portaled popover still bubbles up to the Drawer's `onKeyDown={handleKeyDown}` on the dialog wrapper. Inside `handleKeyDown`, `document.activeElement` (a button inside the portal) is **not** found in the `focusable` array derived from `panelRef.current.querySelectorAll(...)`, so `currentIndex` is `-1`, and the trap unconditionally calls `event.preventDefault()` followed by `focusable[0]?.focus()` — yanking focus out of the calendar and back into the Drawer panel on *every* Tab press while the YearPicker popover is open.

This was already a latent interaction in `Modal` prior to this PR (no change there), but `Drawer` previously had **zero** focus trap/keydown handling at all — any `YearPicker` nested in a `Drawer` tabbed normally. This PR's `useOverlaySurface` extraction gives `Drawer` the *same* trap logic as `Modal` for the first time, and there is a real, reachable production call site that now breaks: the mobile "Filter" `Drawer` (`SearchFilterDrawer.tsx`) renders `SearchFilterFields` → `YearPicker` for "Von Jahr"/"Bis Jahr" directly inside the Drawer body. A keyboard user opening that filter drawer on mobile and trying to Tab through the year-picker's month/year grid will find focus repeatedly bounced back to the drawer chrome.

**Fix:** Either (a) make `getFocusableElements` portal-aware by also scanning any open picker portals (fragile), or — simpler and consistent with `DatePicker`'s existing approach — (b) stop portaling `YearPicker`'s calendar panel to `document.body` and render it inline like `DatePicker` already does (`DatePicker.tsx` renders its panel directly inside the same root `<div ref={rootRef}>`, so it stays inside `panelRef`'s subtree and the existing trap already works correctly for it). Minimal targeted fix:
```tsx
// YearPicker.tsx — render the panel inline instead of portaling to document.body,
// matching DatePicker's already-correct pattern so Tab-trap in Modal/Drawer sees it:
{pickerPanel}
// instead of:
{pickerPanel && typeof document !== 'undefined' ? createPortal(pickerPanel, document.body) : null}
```
If the portal is required for a reason not visible in this diff (e.g. z-index/clipping elsewhere), the alternative is to union `getFocusableElements` across `panelRef.current` and any `[data-year-picker-portal]`-tagged node currently in `document.body`.

## Warnings

### WR-01: `useOverlaySurface`'s initial-focus `setTimeout` is never cancelled, risking a focus-steal race after close

**File:** `frontend/src/components/ui/useOverlaySurface.ts:62-74`

**Issue:**
```ts
useEffect(() => {
  if (!open) return
  previouslyFocusedRef.current = document.activeElement instanceof HTMLElement ? document.activeElement : null
  const focusTarget = initialFocusRef?.current ?? closeButtonRef.current ?? panelRef.current
  window.setTimeout(() => focusTarget?.focus(), 0)

  return () => {
    previouslyFocusedRef.current?.focus()
    previouslyFocusedRef.current = null
  }
}, [open])
```
The scheduled `setTimeout` id is never stored or cleared. If `open` flips back to `false` (or the owning component unmounts) before the macrotask fires, the cleanup already runs synchronously and restores focus to the previously-active element — but the stale timeout then fires afterwards and calls `.focus()` on the old `focusTarget` (close button / panel / `initialFocusRef`), silently stealing focus back to a now-hidden dialog element. This is inherited unchanged from the pre-refactor `Modal` implementation, but this PR is the first time it also applies to `Drawer` (previously `Drawer` had no focus management whatsoever), doubling the real-world surface for the race.

**Fix:**
```ts
useEffect(() => {
  if (!open) return
  previouslyFocusedRef.current = document.activeElement instanceof HTMLElement ? document.activeElement : null
  const focusTarget = initialFocusRef?.current ?? closeButtonRef.current ?? panelRef.current
  const timerId = window.setTimeout(() => focusTarget?.focus(), 0)

  return () => {
    window.clearTimeout(timerId)
    previouslyFocusedRef.current?.focus()
    previouslyFocusedRef.current = null
  }
}, [open])
```

### WR-02: `FormField`'s `pickerSafeProps` can silently clobber a caller-supplied `aria-labelledby` on `DatePicker`/`YearPicker`

**File:** `frontend/src/components/ui/FormField.tsx:132-148`

**Issue:**
```ts
const pickerSafeProps = { ...triggerSafeProps, 'aria-labelledby': labelId }
```
`labelId` is only set when `FormField` is given a `label` (`labelId = label ? \`${resolvedId}-label\` : undefined`). When `FormField` has **no** `label` text but still wraps a `DatePicker`/`YearPicker`, `pickerSafeProps['aria-labelledby']` is `undefined` — but it is still an *own* key on the object passed to `cloneElement`, so `cloneElement` will overwrite (with `undefined`) any `aria-labelledby` the caller explicitly passed directly to the `DatePicker`/`YearPicker` element being wrapped. No current call site passes both "`FormField` without `label`" and "`DatePicker`/`YearPicker` with an explicit `aria-labelledby`" at the same time (verified via grep across all current `FormField` + `DatePicker`/`YearPicker` call sites — every one supplies `label`), so this is latent rather than actively triggered today, but it is a real contract bug in code newly introduced by this PR and will bite the next caller who relies on `aria-labelledby` without also setting `FormField.label`.

**Fix:**
```ts
const pickerSafeProps = labelId
  ? { ...triggerSafeProps, 'aria-labelledby': labelId }
  : triggerSafeProps
```

### WR-03: New danger/success button+badge color tokens depend on unconditioned `color-mix()` with no documented browser floor or fallback

**File:** `frontend/src/styles/tokens/palette.css:116-145`

**Issue:** This PR replaces the previously hardcoded, safe hex triplets for `--button-danger-start/mid/end` and `--button-success-start/mid/end` with `color-mix(in srgb, ...)` derivations from a single seed:
```css
--button-danger-seed: #95405c;
--button-danger-start: color-mix(in srgb, var(--button-danger-seed) 80%, white 20%);
--button-danger-mid: var(--button-danger-seed);
--button-danger-end: color-mix(in srgb, var(--button-danger-seed) 80%, black 20%);
```
`color-mix()` is already used extensively elsewhere in the codebase pre-dating this PR (e.g. `Modal.module.css`, `Spinner.module.css`, `fields.css`), and there is no `browserslist` entry in `frontend/package.json` and no documented browser-support floor anywhere in `CLAUDE.md` or `docs/`. Per the CSS custom-properties spec, if `color-mix()` is unsupported, the custom property resolves to the guaranteed-invalid value, which propagates through `var()` to any declaration consuming it (here, the entire gradient `background` for danger/success — and now also the newly-added warning/info — buttons), rendering those buttons with an invisible/transparent fill in an unsupported browser, with **no fallback value**. This specific migration is new in this PR and removes what were previously safe, static fallback colors for two button tones that did not depend on `color-mix()` at all.

**Fix:** Either document an explicit `browserslist`/minimum-browser-version floor project-wide (if the team has already implicitly decided `color-mix()` support is a baseline requirement, given its pervasive prior use), or add `@supports not (color-mix(in srgb, red, blue))` fallback blocks that set the four affected custom properties back to static hex values for the two newly-migrated tones.

## Info

### IN-01: `ConfirmDialog`'s cancel-button ref relies on a DOM `querySelector` workaround instead of real ref-forwarding

**File:** `frontend/src/components/ui/ConfirmDialog.tsx:26-35`

**Issue:**
```tsx
const cancelButtonRef = useRef<HTMLButtonElement | null>(null)
function captureCancelButton(node: HTMLSpanElement | null) {
  cancelButtonRef.current = node?.querySelector('button') ?? null
}
...
<span ref={captureCancelButton} style={{ display: 'contents' }}>
  <Button variant="secondary" onClick={() => settle(false)}>
    {pending.cancelLabel ?? 'Abbrechen'}
  </Button>
</span>
```
This is explicitly documented as a workaround for `Button` not forwarding a ref to its inner `<button>`, and functionally it works today because `Button`'s rendered output is a single `<button>` with no other nested `<button>` elements. It is nonetheless a fragile pattern (an inline callback-ref function with a new identity every render, re-querying the DOM each time) that would silently break or mis-target if `Button`'s internal markup ever gained a second nested `<button>` (e.g. inside a future `leftIcon`/`rightIcon` slot).

**Fix:** Consider forwarding a ref from `Button` to its underlying `<button>`/`<a>` element (as `IconButton` already does via `forwardRef`), which would let `ConfirmDialog` use `initialFocusRef` directly against a `Button` ref instead of this `querySelector` indirection.
