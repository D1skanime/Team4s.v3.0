# Phase 150 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope Banner — Read This First

**This phase has no intended visual change.** It moves badge threshold/tier/progress
computation from the frontend into the backend. Same tiers, same labels, same progress
texts, same DOM structure, same CSS classes — only the data source changes from
frontend-recomputed values to backend-supplied values.

Consequently this UI-SPEC does **not** define new spacing, typography, color, or copy.
Its job is to (1) lock the exact current visual/textual output as a baseline that must
not change, (2) define a real-data parity verification method (not eyeballing), and
(3) state the one visually-relevant defect fix (`role_entry_<code>` duplicate) as an
explicit before/after guarantee.

**Locked out of this UI-SPEC's scope** (per `.planning/notes/2026-09-06-auftrag-phase150-badge-rules.md`
and the ROADMAP.md Phase 150 entry — do not re-litigate): badge carousel, `FocalCarousel`,
swipe, animations, settle-timer, image sizes/formats, loading behavior, any new badge
families/artwork/design, and any `MemberBadgeChain` structural refactor. The Phase 147
role registry is not reopened.

## Locked Visual Baseline — `role_entry_<code>` Duplicate-Fix Guarantee

**Today (defect, confirmed by ROADMAP.md's measured baseline):** two backend functions
(`loadPublicBadges` and `loadRoleVolumeBadges`) each emit a `role_entry_<code>` entry for
roles above entry tier — one without progress fields, one with. `MemberBadgeChain.tsx`
(lines 628-644) compensates client-side via `Math.max(roleCounts.get(...) ?? 0, count)`
across the duplicate entries to avoid visibly wrong counts.

**After this phase (visual guarantee, must hold exactly):**

1. `public_badges` contains **exactly one** entry per `role_entry_<code>` per role — no
   duplicate, no dropped entry.
2. That single entry carries the progress fields (`current_count`, `current_tier`,
   `next_threshold`, `remaining_count`, `next_tier`) already correctly.
3. The Role Badge Card for that role renders in the **same position** (role ordering via
   `orderForContext(contributionRoles, 'anime_contribution')` is untouched), with the
   **same count, same tier label, same progress bar percentage, same "Noch X bis Y" /
   "Höchste Stufe erreicht" text** as it does today with the `Math.max` workaround.
4. The `Math.max` compensation in `MemberBadgeChain.tsx:628-644` may be simplified or
   removed once the source no longer emits duplicates, but its **removal must not change
   any rendered number** — it is presentation-neutral cleanup of a workaround, not a
   behavior change. If removing it changes any displayed value, the backend fix has not
   actually achieved parity and must not ship.

## Parity Verification Method (must run for real, not eyeballed)

Two real-data captures, taken immediately before and immediately after the backend/DTO
change lands, diffed as text — not a visual screenshot comparison.

**A. Public member profile — reuse the existing evidence harness.**

`frontend/scripts/collect-member-profile-evidence.mjs` already captures
`document.body.innerText`, all `h1`/`h3` headings, and badge-stage-strip elements for a
given member slug via Playwright. Run it (or a minimal script built on the same Playwright
page-object pattern) against the real member the ROADMAP.md regression gate already
names as ground truth — **member `type`** — before and after the change, at
`http://192.168.235.196:3000/members/type` (or the SSH-tunnel path
`http://127.0.0.1:3300/members/type` per `CLAUDE.md`'s canonical UAT path). Diff the two
captured `innerText` blobs for the badge-chain section. Expected zero diff except
whitespace/DOM-order noise already present in the tool's existing normalization.
Cross-check the specific numbers named in ROADMAP.md's regression gate:
`role_volume_typesetter_bronze` must keep `current_count 13 · current_tier bronze ·
next_threshold 108 · remaining_count 95 · next_tier silver`.

**B. Own dashboard — capture via authenticated API response + rendered text.**

`/me/dashboard` is owner-gated, so this cannot run through the same anonymous Playwright
pass as (A) without a session. Two acceptable methods, either is sufficient:

1. `curl` the authenticated `GET` dashboard endpoint before/after with a real bearer
   token for a member that has real points, role-volume, and category-progress data
   (points row, at least one `<Rolle> · Rollen-Volumen` row, and all three contribution
   family rows non-empty), and diff the raw JSON for `total_points`, `role_volume`,
   `category_progress` plus a new points-progress field if the contract adds one.
2. A logged-in Playwright pass (reusing the existing auth/session pattern from
   `frontend/scripts/capture-phase134-uat-evidence.mjs` if it already logs in) capturing
   `document.body.innerText` of the `CategoryProgressTable` rows before/after.

**Default (Claude's Discretion — confirm or override):** use the same member fixtures
already established for this project's profile/dashboard evidence work (`sheppert` /
`csubs-leader`, per `134-UAT.md`) for capture B, since they are known to carry
representative points/role-volume/contribution data and already have documented
credentials in prior phase evidence. If neither has meaningful role-volume or points
data at time of testing, use any real member account with non-trivial dashboard activity
and record which one was used in the phase's completion summary.

Both captures must be retained (as files under the phase's `evidence/` directory, or
inline in a completion doc) so "no visible change" is provable after the fact, not just
asserted.
