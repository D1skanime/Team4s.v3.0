<objective>
Close the seventh threshold-suffix presentation site found during this phase's grounding: the
member's own `/me/profile` badge-visibility manager, `AchievementBadgesCard.tsx`, calls
`getMemberBadgePresentation(badge.badge_code).label` for every badge in the member's own full badge
list (`MemberBadge[]`, from `GET /me/badges`), whose `badge_code` domain includes
`role_volume_<code>_<tier>` per the same dispatch rule `getMemberBadgePresentation` already applies
everywhere else.

**Context Revision 2026-09-06, dritter Durchgang (D-30 enforcement)** originally assigned this fix
to Plan 150-05 as Tasks 4-5. A subsequent plan-checker pass split it out into this dedicated plan
(150-07) purely for context-budget reasons -- Plan 150-05 had grown to 5 tasks / 15 files after
absorbing this fix, crossing both blocker thresholds (task count and file count) simultaneously at
once. The fix's content, scope, and correctness were already reviewed and independently confirmed
against the live codebase; only its packaging across plan files changes here. This plan
`depends_on` both 150-01 (for the `badges.RoleVolume` registry) and 150-05 (because Task 2's
frontend reconstruction depends on Plan 150-05's Task 3 bare-label fix to `resolveRoleVolumePresentation`
having landed first).

The pre-revision draft of this fix declined to touch this site, citing that its backing type
(`MemberBadge`, `frontend/src/types/contributions.ts`) and endpoint (`GetMyBadges`,
`backend/internal/handlers/member_badges_handler.go` / `backend/internal/repository/badge_repository.go`)
carry no progress/threshold fields, and deferred it as an accepted, documented, out-of-scope
consequence. A plan-checker correctly flagged this as a violation of D-30's literal instruction
("ist nach demselben Muster zu behandeln") -- D-30 has no "too much contract work" exception, and
the deferral used exactly the same justification (extending a contract with a small companion field
from an already-available registry call) that Plan 150-02 already executed for the analogous
dashboard gap. This plan closes that site the same way Plan 150-02 closed the dashboard's gap:
`MemberBadge` gains a minimal `current_threshold` field, computed by `GetMyBadges`'s backing
repository from the already-exported `badges.RoleVolume` registry (Plan 150-01) via a tier-suffix
scan on the badge_code itself -- no new query, no new endpoint, no second registry.

**Grounding note carried into the SUMMARY, not silently omitted:** as of this revision, no code path
in the backend ever writes a `role_volume_`-prefixed (or any non-`historical_achievement`/`supporter`/
`platform`-category) badge_code into the `member_badges` table -- `services/badge_service.go`'s
`ComputeAndStoreBadges` only ever upserts `founding_member`, `historical_leader`, `long_term_member`,
`membership_7_years`, `membership_10_years`, `first_contribution`, `productive_bronze/silver/gold`,
`all_rounder`, `verified`. Role-volume/role-entry/contribution/progress-family badges are exclusively
a live, never-persisted projection used by the PUBLIC profile response (`loadPublicBadges`/
`loadRoleVolumeBadges`, a completely different code path from `GetMyBadges`). This means, at present,
`GET /me/badges` cannot actually emit a `role_volume_`-coded row, so this plan's fix is not closing
an observed live bug -- it is completing the contract per D-30's literal, no-exception instruction,
so `MemberBadge`'s shape stays correct and `AchievementBadgesCard.tsx` renders correctly if this
ever changes (e.g. a future phase persists role-volume badges), and so no
`getMemberBadgePresentation` consumer anywhere in the codebase still implicitly depends on a
frontend threshold constant. This plan's Tasks 1-2 must state this grounding fact explicitly in the
SUMMARY, not omit it -- the fix is real and complete, but its current production reachability is
zero by design of the existing persistence model, and that fact is exactly the kind of thing
D-27/D-30 require to be named rather than silently smoothed over.

Purpose: the seventh site has the identical shape of problem as sites 1-6 (recomputing a business
decision -- here, a single threshold number embedded in a label suffix -- from a frontend constant
instead of reading it from the backend), just behind a currently-empty data path.

Output: `MemberBadge`/`GetMyBadges` gain a registry-derived `current_threshold` field and
`AchievementBadgesCard.tsx` reconstructs the suffixed label from it, closing the seventh site per
D-30 with zero remaining frontend threshold literals for role_volume presentation anywhere in the
codebase.
</objective>
