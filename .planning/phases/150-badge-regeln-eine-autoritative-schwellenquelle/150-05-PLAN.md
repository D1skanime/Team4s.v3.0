<objective>
Repoint the four named frontend computation sites (D-12) to read tier/threshold/remaining directly
from the API response instead of recomputing it from a local threshold table, and remove the
derivation functions that become genuinely dead as a result (D-13). Do NOT redesign or touch any
DOM/CSS -- this plan changes data sources only, per 150-UI-SPEC.md's locked baseline.

Purpose: three of the four call sites recompute a business decision (which points milestone /
role-volume tier is the member currently at) that the backend has computed correctly since Plans
150-02/150-03 landed. The fourth (MemberBadgeChain's role-count fallback) exists only because the
backend used to sometimes omit progress fields -- Plan 150-04 removed that gap, so the fallback's
threshold-based guess is now provably unreachable dead code, not a defensive necessity.

Output: `MemberProfileContent.tsx`, `CategoryProgressTable.tsx`, and `MemberBadgeChain.tsx` no
longer derive tier/threshold/remaining themselves at these four sites; `memberBadgeLabels.ts`
loses the functions that have no remaining caller after the swap.

IMPORTANT -- read before starting: 150-CONTEXT.md's D-11 names four memberBadgeLabels.ts exports
(ROLE_VOLUME_TIER_THRESHOLDS, POINT_MILESTONES, ROLE_PROGRESS_STAGES, and the inline threshold
arrays inside FAMILY_DEFINITIONS) as deletion targets. Grounding against the current code (see
this plan's interfaces block) found that all four remain genuinely referenced by code this plan is
explicitly forbidden from touching: the multi-stage progression "ladder" strip rendered inside
FamilyCollectionCard/AnimeProjectAchievementStage/ContributionAchievementStage/MembershipStage/
PointsAchievementStage (via resolveMemberBadgeFamilies's FAMILY_DEFINITIONS stage lists) and the
Role Badge Card's medal ladder (via resolveRoleProgressPresentation, still called at
MemberBadgeChain.tsx around line 726, which is NOT one of the four named call sites).
150-UI-SPEC.md's own "No New Components" section explicitly forbids DOM/CSS changes to
accommodate this and requires routing any such deeper change back through /gsd:ui-phase 150 first
-- it is not this plan's call to make unilaterally. D-13 itself uses the qualifier "soweit sie
danach unbenutzt sind" ("insofar as they become unused") for exactly this reason. Task 3 below
implements the letter of that qualifier: verify what is actually dead after the swap, delete only
that, and document why the rest stays. Do not delete ROLE_VOLUME_TIER_THRESHOLDS,
POINT_MILESTONES, ROLE_PROGRESS_STAGES, resolveRoleProgressPresentation, or any FAMILY_DEFINITIONS
stage array unless your own grep proves zero remaining callers -- if your grep disagrees with this
plan's finding, trust your grep and flag the discrepancy in the SUMMARY.

<interfaces>
The already-correct pattern to mirror (frontend/src/app/me/dashboard/components/CategoryProgressTable.tsx,
function buildCategoryRow, NOT to be changed by this plan): it reads row.current_tier from the
backend, builds badgeCode as `${row.family}_${row.current_tier}` only when current_tier is
non-empty, looks up the next tier's label via a small ordered tier-label map, and calls
formatProgressText(row.next_threshold, row.current_count, nextLabel). 150-UI-SPEC.md names this
function as the model for the two functions this task must fix.

After Plans 150-02/150-03, the response shapes this plan reads are:
- OwnDashboardRoleVolumeEntry (frontend/src/types/dashboard.ts, extended by 150-02): role_code,
  count, plus current_tier (string), next_threshold (number | null), remaining_count
  (number | null), next_tier (string | null).
- OwnDashboardData.points_progress (added by 150-02, type OwnDashboardCategoryProgress): family
  "points", current_tier, current_count, next_threshold, remaining_count, next_tier -- current_tier
  and next_tier here hold FULL badge codes (e.g. "point_milestone_active"), not bare tier tokens,
  because points milestones ARE the badge codes (unlike the bronze/silver/gold contribution
  families).
- PublicMemberBadgeProgress (frontend/src/types/profile.ts, extended by 150-03): gains
  current_tier (string; full badge code for the "points" family, bare tier token for
  "contribution_*"/"progress", full historical-achievement code for "membership") and role_code
  (optional string, only set on the new family:"role_volume" entries).
- PublicMemberBadge (frontend/src/types/profile.ts, unchanged by this phase): already has
  current_count/current_tier/next_threshold/remaining_count/next_tier -- this is what
  role_entry_<code>/role_volume_<code>_<tier> badges in public_badges carry, and, after Plan
  150-04, always carry, for every tier including entry.

The D-12 #4 site (frontend/src/components/profile/MemberBadgeChain.tsx, current lines around
628-644 -- verify exact line numbers against Plan 150-04's landed state before editing): builds a
per-role-code count map from earnedBadges. For each earned badge in the "roles" group, it computes
a fallbackCount (1 for role_entry_* badges, or ROLE_VOLUME_TIER_THRESHOLDS[tier] for
role_volume_<code>_<tier> badges when current_count is absent) and takes
`badge.current_count ?? fallbackCount`. MemberBadgeChain.test.tsx has several role-badge fixtures
(search for `badge_category: 'role_volume'`) that construct a PublicMemberBadge WITHOUT
current_count at all, relying on this fallback to synthesize a plausible count from the tier
suffix for rendering assertions. These are test doubles that do not reflect the real (post-150-04)
backend contract, where current_count is always present. Simplifying the fallback will make these
fixtures render with count 0 unless they are updated to include a realistic current_count first.
