<objective>
Repoint the four originally-named frontend computation sites (D-12) AND the badge-family stage
ladders (D-24/D-25) to read tier/threshold/remaining/stages directly from the API response instead
of recomputing them from local threshold tables, and remove every derivation function/constant that
becomes genuinely dead as a result. Do NOT redesign or touch any DOM/CSS -- this plan changes data
sources only, per 150-UI-SPEC.md's locked baseline.

**Context Revision 2026-09-06 (D-24 through D-28) supersedes this plan's pre-revision resolution.**
The first planning pass on this plan found a real fifth call site
(`resolveRoleProgressPresentation` in `MemberBadgeChain.tsx`'s "roles" carousel, around line 726)
and proposed KEEPING `ROLE_VOLUME_TIER_THRESHOLDS`, `POINT_MILESTONES`, `ROLE_PROGRESS_STAGES`, and
`FAMILY_DEFINITIONS`' inline threshold arrays because they feed the multi-stage "ladder" strips. The
user reviewed and **rejected** that resolution: ROADMAP.md's Success Criterion 2 names these four
constants with no "soweit unbenutzt" qualifier (unlike SC-3's four functions), and keeping them
would leave the visible ladder able to silently desync from the registry -- exactly the drift this
phase exists to eliminate. Plan 150-03 (already revised) now exposes each family's ascending stage
list on `badge_progress[].stages` (including a Go-synthesized "entry" stage for `role_volume`), so
the ladder can render with ZERO frontend threshold literals. This plan's job is to consume that new
field and then delete all four constants with zero survivors -- not to re-litigate whether they are
still needed.

**Context Revision 2026-09-06, zweiter Durchgang (sixth-site correction + a newly found seventh
site) supersedes this plan's Task 3's original `resolveRoleVolumePresentation` resolution.** The
first revision pass's Task 3 found `resolveRoleVolumePresentation`'s label suffix (e.g.
`"Gold · 320+"`) as a sixth survivor of `ROLE_VOLUME_TIER_THRESHOLDS` and proposed deleting the
suffix outright, claiming it was unrendered anywhere. That claim was checked and is **false**:
`CategoryProgressTable.test.tsx:98` (`expect(screen.getAllByText("Bronze · 12+"))`, rendered via
`buildRoleVolumeRow`) proves this exact `"<Label> · <n>+"` string IS live, user-visible dashboard
copy today (`MemberBadgeChain.test.tsx:695`'s `"Silber · 108+ gesperrt"` is a DIFFERENT string,
produced by `resolveRoleProgressPresentation`'s stage list, already fixed by Task 2 -- it does not
involve `resolveRoleVolumePresentation` at all). Deleting the suffix would violate
150-UI-SPEC.md's byte-exact baseline. Rejected.

The corrected fix (D-29): the FORMAT stays exactly as today; only the NUMBER's source moves from a
frontend constant to a server-supplied field. `resolveRoleVolumePresentation`'s own return value
becomes the BARE tier label ("Gold", no suffix) -- matching the "labels only" precedent already set
by `ROLE_VOLUME_TIER_LABELS` itself (kept, per D-25/Task 3, as legitimate non-numeric presentation
data). The ONE production call site that needs the suffixed string --
`buildRoleVolumeRow` in `CategoryProgressTable.tsx` (Task 1) -- reconstructs it itself from a new
`OwnDashboardRoleVolumeEntry.current_threshold` field. That field did NOT exist anywhere in this
phase's already-drafted contract work: grounding confirmed the dashboard's `OwnDashboardRoleVolumeEntry`
(owned by Plan 150-02, not 150-03) has no stage-list or current-tier-threshold field, and
`PublicMemberBadgeProgress.stages` (Plan 150-03) lives on the public member-profile response, which
`/me/dashboard` never fetches. Plan 150-02 has therefore been given a small companion addition
(`current_threshold`, computed the same way as its existing `current_tier`/`next_threshold`
fields, from the same already-loaded registry call) -- see that plan's own revision note. This is
the least invasive of D-29's two offered options: it changes one function's return shape plus one
call site, instead of threading a new parameter through every `getMemberBadgePresentation` dispatch
path (which is called from many non-role_volume badge codes too).

This same grounding pass found a **seventh site**: `frontend/src/app/me/profile/components/AchievementBadgesCard.tsx`
(the `/me/profile` badge visibility manager) calls `getMemberBadgePresentation(badge.badge_code).label`
for every badge in the member's own full badge list (`MemberBadge[]`, from `GET /me/badges`), whose
`badge_code` domain includes `role_volume_<code>_<tier>` per the same dispatch rule
`getMemberBadgePresentation` already applies everywhere else. **Context Revision 2026-09-06, dritter
Durchgang (D-30 enforcement) supersedes this plan's original resolution for this site.** The
pre-revision draft of this task declined to fix this site, citing that its backing type (`MemberBadge`,
`frontend/src/types/contributions.ts`) and endpoint (`GetMyBadges`,
`backend/internal/handlers/member_badges_handler.go` / `backend/internal/repository/badge_repository.go`)
carry no progress/threshold fields, and deferred it as an accepted, documented, out-of-scope
consequence. A plan-checker correctly flagged this as a violation of D-30's literal instruction
("ist nach demselben Muster zu behandeln") -- D-30 has no "too much contract work" exception, and
the deferral used exactly the same justification (extending a contract with a small companion field
from an already-available registry call) that Plan 150-02 already executed for the analogous
dashboard gap. **This plan now DOES modify `AchievementBadgesCard.tsx`, `badge_repository.go`,
`member_badges_handler.go`, `frontend/src/types/contributions.ts`, and `shared/contracts/openapi.yaml`**
(Tasks 4-5, below) to close this site the same way Plan 150-02 closed the dashboard's gap: `MemberBadge`
gains a minimal `current_threshold` field, computed by `GetMyBadges`'s backing repository from the
already-exported `badges.RoleVolume` registry (Plan 150-01) via a tier-suffix scan on the badge_code
itself -- no new query, no new endpoint, no second registry.

**Grounding note carried into the SUMMARY, not silently omitted:** as of this revision, no code path
in the backend ever writes a `role_volume_`-prefixed (or any non-`historical_achievement`/`supporter`/
`platform`-category) badge_code into the `member_badges` table -- `services/badge_service.go`'s
`ComputeAndStoreBadges` only ever upserts `founding_member`, `historical_leader`, `long_term_member`,
`membership_7_years`, `membership_10_years`, `first_contribution`, `productive_bronze/silver/gold`,
`all_rounder`, `verified`. Role-volume/role-entry/contribution/progress-family badges are exclusively
a live, never-persisted projection used by the PUBLIC profile response (`loadPublicBadges`/
`loadRoleVolumeBadges`, a completely different code path from `GetMyBadges`). This means, at present,
`GET /me/badges` cannot actually emit a `role_volume_`-coded row, so Task 5's fix is not closing an
observed live bug -- it is completing the contract per D-30's literal, no-exception instruction, so
`MemberBadge`'s shape stays correct and `AchievementBadgesCard.tsx` renders correctly if this ever
changes (e.g. a future phase persists role-volume badges), and so no `getMemberBadgePresentation`
consumer anywhere in the codebase still implicitly depends on a frontend threshold constant. Tasks
4-5 must state this grounding fact explicitly in the SUMMARY, not omit it -- the fix is real and
complete, but its current production reachability is zero by design of the existing persistence
model, and that fact is exactly the kind of thing D-27/D-30 require to be named rather than silently
smoothed over.

Purpose: three of the four originally-named call sites recompute a business decision (which points

`AchievementBadgesCard.tsx` reconstructs the suffixed label from it, closing the seventh site per
D-30 with zero remaining frontend threshold literals for role_volume presentation anywhere in the
codebase.
