Repoint the contribution-tier switches, the dashboard's independent threshold map, and
badge_service.go's membership/productive thresholds to the Plan 150-01 registry (D-02 #1, #2, #6;
D-04), and close two of the four documented contract gaps: `OwnDashboardRoleVolumeEntry` gains

**Revision 2026-09-06 (companion to Plan 150-05's second revision pass) adds ONE more field to this
plan's Task 2, discovered during 150-05's grounding, not part of the original D-07 scope:**
`OwnDashboardRoleVolumeEntry` also gains `CurrentThreshold *int64` (`json:"current_threshold"`) --
the registry threshold belonging to the row's OWN `current_tier` (e.g. 12 for "bronze"), which is a
DIFFERENT number from `NextThreshold` (the *next* tier's threshold, already covered). Plan 150-05's
dashboard role-volume badge label ("Bronze · 12+") needs exactly this number and has no other
server-supplied source for it: `PublicMemberBadgeProgress.stages` (Plan 150-03) lives on the public
member-profile response, not on `/me/dashboard`, and grounding confirmed the two response shapes are
not shared. This is the same shape of field this task already adds four of in the same struct
(`CurrentTier`/`NextThreshold`/`RemainingCount`/`NextTier`), computed in the same function
(`GetOwnDashboard`) from the same already-loaded registry call -- not a new query, not a new
endpoint, not a second registry (D-15 unaffected).

Purpose: `member_profile_dashboard_repository.go`'s own comment claims
`contribFamilyAscendingThresholds` mirrors the contribution repository "wortgetreu" — it is
actually a second, independently-maintained copy of the same three numbers. This plan removes
that copy and the corresponding dashboard contract gaps in one pass, since both changes touch
the same file.

Output: `member_profile_contribution_badges_repository.go`, `member_profile_dashboard_repository.go`,
`services/badge_service.go` read every threshold from `internal/badges`; `OwnDashboardData`
carries the two new fields the frontend needs to stop computing dashboard tiers itself, plus the
one additional `current_threshold` field Plan 150-05's revision requires.
