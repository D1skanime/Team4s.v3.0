<objective>
Repoint `member_profile_role_volume_repository.go`'s two independent threshold switches (D-02 #4,
#5) and `member_profile_progress_repository.go`'s `loadBadgeProgress` literal threshold arrays
(D-02 #3) to the Plan 150-01 registry, and close the remaining two of the four documented contract
gaps: `PublicMemberBadgeProgress` gains `current_tier` (D-05) and `role_volume` becomes a real
family inside `badge_progress` (D-06).

**Context Revision 2026-09-06 (D-24 through D-28) adds a fifth piece of work to this plan's
Task 2, superseding the pre-revision plan for 150-05, not this plan's original scope:**
`PublicMemberBadgeProgress` also gains a per-family ascending **stage list** (`stages`: an array of
`{code, threshold}` pairs), for all seven families including `role_volume`. This is the data Plan
150-05's frontend rewiring needs to render the multi-stage "ladder" strips (Anime-Projekte,
Beiträge, Mitgliedschaft, Punkte, and the role badge card's medal ladder) without holding a single
threshold number client-side. Backend-side this is nearly free: `buildBadgeProgress` already
receives each family's ascending threshold list as a parameter — this plan's job is to also copy
that same list into the new `Stages` output field, plus synthesize role_volume's "entry" stage
(threshold 1, absent from `badges.RoleVolume.Tiers` by design) directly in Go so the frontend never
needs that literal either.

Purpose: `member_profile_role_volume_repository.go` alone holds the role_volume thresholds twice
in the same file (`highestRoleVolumeTier`'s switch and `roleVolumeProgressBadge`'s switch) --
the single worst duplication in the whole phase. `loadBadgeProgress` is the one function that
already centralizes literals for four different families (progress/points/contribution/
membership) in one place, which makes it the natural place to also add the `current_tier` and
`stages` computations the frontend needs.

Output: both role-volume switches and `loadBadgeProgress`'s thresholds read from
`internal/badges`; `PublicMemberBadgeProgress` carries `current_tier` and `stages` for every
family, `role_code` for the new `role_volume` entries, and a Go-synthesized "entry" stage prefix on
every `role_volume` entry's `stages` list.

Note: this plan's file overlap with 150-02 on `shared/contracts/openapi.yaml` (different schema
sections -- OwnDashboard* there, PublicMemberBadgeProgress here) is why it depends on 150-02 as
well as 150-01, even though its Go-side work has no functional dependency on 150-02's contents.
</objective>
