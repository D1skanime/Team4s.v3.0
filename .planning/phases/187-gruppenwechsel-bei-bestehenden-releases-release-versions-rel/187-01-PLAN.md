<architecture_decisions>
These two open questions from 187-RESEARCH.md are resolved HERE, for the whole phase. Every later
plan must follow them without re-litigating:

- **A2 (pre-check vs savepoint, Pitfall 1): PRE-CHECK chosen.** The guard is a pure SELECT that
  runs BEFORE any DELETE/INSERT for a given mapping/patch. No savepoints anywhere in this phase.
- **A3 (fake-interface vs real-fixture for handler tests): REAL-FIXTURE chosen.** No new interface
  field is added to `FansubHandler`/`AdminContentHandler`. Handler tests in Plans 02/04/05 construct
  the real handler struct against a real Postgres fixture pool (mirrors
  `evecFixtureHandler`/`evecFixtureRequest` in `admin_content_episode_version_editor_context_test.go`).
- **Unification insight (resolves Pitfall 3 without special-casing):** Let `removed = current-group-IDs
  minus new-group-IDs` (pure set difference). D-07 ("removing a partner group follows the same
  Stufe-2 logic, no exception") and D-12 ("same-group update / adding a partner group is always
  allowed, only an actual replace is guarded") are BOTH already true of this definition: a same-group
  update or an add-only change has `removed = []` (guard is a no-op); only an actual replace/removal
  produces a non-empty `removed`. Plan 02 and Plan 03 therefore call the EXACT SAME two guard
  functions below with no call-site-specific exception logic -- only the surrounding
  alias-learning/theme-autoassign code differs between the two write paths, not the guard itself.
- **D-09 interpretation:** `release_crew_snapshots` rows are NEVER counted as a dependent by this
  guard, in either `inherited` or `independent` mode. The table holds no actual crew content of its
  own (only `release_version_id, fansub_group_id, snapshot_mode`) -- real credit content lives
  exclusively in `release_role_credit_lifecycles`, which DOES carry an ON DELETE RESTRICT FK and IS
  counted. This reading is why D-09's "leerer inherited-Snapshot zaehlt nicht" holds without any
  extra snapshot-content branching.
</architecture_decisions>
</context>
