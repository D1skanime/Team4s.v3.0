<objective>
Wire the existing Create-page controller to support the Discovery hand-off end to end: auto-adopt a
Jellyfin candidate from a `?jellyfin_id=` query param (reusing the existing, unmodified
`handleJellyfinCandidateAdopt` pipeline, D-08), prefill (never auto-run) the AniSearch search field with the
Jellyfin series name (D-09/D-26), branch the post-create redirect between the untouched manual path and the
new assisted path (D-10), and extract/extend the existing AniSearch conflict block into a real
"verbinden"/"neu anlegen" decision that fires at both the AniSearch-selection point (D-02) and the
save-time re-check from 165-03 (D-20).

**D-23 correction (live walkthrough 2026-09-21, AniSearch-ID 2788 -> Naruto #4):** the assumption that the
conflict block already renders correctly today and just needs new buttons was WRONG. `loadAniSearchDraftByID`
(`useAdminAnimeCreateController.ts` ~line 1014-1024) currently sets `aniSearchConflict` AND immediately fires
`window.location.href = resolved.redirect.redirectPath` in the same block — the hard navigation wins the race
against React's render, so the conflict UI (and this plan's whole "verbinden"/"neu anlegen" decision) is never
seen; the adopted Jellyfin draft is silently discarded. This plan's Task 2 removes exactly that one line
(and only that line — the unrelated, correct `window.location.href` in `handleCreateSubmit` for the manual/
D-10 redirect stays byte-identical). Making "Als neuen Anime anlegen" actually work after that fix additionally
requires a backend bypass, because `AnimeCreateEnrichmentService.Enrich` unconditionally returns the
conflict/redirect result once `FindAnimeBySource` finds a match and never fetches the real AniSearch draft in
that case — that backend half is 165-13 (new plan, same wave, independent files: `backend/internal/models/
admin_content.go`, `backend/internal/services/anime_create_enrichment.go`). Task 2 threads a `force_new: true`
flag through the existing enrich request on retry; 165-13 is the plan that makes the backend honor it. Both
plans can execute in parallel (no shared files) — by the end of this wave the feature works end to end.

Purpose: this is the single plan that touches the Create page's central state (`useAdminAnimeCreateController.ts`)
for every Discovery-related concern, avoiding a same-wave file conflict that would occur if this work were
split across two plans. `useAdminAnimeCreateController.ts` is already 1451 lines — over CLAUDE.md's
450-line limit before this plan touches it — so the auto-adopt-once + AniSearch-prefill logic (D-08/D-09)
is built as a new sibling hook file (`useCreatePageDiscoveryHandoff.ts`) that needs zero changes to the
controller itself (it only consumes values/callbacks the controller already exposes); only the D-20
second-trigger 409-handling, the D-23 auto-redirect removal, the ForceNew retry wiring, and the redirect
if/else — all of which live at or near the existing `loadAniSearchDraftByID`/`handleCreateSubmit` call
sites — remain as minimal additive edits inside the controller file.
(D-11's other two target pages — the episodes overview and edit pages — are wired in the separate,
dedicated 165-12 plan, kept out of this plan to stay within the 2-3-task-per-plan budget.)
Output: `AniSearchDuplicateDecision.tsx` (new), `useCreatePageDiscoveryHandoff.ts` (new),
`page.tsx`/`useAdminAnimeCreateController.ts`/`createAniSearchControllerHelpers.ts`/
`CreateAniSearchIntakeCard.tsx` extended additively.
