<objective>
Build the three pure/service-layer building blocks the Discovery feature needs before any HTTP handler
exists: (1) a TTL-cached, multi-library Jellyfin snapshot builder covering Series AND Movie item types
(D-06), (2) a pure status-priority resolver covering all four eventual Discovery states so later plans
(Ignore in 165-02/165-06, "Teilweise" in the checkpoint-gated 165-11) only need to pass booleans into an
already-tested function, and (3) a Discovery-specific seek cursor that reuses the existing cursor-pair
codec but seeks against an in-memory/cached snapshot instead of a SQL `ORDER BY` sequence (RESEARCH.md
Pitfall 4).

**D-27 correction (live walkthrough 2026-09-21):** `docker-compose.yml`'s `team4sv30-backend` service does
NOT pass `JELLYFIN_ALLOWED_LIBRARY_IDS` through to the container at all (only `JELLYFIN_API_KEY`/
`JELLYFIN_BASE_URL`/`JELLYFIN_STREAM_PATH_TEMPLATE` are in its `environment:` block) — `h.jellyfinAllowedLibraryIDs`
is therefore ALWAYS an empty slice at runtime today. `searchJellyfinSeries` (`jellyfin_client_series.go:59-76`)
already handles this correctly with a single unfiltered global `/Items` request; only when the list is
non-empty does it loop per-library with `ParentId` filtering (lines 78-103). Task 2's snapshot builder MUST
mirror BOTH of these branches, not just the filtered one — otherwise, with today's live runtime config, the
builder's per-library loop would execute zero times and Discovery would be silently empty in production,
unlike the existing direct-search endpoint which works fine via its own fallback. RESEARCH.md §17b also
flags that the global branch's real response size has not been individually live-measured (unlike the
filtered single-library request, which returned all 2111 items unbounded, §5b) — so the builder adds
defensive `StartIndex`/`Limit` pagination as a safety net against an undocumented Jellyfin-side response cap.

Purpose: Wave-1 foundation for the Discovery list handler built in 165-06. Building these three files
independently first lets 165-06 be a thin composition layer instead of a monolith, and lets the status
resolver's full truth table (including the "ignoriert"/"teilweise" branches that land in later plans) be
locked down and tested now, before any handler wiring exists to get it wrong.
Output: `jellyfin_discovery_cache.go`, `jellyfin_discovery_status.go`, `jellyfin_discovery_cursor.go`, each
with a dedicated `_test.go`.

**Operational note (not a task in this phase):** `JELLYFIN_ALLOWED_LIBRARY_IDS=5` in the live `.env` is not
a valid Jellyfin-12 library GUID (RESEARCH.md Pitfall 1, live-verified 2026-09-21). The correct GUID is
`5f65d0c8bdd71b782fc98205814a0d76`. This blocks live/manual Discovery testing until an operator corrects
the `.env` value — do not fix `.env` as part of this plan (config, not code, per D-12). All automated tests
in this plan use `httptest.NewServer` fakes and are unaffected. Because of D-27's global-fallback
requirement above, this misconfiguration does NOT block Discovery from working in production today — it
only means the empty-allowlist (global) branch is the one actually exercised live.
</objective>

## Trust Boundaries

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-165-01 | Information Disclosure | `jellyfin_discovery_cache.go` cache key | accept | Cache key is a fixed constant (`"jellyfin:discovery:snapshot:v1"`), not derived from user input — no cache-key injection surface. |
| T-165-02 | Denial of Service | Jellyfin snapshot fetch | mitigate | TTL cache (5 min) + explicit bypass flag prevents unbounded per-request Jellyfin fan-out; defensive `StartIndex`/`Limit` pagination (D-27) bounds each individual upstream response size too; this plan does not yet expose the bypass over HTTP (that is 165-06's concern, which must rate-reason about it at the endpoint layer). |
| T-165-03 | Tampering | Discovery cursor | accept | Cursor only encodes a seek position (`name|jellyfinItemID`), not an authorization decision; an invalid/tampered cursor silently restarts at page 1 per existing repo convention — no data leak possible from a manipulated cursor. |
</threat_model>
