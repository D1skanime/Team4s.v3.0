<objective>
Build the three pure/service-layer building blocks the Discovery feature needs before any HTTP handler
exists: (1) a TTL-cached, multi-library Jellyfin snapshot builder covering Series AND Movie item types
(D-06), (2) a pure status-priority resolver covering all four eventual Discovery states so later plans
(Ignore in 165-02/165-06, "Teilweise" in the checkpoint-gated 165-11) only need to pass booleans into an
already-tested function, and (3) a Discovery-specific seek cursor that reuses the existing cursor-pair
codec but seeks against an in-memory/cached snapshot instead of a SQL `ORDER BY` sequence (RESEARCH.md
Pitfall 4).

Purpose: Wave-1 foundation for the Discovery list handler built in 165-06. Building these three files
independently first lets 165-06 be a thin composition layer instead of a monolith, and lets the status
resolver's full truth table (including the "ignoriert"/"teilweise" branches that land in later plans) be
locked down and tested now, before any handler wiring exists to get it wrong.
Output: `jellyfin_discovery_cache.go`, `jellyfin_discovery_status.go`, `jellyfin_discovery_cursor.go`, each
with a dedicated `_test.go`.

**Operational note (not a task in this phase):** `JELLYFIN_ALLOWED_LIBRARY_IDS=5` in the live `.env` is not
a valid Jellyfin-12 library GUID (RESEARCH.md Pitfall 1, live-verified 2026-09-21). The correct GUID is
`5f65d0c8bdd71b782fc98205814a0d76`. This blocks live/manual Discovery testing until an operator corrects
the `.env` value — do not fix `.env` as part of this plan (config, not code, per D-12). All automated tests
in this plan use `httptest.NewServer` fakes and are unaffected.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Backend → Jellyfin | Server-side-only HTTP calls via `fetchJellyfinJSON`, reusing the existing `Authorization: MediaBrowser Token` transport from Phase 161 — no new transport code in this plan. |
| Backend → Redis | New trust boundary: the Discovery snapshot cache is written/read via an injectable client interface, keyed by a fixed non-user-controlled key. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-165-01 | Information Disclosure | `jellyfin_discovery_cache.go` cache key | accept | Cache key is a fixed constant (`"jellyfin:discovery:snapshot:v1"`), not derived from user input — no cache-key injection surface. |
| T-165-02 | Denial of Service | Jellyfin snapshot fetch | mitigate | TTL cache (5 min) + explicit bypass flag prevents unbounded per-request Jellyfin fan-out; this plan does not yet expose the bypass over HTTP (that is 165-06's concern, which must rate-reason about it at the endpoint layer). |
| T-165-03 | Tampering | Discovery cursor | accept | Cursor only encodes a seek position (`name|jellyfinItemID`), not an authorization decision; an invalid/tampered cursor silently restarts at page 1 per existing repo convention — no data leak possible from a manipulated cursor. |
</threat_model>
