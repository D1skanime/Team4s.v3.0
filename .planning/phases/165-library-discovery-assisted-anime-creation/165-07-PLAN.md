<objective>
Extend the existing single-folder Jellyfin metadata context/apply pipeline to a true multi-folder model:
(1) fix the D-05 "Verbinden" write path so it never force-overwrites an `anime.source` that already carries
an `anisearch:` reference — it writes the new Jellyfin folder additively into `anime_source_links` instead
(RESEARCH.md Pitfall 3); (2) extend `buildAnimeJellyfinContext` to return every connected `jellyfin:`
folder, not just the first, correctly flagging the main one; (3) add the missing `DELETE` path for
non-main folders, guarded server-side against removing the main folder; (4) audit both the connect and
folder-remove actions (D-21). D-16 (a renamed folder reconnecting via a new Jellyfin ID) needs no new code
— it is the same additive path, verified here by a regression test rather than new logic.

Purpose: this is the backend counterpart to 165-10 (frontend `AnimeJellyfinFolderList`), and it reuses
165-04's shared `collectJellyfinFolderOptions` helper (folder enumeration) so the D-14 episode-import
selector and the D-18 edit-page folder list are guaranteed to agree on what "connected" means. It shares
`admin_routes.go` with 165-06, hence the Wave-3 sequencing. `jellyfin_metadata_resync.go` is already 627
lines — over CLAUDE.md's 450-line limit before this plan touches it — so the additive-connect decision
logic and the entirely new DELETE handler both live in a new sibling file
(`jellyfin_source_folder_management.go`), mirroring 165-04's existing discipline for
`admin_episode_import_ownership.go`. Both new Postgres-touching repository functions
(`LinkAdditionalJellyfinSource`/`removeAnimeSourceLink`) are tested against a disposable, env-DSN-gated
database — never `team4s_v2` — using the exact same safety-gate pattern 165-02 already established for
`library_discovery_ignored_items_test.go`.
Output: extended context/apply handlers, new `LinkAdditionalJellyfinSource`/`removeAnimeSourceLink`
repository functions + DELETE endpoint, audit writes for both mutating actions.
</objective>
