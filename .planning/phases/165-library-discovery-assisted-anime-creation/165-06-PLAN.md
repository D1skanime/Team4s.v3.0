repository) into the actual `GET /admin/jellyfin/discovery` list endpoint, plus the `POST`/`DELETE`

within one wave — splitting them would create an artificial dependency without reducing complexity.

guard test proving the D-07 budget.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Admin browser → GET /admin/jellyfin/discovery | New read endpoint, admin-gated (`h.requireAdmin`), proxies Jellyfin-derived data — no write. |
| Admin browser → POST/DELETE /admin/jellyfin/discovery/ignore | New admin-mutating endpoints. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-165-11 | Elevation of Privilege | GET /admin/jellyfin/discovery | mitigate | `h.requireAdmin(c)` guard, identical to every other admin Jellyfin endpoint in the package (`jellyfin_search.go:36-39`) — no new authz pattern introduced. |
| T-165-12 | Denial of Service | Jellyfin snapshot fan-out via `refresh=true` | accept | Bounded by the number of allowed libraries (typically 1); admin-only surface, no anonymous access; TTL cache from 165-01 remains the default path. |
| T-165-13 | Repudiation | Ignore/unignore mutations | mitigate | Every mutation writes an `audit_logs` entry with `actor_app_user_id`/`actor_legacy_user_id` (D-21) before returning success. |
| T-165-14 | Tampering | `jellyfin_item_id` in ignore/unignore requests | accept | The ID is opaque and only ever used as a lookup/insert key against the isolated `library_discovery_ignored_items` table (no cross-table foreign-key trust implied); an admin ignoring an arbitrary/nonexistent Jellyfin ID has no security impact, only a no-op UI state. |
</threat_model>
