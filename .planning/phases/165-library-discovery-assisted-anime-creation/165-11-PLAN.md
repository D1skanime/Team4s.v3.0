<objective>
D-15 (CONTEXT.md, Auftraggeber-Entscheidung 2026-09-21) requires that any new table/migration or any new
`anime_source_links.source` semantics needed to store a Jellyfin-season-to-anime mapping be presented to
the Auftraggeber for approval BEFORE any migration or implementation work happens. This plan is that
presentation-and-approval gate, followed by the actual implementation ONLY after approval.

**This plan is deliberately isolated:** no other Phase 165 plan depends on it, and it depends on no other
Phase 165 plan. It is placed in the final wave specifically so it reads as optional/deferred relative to
the rest of the phase. The "Teilweise" badge visual state itself (color, copy, priority-ordering
placeholder) was already built as inert/unreachable code in 165-01's `resolveDiscoveryItemStatus` (the
`partial` parameter is hard-coded `false` everywhere until this plan lands) — the other three Discovery
states (Offen/Bereits vorhanden/Ignoriert) ship and work correctly without this plan ever executing.

Purpose: close the D-15 gap once schema approval exists, without blocking or gating any other phase
deliverable on that approval.
Output: (after approval only) a season→anime mapping storage mechanism, a batched
`IncludeItemTypes=Season` snapshot fetch, and "teilweise" status wiring into the already-existing status
resolver.
</objective>

  <options>
    <option id="option-a">
      <option-title>Option A — neue Tabelle `jellyfin_season_anime_mappings`</option-title>
      <pros>
        Saubere, eigenständige Struktur analog zu `anime_source_links`, aber mit zusätzlicher
        `season_index`-Dimension. Einfache Queries (`WHERE jellyfin_series_item_id=$1`). Erweiterbar für
        D-22 (Mehrserver, `server_key`-Spalte von Anfang an). Kardinalität (1 Staffel : 1 Anime vs. n:m)
        ist explizit modellierbar statt implizit über einen globalen UNIQUE-Constraint erzwungen.
      </pros>
      <cons>
        Neue Tabelle + neue Migration + neuer Repository-/Handler-Code (mehr Aufwand als Option B). Die
        Kardinalitätsfrage (kann eine Staffel zu mehr als einem Anime gehören?) muss beim Schema-Design
        explizit beantwortet werden, nicht implizit vom bestehenden Constraint geerbt.
      </cons>
    </option>
    <option id="option-b">
      <option-title>Option B — neue Semantik in `anime_source_links.source` (z. B. `jellyfin-season:&lt;seriesId&gt;:&lt;seasonIndex&gt;`)</option-title>
      <pros>
        Keine neue Tabelle, nutzt bestehende Infrastruktur (Composite-PK, bestehende Lese-Pfade
        `loadAnimeSourceLinks`, bestehende Existenzprüfung). Minimal-invasiv — die Existenzprüfung
        (`FindExistingAnimeByJellyfinIntakeRefs`) müsste nur um dieses Präfix-Muster erweitert werden.
      </pros>
      <cons>
        `anime_source_links.source` hat ein GLOBALES `UNIQUE(source)`-Constraint (nicht nur
        `UNIQUE(anime_id, source)`, `0047_add_anime_source_links.up.sql:6`) — passt zur 1-Staffel-zu-1-Anime-
        Annahme, verhindert aber jede zukünftige Mehrdeutigkeit ohne Schema-Änderung. Vermischt zwei
        fachlich unterschiedliche Konzepte (Ordner-Verknüpfung vs. Staffel-Verknüpfung) in einer Spalte mit
        reiner String-Konvention statt Typisierung.
      </cons>
    </option>
    <option id="option-c">
      <option-title>Option C — D-15 für diese Phase komplett zurückstellen (keine Persistenz)</option-title>
      <pros>
        Kein Schema-Änderungsrisiko, keine weitere Umsetzung nötig. Die restlichen drei Discovery-Status
        (Offen/Bereits vorhanden/Ignoriert) sind bereits vollständig funktionsfähig ohne D-15.
      </pros>
      <cons>
        Widerspricht D-15 direkt (Mehrstaffel-Ordner bleiben ohne erkennbaren "Teilweise"-Hinweis in der
        Liste — der Admin sieht sie schlicht als "Offen", auch wenn bereits ein Teil der Staffeln als Anime
        angelegt wurde). Betrifft laut Live-Messung ca. 1,3 % der Bibliothek (27/2111 Serien) — ein
        Nischenfall, aber kein Nullfall.
      </cons>
    </option>
  </options>
