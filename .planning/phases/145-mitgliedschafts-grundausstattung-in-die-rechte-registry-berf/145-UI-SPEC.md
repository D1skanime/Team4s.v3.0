## Scope Note (read first)

This phase is primarily backend/data-migration (moving `membershipBaselineActions` from a Go
slice into the `role_definitions`/`role_capabilities` registry as a reserved, non-assignable
pseudo-role). **No new page, no new route, no new visual surface is introduced.** The only UI
touched is the existing Capability Matrix at `/admin/roles` (`RolesClient.tsx` +
`RoleRail.tsx` + `RoleDetailPanel.tsx` + `RoleCapabilityDetail.tsx`), which already uses the
project's global `@/components/ui` primitives exclusively (`Button`, `Tabs`, `Accordion`,
`Switch`, `EmptyState`, `LoadingState`, `ErrorState`) and existing CSS custom-property tokens.
Zero new tokens, zero new components, zero new copy patterns beyond what is specified below.

Confirmed dead end, not in scope: `/admin/role-capabilities` (`RoleCapabilityTable.tsx`) is a
**redirect-only shim** to `/admin/roles` since Quick 260824-ek3 (see its own file header
comment) — it renders no real UI and needs no change.

Confirmed no-UI-change zones (verified in code, listed so the checker doesn't flag them as
missing): `GuidedRevokeFlow.tsx`'s `decisiveSourceFallback()` and
`userGroupRightsHelpers.ts`'s `decisiveSourceLabel()` already branch on
`decisive_source === 'membership_baseline'` distinctly from `'group_role'` and render
"Mitglieds-Grundrecht" / "dem Mitglieds-Grundrecht". Success criterion 3 requires this string
and this branch to stay byte-identical — the backend resolver must keep emitting
`decisive_source: 'membership_baseline'` (never `'group_role'`) even though the right is now
internally sourced from the pseudo-role's `role_capabilities` rows. This file is the record of
that "no change" contract; the executor must not touch these two functions.

## Interaction Contract (executor must implement exactly this — not a generic "handle it")

1. **New `role_kind` value.** Backend's role classification (wherever `RoleEntry.role_kind` is
   computed for the `/admin/roles` matrix response) must emit `role_kind: "reserved_baseline"`
   for the pseudo-role (code `group_member`, exact code confirmable by planner/executor against
   the locked backend decision — this UI-SPEC assumes `group_member` per STATE.md's example and
   the ROADMAP.md decision note). `frontend/src/types/admin-capability.ts`'s `role_kind` field
   type (`'global_app_role' | string`) already accepts this without a type change.

2. **`RoleRail.tsx` — `roleKindLabel()`:** add a branch **before** the existing
   `if (!isEditable && ...)` checks:
   ```
   if (role.role_kind === 'reserved_baseline') return 'Grundausstattung aller aktiven Mitglieder'
   ```
   Placement in the rail: the pseudo-role still falls under the existing "Gruppenrollen" bucket
   (`role_kind !== 'global_app_role'`) since no new rail section is introduced (out of scope —
   the user's locked decision is representation via the existing registry machinery, not a new
   grouping tier). Sort it **first** within "Gruppenrollen" (lowest `sort_order` among group
   roles) so admins see the foundational baseline before scanning named roles.

3. **`RoleRail.tsx` / `RoleDetailPanel.tsx` — `rowCountText()` / `holderCountText()`:** leave
   unchanged. `group_holder_count`/`global_assignment_count` stay `null`/`undefined` for this
   role (no new count query is introduced — out of scope, keeps backend surface minimal); the
   existing fallback already renders `–`. Do not wire a new "total active members" count query
   for this phase.

4. **`RolesClient.tsx` — `handleSelectRole()`:** the tab-default ternary
   `role?.role_kind === 'global_app_role' ? 'caps' : 'holders'` must also treat
   `role_kind === 'reserved_baseline'` as `'caps'`. The subsequent
   `if (role && role.role_kind !== 'global_app_role') { void loadHolders(roleCode) }` must
   likewise exclude `'reserved_baseline'` — **do not call `listRoleHolders('group_member')`**,
   its result semantics are undefined for a non-assignable pseudo-role.

5. **`RoleDetailPanel.tsx` — "Inhaber" tab content:** add a branch parallel to the existing
   `isGlobalRole` ternary for `role.role_kind === 'reserved_baseline'`, rendering the
   explanatory paragraph from the Copywriting Contract above (same paragraph style as the
   existing global-role branch), with no button below it.

6. **`RoleCapabilityDetail.tsx` — the `membershipBaselineCodes` filter:** currently *every*
   role's `configurableActions` excludes these 3 codes unconditionally. Change to: exclude them
   **only when `role.role_kind !== 'reserved_baseline'`**. For the pseudo-role itself, the 3
   actions flow through the normal category/accordion/`Switch` rendering unchanged — no special
   rendering path, they behave exactly like any other role's capabilities (this is the whole
   point of the phase: making them editable through the existing machinery).

7. **`RoleCapabilityDetail.tsx` — the static explanatory sentence:** currently rendered
   unconditionally for every `isEditable` role
   (`"Grundrechte aller aktiven Mitglieder: ..."`). Split into two cases:
   - `role.role_kind === 'reserved_baseline'`: render the new caution-line copy from the
     Copywriting Contract instead (no link — this *is* the target of the link).
   - every other `isEditable` role: render the updated sentence + `Button` deep link from the
     Copywriting Contract, replacing today's static, non-interactive sentence.

8. **No change** to `RoleCapabilityImpactPreviewModal.tsx`'s grant/revoke confirmation flow,
   `GuidedRevokeFlow.tsx`, or `userGroupRightsHelpers.ts` — verified in code, see Scope Note.
