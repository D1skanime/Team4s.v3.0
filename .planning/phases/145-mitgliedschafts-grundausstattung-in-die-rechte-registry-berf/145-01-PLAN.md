<objective>
Turn the membership baseline (three rights every active fansub-group member holds regardless of
role: `fansub_group.members.view`, `fansub_group_media.view`, `fansub_group_media.upload`) from a
hardcoded Go slice (`membershipBaselineActions`, `effective_rights.go:74-78`) into a reserved,
non-assignable pseudo-role (`group_member`) represented in `role_definitions`/`role_capabilities`,
per the locked ROADMAP.md decision (D-01 in the phase's "Getroffene Entscheidung" note). Wire a new
fail-closed startup check so a botched migration/seed can never silently leave active members with
fewer rights than before.

Purpose: closes ROADMAP.md Phase 145 Success Criteria 1, 3 (precedence unchanged), 4 (user_deny
still overrides, active-membership-only still holds), 5 (unassignable-but-capability-editable), and
6 (fail-closed on missing registry rows) at the Go/SQL foundation layer, before any Postgres
integration proof or frontend work depends on it.

Output: migration 0160 (reversible), `RoleMembershipBaseline` constant, cache-driven
`IsMembershipBaselineAction`, new `validateMembershipBaselineRegistryPresence` startup gate, and the
`LoadFansubGroupRoles` SQL fix that keeps the pseudo-role out of the assignable-role catalog despite
carrying the `fansub_group` context.
</objective>

  backing `IsCapabilityBearingRole()`, which gates the actual grant/revoke Switch in the Capability

  incorrectly become "assignable" (usable via `PUT` role-assignment endpoints that gate on
  `IsKnownFansubGroupRole`) unless explicitly excluded. This is a real correctness gap found by
  reading the actual SQL, not just the ROADMAP text — Task 3 below closes it.
- `IsMembershipBaselineAction` (`effective_rights.go:80-83`) has exactly one call site: the
  precedence `switch` in `evaluateGroupRights` at `effective_rights.go:356`, positioned after
  `state.UserAllow` and before `len(state.GrantingRoles) > 0`. This exact case ordering is the
  precedence contract (D01 from Phase 137) and MUST NOT move.
- `loadedCache` (`permissions.go:204-206`) is a package-level `map[string][]Action` populated only
  by `LoadCache`/`LoadFansubGroupCatalog`. Making `IsMembershipBaselineAction` read this cache (via
  `roleAllows`) instead of a static slice means every existing test fixture that calls
  `svc.LoadCache`/`svc.ReloadCache` with its OWN hand-built `map[string][]Action` and expects the 3
  baseline actions to resolve `Allowed:true`/`membership_baseline` MUST now also include a
  `RoleMembershipBaseline` entry with those 3 actions in that fixture, or the fail-closed check
  added in Task 2 will reject it. Two fixtures are confirmed to need this fix (found by reading, not
  assumed): `roleMatrixStubData()` in `capability_registry_test.go` (loaded once via that file's
  own `TestMain` for the WHOLE `permissions` package test binary) and `fullValidCacheData()` in
  `permissions_reload_test.go` (used directly by `TestReloadCacheReplacesCacheAtomically` and
  `TestReloadCacheFailsafe`). Both are explicit tasks below — skipping either breaks existing green
  tests.
- `backend/internal/repository/testmain_test.go` and `backend/internal/handlers/testmain_test.go`
  each call `LoadFansubGroupCatalog` with a stub implementing ONLY `CatalogLoader` (no
  `LoadRoleCapabilities` method) — the `loader.(CacheLoader)` type assertion in
  `LoadFansubGroupCatalog` fails for them, so `loadedCache` is never touched by those two
  `TestMain`s and the new fail-closed check in Task 2 is never reached from them. Do not add a
  `LoadRoleCapabilities` method to either stub — that would be an unrequested, unrelated behavior
  change to two other packages' shared test fixtures.
