## Component Contract — New "Prüf-/Freigabe-Rechte" Section (RDEL-03)

### Placement (locked by 140-CONTEXT.md + 140-RESEARCH.md Pattern 3)

- New component: `frontend/src/app/admin/users/tabs/ReviewDelegationSection.tsx`.
- Mounted in `GroupSection.tsx` as a **sibling** to `GroupRolesSection` and the Accordion — same tree level, same visual tier (own `SectionHeader` at `level={3}`), never nested inside the Accordion/`CategoryTable`.
- Rendered once per group membership card, directly below `GroupRolesSection` and above the generic effective-rights Accordion, so the reading order top-to-bottom is: group name → roles → **Prüf-/Freigabe-Rechte** → generic capability categories (including the now-deny-only "Review" category row).
- This ordering is deliberate: it establishes the dedicated section as the primary, first-encountered surface for these three actions, before the admin ever reaches the generic Accordion's "Review" category further down — reinforcing "grant lives here, not there."

### Visual separation contract (the core RDEL-03 requirement)

The section must be recognizable as a *different kind of control* from both `GroupRolesSection` (role chips) and the generic Accordion (capability rows), not merely a copy of one styled differently:

1. **Own `SectionHeader`** with `title="Prüf-/Freigabe-Rechte"` and a `description` that states the mechanism in one sentence (see Copywriting Contract) — the description is what a plain Accordion category row does NOT have, and is the single strongest visual/textual differentiator.
2. **Fixed, non-expandable row list** (exactly 3 rows, one per delegable action, in this fixed order: Medien/Bilder → Notizen/Texte → Mitwirkungen). Unlike `CategoryTable`'s rows, these rows are never click-to-expand — there is no accordion chevron, no "Rollenquellen/Reason-Code" detail panel. This is deliberate: delegation has no roles, no reason, no history-of-role-provenance to disclose, so offering an expand affordance here would visually imply parity with the generic mechanism that this decision explicitly says is NOT the same mechanism.
3. **`Switch` control, not `Button` verbs.** The generic Accordion uses business-verb buttons ("Recht zusätzlich erlauben" / "Recht entziehen"). This section instead uses one `Switch` per row (checked = currently delegated). This is an intentional interaction-pattern difference, not just a style change — it signals "this is a direct toggle of a specialized grant," distinct from the generic override's verb-driven confirm flow.
4. **No shared component tree with `GuidedGrantFlow`/`GuidedRevokeFlow`.** Confirmed by 140-RESEARCH.md: those components require a `reason` field this domain's `ReviewDelegationCommand` does not have, and the audit-event DB trigger forbids a reason on delegation events. Build a small, self-contained mutate handler local to `ReviewDelegationSection.tsx` (or a co-located `ReviewDelegationRow.tsx` if the file approaches the 450-line cap — see File Size Note below).

### Row anatomy (3 fixed rows)

Each row (visually: a horizontal flex row inside a bordered card, `gap: var(--space-2)`, rows separated by `gap: var(--space-3)`):

```
[ Switch ]  Medien/Bilder prüfen           [ status text / inline error, right-aligned or below on narrow width ]
[ Switch ]  Notizen/Texte prüfen           [ ... ]
[ Switch ]  Mitwirkungen prüfen            [ ... ]
```

- Row label is plain body text (16px/400), never a `Badge` — `Badge` is reserved for status/provenance elsewhere in this phase (see below), not for the row's own name, to avoid visually equating "row label" with "status pill" the way `CategoryTable`'s "Effektiv" column does.
- Row order is fixed and NEVER derived from a sorted list — it must always render `review.image.decide`, then `review.text.decide`, then `review.contribution.decide`, matching `isDelegableReviewAction`'s canonical order and the CONTEXT.md wording ("Medien/Bilder, Notizen/Texte, Mitwirkungen").

### Interaction model (per 140-RESEARCH.md Pitfall 3 + Pitfall 4 + Assumption A3 — deliberate design choice made here, not copied from guided flows)

This section uses **optimistic toggle + inline error**, with an asymmetric eligibility rule matching the backend's own asymmetric grant/revoke behavior:

| State | Switch appearance | Click behavior |
|-------|---------------------|-----------------|
| Currently granted (`checked=true`) | Enabled, "on" (accent) regardless of the target's current eligibility | Click immediately flips to unchecked (optimistic), fires `PUT .../review-delegations {action_code, grant: false}`. On success: stays unchecked, transient success text disappears after a few seconds (or no persistent text at all — the unchecked state IS the confirmation). On failure: Switch snaps back to checked, inline error text appears below the row (see Copywriting Contract), Switch remains interactive for retry. |
| Not currently granted, target eligible | Enabled, "off" | Click immediately flips to checked (optimistic), fires `PUT .../review-delegations {action_code, grant: true}`. On success: stays checked. On failure (e.g. a race where eligibility changed server-side between page load and click): Switch snaps back to unchecked, inline error text appears, matching CONTEXT.md's confirmed 422 semantics. |
| Not currently granted, target ineligible (from RDEL-01's read response eligibility context) | Disabled (`aria-disabled`, visually muted per `Switch`'s existing `disabled` styling — do not invent a new disabled visual) | No click handler fires; a static inline note (13px, `var(--color-text-secondary)`) explains why, e.g. "Nicht aktiv in dieser Gruppe." / "Konto ist deaktiviert." / "Keine verifizierte historische Zuordnung." — exact copy in Copywriting Contract |

No confirmation modal, no reason field, no destructive-action styling on revoke — this matches the locked decision that `ReviewDelegationCommand` carries no reason and revoke is a low-friction, frequently-reversible admin action (unlike role removal or a generic user-deny, which do go through confirmation elsewhere in this codebase). If the checker flags "destructive action without confirmation," this is a deliberate, CONTEXT.md-grounded exception: cite this section, not an oversight.

### Empty / loading / error states for the section as a whole

- **Loading** (initial GET in flight): render the 3 rows with each `Switch` in a disabled placeholder state (or reuse the project's existing skeleton convention if `UserGroupRightsTab` already has one — check `LoadingState` primitive before inventing a new skeleton). Do not show `EmptyState` while loading.
- **Section-level fetch failure** (GET itself fails, not a per-row mutation failure): replace the 3-row list with `ErrorState` (`title="Fehler beim Laden"`, `description` from `getErrorStateCopy(error, { defaultDescription: 'Die Prüf-/Freigabe-Rechte konnten nicht geladen werden.' })`), reusing the exact existing helper — do not hand-roll a new error-copy function.
- **No "empty state" concept applies** — the 3 rows always render (they are fixed, not data-driven), so `EmptyState` is never shown inside this section itself.

### Provenance surfacing in the generic rights view (RDEL-03's "no silent loss of control" requirement)

This is the second mandatory behavior this UI-SPEC must define, per the CONTEXT.md binding decision. Changes to `CategoryTable.tsx` / `CapabilityDetailRow.tsx` for the three `review.*.decide` action codes only:

1. **Grant control removal.** In `CapabilityDetailRow.tsx`, the `showGrant` condition (`!state.allowed`) must become `!state.allowed && !isReviewDelegationAction(state.action_code)` for these three actions specifically — i.e., when one of the three review actions is not currently allowed, the "Recht zusätzlich erlauben" button is **not rendered** at all for it. In its place, render a static, non-interactive explanatory line (13px, `var(--color-text-secondary)`) reading exactly: **"Gewähren nur über „Prüf-/Freigabe-Rechte" oben."** (see Copywriting Contract) with a `Button variant="ghost" size="sm"` labeled **"Zu Prüf-/Freigabe-Rechte springen"** that scrolls/focuses the new section (anchor-link or `scrollIntoView` on the `ReviewDelegationSection` root — reuse whatever scroll-to-section mechanism already exists in this codebase for deep-linking, e.g. the pattern noted in Phase 128's "owner deep link" precedent, if one is reusable; otherwise a simple `id`+`scrollIntoView({behavior: 'smooth'})` is acceptable and does not need a new primitive).
2. **Deny control stays, unchanged.** `showRevoke` (`state.allowed && !state.non_deniable`) and the "Abweichung entfernen" ghost button both remain exactly as they are today for these three actions — no code path change to the deny/revoke side.
3. **Decisive-source labeling already handles the specialized-grant case.** `decisiveSourceLabel`'s existing `specialized_grant` branch already renders the human-readable specialized-grant label (from `state.specialized_grants`) instead of a role name — this already answers "where did this allow come from" for the "Quelle" column. No change needed there. What's missing (and must be added) is the **grant-affordance replacement** described in point 1, so the admin who previously saw a working "Recht zusätzlich erlauben" button for `review.image.decide` and no longer does is told exactly why and where to go, rather than the button silently vanishing.
4. **Category row itself is unaffected.** The "Review" category continues to appear in `CATEGORY_ORDER` and the Accordion exactly as today (Option (a) territory per 140-RESEARCH.md's Contradiction section — this UI-SPEC does NOT hide/filter the whole category; only the grant affordance inside it changes for these three specific action codes). This keeps the deny path fully visible and discoverable, per the binding decision's explicit rationale for why deny must survive.

This is the exact, concrete mechanism the CONTEXT.md/RESEARCH.md's "no silent loss of a control" requirement demanded a decision on — do not leave it as "TBD, planner's choice."

### File Size Note (CLAUDE.md's 450-line cap)

- `ReviewDelegationSection.tsx`: expect roughly 90–140 lines for 3 fixed rows + fetch/mutate wiring. Should comfortably stay under 450 lines as a single file; no proactive split needed unless the planner also inlines the API-client calls and error-copy logic here — if so, extract a `useReviewDelegations` hook (mirroring `useGroupMembersClaimActions.ts`'s precedent) to keep the component itself lean.
- `CapabilityDetailRow.tsx` (currently 98 lines): the point-1 change above adds roughly 15–25 lines (one conditional branch + one ghost button + one static note). Stays far under the cap — no split needed.
- `userGroupRightsHelpers.ts` (currently 102 lines): add one small exported predicate, e.g. `isReviewDelegationAction(actionCode: string): boolean` (mirrors `isDelegableReviewAction` on the backend, duplicated client-side as a pure string check against the three known codes — do not fetch this from the matrix, since it's a fixed, hardcoded triad per CONTEXT.md, not catalog-driven). Adds ~6 lines. No split needed.
- `GroupSection.tsx` (currently 105 lines): mounting the new section adds ~5–8 lines. No split needed.

## Cross-Reference to Backend Contract (for planner/executor alignment — not a UI decision, restated for convenience)

- `GET .../review-delegations` response must carry, per row, at least: `action_code`, `granted: bool`, and eligibility context (`membership_active`, `app_user_active`, `has_verified_claim` or an equivalent combined `eligible_for_grant: bool`) so the UI can render the disabled/muted "ineligible" row state above without waiting for a 422. This is restated from 140-CONTEXT.md's adopted recommendation — the UI contract in this document depends on that field existing; if the planner scopes it out, the "ineligible, greyed out" row state in this spec cannot be implemented and must fall back to "always enabled, reactive 422-only" (a materially worse but not blocking UX regression — flag it if it happens).
- Mutation is a single `PUT .../review-delegations` with `{action_code, grant: boolean}`, matching the existing `capability-overrides` PUT shape — the optimistic-toggle interaction model above assumes this single-endpoint, boolean-intent shape.
