already. It has `props.animeID: number`, `props.groupID: number`, `props.title: string`
(release/episode title, NOT the anime title -- for this entry point's context line, the anime
title is not directly available on this component's props; use `props.episode_title ?? props.title`
as the closest available "what this report is about" label, since the full `AnimeDetail` is not
threaded down to this leaf), and `props.groups: {name: string}[]` (the groupLine logic at line 23
already derives `groupNames` from it). Mount after the `heroGroupLine` paragraph (line ~61), inside
the `heroIdentity` div, but ONLY when `props.groups.length === 1` (coop releases with multiple
groups have no single unambiguous target group for a hint -- document this as the plan's explicit
scope boundary, not a bug to fix now).

Plan 191-17 already built: `isEligibleForContributions` (`@/lib/contributionsEligibility`),
`ProposalForm`'s `prefill` prop (`{fansubGroupId, fansubGroupName, animeId, animeTitle}`).
`MyProposalsSection.tsx` (unchanged by this plan) is the reference pattern for how an authenticated
page already resolves `ownGroups` (`getMyMemberships()`) and `roleDefinitions`
(`useRoleCatalog('anime_contribution')` + `contributionRoleDefinitions(roles)` from
`./contributionRoles`) before rendering `ProposalForm` -- `ReportHintEntryPoint` needs the same two
pieces of data once a user clicks through, so it may defer fetching them until the click (lazy,
since most page visitors never click) or fetch them eagerly alongside the eligibility check --
plan's discretion, document the choice.
