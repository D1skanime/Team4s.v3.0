<objective>
Wire D-29's release selection into the live wizard: Step 1 gains an optional release `Select`
(global `@/components/ui` primitive) right after the anime/project field, backed by Plan 191-33's
`useProposalFormReleaseOptions` hook, and the chosen release flows through to BOTH submit paths --
`release_version_id` on the existing, already-backend-ready own-group `anime_contributions` path
(the backend has validated this field via `GroupParticipatesInReleaseVersion` since Phase 67, no
backend change needed there), and the new `related_release_version_id` on the foreign-group
`fansub_group_hints` path (validated server-side by Plan 191-32's `ensureHintReleaseContext`). The
Select's actual markup is built as its own small component, `ProposalReleaseSelect`, specifically so
Plan 191-35 (D-30's release-page entry point, where Step 1 is skipped because the project/group are
already known via `prefill`) can mount the exact same control in its context header instead of
duplicating the option-list/loading-state markup a second time. Also closes D-33's frontend half:
the 409 error text shown to the user must match whichever of Plan 191-32's two literal conflict
strings the backend actually returned, keyed off whether the submitted hint was release-scoped.

Purpose: a release select that only lived in the backend/types layer would be invisible to users;
this plan is what actually lets a member narrow a hint to one specific release instead of always
hitting "whole project", unblocking the exact UAT complaint behind D-29 (two correction hints to
different releases of the same project were wrongly treated as duplicates before D-32's index fix).
Output: a working release Select in the wizard, extracted into its own reusable component; both
submit paths carry the selection; the 409 message matches the backend precisely.
</objective>
