<objective>
Close D-30, a real bug plus a UX gap exposed once Plan 191-34 made the release selection real:
`ReleaseDetailHero.tsx` passes `ReportHintEntryPoint` the EPISODE/release title
(`props.episode_title ?? props.title`) as `animeTitle` -- never the actual project title, even
though `releaseDetailPageData.tsx` already loads it (`animeTitle = animeResponse.data.title`,
line 72) and simply never forwards it. Separately, the release page is exactly the context where a
user is MOST likely to want to narrow a hint to that one release -- yet the prefilled flow (Plan
191-17/18) skips Step 1 entirely, which is where Plan 191-34 mounted the release Select. This plan:
(1) fixes the bug by threading the real `animeTitle` through `releaseDetailPageData.tsx` ->
`ReleaseDetailHero.tsx` -> `ReportHintEntryPoint`; (2) extends `ProposalFormPrefill` with two new
optional fields (`relatedReleaseVersionId`, `relatedReleaseLabel`) so the release page's entry point
can both preselect the current release AND show it synchronously in the context header without
waiting on a network round-trip; (3) mounts Plan 191-34's `ProposalReleaseSelect` in the prefilled
form's context header (the only place it CAN live when Step 1 is skipped), wired to the same
`useProposalFormReleaseOptions` hook already running in `ProposalForm.tsx`, so the preselection
remains changeable exactly as D-30 requires on the project-page entry point.

Purpose: a release select nobody can reach from the two "Fehler melden" entry points (D-12) would
leave D-29's whole-plan value locked behind the one, harder-to-find `/me/contributions` entry point;
the `animeTitle` bug independently misleads users about which project they are reporting on.
Output: a correct project title in the context header; both entry points can preselect AND change
the release; zero regression on the existing HeroSection.tsx call site.
</objective>
