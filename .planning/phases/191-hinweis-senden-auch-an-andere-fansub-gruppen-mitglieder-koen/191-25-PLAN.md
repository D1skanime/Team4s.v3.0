<objective>
Close D-23: `POST /api/v1/me/fansub-group-hints` currently only checks that `related_anime_id`
references a row in `anime` (FK existence) -- it never checks that the chosen
`(target_fansub_group_id, related_anime_id)` pair actually has a matching row in
`anime_fansub_groups`. Live proof of the bug: hint id 4 linked fansub group 29 (AnimeOwnage) to
anime id 2 (11eyes), even though `anime_fansub_groups` has no row for that pair (only groups
24/25/26 are actually linked to anime 2). Fix it by reusing the existing, exact-purpose helper
`ensureAnimeFansubProjectContextExistsInDB` (`anime_project_notes_repository.go:19-39`, same
`repository` package, already returns `ErrInvalidAnimeFansubContext`) from inside
`FansubGroupHintsRepository.CreateHint`, and map that error to a 404 in the handler using the
exact precedent in `admin_content_anime_project_timeline.go:50-53`. Also close out the D-25
comment sweep for every backend file this round touches (directly, by this fix, or because it was
separately named in D-25's file list without being touched by anything else this round).

Purpose: D-23 is a real data-integrity gap at a trust boundary -- the server must not let a
client assert an arbitrary group/project pairing that has no basis in `anime_fansub_groups`, since
a Leader or Platform-Admin acts on the hint believing the pairing is real.
Output: a server-enforced, tested group/project validation on hint creation; every pre-existing
repository test updated to seed the now-required `anime_fansub_groups` row; six backend files
with D-25-compliant, fact-first code comments; a `docs/BACKEND_ARCHITEKTUR.md` note describing
the new check.
