<objective>
Close the D-12 gap surfaced during live-UAT review: the invite 'Registrieren' path currently
only PREFILLS the email (via `login_hint`, 135-01) but cannot LOCK it, and the Keycloak
registration page shows no invite context. Both are properties of Keycloak's registration FORM,
which lives in the `team4s` login theme -- and that theme today ships only messages/resources/
theme.properties, NO `.ftl` template overrides, so it inherits Keycloak's stock register form.

This plan adds a custom register template to the `team4s` theme that (D-12) renders the email
field prefilled + read-only when an email is supplied, and (D-13) shows a short invite-onboarding
context line. Purpose: a cold, zero-context invitee is guided cleanly through account creation and
cannot silently change the email into a later accept-time `email_match` rejection.

REALITY / SCOPE HONESTY (read before implementing):
- Keycloak's registration form does NOT natively prefill from `login_hint` the way the login form
  does. Task 1 MUST first determine, against the running Keycloak, (a) its exact version and which
  stock template applies (`register.ftl` vs user-profile `register-user-profile.ftl`), and (b) the
  actual mechanism by which the invited email reaches the template (login_hint attribute, a
  `firstName`/`email` form value, or an added query param the FTL can read). Implement against what
  is TRUE for this Keycloak, not an assumption.
- The DYNAMIC group/role name is very likely NOT available to the register template (Keycloak does
  not forward arbitrary invite context to its theme). D-13 therefore requires only a GENERIC
  invite-context line (e.g. "Du erstellst ein Konto, um eine Team4s-Einladung anzunehmen."). A
  dynamic group name is a stretch goal ONLY if Task 1 finds a clean, theme-readable mechanism;
  otherwise ship the generic line and record the limitation in the SUMMARY.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Keycloak register form (theme template) rendering an invitee-supplied email | The email is a client-controllable UX prefill only; making it read-only is a usability guard, NOT a security control. Authoritative enforcement stays the server-side accept-time `email_match` in `FansubGroupInvitationRepository.Accept()` (unchanged). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-135-08-01 | Tampering | readonly email field (client-side) | accept | A determined user can still bypass `readonly` via devtools; that is fine -- the accept-time server `email_match` rejects any mismatch regardless. The lock is UX (prevent accidental change), not a boundary. |
| T-135-08-02 | Spoofing | invited email injected into the register template | mitigate | Escape the value in FreeMarker (`?html`); never render it unescaped. No new realm-level trust granted; open registration behavior is unchanged when no invite context is present. |
</threat_model>
