# Phase 133 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note (from CONTEXT.md/RESEARCH.md):** This is a hardening phase, not a redesign. No new
visual language is introduced. This contract LOCKS the existing design-token values already
established in `frontend/src/styles/globals.css`, `frontend/src/components/ui/ui.module.css`, and
the profile CSS modules, and gives prescriptive rules for the concrete work items this phase must
execute (CSS-module split, container-query conversion, a11y fixes, image budgets). Where the
codebase currently contains conflicting/duplicate values for the same purpose (see RESEARCH.md
"Pattern 1"), this contract picks ONE canonical value — the executor must consolidate to it, not
invent a third variant.

## Typography

These are the EXISTING sizes already used consistently across `profile.module.css` and
`ui.module.css`. This phase does not introduce a new type scale. Any NEW or MODIFIED heading text
this phase produces (specifically the memorial-hero heading fix, any new `aria-live` status
copy, any new disclosure-toggle labels) MUST use one of these four values — do not add a fifth
size.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px (1rem) | 400 (regular) | 1.5 |
| Label | 14px | 700 (bold) | 1.5 |
| Heading | 20px | 700 (bold) | 1.25 |
| Display (page H1) | 32px (2rem) | 700 (bold) | 1.05 |

Weights: exactly two — 400 (body copy, descriptions, bio text) and 700 (labels, eyebrows,
headings, the page H1, all button text). No 500/600 weight exists anywhere in the current profile
CSS; do not add one.

**Pre-existing legacy sizes out of this phase's scope:** the profile CSS modules also contain many
smaller ad hoc sizes (e.g. `0.78rem`–`0.95rem`, `1.35rem`, `3rem`, `clamp(2rem,3vw,2.75rem)`) used
for badge chips, timeline meta, avatar initials, etc. These are pre-existing visual debt.
Consolidating them into the 4-size scale above is a redesign and is explicitly OUT OF SCOPE
(CLAUDE.md/REQUIREMENTS.md forbid general redesign in this milestone) — leave them as-is unless a
specific PMUI-05 duplicate-selector conflict (RESEARCH.md "Pattern 1") forces a choice between two
existing values for the SAME selector, in which case pick the value closer to this table's Label/
Heading rows.

### Heading hierarchy decision (PMA11Y-01, resolves RESEARCH.md Open Question A3 / Pitfall 6)

`MemberProfileMemorialHero.tsx` currently renders the member name twice: once as `<h1>` via
`PageHeader`'s `title` prop (`.pageTitle`, `clamp(2rem,3vw,2.75rem)`/700), and again as `<h2
className={styles.heroTitleRow}>` (visually styled via `.heroTitle`-adjacent rules) a few lines
later. This is a duplicate accessible name and must be fixed as part of this phase, not deferred.

**Locked decision:** The memorial hero keeps exactly ONE heading for the member name, and it is
the visually styled one already used by the non-memorial hero:
- Render the member name as `<h1 className={styles.heroTitle}>` (32px/700/1.05 — the Display row
  above) inside `.heroCopy`, matching `MemberProfileHero.tsx`'s existing non-memorial pattern
  exactly.
- Drop `PageHeader`'s `title` usage for the memorial hero entirely (do not render a second,
  differently-styled H1 above the panel).
- If the "Fansub-Member" eyebrow text is still wanted above the hero panel, render it as a plain
  `<p className={styles.eyebrow}>` (14px/700, per Label row) — reusing `profile.module.css`'s own
  `.heroEyebrow` class, not `PageHeader`.
- Net result: every profile page state (public, owner-preview, memorial) has exactly one `<h1>`
  containing the member's display name, and no component below it skips a heading level.

## Color

These are the EXISTING semantic tokens from `globals.css`. No new colors are introduced by this
phase — this table documents the 60/30/10 split of tokens ALREADY governing the profile surface,
so the executor knows exactly which token is "the accent" when touching CSS during the split/
de-duplication work.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--surface-canvas` (`#f6f4ef`) via `--bg-primary` | Page background, `body` background |
| Secondary (30%) | `--surface-card` (`#ffffff`) | Hero panel base, membership cards, badge cards, `.rhythmBand` panels |
| Accent (10%) | `--color-primary` (`#5f84dd`) / `--accent-deep` (`#185fa5`) | See "Accent reserved for" below |
| Destructive | `--color-error` (`#dc3545`) / `--button-danger-*` (Wine family) | Destructive actions only (none in this presentation-only phase, but any error-state iconography/border must reuse this token) |

Accent reserved for (explicit list — do not add new accent usage while touching CSS this phase):
- Primary interactive elements already using the accent: role/project/badge progress-bar fill
  (`.projectProgress span` gradient), membership-card link icon color (`.membershipAction`),
  contribution cover icon color, `data-role-code` chip accents (each role has its own dedicated
  `--role-accent-*` token — these are semantic role identity colors, not decorative, and stay
  as-is).
- **Focus indication uses a SEPARATE accent**, not the primary blue: `--focus-outline`
  (`rgba(255, 106, 61, 0.62)`, an orange/coral) and `--focus-ring`
  (`rgba(255, 106, 61, 0.18)`) are the ONLY colors allowed for `:focus-visible` treatment
  (PMA11Y-03/04). This is already the global `:focus-visible` rule in `globals.css` — every new or
  moved interactive element (carousel controls, disclosure toggles, badge-stage buttons) inherits
  it automatically via `outline: 2px solid var(--focus-outline)`; do not override with the blue
  primary accent or invent a third focus color.
- Do not extend the blue accent to purely decorative elements (backgrounds, borders that aren't
  interactive-state) — that is the specific over-use pattern the project's own
  `docs/frontend/ui-system.md` "Offene Designfragen" flags as unresolved and this phase does not
  need to resolve it further.

### Responsive strategy (PMUI-01/02/03/06, CONTEXT.md D-01/D-02/D-03)

- **Page-level composition** (`frontend/src/app/members/[slug]/page.module.css`) keeps its
  existing purpose-based `@media` breakpoints (1399px / 1099px / 760px, collapsing the 2-column
  `.profilePair`/`.contributionPair*` grids to 1-column). Do NOT convert this file's page-level
  transitions to container queries — RESEARCH.md's Architecture Patterns section explicitly
  scopes `@media` to page-level composition only.
- **Every reusable component** (hero, badge chain and its split children, membership cards,
  project/contribution cards) uses `@container` exclusively for its own internal responsive
  behavior, scoped via `container-type: inline-size` on its own wrapping element — mirroring
  `FocalCarousel.module.css`'s existing pattern (1 `@media` block total, and that one is for
  `prefers-reduced-motion`, not layout). Target: after the split, no reusable component module
  should contain a device-width `@media` rule for layout purposes.
- No document-level horizontal overflow at any width from 320px through widescreen and at 400%
  zoom (PMUI-01/06): every flex/grid child that can overflow gets `min-width: 0` (already the
  dominant pattern in `page.module.css`/`profile.module.css` — preserve it in split-out modules).
- Long German text and correct umlauts must remain readable, not clipped, at 400% zoom: keep
  `rem`-based sizing and natural word wrapping; do not introduce `overflow-wrap: anywhere` as a
  blanket fix (`docs/frontend/ui-system.md` explicitly forbids this) — use it only on already-flagged
  special cases (e.g. `.heroSpecialAward`, `.recentItemBody strong` already use it correctly for
  unpredictable user-generated names).

### Image delivery contract (PMPF-06/08, CONTEXT.md D-07/D-08/D-09)

- Keep `next/image` via the existing `ResponsiveImage` wrapper (`frontend/src/components/ui/ResponsiveImage.tsx`) — do not hand-roll `<img>`/custom `srcset`.
- Every image request supplies a **truthful `sizes`** string matching the actual rendered width at
  each container-query breakpoint introduced by the responsive work above (avatar, hero backdrop,
  badge artwork, membership logos) — no generic `100vw` fallback where the real display width is
  known and bounded.
- Reserve geometry for every image (explicit `width`/`height` or `aspect-ratio`) to avoid CLS —
  the `.roleHeroArtwork` `aspect-ratio: 1` resolution above is the canonical pattern to copy for
  any other artwork element.
- Bound quality explicitly via `next.config.mjs`'s `images.qualities` array (Next.js 16) rather
  than per-call-site quality props.
- `dangerouslyAllowLocalIP` in `next.config.mjs` must be gated to non-production
  (`process.env.NODE_ENV !== 'production'` or an explicit env flag) — it is currently
  unconditional (RESEARCH.md Pitfall 2), a real SSRF-adjacent config gap per Next.js's own docs.
- `localPatterns` MUST retain `/media/**`, `/member-achievement-badges/**`, and `/covers/**`
  verbatim after any `next.config.mjs` edit (RESEARCH.md Pitfall 3 — a documented E426-crash
  precedent in this repo).
- Byte budgets are measurement-anchored (D-08): extend
  `frontend/scripts/collect-member-profile-evidence.mjs`'s `--mode budget-check` /
  `LOCKED_BUDGETS`/`evaluateBudget()` with per-image and aggregate KB ceilings derived from a real
  baseline measured on both seed profiles (`sheppert`, `csubs-leader`) — exact KB numbers are set
  during planning/execution from that measurement, not invented here. Do NOT extend
  `verify-profile-image-delivery.mjs` for byte budgets — that script is a format/cache correctness
  probe with unrelated fixed fixtures (RESEARCH.md Pitfall 1).
