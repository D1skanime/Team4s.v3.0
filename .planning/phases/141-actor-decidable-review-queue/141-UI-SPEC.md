## Component Contract 1 — Two Tracks, Unmistakably Separated (RQUE-02/RQUE-03/D01/D03)

### Decision: `Tabs` primitive at the track level, existing Button-toggle stays at the sub-view level

Do **not** add `"own"` as a third value inside the existing "Offen"/"Verlauf" `Button`-toggle
(`ReleaseReviewsSection.tsx:263-278`). That toggle switches between two views of the **same**
actionable track (open vs. decided-history, both still governed by capability + self-exclusion
predicates). Mixing "Wartet auf Fremdprüfung" into that toggle would visually imply it is a third
view of the same list — exactly the confusability this phase must prevent.

Instead, wrap the whole "Prüfungen" region in the global `Tabs` primitive
(`@/components/ui` — already used for `UserDetailPageClient`'s D-03 tab rewrite and
`GroupSection.tsx`'s Rollen/Änderungen tabs, Phase 138) with exactly two top-level items:

```tsx
<Tabs
  items={[
    {
      id: 'queue',
      label: 'Zu prüfen',
      badge: <Badge variant="info">{actionableCount}</Badge>,
      content: <ReleaseReviewsSection fansubId={fansubId} />, // existing component, modified per below
    },
    {
      id: 'own-pending',
      label: 'Wartet auf Fremdprüfung',
      badge: <Badge variant="muted">{ownPendingCount}</Badge>,
      content: <OwnPendingReviewsSection fansubId={fansubId} />, // NEW component
    },
  ]}
  activeId={lane}
  onActiveIdChange={setLane}
  keepMountedIds={new Set(['queue', 'own-pending'])}
/>
```

- `actionableCount = counts.text + counts.image` (sum of the two backend-computed,
  already-self-excluded, already-capability-filtered counts — see Cross-Reference to Backend
  Contract). Never a global/unfiltered number (D06).
- `ownPendingCount` comes from the new `view=own` counts response (own submissions currently
  pending, per D01/D03's Pattern 2). This number is **not** added to `actionableCount` anywhere,
  in any badge, at any level — the two counts are structurally never summed or compared in the UI.
- URL sync: reuse the existing `?tab=pruefungen` parent-level param
  (`ReleaseReviewsSection.tsx:81`) and add a sibling `?lane=queue|own` param (default `queue`,
  omitted from the URL when default — mirrors the existing `view`/`type`/`category` omit-if-default
  convention at lines 82-87). `Tabs`'s controlled `activeId`/`onActiveIdChange` wires directly to
  this, matching the `UserDetailPageClient`'s `?tab=` precedent (138-15).
- `keepMountedIds` for both tabs: each lane owns its own independent fetch/filter state: switching
  tabs must not discard in-flight filters or force a refetch of the other lane (mirrors
  `UserGroupRightsTab`'s D-03 lazy-fetch-once precedent). Do NOT unmount-and-remount `queue` when
  `own-pending` is active or vice versa.

### Why this satisfies the "unmistakable separation" requirement

1. **Different component idiom.** `Tabs` (ARIA `tablist`/`tab`/`tabpanel` roles, distinct visual
   strip) is reserved exclusively for the queue-vs-own-pending split. The pre-existing
   "Offen"/"Verlauf" `Button` toggle stays as-is *inside* the "Zu prüfen" tab only — a reviewer
   never sees both mechanisms competing for the same job.
2. **Different badge color.** "Zu prüfen" always uses `Badge variant="info"` (accent-adjacent
   blue). "Wartet auf Fremdprüfung" always uses `Badge variant="muted"` (grey, deliberately
   de-emphasized). This is a locked, permanent asymmetry, not a stylistic default — it visually
   encodes "this is your actionable work" vs. "this is just status information about you."
3. **Different label semantics.** "Zu prüfen" is an imperative/actionable label. "Wartet auf
   Fremdprüfung" ("waiting for someone else's review") is explicitly passive and third-person —
   the label itself states that the actor is not the one who acts here.
4. **No shared numeric surface.** The two counts are never concatenated, summed, or shown as
   "X of Y" anywhere (closes D06 for this specific UI surface too).

### `ReleaseReviewsSection.tsx` changes required inside the "Zu prüfen" tab

- **Remove** the "Mitwirkungen {counts.contribution}" badge (`ReleaseReviewsSection.tsx:261`)
  entirely. Per 141-RESEARCH.md Pitfall 4, `counts.contribution` is a literal SQL `0` today and
  always was — an honest, real, non-fabricated counter is the whole point of this phase; a
  permanently-fake zero directly contradicts that. Do not replace it with anything — the row
  becomes `<Badge variant="info">Texte {counts.text}</Badge> <Badge variant="info">Bilder
  {counts.image}</Badge>` only, both using `variant="info"` (previously `Texte`/`Bilder` were
  already `info`; only the fake `muted` Mitwirkungen badge is deleted).
- **Counters row `aria-label`** changes from `"Offene Prüfungen nach Typ"` to **`"Prüfungen, die
  du entscheiden kannst, nach Typ"`** — makes the ownership/scope of the count explicit in the
  accessible name, not just visually implied.
- **`SectionHeader` description** changes from `"Release-Texte und Release-Bilder einzeln prüfen
  und sicher entscheiden."` to **`"Release-Texte und Release-Bilder einzeln prüfen und sicher
  entscheiden. Eigene Einreichungen zählen nicht mit — sie erscheinen unter „Wartet auf
  Fremdprüfung".` ** — the description itself states the counting rule in plain German, satisfying
  the "counter's presentation must make unambiguously clear what it is counting" requirement
  through explicit text, not just structural separation.

### NEW component: `OwnPendingReviewsSection.tsx`

Location: `frontend/src/app/admin/fansubs/[id]/edit/OwnPendingReviewsSection.tsx` (sibling to
`ReleaseReviewsSection.tsx`, per 141-RESEARCH.md's Recommended Project Structure).

- **No sub-view toggle.** Unlike the queue's Offen/Verlauf split, this lane has exactly one state:
  the actor's currently-pending own submissions. Per D14, a decided item simply disappears (the
  lane naturally re-fetches/filters to pending-only) — there is no "own-pending history" to expose
  (D14 explicitly forbids adding one). Do not render an Offen/Verlauf toggle here.
- **Filters:** reuse the full existing filter dimension set (Projekt/Anime, Episode/Release, Typ,
  Bildkategorie, Suche) per 141-RESEARCH.md Open Question 1's recommendation (minimal new surface,
  consistent UX). Unlike the queue's Typ filter (see Contract 2 below), **both** `Texte`/`Bilder`
  options are always shown here regardless of the actor's review capability — D10 explicitly says
  this lane's filters are independent of review capability, since it only ever contains the
  actor's own rows.
- **Table columns:** `Eingereicht` (submitted_at) · `Projekt` · `Episode / Release` · `Typ` ·
  `Status`. **No `Aktion` column, no `Einreicher` column** (the submitter is always the viewing
  actor — redundant), **no per-row navigation link into the review detail page.** The review
  detail page (`/admin/fansubs/[id]/reviews/[reviewId]`) is a decision-workflow surface; this lane
  is read-only status information the actor already fully knows the content of (they submitted
  it) — adding a link would either need a redundant no-actions detail variant or would confusingly
  land on a page shaped for reviewing. Keep this lane list-only. Use `Table` (not
  `variant="withActions"`) — no action column exists.
- **Status badge variants:** reuse `releaseReviewQueueStatus()` from `releaseReviewPresentation.ts`
  unchanged (already returns the correct label/variant pairs for pending/confirmed/rejected/
  tombstoned) — do not invent a parallel status-label function.
- **No `EmptyState`/loading duplication:** reuse `TableEmptyState` (inside the `Table`) and
  `LoadingState` exactly like `ReleaseReviewsSection.tsx` does today — same primitives, same
  visual weight, so the two lanes still feel like siblings in the same design system even while
  being structurally distinct per the points above.

## Component Contract 2 — No Leakage of Inaccessible Work (RQUE-05/D06/D07/D10/D13)

### Filters only show actor-usable review types (D10)

Today's `ReleaseReviewsSection.tsx:310-324` unconditionally renders `<option
value="text">Texte</option>` and `<option value="image">Bilder</option>` in the "Typ" filter,
regardless of what the actor can actually review. This must change:

- The `Typ` `<Select>` renders an `<option>` **only** for review kinds present in a new
  `allowed_types: ReleaseReviewType[]` field returned alongside `counts` (see Cross-Reference to
  Backend Contract). Do not infer "allowed" from `counts.text > 0` / `counts.image > 0` — a
  capability the actor holds but with zero currently-open items must still render as a selectable,
  honestly-empty option (an actor who can review images but has 0 open images right now should
  still see "Bilder" as a filter choice, just yielding an empty list); a capability the actor does
  **not** hold must never appear as an option at all, full stop, regardless of count.
- **If `allowed_types.length <= 1`**: omit the entire `Typ` `FormField`/`Select` from the toolbar
  — a filter with zero or one real choice is noise, and for an image-only reviewer, rendering a
  disabled/single-option "Typ" selector would itself be a subtle leak ("there's a dropdown here,
  so there must be other types somewhere"). Full omission, not a disabled control.
- **Bildkategorie filter**: only rendered if `'image' ∈ allowed_types`. If the actor cannot review
  images at all, omit this `FormField` entirely too (today it is shown-but-disabled when
  `type !== 'image'` — that disabled-but-visible behavior is fine for the *within-queue*
  text-vs-image toggle, but must not apply when the actor structurally cannot review images at
  all, per the same "no dropdown implying hidden types" reasoning above).
- **Projekt/Episode/Suche filters**: unchanged — these operate on already-authorized data
  (whatever `items`/`animeOptions`/`releaseOptions` the backend already returned), so they carry
  no leakage risk regardless of capability shape.

### Neutral empty state — exact copy locked (D13)

`TableEmptyState` inside the "Zu prüfen" tab, `view === 'open'`, **no filters active** (the true
empty-queue case):

- title: `Keine offenen Prüfungen`
- description: **`Aktuell keine Prüfungen für dich offen.`** (verbatim D13 lock — do not
  paraphrase, do not add "of N", do not add a reason)

`TableEmptyState`, `view === 'open'`, **filters active**, zero matching rows (a distinct case from
the true empty state — filtering narrowed an otherwise non-empty or empty set, and the copy must
stay equally neutral about *why*):

- title: `Keine offenen Prüfungen`
- description: `Für die gewählten Filter sind aktuell keine Prüfungen offen. Passe die Filter an
  oder setze sie zurück.` (neutral, filter-scoped, does not imply reviews exist elsewhere or that
  the actor lacks rights for more — reuses the existing "Filter zurücksetzen" button already in
  the toolbar as the next action, no new button needed)

`TableEmptyState`, `view === 'history'`: unchanged behavior, adjust description only for parity:
`Für die gewählten Filter liegen keine vergangenen Entscheidungen vor.`

**What the empty state must never show** (explicit, per D06): no "0 of N" phrasing anywhere, no
global/unfiltered total, no disabled-but-visible filter option for a type the actor cannot review
(see filter contract above), no secondary text implying other reviewers have more work, no link or
hint toward reviews the actor cannot access.

### "Wartet auf Fremdprüfung" reveals no reviewer information (D07)

- `OwnPendingReviewsSection.tsx`'s `SectionHeader` description: `Deine eigenen offenen
  Einreichungen — sie warten auf Prüfung durch eine andere Person.` States the *fact* of pending
  external review without naming or counting who. Never render a reviewer name, reviewer count,
  "assigned to," or "N Personen können das prüfen" anywhere in this lane's rows, detail, or empty
  state.
- Own-pending empty state (`TableEmptyState`, zero own-pending rows): title `Keine offenen
  Einreichungen`, description `Du hast aktuell keine eigenen Einreichungen, die auf Prüfung
  warten.` — again strictly about the actor's own submission count, zero mention of reviewer
  availability.
- The status `Badge` shown per row is the existing pending/confirmed/rejected/tombstoned vocabulary
  (`releaseReviewQueueStatus()`) — never a custom "in Bearbeitung von X" or "wartet auf N Prüfer"
  label.

## Component Contract 3 — Honest 403 / 409 / Next-Exhausted (RQUE-05/D04/D05/D08/D11)

All three states below reuse the existing `ErrorState`/inline-status primitives already shipped
in this codebase — no new primitive is introduced.

### 403 on detail (D04) — existing catch-all must be replaced

Today, `frontend/src/app/admin/fansubs/[id]/reviews/[reviewId]/page.tsx:68,103-104,208-217` treats
**every** load failure identically: a boolean `loadError` flag renders one generic inline message
(`"Diese Prüfung konnte nicht geladen werden. Kehre zur Prüfliste zurück und versuche es
erneut."`) regardless of whether the backend returned 404 (genuinely missing/cross-group, existing
`TestReleaseReviewDetailCrossGroupIsScopedNotFound` behavior) or the new D04 403 case
(exists, but not actor-decidable: either lacking capability or the actor's own submission).

**Required change:**

1. `loadError` becomes `loadError: unknown` (store the actual thrown error, mirroring
   `ReviewDelegationSection.tsx`'s existing `loadError: unknown` + `getErrorStateCopy` pattern),
   not a boolean.
2. Branch on `getErrorStatus`-equivalent (reuse `ApiError`'s `.status`, already imported in this
   file for the 409 branch) inside the render:
   - **`status === 403`**: render `ErrorState` directly (bypass `getErrorStateCopy`'s built-in 403
     branch — its default "Keine Berechtigung" / "wende dich an einen Fansub-Admin" copy is
     misleading here, since asking an admin cannot fix "this is your own submission," and the
     actor may well hold the relevant capability in general, just not for this item). Use this
     phase-specific, locked copy instead:
     - title: `Nicht entscheidbar für dich`
     - description: `Diese Prüfung ist entweder dein eigener Beitrag oder du hast aktuell keine
       Berechtigung dafür.`
     - action: `<Button href={returnHref} variant="secondary">Zurück zur Prüfliste</Button>`
       (reuses the existing `returnHref` constant already defined in this file, line 80)
   - **`status === 404`** (or no status / network failure): keep the existing generic message
     unchanged (`"Diese Prüfung konnte nicht geladen werden..."`) — this already correctly covers
     "genuinely does not exist / cross-group," which is deliberately a different, more opaque
     message than the 403 case (per 141-RESEARCH.md Pattern 3's explicit contrast with the
     Phase-128 neutral-404 convention — that convention is for public member privacy and is NOT
     imported here; Phase 141's 403 is intentionally more informative than a neutral 404, matching
     D04's explicit requirement that 403 and "not found" be semantically distinguishable to the
     user, not just to the network layer).
3. Both branches use the same `ErrorState` component (danger-styled) and the same
   `Button variant="secondary"` return-to-list action — visually consistent, textually distinct.

### 409 on decide (D08, D11) — existing pattern already correct, lock it as canonical

`page.tsx:161-181`'s existing `decisionState.kind === 'conflict'` branch already implements
exactly what D08/D11 require: a specific "already decided by someone else" message plus two clear
recovery actions, not a silent failure or generic error. **This is correct today — do not change
its mechanics.** Lock it as the canonical pattern for this phase:

- Message (unchanged): `Diese Prüfung wurde bereits von einer anderen Person entschieden.`
- Actions (unchanged): `Button variant="secondary"` → `Aktuellen Stand laden` (re-fetches detail)
  and `Button variant="secondary"` → `Zurück zur Prüfliste`.
- **New requirement for this phase**: the same 409 branch must also fire for the *newly-introduced*
  "no longer pending" case (D11 — an item that became non-pending for a reason other than a
  competing decision, e.g. a lifecycle change), not only `REVIEW_ALREADY_DECIDED`. Extend the
  existing `error.code === 'REVIEW_ALREADY_DECIDED'` check (`page.tsx:165`) to also match whatever
  sentinel code the plan assigns the "target not pending" 409 case (per 141-RESEARCH.md,
  `ErrReviewTargetNotPending` already exists server-side) — both must route to the **same**
  `conflict` UI state and message; do not add a second, differently-worded panel for this second
  409 cause, since to the actor both mean the same thing ("someone else's action already changed
  this before yours landed").

### "Next" — three states, none of them silent (D05)

Two related surfaces both need this treatment, sharing one presentational contract
("NextReviewControl"):

**A. Post-decision "next" (existing, `page.tsx:357-368`)** — currently silently omits the
"Nächste offene Prüfung" button when `decisionState.response.data.next` is `null`, with **no**
replacement message. This is exactly the "unexplained disappearance" this phase must fix.

**B. Standalone "skip to next" while still viewing a pending item (NEW)** — the existing
`getNextReleaseReview` API function (`frontend/src/lib/api.ts:10541`) is wired but currently never
called from any UI. Add a `Button variant="secondary"` labeled `Nächste Prüfung` next to the
existing decision actions (`page.tsx`'s `styles.decisionActions` row), visible whenever
`detail.status === 'pending'` and `showDecisionActions` is true (i.e., whenever Approve/Reject
themselves are shown) — this lets a reviewer move past an item without deciding it.

**Locked states for both A and B** (same three outcomes, same copy, reused as one small
presentational unit — extract a shared `NextReviewControl` helper/component if the file would
otherwise exceed 450 lines, see File Size Note):

| State | Behavior |
|-------|----------|
| Resolving | `Button` renders with its existing `loading` prop (already used elsewhere in this file for decision buttons) — never an unbounded/separate spinner element. Button remains disabled while loading; a second click cannot double-fire. |
| Next item available | Navigate immediately (post-decision: `router`/`href` to `next.id`'s detail route, unchanged existing behavior; standalone skip: same navigation, via the `getNextReleaseReview` response). |
| **No next item available (exhausted)** | Do **not** silently omit the button/hide the control. Replace the `Button` with a neutral inline message, same visual slot: **`Keine weiteren Prüfungen für dich offen.`** (deliberately echoes D13's locked empty-state wording for consistency — this is genuinely the same fact, reached via a different path). For case A (post-decision success), this message renders alongside the existing "Zurück zur Prüfliste" button, replacing only the now-absent "Nächste offene Prüfung" button. For case B (standalone skip), this message renders in place of the "Nächste Prüfung" button and stays visible (does not silently re-enable) until the underlying data changes (e.g. a subsequent successful decision re-triggers the same check). |
| Fetch error (network/5xx, standalone skip only — case A's next comes bundled with the decision response and shares that response's own error handling) | Reuse the existing `styles.inlineError` + `role="alert"` + `Button variant="secondary"` retry convention already used for `pageError`/`loadInitial` failures elsewhere in this same component family — do not invent a new error-copy pattern for this one control. |

## Cross-Reference to Backend Contract (for planner/executor alignment — not a UI decision, restated for convenience)

- `GET .../release-reviews/counts` (queue tab) must gain **`allowed_types:
  ('text'|'image')[]`** alongside the existing `text`/`image`/`contribution`/`image_categories`
  fields, reflecting the actor's actual review capability independent of current open-item counts.
  The Typ/Bildkategorie filter-omission contract above depends on this field existing distinctly
  from a zero count.
- `GET .../release-reviews?view=own` (or equivalent, per 141-RESEARCH.md Pattern 2) and its
  paired counts call feed `OwnPendingReviewsSection.tsx` and the `own-pending` tab's badge count.
  Per D10, this view's response is **not** filtered by `allowed_types` — both text and image rows
  the actor personally submitted are always included regardless of the actor's own review
  capability.
- `GET .../release-reviews/:id` must return **403** (not 404) with a distinguishable error (e.g. a
  new `REVIEW_FORBIDDEN` code, matching this handler's existing `writeReadError` switch-on-sentinel
  pattern per 141-RESEARCH.md) for an existing-but-not-actor-decidable item, and the frontend's
  `ApiError.status`/`.code` must be inspectable from the thrown error the same way the existing 409
  `REVIEW_ALREADY_DECIDED` check already works (`page.tsx:161-166`) — the 403-branch UI contract
  above assumes this shape.
- `POST .../release-reviews/:id/decision` must map **both** "already decided" and "no longer
  pending" outcomes to 409 with codes the frontend can route to the same `conflict` UI state (see
  Component Contract 3's 409 section) — reuses the existing `ErrReviewAlreadyDecided`/
  `ErrReviewTargetNotPending` sentinels already present server-side per 141-RESEARCH.md.
- `GET .../release-reviews/:id/next` (the existing, currently-unused `getNextReleaseReview`
  function) must, when there is no further actor-decidable item, return a response the frontend
  can distinguish from a transient fetch failure (e.g. `data: null` with a 200, matching its
  existing typed return shape `ReleaseReviewNextResponse` — already `{ data: ReleaseReviewQueueItem
  | null }`, no contract change needed here, only a UI consumer that finally uses it, per
  Component Contract 3 case B).
