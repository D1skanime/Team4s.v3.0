<objective>
Eliminate the real, evidence-found N+1 in the release-review read path (141-RESEARCH.md
Pitfall 1: `authorizedKinds()` calls `CanReviewForFansubGroup` once per review kind, and each
call independently re-runs the full `ResolveGroupRights` source load) by resolving group
rights exactly once per handler call and projecting both `review.text.decide` /
`review.image.decide` states from that single resolution -- without weakening the existing
`ReviewContextResolver` verified-membership gate `CanReviewForFansubGroup` applies before it
ever consults `ResolveGroupRights` (a real elevation-of-privilege risk if a naive
"just call ResolveGroupRights directly" refactor were used instead -- see the threat model).
Also closes L-01's remaining test gap for the decision-time guard's concurrency behavior
under a mid-flight delegation revoke.

Purpose: this consolidation is the shared foundation every later plan in this phase builds
on (self-exclusion, own-pending view, Detail/Next predicate sharing) -- doing it first and
correctly means those plans extend one clean resolution path instead of three divergent ones.
`review_service.go` (Decide's own, separate, transaction-scoped authorization call at
review_service.go:180-182) is explicitly NOT touched by this plan -- it must remain
byte-for-byte authoritative, per 141-CONTEXT.md D11 and the orchestrator's binding carry-over
note 3.

Output: `permissions.Service.ResolveReviewGroupAuthorization`, an extracted
`release_review_handler_authz.go`, an updated `releaseReviewPermissionService` interface, a
regression test proving single-resolution, and a new real-Postgres concurrency test proving
the decision-time guard survives a mid-flight revoke.
</objective>
