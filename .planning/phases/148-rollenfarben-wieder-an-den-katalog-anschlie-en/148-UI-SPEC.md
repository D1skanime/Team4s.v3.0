# Phase 148 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Phase framing (read first)

This phase is **CSS-variable plumbing, not new UI**. No new component, layout, spacing value,
typography value, or copy string is introduced. The binding baseline, the 10 affected CSS
modules/files, and the 9 success criteria are defined verbatim in `.planning/ROADMAP.md` under
"### Phase 148: Rollenfarben wieder an den Katalog anschließen" — that section remains the
authoritative source of truth; this document translates it into a design contract so the
checker/planner/executor have one place to verify visual-restoration parity and contrast safety.

The "design decision" this phase makes is: **restore the exact pre-regression visual formulas
using the already-proven `data-color-key` → `--role-chip-accent` seam**, and **prove text/border
contrast holds for all 15 catalog hex values** on every restored surface. Sections below that do
not apply to a CSS-plumbing phase (Spacing, Typography, most of Copywriting, Registry) are marked
N/A with a one-line reason rather than inventing scope.

### Restoration Rule (locked design decision for this phase)

Every one of the ten dead surfaces must restore **its own pre-existing color-mix formula and
ratio exactly as originally authored** — the only change is the *source token*
(`--role-accent-<code>` / `--role-accent-default` / `--role-accent-base` → `--role-accent` derived
from the `data-color-key` seam). No surface may invent a new mix ratio, tint percentage, or
fallback value as part of this phase — that would silently change the visual outcome and is out
of this phase's scope (see ROADMAP Scope-Grenze). The one documented exception is
`ContributionCard`, which today has no live color formula at all (plain `Badge variant="info"`)
and, if wired for color in this phase, must adopt the already-proven `.role-catalog-chip`
14%-background / border / text formula rather than a bespoke one.

### Contrast Requirements (WCAG gate for the restored formulas)

Two thresholds apply, matching the existing precedent in `frontend/src/lib/roleCatalog.accessibility.test.ts`:

- **Text on a role-tinted background → WCAG AA 4.5:1** (normal text; use 3:1 only for genuinely
  large/bold text ≥24px or ≥19px-bold, e.g. avatar-initial glyphs may qualify — treat as normal
  text 4.5:1 by default unless the executor confirms the large-text exception applies).
- **Non-text UI indicators (borders, focus rings, chip outlines, progress/status indicators) on a
  role-tinted or adjacent surface → WCAG AA 3:1** (WCAG 1.4.11 non-text contrast).
- **Purely decorative effects with no text/boundary semantic** (radial-gradient glows, drop-shadow
  bloom on `RoleBadgeCard`/`.status`) are **exempt**, matching the existing test's scope (it only
  asserts text/border/focus, never decorative gradients) — do not invent a new gate for these.

| Surface | Formula (existing, being restored) | Rule | Threshold |
|---|---|---|---|
| `PublicNoteCard` `.head` | `color-mix(role-accent 55%, --color-border)` bg, `--text-primary` text | text | 4.5:1 |
| `PublicNoteCard` `.role` | `color-mix(role-accent 38%, --text-primary)` text on `.head` bg | text | 4.5:1 |
| `PublicNoteCard` `.avatar` | `color-mix(role-accent 70%, #000)` bg, white text | text | 4.5:1 |
| `PublicNoteCard` `.card` bottom stripe | solid `role-accent` 8px border vs. adjacent `--surface-card`/`--color-border` | non-text indicator | 3:1 |
| `ProjectMemberPage` / `ProjectMemberReleasesSection` / `MemberCurrentProjectsSection` chips | text `color-mix(role-accent 78–82%, --text-primary)` on bg `color-mix(role-accent 12–14%, --surface-card)`; border `color-mix(role-accent 32–34%, transparent)` | text + border | 4.5:1 text / 3:1 border |
| `RoleBadgeCard.stages` / `MemberBadgeChain` roles group | `color-mix(role-accent 28–42%, --border-subtle)` borders/box-shadows | non-text indicator | 3:1 |
| `FansubEdit` role-toggle (unselected) | raw `--role-accent` used directly as **text and border color** (no mix, 100% strength) against the toggle's own background | text | 4.5:1 — **highest-risk case**, verify per hex |
| `FansubEdit` role-toggle (selected) | solid `--role-accent` fill, **white `#fff` text** | text | 4.5:1 — **highest-risk case**, verify per hex |
| `FansubEdit` historical-role small label | `color-mix(role-accent 74%, --text-secondary)` text | text | 4.5:1 |
| `ContributionCard` role Badge (once wired) | must reuse `.role-catalog-chip` formula (14% bg mix, fixed `--role-chip-text`/`--role-chip-border`/`--role-chip-focus`) | text + border | 4.5:1 text / 3:1 border (already proven by existing test) |
| `/me/projects` role row | 3px `borderInlineStart: var(--role-accent)` vs. row background | non-text indicator | 3:1 |

**The two "unselected"/"selected" `FansubEdit` role-toggle rows are the only cases in this phase
where a catalog hex is used at full 100% strength as text color or as a solid fill behind white
text**, rather than tinted/mixed with a neutral surface. This is the row most likely to fail 4.5:1
for lighter/warmer hex values in the palette (e.g. `#a16207`, `#6b7f2a`) — flag this explicitly for
verification during implementation; if any of the 15 hex values fails, the fix must stay within
the *formula* (e.g. adopt a mixed/tinted treatment analogous to the proven chip pattern) and must
NOT alter the locked hex palette itself.

**Dark theme:** confirmed not applicable — `frontend/src/styles/globals.css` defines a single
light palette with no `[data-theme]` attribute, no `prefers-color-scheme` media query, and no
`ThemeProvider` anywhere in `frontend/src`. No dark-mode contrast variant is required for this
phase.

**How this is checked:** `frontend/src/lib/roleCatalog.accessibility.test.ts` already proves
4.5:1/3:1 for the six working surfaces' shared `.role-catalog-chip` 14%-mix formula, for all 15
`ROLE_COLOR_KEYS` plus the neutral fallback, by reading the real `globals.css` and computing
`color-mix` output in test code (no browser required). This phase's automated gate must extend
this pattern — either new assertions in the same file or a sibling test — to additionally cover
every formula in the table above that is **not** already the proven `.role-catalog-chip` formula
(i.e., every row except `ContributionCard`), computed per one of the 15 `ROLE_COLOR_KEYS` hex
values, reading each restored CSS module's actual color-mix expression rather than hand-copying
percentages into the test. This is the "analogous automated contrast test" required by ROADMAP
Success Criterion 8 (`getComputedStyle`-measured, not by eye) and by this phase's Ausgangsbefund.

**Neutral/unresolved fallback:** if `color_key` does not match one of the 15 catalog values (or is
absent), the seam already falls back to `[data-color-key='neutral'] { --role-chip-accent: #596176 }`
for the six working surfaces. The ten restored surfaces must fall back identically — no surface
introduces a second, different "no color" treatment.
