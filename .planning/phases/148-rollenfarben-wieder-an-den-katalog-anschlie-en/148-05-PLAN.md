<objective>
Thread `role_color_key` through the public note pipeline analogous to how Phase 147 threaded
`role_code` (CONTEXT decision #6): backend DTOs `PublicReleaseNote`/`ProjectMemberNote`, all three
query sites (`ListReleaseVersionNotesCursor`, `loadNotes`, `ProjectMemberPublicRepository.ListNotes`
— all three already `LEFT JOIN role_definitions rd`), the OpenAPI contract, both TypeScript types,
`PublicNoteCard`'s prop surface, and its two consumers (`ReleaseNotesList.tsx`,
`ProjectMemberNoteCard.tsx`). No additional catalog fetch is introduced on the public SSR pages —
the field rides the existing join, exactly like `role_code` did.

Purpose: the public note card cannot color itself today because `color_key` never reaches it —
`role_code` was added in Phase 147 but `PublicNoteCard`, unlike the six `categoryForRole`
consumers, has no catalog provider to look color up from (per ROADMAP Ausgangsbefund).

Output: `role_color_key` present end-to-end (Go struct field → SQL column → OpenAPI schema → TS
type → `PublicNoteCard`'s `roleColorKey` prop → `data-color-key` on the rendered `<article>`); a
new integration sub-case in `public_note_role_code_integration_test.go` proving the field at all
three query sites against real Postgres; a new unit-test case in `PublicNoteCard.test.tsx` proving
`data-color-key` renders from `roleColorKey` and is stable across a `roleLabel` change.
</objective>
