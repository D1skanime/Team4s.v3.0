# Phase 173 Plan 01: Display-Variant Backend (Static JPEG + Animated WebP) Summary

**processImage now writes a third `display` media-file variant (JPEG re-encode capped at 1920px for static images, animated WebP capped at 960px for animated GIFs via ffmpeg) and stops silently re-encoding WebP originals to `.jpg`.**

## Performance

- **Completed:** 2026-10-02T15:45:38Z
- **Tasks:** 2
- **Files modified:** 3

## Accomplishments
- Every static image upload (JPEG/PNG/GIF-single-frame/WebP) through `POST /api/v1/admin/upload` now produces an additional `display` `media_files` row (long edge <=1920px, never upscaled, JPEG quality 88) via the new `generateStaticDisplayVariant` helper
- Animated GIF uploads now produce a `display` row that is a genuine animated WebP (VP8X+ANIM chunks, long edge <=960px, infinite loop), generated by shelling out to ffmpeg (`libwebp_anim` codec) with a fixed argument vector
- Fixed a pre-existing bug: WebP-mimetype uploads were silently re-encoded to JPEG and renamed `.jpg` (`imageExtFromMime`'s default branch); WebP originals now keep their `.webp` extension and exact uploaded bytes
- Because `StoreGeneratedAnimeImage` (segment-preview auto-generation, Phase 172) and the planned Phase 173 backfill CLI (173-07) both call `processImage` internally, this single change transitively fixes 3 of the 6 write paths identified in `173-RESEARCH.md`
- Exported `GenerateAnimatedWebPDisplay(ffmpegPath, srcGIFPath, destWebPPath)` for reuse by the 173-07 backfill tool
- No new HTTP route registered — `processImage` stays a private method; `main.go` route count unchanged (98, verified via `grep -c 'v1\.\(GET\|POST\|PUT\|DELETE\)'`)

## Decisions Made
- Display variant for static images is always JPEG regardless of source mimetype (no new encoder dependency)
- WebP thumb/display encoding paths both re-encode to JPEG (imaging library can decode but not encode WebP); only the `original` variant preserves raw WebP bytes
- ffmpeg failure for the animated-WebP display path is treated as non-fatal (same posture as `saveSegmentVideoPreview`'s preview-generation failure handling)

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Fixed WebP-thumb generation crash caused by the new webp extension mapping**
- **Found during:** Task 1 (adding `case "image/webp": return "webp"` to `imageExtFromMime`)
- **Issue:** Once `imageExtFromMime("image/webp")` returned `"webp"`, the existing `thumbFilename := "thumb." + ext` line produced `thumb.webp`, and `imaging.Save` cannot encode WebP (decode-only), causing `TestMediaUploadHandler_UploadPreservesWebPOriginalExtensionAndBytes` to fail with `imaging: unsupported image format` (HTTP 500).
- **Fix:** Decoupled `thumbExt` from `ext`: WebP sources now compute `thumbExt = "jpg"` so the thumb is re-encoded as JPEG, while the `original` variant still uses the raw-bytes `.webp` path from the webp branch.
- **Files modified:** `backend/internal/handlers/media_upload_image.go`
- **Verification:** `TestMediaUploadHandler_UploadPreservesWebPOriginalExtensionAndBytes` passes (original.webp has correct RIFF/WEBP bytes, display.jpg present).
- **Committed in:** `8c1f0507` (Task 1 commit)

**2. [Rule 1 - Bug] Updated pre-existing test assertion for the new display-variant count**
- **Found during:** Task 1 verification (full `-run TestMediaUploadHandler` pass)
- **Issue:** `TestMediaUploadHandler_StoreGeneratedAnimeImage` asserted `repo.files["4701"]` has exactly 2 entries (original+thumb). Since `StoreGeneratedAnimeImage` calls `processImage` internally (as documented in this plan's objective), it now also receives the new `display` row, making the assertion fail with "has 3 item(s)".
- **Fix:** Updated the assertion to `require.Len(t, repo.files["4701"], 3)` and added a comment explaining why, since this is the intended consequence of extending `processImage`.
- **Files modified:** `backend/internal/handlers/media_upload_segment_preview_test.go`
- **Verification:** `TestMediaUploadHandler_StoreGeneratedAnimeImage` passes.
- **Committed in:** `8c1f0507` (Task 1 commit)
