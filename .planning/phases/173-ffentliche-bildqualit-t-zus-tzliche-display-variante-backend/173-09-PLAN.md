<objective>
Fix four backend read sites that resolve a public image URL WITHOUT any `thumbnail_url`/`original_url`
split today (so D-05's "add a new display_url field alongside" pattern from 173-08 does not apply —
there is nothing to add it "alongside"). Instead, per D-02's intent ("display becomes the authoritative
source for public image delivery"), these sites are fixed **in place**: the SQL that already resolves
a single URL (`preview_url`, `cover_image`, `banner_url`) is changed to prefer the `display` media_files
variant ahead of whatever it preferred before (`thumb`/`original`), with the exact same fallback-to-original
safety net every other site in this phase already uses. This requires **zero frontend type changes** —
the field names and shapes are unchanged, only the server-side resolution priority improves.

Covers two groups, found during revision research by tracing every consumer in 173-CONTEXT.md's
`<findings>` back to its actual backend source (several of the ten named public components turned
out to be fed by sites 173-08's four-site list did not include):

1. **Kara segment fallback preview** (`theme_segment_preview.go`) — CONTEXT.md explicitly names
   `theme_segment_preview.go:97-101,371-375` as a pixelation source (the exact bug that triggered this
   phase). Both the single-asset resolver (`resolveThemeSegmentPreviewAsset`'s fallback branch) and the
   batch resolver (`resolveThemeSegmentPreviewAssetsBatch`'s fallback branch) currently do
   `COALESCE(mf_thumb.path, mf_orig.path, ma.file_path)` — thumb-first. Since this image's source is a
   `release_version_media` row, which 173-02 already gives a `display` variant, adding `mf_display`
   ahead of `mf_thumb` fixes the Kara-fallback sharpness bug directly at its root (the manual/auto preview
   branches earlier in the same file already resolve `original`-only and are NOT touched — they are not
   part of CONTEXT's cited pixelation finding).
2. **Anime cover/banner/logo (persisted self-hosted assets) + fansub project banner** — `anime_v2.go`'s
   `GetAnimeDetailV2` (feeds `app/anime/[id]/page.tsx`'s poster and `HeroSection.tsx`'s `anime.banner_url`),
   `anime_assets.go`'s `GetResolvedAssets`/`getResolvedAssetsV2` (feeds `AnimeMediaProvider.tsx`'s
   persisted-asset manifest, read through the D-16-protected `imageDisplay.ts` on-the-fly resizer — see
   173-13's objective for why `AnimeMediaProvider.tsx`/`app/anime/[id]/page.tsx`'s own component code is
   intentionally NOT touched), and `fansub_project_artwork.go`'s shared `publicProjectBannerSelectSQL`/
   `publicProjectBannerJoinSQL` (feeds `FansubProjectBannerCard.tsx`, consumed in 173-14) currently all
   resolve straight to the `original` media_files variant (no thumb concept exists at these sites at all —
   CONTEXT.md's finding is "unnötig große Originale", not pixelation). Adding `display` ahead of `original`
   caps the served long edge at 1920px while staying visually indistinguishable, directly serving D-02's
   "never optimize the giant original" goal and reducing RAM/CPU load measured in 173-16's live D-13 UAT.

Purpose: these four sites would otherwise silently keep serving stale (thumb-pixelated or
oversized-original) sources even after every frontend component in 173-13/173-14 switches to
"prefer the best available source" — the frontend plans depend on THIS plan's backend fix, not the
other way around.

Output: `theme_segment_preview.go`'s two fallback queries, `anime_v2.go`'s poster/banner LATERAL
joins, `anime_assets.go`'s V1 and V2 resolved-asset queries, and `fansub_project_artwork.go`'s shared
banner SQL all prefer `display` ahead of `thumb`/`original`, under their existing field names.
