<objective>
Finish the backend read-side half of D-02 for the two remaining public surfaces named in
`173-CONTEXT.md`'s `<findings>` that neither 173-08 (new `display_url` field, four DTOs that already
split thumb/original) nor 173-09 (in-place thumb/original→display swap, no animated-preservation
concern) could safely cover on their own:

1. **Fansub group logo/banner** (`fansub_repository.go`'s `getPublicGroupBase`, feeding
   `FansubBannerDisplay.tsx`/`FansubProfileTabs.tsx` via `/fansubs/[slug]`) — `logo_url`/`banner_url`
   are plain STORED columns on `fansub_groups` (set once at upload time, not derived via a
   `media_files` join at read time today). Fixed the same way as 173-09's in-place sites: a
   `LEFT JOIN` against `media_files` keyed on the row's own `logo_id`/`banner_id`, preferring
   `display`, falling back to the stored column untouched. **Placed in wave 4, not wave 1**, because
   `fansub_repository.go` is also touched by 173-08 (Site 4, `listPublicFansubMedia`) — same file,
   later wave to avoid a parallel-wave write conflict.
2. **Public member profile avatar/background** (`member_profile_public_repository.go`, feeding
   `MemberProfileContent.tsx`/`MemberProfileHero.tsx` via `/members/[slug]`) — this is a GENUINELY
   DIFFERENT backend site from the one 173-05 already fixed for the OWN-profile editor
   (`member_profile_ensure_repository.go`'s `ensureProfileBase`, used by `/me/profile`). The public
   site reads `media_assets.file_path` directly (the TRUE ORIGINAL, no `media_files` join at all) and
   has NO existing thumb/original split, UNLIKE the Kara/anime/project-banner sites in 173-09 — so
   this one genuinely needs the explicit **new field** approach (`display_url` alongside the
   unchanged `public_url`), for one load-bearing reason: `MemberProfileHero.tsx` already has an
   existing, deliberate branch that detects an ANIMATED avatar (GIF/animated WebP) by inspecting the
   URL's file extension and renders it `unoptimized` from the TRUE ORIGINAL, per D-07. If this plan
   did an in-place swap of `public_url` itself to prefer `display` (which 173-05's avatar/background
   display generator makes a STATIC-ONLY JPEG, even for an animated source), the animated-detection
   would silently stop firing (the URL would now end in `.jpg`) and animated avatars would regress to
   a static frame — a real D-07 violation. Keeping `public_url` as the untouched original and adding
   `display_url` as a new, purely additive field lets the dependent frontend plan (173-15) keep using
   the ORIGINAL url for animated detection while rendering `display_url` for the non-animated case.
   **Placed in wave 4, not wave 1**, because `models/member_profile.go` (where the new field is added)
   is also touched by 173-05 (wave 2) and 173-06 (wave 3) — same file, later wave avoids a conflict.

Purpose: without this plan, `FansubBannerDisplay.tsx`/`FansubProfileTabs.tsx`/
`MemberProfileContent.tsx` in 173-14/173-15 would have nothing new to read — their backend source
would still be the old pixelated/oversized value.

Output: `getPublicGroupBase` prefers `display` for `logo_url`/`banner_url` (same field names);
`GetPublicMemberProfileByID` gains `display_url` on `Avatar`/`BackgroundImage` with a correct
original-fallback chain, animated-avatar-safe by construction.
