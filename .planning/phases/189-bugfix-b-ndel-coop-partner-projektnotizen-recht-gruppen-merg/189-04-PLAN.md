<objective>
Fix the Projektnotizen write-permission bug: `UpsertAnimeFansubProjectNote`/
`DeleteAnimeFansubProjectNote` currently call `requireFansubGroupNoteWriteAccess` -- the SAME
group-wide guard used for plain group notes (`ActionFansubGroupNotesWrite` + `CanForFansubGroup`,
no `animeID` involved at all) -- even though the route already carries `animeId` in its path.
Confirmed project roles from `anime_contribution_roles` never factor into the decision today.

This is the exact structural bug Phase 188 already fixed once for the Projektzeitraum action
(`anime_fansub_project.timeline.update` via `CanForAnimeProject`) -- this plan applies the
identical, already-proven fix to the separate `anime_fansub_project.notes.write` action. Per
RESEARCH.md's confirmed findings: the permission catalog work is ALREADY DONE (the action and
its `role_capabilities` rows -- editor/fansub_lead/project_lead/quality_checker -- already exist
since migration `0108_capability_registry.up.sql`, and `CanForAnimeProject` is already generic
over the action parameter). This plan is pure wiring: a new handler access-check function and a
new, separate frontend-facing capability field -- no migration, no new permission
infrastructure.

Per D-08: a SEPARATE new capability (`can_edit_project_notes`) is added; `can_edit_notes` (which
also gates the notes tab's visibility) is left completely untouched. Per D-09: the real
observed access loss (member 5, New-Subs, Buddy Complex: founder/encoder only, no overlapping
project role) is accepted, not compensated. Per D-10: `role_capabilities` is NOT extended to
grant `co_leader`/`founder` the new action -- doing so would undermine the fix's whole point.

Purpose: Projektnotizen write access reflects confirmed project-specific contribution, not
incidental group leadership with no connection to the project.
Output: one new handler guard function, one new capability field + computation block, three new
regression tests proving the gain case, the unchanged case, and the D-09 loss case.
</objective>
