<objective>
Introduce a delete-lock for fansub groups (D-12), the direct replacement for the merge feature
Plans 189-05/189-07 remove: with merge gone, "reassign the release's group via the editor, then
delete the now-empty wrong group" (the existing Phase-187 guarded path) becomes the ONLY
correction path for a mis-mapped group -- and `DeleteGroup` today deletes unconditionally except
for two explicit `DELETE`s, letting everything else vanish via whatever `ON DELETE` the FK
happens to specify.

RESEARCH.md's FK-grep found CONTEXT.md's own dependents list incomplete by four categories, two
of which (`review_decisions`, `review_audit_events`) have NO `ON DELETE` clause (`NO ACTION`) --
a group that was ever reviewed ALREADY hard-fails `DeleteGroup` today with a raw, uncaught FK
error, the same failure shape documented for the removed merge bug. This plan turns every
silent-CASCADE or raw-FK-error case into one consistent, counted, German 409, mirroring the
already-proven Phase-187 `release_version_group_guard.go` pattern, extended with a new,
group-scoped (not release-version-scoped) summary type.

`fansub_repository_groups.go` is already 771 lines (over the 450-line limit) BEFORE this plan
touches it -- the split happens first, as its own behavior-preserving commit, mirroring this
package's existing `_aliases/_members/_links/_public_profile.go` domain-split convention.

Purpose: make the one remaining group-correction path (reassign + delete) safe against silently
orphaning real data.
Output: a 4-way file split, a new `FansubGroupDependencySummary` type with its own counting
function, a new typed error, `DeleteGroup`'s pre-check, and `DeleteFansub`'s 409 translation --
each proven by real-Postgres and httptest coverage.
</objective>
