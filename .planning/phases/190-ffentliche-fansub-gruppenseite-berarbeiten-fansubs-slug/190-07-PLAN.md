Root cause of the "orphaned third value" bug: `.heroMetricItem` has no `flex-grow`/`flex-basis` at
any breakpoint, so flex items size strictly to their own content width. With 3 items and no
`justify-content` override, two items pack onto row 1 (left-aligned) and the third wraps to row 2,
also left-aligned and sized only to its own short content — it visually "floats" alone at the left
of an otherwise-empty row instead of looking like an intentional, evenly-distributed layout element.

Six call sites to verify LIVE at 375px in Plan 190-08 (not this plan — this plan is CSS-only, no
live check here): `frontend/src/app/anime/[id]/group/[groupId]/sections/ProjectStats.tsx`,
`frontend/src/components/fansubs/FansubHeroSection.tsx`,
`frontend/src/components/profile/MemberProfileHero.tsx`,
`frontend/src/components/fansubs/projectMember/ProjectMemberHero.tsx` (uses `variant="inline"`,
which is a structurally different CSS path — `.heroMetricsInline`/`.heroMetricsInline .heroMetricItem`
— not touched by this plan; included in the checkpoint purely for completeness per D-u's explicit
six-site mandate, not because this fix applies to it),
`frontend/src/app/me/dashboard/components/DashboardMetrics.tsx`,
`frontend/src/app/dev/ui-system/page.tsx`.

Existing test, `frontend/src/components/ui/HeroMetrics.test.tsx` (full file, 79 lines) — uses jsdom,
which cannot compute real flex-wrap layout at a given viewport width (confirmed by that file's own
comment at lines 64-68 about jsdom being unable to compute live pseudo-class/layout styles) — this
is why the pass/fail check for this specific bug is necessarily manual/live, not unit-testable.
Locked, do-not-change values in the mobile media query per UI-SPEC: `dt` font-size `11px`, `dd`
font-size `20px` — this task touches `.heroMetricItem`'s box-model properties only, never font-size/
color/weight.
