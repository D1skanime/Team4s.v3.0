Uses `testsupport.OpenPhase134MaintenancePool(t)`, `testsupport.DropAndCreatePhase134FreshDatabase(t, maintPool)`,
`testsupport.Phase134FreshDatabaseDSN(...)`, `migrations.ResolveMigrationsDir("")`, `migrations.NewRunner(freshPool, migrationsDir)`,
`runner.Up(ctx)`. Reuse these exact helpers rather than inventing new ephemeral-DB plumbing.

`Runner.Up(ctx)` (`backend/internal/migrations/runner.go`) tracks applied versions in the
`schema_migrations` table and SKIPS (via `continue`) any version already recorded there — so
calling `runner.Up(ctx)` twice in a row is a guaranteed no-op for ANY migration regardless of its
SQL content; it does NOT by itself prove 0159's raw SQL is idempotent. To actually re-execute
0159's `.up.sql` a second time (the real proof required by 143-VALIDATION.md Criterion 2), delete
0159's own tracking row directly against `freshPool` between the two `Up()` calls:
`freshPool.Exec(ctx, "DELETE FROM schema_migrations WHERE version = $1", int64(159))`. This forces
`Runner.Up`'s `appliedVersions[159]` check to be false on the second call, so it re-runs
`applyUp` for version 159 only (re-executing the real `DELETE FROM role_capabilities;` +
`INSERT ... ON CONFLICT DO NOTHING` SQL against the already-populated table) while every other
already-applied version (1..158, and re-inserted 159 itself afterward) stays tracked and is not
re-run. This is the pattern Task 2 below must implement.
