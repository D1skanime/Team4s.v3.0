## Befunde

### UAT-01 — Review-Detail zeigt nach der Ablehnung weiter „In Prüfung"

**Schwere:** funktional
**Datei:** `frontend/src/app/admin/fansubs/[id]/reviews/[reviewId]/page.tsx:248`

```tsx
<Badge variant={status.variant}>{status.label}</Badge>
```

`status` wird aus `detail` abgeleitet, dem geladenen Review-Objekt. `submitDecision` setzt nur
`decisionState` auf `{ kind: 'success', response }` und lässt `detail` unverändert. Der Badge oben
rechts zeigt deshalb weiterhin „In Prüfung", während der Entscheidungsblock darunter korrekt
„Beitrag abgelehnt. Der Einreicher kann ihn bearbeiten und erneut einreichen." meldet. Die Seite
widerspricht sich selbst.

**Erwartet:** Nach erfolgreicher Entscheidung zeigt der Badge den neuen Zustand („Abgelehnt" bzw.
„Freigegeben").

**Hinweis:** Die Entscheidung selbst ist korrekt persistiert — das ist rein ein Anzeigefehler, aber
einer, der den Prüfer glauben lässt, seine Entscheidung sei nicht angekommen.

### UAT-02 — Projektliste unterscheidet „abgelehnt" nicht von „nie angefangen"

**Schwere:** UX / Semantik
**Dateien:** `frontend/src/app/me/projects/[animeId]/group/[fansubGroupId]/page.tsx:53, 337, 343-345`

Eine Folge mit ausschließlich abgelehnter Notiz zeigt den Badge **„Offen"**. „Offen" bedeutet für
den Nutzer aber „hier wurde noch nichts gemacht" — tatsächlich wurde gearbeitet und die Arbeit
wurde abgelehnt. Der Badge verschluckt genau die Information, um die es geht.

Der ROADMAP-Text zu Kriterium 5 nennt beide Varianten („als ‚Überarbeitung nötig' bzw. offen
sichtbar"); umgesetzt wurde nur die zweite. Formal erfüllt, inhaltlich unbefriedigend.

Technische Ursache: `isDone()` ist `has_own_notes || has_own_media`, und `has_own_notes` schließt
abgelehnte Notizen seit Kriterium 5 korrekt aus. Damit existiert die Information „hier liegt eine
Ablehnung" im DTO gar nicht mehr — für einen dritten Zustand braucht es ein eigenes Feld.

**Folgeeffekt in derselben Datei (Zeile 337):**

```tsx
const hasOwnArtifacts = release.has_own_notes || release.has_own_media
```

steuert die Button-Variante. Bei einer nur-abgelehnten Folge ist `hasOwnArtifacts` jetzt `false`,
der „Notizen & Medien"-Button wird also auf `secondary` heruntergestuft — obwohl dort Arbeit liegt,
die überarbeitet werden muss. Er sollte eher prominenter sein, nicht schwächer.

**Vorschlag:** Feld `has_own_rejected_notes` auf `MeProjectReleaseVersion`, durchgezogen von
Repository über Go-DTO und `shared/contracts/openapi.yaml` bis zum TypeScript-Typ. Daraus drei
Zustände statt zwei: **Erledigt** / **Überarbeitung nötig** / **Offen**. „Überarbeitung nötig" läuft
im Filter „Offen" mit, weil es nicht erledigt ist, und der Zähler „X offen · Y erledigt" bleibt
dadurch korrekt.

### UAT-03 — Dashboard-Karte unnötig hoch im Ein-Eintrag-Fall

**Schwere:** Layout
**Dateien:** `frontend/src/app/me/dashboard/components/AttentionSection.tsx`,
`AttentionSection.module.css:63-87`

Die neue Lane rendert zwei gestapelte Ebenen: `noteGroupHeader` (Anime · Gruppe + Badge) und
darunter eine verschachtelte `noteRevisionList` mit `margin-top: var(--space-3)`, deren Zeilen
zusätzlich `padding: var(--space-2) var(--space-3)` tragen. Die übrigen Lanes haben eine einzige
Link-Zeile direkt in der Card.

Bei genau einem Eintrag summiert sich das zu Card-Padding + Header + Abstand + Zeilen-Padding für
eine Zeile Inhalt. Die Karte ist dadurch deutlich höher als die benachbarten und wirkt leer.

Die Gruppierung selbst ist richtig und vom Kriterium gefordert — gestaltet werden muss der
Ein-Eintrag-Fall.

### UAT-04 — Neue Lane führt hartkodierte Farb-Fallbacks mit falschen Werten ein

**Schwere:** Regelverstoß
**Datei:** `frontend/src/app/me/dashboard/components/AttentionSection.module.css:91, 102`
**Eingeführt von:** `b7ac77cc feat(143-14): add rejected-own-notes lane to AttentionSection`

```css
.noteRevisionRow:hover { background: color-mix(in srgb, var(--color-primary, #2f5fe3) 8%, transparent); }
.noteRevisionEpisode   { color: var(--text-soft, #6b6b70); }
```

Die Fallback-Werte sind schlicht falsch: `--color-primary` ist real `#5f84dd`, nicht `#2f5fe3`;
`--text-soft` ist `#625c56`, nicht `#6b6b70`. Sollte ein Token je nicht auflösen, rendert die
Oberfläche in einer anderen Farbe als der Rest.

Bemerkenswert ist der Rückfall: Kriterium 6 **derselben Phase** hat genau dieses Muster in
`workspace.module.css` beseitigt. Hier wurde es aus den umliegenden Zeilen derselben Datei
(41, 55, 57, 58 — vorbestehend) in neuen Code kopiert. Lokale Datei-Konsistenz hat die globale
Regel geschlagen, was CLAUDE.md ausdrücklich verbietet.

**Erwartet:** Fallbacks entfernen, Tokens direkt verwenden. Die vier vorbestehenden Vorkommen in
derselben Datei gehören bei der Gelegenheit mit bereinigt — sonst bleibt die Vorlage stehen, aus
der das nächste Mal wieder kopiert wird.
