<interfaces>
Current `designTokens.ts` (read the full file — this is a pointer): `extractDesignTokens(cssText)`
returns `{ name, value }[]` from the real `:root` block text; `groupDesignTokens(tokens)` groups by
first `--`-segment (`groupKeyFor`) into `{ key, label, tokens }[]`, German-labeled via the existing
hand-maintained `GROUP_LABELS` dict (e.g. `space: 'Abstände'`, `card: undefined → falls back to
'Card'` since `card` has no entry today). `isColorLikeValue(value)` already detects color-like
values for swatch previews. This plan ADDS a classification layer on top (new exported function,
e.g. `classifyToken(token, groupKey): 'foundation' | 'purpose' | 'component'`), it does NOT replace
the existing extraction/grouping — `DesignTokensShowcase.tsx` composes BOTH.

Known concrete examples the human cited for each tier (use these as calibration points for the
classifier, not an exhaustive list):
- **Foundation**: the raw palette/scale entries themselves — `--space-1`..`--space-9` (NOT
  `--space-section`), `--radius-sm`/`-md`/`-lg`/`-pill` (NOT `--radius-surface`), the raw color
  palette (`palette.css`), shadow tiers, typography scale entries, breakpoint-ish raw values.
- **Purpose**: `--space-section`/`--space-badge-row` (and siblings), `--radius-surface`, every
  token introduced by this phase's own Befund 24/26 work (the `--space-*`/`--split-layout-column-
  poster*` purpose tokens in `layout.css`, the five `effects.css` recipes) — i.e. tokens that share
  a FAMILY PREFIX with a foundation group (`space`, `radius`, etc.) but whose own name is a named
  purpose, not a bare scale index/short structural keyword.
  **A workable, still-fully-automatic heuristic** (verify it actually produces sane output against
  the real token set before committing to it, adjust if it misclassifies): within a foundation-
  family group (`space`/`radius`/`shadow`/etc.), a token whose name segment AFTER the family prefix
  is purely numeric (`--space-3`) or matches a tiny, explicit set of known STRUCTURAL (not
  purpose-naming) keywords (e.g. `sm`/`md`/`lg`/`xl`/`pill`/`hairline`/`thin`/`thick` for radius/
  border-width families) is "foundation"; every OTHER token in that same family is "purpose".
  Tokens whose family prefix does not match any foundation family at all fall through to the
  component-tier classification below.
- **Component**: groups whose key maps to an actual named Grundbaustein/zusammengesetzter Baustein
  (`card`, `button`, `avatar`, `modal`, `drawer`, `field`, `picker`, `focal`/`grid` → "Fokus-
  Karussell", `split` → "Zwei-Spalten-Raster", `disclosure` → "Aufklapp-Kopfzeile", `selection`,
  `ach` → Erfolgsabzeichen, etc.) — German group names per the human's explicit examples: "Card",
  "Button", "AdjacentNavigation" → "Nebeneinander", "DatePicker" → "Datum", "MetricList"/"Empty" →
  "Leer-Zustand", "FocalCarousel" → "Fokus-Karussell", "SplitLayout" → "Zwei-Spalten-Raster",
  "DisclosureTrigger" → "Aufklapp-Kopfzeile". Extend the EXISTING `GROUP_LABELS` dict in
  `designTokens.ts` (already a hand-maintained namespace→German-label map, same mechanism, no new
  parallel list) rather than inventing a second lookup table.

`components/ui/Accordion.tsx`'s API (read it in full): `items: AccordionItemDef[]` where each item
is `{ id, title, children }`; `mode="multi"` (default) allows several groups open at once —
appropriate here so a reader can compare two component groups side by side if they choose.

Jargon words the human explicitly named for removal from VISIBLE Autodocs copy (code comments may
keep technical terms): "CSS-Custom-Properties", "domänenspezifische Komposition" or synonymous
jargon.

"Raw-literal marking" requirement: within the component tier, a value counts as "still a raw
literal instead of a purpose token" if its declared `value` text (from `extractDesignTokens`, the
RAW source text, e.g. `"4px"` vs `"var(--space-3)"`) does NOT start with `var(` — i.e. it is a
direct number/hex/function value rather than a reference to another token. Mark these visibly (e.g.
a small badge/icon next to the token row) WITHOUT changing the underlying CSS — this plan is
marking-only, cleanup is explicitly future work per the addendum.
