<interfaces>
Current `Card.tsx`'s established override-hook pattern (tintHue/tintSaturation/tintLightness/
tintSurfaceAlpha/tintBorderAlpha) — the new padding prop follows this EXACT shape, not a new
mechanism:
```
export interface CardProps extends HTMLAttributes<HTMLDivElement> {
  variant?: CardVariant
  tintHue?: number           // generic numeric value, Card itself assigns no domain meaning
  tintSaturation?: number    // optional fine-tune, read via var(--x-override, var(--x))
  ...
}
// mergedStyle sets '--card-tint-hue': tintHue, etc. -- ONLY when the prop is actually passed
```
`Card.module.css` currently HARDCODES `padding: 0;` (not token-driven) on `.cardGlass`,
`.cardGlassStrong`, `.cardPublicSection`, `.cardPublicHero`, `.cardPublicPoster`,
`.cardPublicHeroInfo`, and uses `padding: var(--card-padding)`/`var(--space-4)`/
`var(--card-nested-flat-padding)`/`var(--space-1) 0 0` on the other variants (`.card`,
`.cardCompact`, `.cardNested`, `.cardNestedFlat`). The new override must NOT change any of these
defaults when the new prop is not passed — add `var(--card-padding-override, <existing-value>)` as
the padding value on every variant rule that currently declares its own `padding`, so a caller can
request a DIFFERENT padding on a per-instance basis without any variant gaining a new hardcoded
padding value.

`components/ui/index.ts` barrel — alphabetically ordered `export * from './X'` lines; the new
`Divider` entry goes between `DisclosureTrigger` and `EmptyState` alphabetically.

`frontend/src/components/ui/foreignVariableOverrides.regression.test.ts` scans every
`components/ui/*.module.css` file for (a) any custom property set by more than one file (or a
registered-but-foreign setter) and (b) any raw px/rem/hex/rgba literal outside an `@media`/
`@container` condition. `Divider.module.css` must therefore use ONLY `var(...)` token references
(reuse the EXISTING `--border-on-media`/`--border-on-media-strong` tokens from
`styles/tokens/components.css` — do not invent new color tokens) and must not declare
`--card-padding-override` or any other foreign Card variable.

Existing closest-analog already in `components/ui`: `AccentRule.tsx` (`thickness` prop, renders a
`<span>` with `background: var(--ui-line)`). Read it before building `Divider` — `--ui-line`
(`palette.css`) resolves to `#82122c`, the project's wine/brand accent color, semantically a
DIFFERENT thing from the two `<hr>`s being replaced here, which both read `var(--border-on-media)`/
`var(--border-on-media-strong)` (translucent white, the "border on dark/photo surface" family
already used by `Card.module.css`'s `.cardGlass`/`.cardGlassStrong` border-color and by
`ReleasePreviewRow.module.css`'s `.logo` border). Document in `Divider.tsx`'s top comment WHY this
is a new component and not a new `AccentRule` variant (different token family / different semantic
role: `AccentRule` = branded accent flourish, `Divider` = neutral on-media content separator) — do
not silently duplicate without that justification on record.

Current two `<hr>` usages being targeted by the LATER plan (read-only here, for sizing the new
component's API — do not edit these files in this plan):
```css
/* AnimeDetailHero.module.css */
.posterDivider { height: var(--border-width-thin); margin: var(--space-1) 0; border: none; background: var(--border-on-media); }
/* mobile: .posterDivider { display: none; } */
.divider { height: var(--border-width-thin); margin: var(--space-5) 0; border: none; background: var(--border-on-media-strong); }
/* mobile: .divider { background: var(--border-on-media); } */
```
Both lines are `<hr className={styles.X} />`. The new `Divider` Grundbaustein must be able to
reproduce BOTH (different margin amount, different tone) via props alone, with ZERO margin/tone
left for the composite file's className to supply — the composite file may still use its own
className for RESPONSIVE visibility (`display: none`) since that is not forbidden layout CSS, but
must not set margin or background.
