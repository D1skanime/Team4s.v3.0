Current `Card.tsx` (read in full before editing -- confirmed current state):
```
export type CardPaddingPurpose = 'content' | 'nestedBlock' | 'dividedSection' | 'none'
const PADDING_PURPOSE_TOKENS: Record<Exclude<CardPaddingPurpose, 'none'>, string> = {
  content: 'var(--card-padding-content)',
  nestedBlock: 'var(--card-padding-nested-block)',
  dividedSection: 'var(--card-padding-divided-section)',
}
```
`padding` resolves to `--card-padding-override`, read by every padding-bearing variant rule via
`var(--card-padding-override, <its own default>)`. `bleedBelowMd?: boolean` is the existing precedent
for a boolean capability implemented as a modifier class (`styles.cardBleedBelowMd`) rather than a
CSS-variable hook, because a custom property cannot conditionally activate a selector.

**1) New padding purpose `'section'` (32px).** Add to `CardPaddingPurpose` and
`PADDING_PURPOSE_TOKENS`. New token in `layout.css`:
`--card-padding-section: var(--space-6);` with a German comment distinguishing it from
`'nestedBlock'` (16px, padding of a block nested INSIDE an outer card) by value and by being "volle
Innenabstand-Polsterung eines eigenständigen Seitenabschnitts (z. B. der Episoden-Bereich-Rahmen)".
Note: `Card` already has an unrelated `CardVariant` member literally named `'section'`
(`.cardSection`, a background-only admin variant) -- this is a different prop (`padding` vs.
`variant`), no TypeScript collision, but name both explicitly in the doc comment so a future reader
does not conflate `variant="section"` with `padding="section"`.

**2) New padding purpose for a standalone context/hint card (24px).** Read
`frontend/src/components/fansubs/FansubGroupContext.module.css`'s current `.card { padding:
var(--space-5); ... }` to confirm the exact value this must reproduce. New token in `layout.css`,
e.g. `--card-padding-context-card: var(--space-5);` -- exact purpose name at this plan's discretion,
must describe "Innenabstand einer eigenständigen Kontext-/Hinweiskarte" (the addendum's own wording),
not the FansubGroupContext caller name.

**3) New width-purpose capability for a capped-width preview card.** Read
`frontend/src/components/anime/AnimeEdgeNavigation.module.css`'s current `.previewCard { ... width:
min(260px, 90vw); }` to confirm the exact value. Add a new, independent boolean-or-enum prop on
`Card` (exact shape at this plan's discretion -- propose `widthPurpose?: 'compactPreview'`, following
the same modifier-class pattern as `bleedBelowMd` since a fixed `width` cannot be expressed as a pure
CSS-variable default the way `padding`/`radius` overrides are, unless implemented as
`width: var(--card-width-override, auto)` read by a NEW `.card` base rule -- choose whichever
mechanism keeps every existing Card consumer byte-identical). New token in `layout.css`, e.g.
`--card-width-compact-preview: min(260px, 90vw);` with a German comment: "Card: schmale, auf eine
Höchstbreite begrenzte Vorschaukarte (z. B. die Randnavigations-Vorschaukarte)" -- named by function
(a capped-width preview card), not by the AnimeEdgeNavigation caller name, so a future floating
preview card elsewhere could reuse it.

**4) EpisodeGlassCard's radius-free nested-card conflict.** Read
`frontend/src/components/fansubs/EpisodeGlassCard.tsx` and `.module.css` in full (the `.versionList`
rule and the `<Card variant="flat" padding="dividedSection">` call site it wraps) and
`frontend/src/components/ui/Card.module.css`'s `.cardNested`/`.cardNestedFlat`/`.cardFlat` rules.
`.versionList` currently declares `border-width: 0; border-radius: 0; background: transparent;`
locally to cancel `variant="flat"`'s inherited 4px `border-radius`/1px border -- this becomes a
forbidden `border-radius` declaration once Plan 192-34 widens the guard (which checks `border-radius`
unconditionally, with NO zero-value exemption, per the addendum: "die Rundungs-Entscheidung selbst
gehört in den Grundbaustein"). Resolve this by EITHER (a) confirming whether an EXISTING `Card`
variant (`nested`/`nestedFlat`) already produces a pixel-identical nested card for this exact use
case (radius, border, background all match what `.versionList` currently achieves) -- if so, no new
Card capability is needed, Plan 192-32 just switches the call site's `variant` prop -- OR (b), if no
existing variant matches exactly, add a minimal new capability (e.g. a boolean `seamless?: boolean`
prop, following the `bleedBelowMd` modifier-class pattern) that zeroes radius/border/background for a
Card instance meant to sit flush and borderless inside its parent. Decide based on a direct, measured
comparison of the current rendered values -- this specific conflict is a genuine gap this round's
guard-widening audit did not enumerate (discovered via direct file reading during planning), not an
item to solve by guessing. Document the chosen resolution precisely in the SUMMARY so Plan 192-32 can
apply it without re-deriving it.

`gapPurposeNaming.guard.test.ts` already guards `padding="[1-9]"` at 6 call-site files (see its
`forbiddenRawValuePatterns`/`allowedSample`). Extend the positive counter-example sample with the two
