**Explicit answer to the phase-wide HC-03 authorization-regression question:** deriving
`validGlobalRoles`/`AssignableRoles`/the error text from `models.AppGlobalRoles` cannot widen or
narrow the assignable-role set relative to today, because `AppGlobalRoles` is built from the exact
same three pre-existing constants (`AppGlobalRolePlatformAdmin`, `AppGlobalRoleContentAdmin`,
`AppGlobalRoleUser`) in the exact same order every consumer already hard-coded. The risk is not in
this plan's diff — it is in a *future* uncontrolled edit to `AppGlobalRoles` — which is exactly what
Task 2's source-contract test guards against going forward.

applicable to this plan — this plan's diff touches only `models.AppGlobalRoles` and its four
Go-internal consumers (handler/repository role-set derivation, an admin-authenticated error
message); it does not add, remove, or touch any public-facing note/response field. Plan 147-01
owns the `role_code` public-disclosure assessment (see its T-147-01 entry).
