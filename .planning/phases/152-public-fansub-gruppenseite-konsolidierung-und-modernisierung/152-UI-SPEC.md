# Phase 152 — UI Design Contract

> **This is a CONFIRM-AND-CONSTRAIN contract, not a redesign spec.** Phase 152 is a targeted
> consolidation (D02 in `152-CONTEXT.md`): the History timeline's visual language does not change.
> The only thing that changes is WHERE the badge artwork's sizing geometry comes from — the local
> `--history-badge-size` CSS-variable chain is replaced by the shared Phase-151
> `AchievementArtwork` slot. This document locks the exact seams so the planner/executor do not
> re-litigate them and do not introduce a second badge architecture (D03).
>
> Generated by gsd-ui-researcher, verified by gsd-ui-checker. Grounded in `152-CONTEXT.md`
> (locked decisions D01-D11, verified audit findings) and `152-RESEARCH.md` (Architecture Patterns
> 1-3, Pitfalls 2-3, Assumptions A1-A2) — see those files for full evidence/line numbers; this
> document only restates the parts that are binding for visual/interaction implementation.

| Property | Value |

**Primitive-usage constraint (binding on every executor subagent, per CLAUDE.md):** any new
user-facing markup this phase touches (media-thumbnail button, history "Weitere anzeigen" action)
MUST continue to use `Button`/`EmptyState`/`SectionHeader` from `@/components/ui` — no hand-built

(`FansubHistorySection.tsx` uses `Button`/`SectionHeader`; `FansubGroupMediaBlock.tsx` uses

## Color

This phase does not introduce a new palette. It extends the file's own already-correct
`color-mix(... var(--ach-color) ...)` idiom to the two places that currently bypass it (the emphasis
glow blocks). Confirmed tone-driver pattern at `FansubPublicSections.module.css:199-251` — each
`.ach*` tone class sets three local custom properties (`--ach-color`, `--ach-grad`, `--ach-soft`),
consumed throughout the timeline card/badge chrome.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `var(--surface-canvas)` / `var(--surface-card)` (page canvas / card surface) | Page background, timeline card background |
| Secondary (30%) | `var(--color-border)`, `var(--text-secondary)` | Card border, secondary text (year, note) |
| Accent (10%) | `var(--ach-color)` (per-entry, resolved via the entry's `tone`) | Timeline spine gradient, axis-year ring/text, card border tint, type-badge background/text, badge drop-shadow |
| Destructive | `var(--color-error)` (`#dc3545`, site-wide token) | Not used on this page — no destructive action exists in the History section |

Accent reserved for: the axis-year chip border/background/text, the badge's drop-shadow and
`::before` glow ring, the card's left-edge border tint and ambient glow, and the type-badge
pill background/text — i.e., exactly the elements that already read `var(--ach-color)` /
`var(--ach-soft)` today. No new elements gain accent color in this phase.

### Emphasis tokens (A4 + C2 combined — see "Emphasis Contract" below)

`.achLegendary` already exists and already carries a token-driven identity
(`--ach-color: #a16207`, `--ach-grad: linear-gradient(135deg, #fef3c7, #c4b5fd 52%, #67e8f9)`,
`--ach-soft: #fef3c7` — `.module.css:247-251`). The hardcoded hex/rgba values in the emphasis glow
blocks (`#7c3aed`, `#facc15`, and their `rgba(...)` derivatives, `.module.css:572-648`) MUST be
replaced by `color-mix(in srgb, var(--ach-color) N%, transparent)` / `var(--ach-grad)` /
`var(--ach-soft)` — reusing the already-declared `--ach-legendary` family, not inventing new custom
property names. This is a pure token-source swap; the `.achLegendary` tone class itself and the
other tone classes (`achBlue`, `achViolet`, etc., which already use local hardcoded hex per their
existing established pattern) are unchanged.

## Migration Contract — Artwork Slot Embedding (binding, resolves Research Pattern 1 + Pattern 2)

This is the concrete, locked resolution to the phase's central open question
(`152-RESEARCH.md` "Open Questions #2", Assumption A1). The planner/executor must implement exactly
this, not re-derive it.

### 1. Container-query context placement

Wrap **`.historyTimelinePair`** (the full grid row: year marker + badge + card — NOT just the tight
`.historyTimelineBadge` box) with `artworkStyles.container` from
`@/components/profile/AchievementArtwork.module.css`, mirroring the exact convention already used in
`RoleAchievementCard.tsx:55` (`<div className={artworkStyles.container} data-role-card-container>`
wraps the *entire* card row, not the artwork alone).

**Why the row, not the badge box:** `AchievementArtwork`'s container-query steps (562px/658px,
`AchievementArtwork.module.css:114-131`) key off the inline-size of whichever ancestor establishes
`container: achievement-card / inline-size`. The current `.historyTimelineBadge` box is only
108-300px wide across breakpoints (`.module.css:281,485,496,512,562,614`) — far too narrow to ever
cross 562px/658px on its own, which would permanently lock the badge at its smallest (192px) hero
step and silently defeat the container-query scaling. `.historyTimelinePair` is a full-width grid
row (`width: 100%`, `.module.css:289-295`) and is reliably well over 658px wide whenever the desktop
3-column grid layout is active (≥1100px breakpoint) — giving the badge genuine two-step scaling
(192px mobile/narrow → 216px → 240px desktop) exactly as `AchievementArtwork` intends elsewhere.

```tsx
// FansubHistorySection.tsx — inside the .map, replacing the raw <img> block
<div className={artworkStyles.container}>
  <div className={styles.historyTimelinePair}>
    {item.year ? <span className={styles.historyTimelineAxisYear} aria-hidden="true">{item.year}</span> : null}
    <div className={styles.historyTimelineBadge}>
      <AchievementArtwork
        descriptor={{ kind: 'direct', src: presentation.imageSrc }}
        badgeCode={item.event_type}
        alt=""
        size="hero"
        decorative
      />
    </div>
    <article className={styles.historyTimelineCard}>
      {item.year ? <span className={styles.historyTimelineYear}>{item.year}</span> : null}
      <strong>{publicHistoryTitle(item, presentation)}</strong>
      <span className={styles.historyTimelineType}>{publicLabel}</span>
      {item.note ? <p className={styles.historyTimelineNote}>{item.note}</p> : null}
    </article>
  </div>
</div>
```

Do NOT wrap only `.historyTimelineBadge` — that reproduces the too-narrow-container failure mode
above.

### 2. Grid-track replacement for the deleted `--history-badge-size`

`.historyTimelinePair`'s middle grid column (`.module.css:291`) and `.historyTimelineBadge`'s
explicit box size (`.module.css:302-303`) both consume `--history-badge-size` today. Once
`AchievementArtwork` owns the badge's actual rendered size, both consumption sites change:

- **`.historyTimelinePair { grid-template-columns: minmax(0,1fr) var(--history-badge-size) minmax(0,1fr); }`**
  → `grid-template-columns: minmax(0,1fr) 240px minmax(0,1fr);` — a **fixed** `240px` middle track,
  matching `AchievementArtwork`'s largest declared hero step (`AchievementArtwork.module.css:127-130`).
  This value only matters at the ≥1100px breakpoint where the 3-column grid is active
  (`.module.css:518-522` already collapses to a single `1fr` column at ≤1100px, where no
  fixed-width middle track is needed at all).
- **`.historyTimelineBadge { width/height: var(--history-badge-size); }`** → **remove** the explicit
  width/height. Let the wrapper size to its `AchievementArtwork` child's intrinsic slot size
  (192/216/240px, self-governed by `AchievementArtwork`'s own container queries) instead of forcing
  a size from outside. `display: grid; place-items: center` (already present) continues to center it.
  The `::before` glow pseudo-element (`.module.css:336-344`, percentage-based `inset: 18%`) keeps
  working unchanged because the box still resolves to a definite size from its content.

**Do NOT** introduce a new breakpoint, a new clamp(), or any viewport-based override of `240px` —
that would reintroduce exactly the pattern A3 removes. `240px` is a single fixed value, not a
responsive one; responsiveness comes entirely from `AchievementArtwork`'s own container queries,
which is the point of the migration.

### 3. Sizes explicitly NOT to touch (Phase-151 binding authority)

Hero `192 / 216 / 240px`, Stage `64 / 80px`, `8px` inset, container-query steps `562` and `658` are
declared **exclusively** in `AchievementArtwork.module.css`. Phase 152 must not duplicate, override,
or shadow any of these values, and must not add achievement-family-specific size or breakpoint
logic anywhere they'd be visible to `AchievementArtwork`'s consumers. Phase-151's verification record
states: *"Es existiert keine familienspezifische Größen- oder Breakpoint-Logik"* — this statement
must remain true after Phase 152. Only `size="hero"` is used for History (no `stage` usage — History
has no locked-progression stages, unlike role badges).

### 4. Descriptor shape

Always `{ kind: 'direct', src: presentation.imageSrc }` — History badges are single-layer PNGs (one
`imageSrc` per registry entry, no motif/frame pair), so the `layered` branch is never exercised here.
This directly satisfies D05: no `resolveBadgeArtwork`/`resolveLayeredRoleArtwork` import, no adoption
of the member-profile badge-code resolver.

### 5. Visual verification obligation

The `240px` track value and the resulting badge scaling ARE a visual judgment call
(`152-RESEARCH.md` Assumption A1) — confirm at the mandatory Visual QA viewports
(320/390/520/768/1024/1440/1920/2560) that the timeline's left/right card columns stay visually
aligned and the badge never clips or overflows its track at any of them, before merge.

## Emphasis Contract (resolves A4 + C2 together, per Research Pattern 3)

**What emphasis replaces:** the current hard `if`-chain in `achievementEventStyle()`
(`FansubHistorySection.tsx:31-38`) and the two bespoke hardcoded-hex glow blocks
(`.historyTimelineEventProjects500`/`.historyTimelineEventReleases10000`, `.module.css:572-648`).

**Registry extension (additive field, per D03/D06 — one registry, no second one):**

```ts
// frontend/src/lib/group-history-events.ts
export interface GroupHistoryEventPresentation {
  // ...existing fields unchanged...
  emphasis: 'none' | 'legendary'   // additive — 'rare' is a reserved future value, not assigned this phase
  publicLabel: string               // see Copywriting Contract below
}
```

- `emphasis: 'legendary'` on exactly the two entries that already have bespoke glow today:
  `projects_500` and `releases_10000` (both already `tone: 'legendary'` — the emphasis field rides
  the same entries, not a new selection).
- `emphasis: 'none'` on all other 21 entries.
- Do NOT introduce a `'rare'` tier this phase — no current entry needs it, and adding an unused enum
  value with no consumer would violate "no speculative scope."

**Visual means emphasis MAY use:** color (via `var(--ach-color)`/`var(--ach-grad)`/`var(--ach-soft)`,
already legendary-tone-driven), box-shadow/drop-shadow glow intensity, border-color tint, background
gradient overlay on the card — i.e., exactly what the current two hardcoded blocks already do,
minus the hardcoded hex.

**Visual means emphasis MUST NOT use:** artwork size (no `emphasis`-driven width/height override —
size is `AchievementArtwork`'s exclusive authority per the Migration Contract above), and no
emphasis-specific `@media`/`@container` breakpoints of its own (drive it off the existing
`achievement-card` container the badge already sits in, or off no container query at all if the glow
doesn't need to scale).

**Implementation shape:** one generic selector (e.g. `.historyTimelineEmphasisLegendary`), applied
via `styles[...]` the same way tone classes are applied today, replacing the two separate
`.historyTimelineEventProjects500`/`.historyTimelineEventReleases10000` selectors. Both entries'
glow becomes visually identical (gold→violet→cyan gradient family, matching `.achLegendary`'s
existing `--ach-grad`) instead of two distinct bespoke palettes.

**Visual QA flag (mandatory, explicit sign-off item):** this measurably changes the rendered glow on
`releases_10000` (today: yellow/cyan) and `projects_500` (today: violet/amber) to one shared
treatment. Call this out explicitly as an *expected* visual delta in the phase's acceptance
checklist, not an accidental regression — do not silently ship it as if nothing changed.

**Pixel shifts (`--history-image-x/y` on `releases_500/1000/5000/10000`, `.module.css:598-616`):**
per D08, remove by default. Only keep a pixel-shift for a specific entry if, after visual inspection
post-migration, that entry's PNG is objectively mis-centered inside the new `AchievementArtwork`
slot's `object-fit: contain` box — and if so, document the root cause (source asset padding
asymmetry) rather than re-adding a blind CSS nudge.

## Accessibility Contract (resolves D3/D4, binding)

### Duplicate year in the a11y tree

Today `historyTimelineAxisYear` (spine marker, `.module.css:312-334`) and `historyTimelineYear`
(inside the card, `.module.css:395-400`) both render the same year number with neither excluded from
the accessibility tree.

**Decision:** `historyTimelineAxisYear` gets `aria-hidden="true"` (it is a purely visual spine
marker, redundant with and out of reading-order relative to the card's own content).
`historyTimelineYear` (inside `<article>`, read together with title/type/note as one coherent item)
**stays in the accessibility tree, unchanged.** See the code block in the Migration Contract section
above — `aria-hidden="true"` is already shown on the axis-year `<span>`.

### Badge artwork must be decorative

`<AchievementArtwork alt="" decorative>` — matches the existing prop contract exactly
(`AchievementArtwork.tsx:39-40`: `decorative` forces `alt=""` + `aria-hidden`). The current raw
`<img alt="">` is already decorative-equivalent; this preserves that, just through the shared
component's own mechanism instead of a hand-rolled empty `alt`.

### Media thumbnail double-labeling (`FansubGroupMediaBlock.tsx:94-115`)

Today the `Button` wrapping the thumbnail carries `aria-label={title}` (line 98) AND the inner
`next/image` carries `alt={title}` (line 104) — both announce the same string inside one interactive
control, which most screen readers surface as either duplicated or conflicting accessible-name
content.

**Decision: the `Button`'s `aria-label={title}` wins.** It is the accessible name of the interactive
control (what a screen reader announces for the button), which is the correct target for a full
image-title string on a clickable trigger. Set the inner `<Image alt="">` (empty) — it becomes
purely decorative content inside an already-labeled control, following the same "labeled ancestor,
decorative descendant" pattern already used for `AchievementArtwork`'s badges. The visible `<strong>`
title in `.mediaCardBody` (line 123) is unaffected — it stays as visible, non-interactive text.

### Axe coverage

Add `jest-axe` coverage to `FansubHistorySection.test.tsx` and the new
`FansubGroupMediaBlock.test.tsx` (does not yet exist — Wave-0 gap per `152-RESEARCH.md`), following
the exact existing pattern in `FocalCarousel.test.tsx`/`MemberProfileHero.test.tsx`:
`expect(await axe(container)).toHaveNoViolations()`.
