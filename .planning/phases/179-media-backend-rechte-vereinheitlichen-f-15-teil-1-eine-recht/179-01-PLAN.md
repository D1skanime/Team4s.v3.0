`permissions.go`'s `Action` type is a plain Go `string` type alias (`type Action string`). The
const block (lines 20-66) declares all known actions as typed string constants, e.g.:
`ActionReleaseVersionMediaUpload Action = "release_version_media.upload"`. `allKnownActions`
(line 224, a `[]Action` slice) is the complete action universe consulted by
`validateCapabilityCatalog` (line 402) — every entry MUST appear as a key's value-list member in
whatever map `LoadCache`/`ReloadCache` is given, or be listed in `standaloneActions` (line 271,
currently `[]Action{ActionFansubGroupInvitationsAccept}` only). This is a fail-closed startup
check: `validateCapabilityCatalog` returns `fmt.Errorf("permission cache: Action %q fehlt in
role_capabilities und ist keine standalone-Action — Startup abgebrochen", a)` for any
`allKnownActions` entry missing from both.

**Critical consequence:** every Go test file across `backend/internal/{handlers,services,
repository,permissions}` that constructs a hardcoded `map[string][]permissions.Action` fixture to
satisfy `permissions.Service.LoadCache` (so the fixture passes `validateCapabilityCatalog`) will
FAIL once `ActionReleaseThemeAssetUpload` is added to `allKnownActions`, unless that fixture is
also updated to include the new action somewhere in its map. This is a known, established,
repeating pattern in this codebase (every one of the 9 files below already carries this exact
kind of fixture, usually with a comment like "satisfying LoadCache's D-10 completeness check" or
"parked under an unused role").
