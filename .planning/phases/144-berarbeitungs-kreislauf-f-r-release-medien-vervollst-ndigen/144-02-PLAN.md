<objective>
Build the new repository-layer building block that Zielbild 1 needs: a way to swap the stored file
on an existing `release_version_media` row (its `media_asset_id`) while its primary key `id` never
changes, plus a way to enqueue the OLD file for async cleanup so it does not end up orphaned in
storage. This is pure repository code — no HTTP surface yet (that is 144-04, which depends on this
plan).

Purpose: this is the "define contracts" step for the new file-replace feature. 144-CONTEXT.md's
first open design decision ("Route oder Erweiterung?") resolves here as "own route, own repository
method" (matches 144-PATTERNS.md's file classification — a dedicated new file, not appended to the
already-1148/680-line existing handler/repository files). The second open decision ("Alte Datei
behalten oder verwerfen?") resolves here as "verwerfen" (discard) — reusing the EXISTING
`release_review_file_delete_jobs` outbox table and its already-running worker
(`backend/internal/services/release_review_cleanup.go`), not inventing a retention/history table.
Output: `backend/internal/repository/release_version_media_replace_repository.go` with two new
methods on `*MediaRepository`, proven correct against a real Postgres fixture for identity
preservation, lifecycle reset, old-file cleanup enqueue, and the points/archivist non-side-effect
invariant.
</objective>
