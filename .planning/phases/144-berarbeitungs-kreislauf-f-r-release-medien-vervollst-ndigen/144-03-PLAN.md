<objective>
Give the release-review Detail response (`GET .../reviews/:reviewId`, backed by
`ReleaseReviewQueryRepository.Detail`) the data the reviewer-facing UI needs to show "this is the
revised version of what I rejected" instead of a bare status. Today `ReleaseReviewDetail` carries
no history at all — grepping for `source_revision|Überarbeitet|revision` in the reviewer page only
matches the unrelated `expected_revision` conflict guard (144-VALIDATION.md's own finding). This
plan closes the backend half of Zielbild 3; the frontend badge/context-line rendering is a later
Wave-5 plan (144-07) that consumes the field this plan adds.

Purpose: closes the third of four Zielbild goals in 144-CONTEXT.md.
Output: `ReleaseReviewDetail` gains an optional `PriorRejection` field, populated only when the
current `source_revision > 1` AND a `review_decisions` row with `decision = 'reject'` exists for
revision `source_revision - 1` on the same source. OpenAPI and the frontend `ReleaseReviewDetail`
type mirror the new field.
</objective>
