<objective>
Ship the new HTTP endpoint Zielbild 1 needs: `PUT /admin/release-versions/:versionId/media/:relationId/file`.
This is a single-file multipart request that replaces the file on an existing relation and, in the
same request, optionally updates category/caption/is_preview_candidate — resolving CONTEXT.md's
"Kategorie ist im selben Formular änderbar" (Zielbild 2) requirement for the specific case where the
submitter is ALSO replacing the file, without a second HTTP round-trip that would double-bump the
review-lifecycle revision (SubmitMedia's optimistic `ExpectedRevision` guard would reject a stale
second call). When only category/caption/preview change (no new file), the submitter still uses the
already-unblocked PATCH endpoint from 144-01 — this plan's endpoint is specifically for "a file is
being replaced, possibly together with other fields, in one atomic submission."

Purpose: closes the fourth Zielbild goal's "eigener Endpunkt" branch of CONTEXT.md's open question
("Route oder Erweiterung?") with a stated rationale: a dedicated route keeps the metadata-only PATCH
(144-01) simple/unchanged in shape, while giving the file-replace case exactly one atomic
SubmitMedia call regardless of how many fields change alongside the file.
Output: new handler `ReplaceReleaseVersionMediaFile`, registered route, OpenAPI path, and a
permission-invariant test.
</objective>
