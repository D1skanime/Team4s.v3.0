# Phase 144 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope Note

This phase is backend-heavy (revision-lifecycle jump on `release_version_media`), but it adds three
real UI surfaces:

1. A **file-replace control** inside the existing "Medium bearbeiten" drawer
   (`frontend/src/app/admin/episode-versions/[versionId]/edit/ReleaseVersionMediaSection.tsx`) for a
   rejected item, so the submitter fixes the actual file instead of only the caption.
2. A **category field** in the same drawer, so "falsche Kategorie" is fixable without a new upload.
3. A **resubmission indicator** on the reviewer side (`.../fansubs/[id]/reviews/[reviewId]/page.tsx`
   and its list) so a reviewer can see "this is the revised version of what I rejected", not a
   stranger's new submission.

No new route, page, or standalone screen is introduced. Every element below extends an existing,
already-styled surface — do not invent a parallel visual language for it.

## Spacing Scale

This project's global spacing scale (`frontend/src/styles/globals.css`) is already declared and in
active use — reuse it as-is, do not invent ad-hoc px/rem values for new markup:

| Token | Value | Usage |
|-------|-------|-------|
| `--space-1` | 4px | Icon gaps, badge inline padding |
| `--space-2` | 8px | Compact row gaps (checkbox rows, badge rows) |
| `--space-4` | 16px | Default `FormField`/drawer stack gap |
| `--space-5` | 24px | Section padding inside cards |
| `--space-6` | 32px | Drawer section breaks |
| `--space-7` | 48px | Major layout breaks (not used at this component scale) |

`--space-3` (12px) exists globally but is **not** part of the standard 8-point scale (4, 8, 16, 24,
32, 48, 64) and is not needed by this phase's new markup — the category `Select`/`FormField` use the
existing primitives' own baked-in padding, and the file-replace drop-zone reuses the existing
`.dropZone` classes below (rem literals, not the token scale). Do not reach for `--space-3` when
writing new CSS this phase; use `--space-2` or `--space-4` if a form-control padding value is needed.

Exceptions: the existing `ReleaseVersionMediaSection.module.css` uses literal `rem` values
(`0.75rem`, `1rem`, etc.) instead of the `--space-*` tokens throughout. This is pre-existing,
out-of-phase-scope debt — new rules added by this phase (the replace-file control, the category
field, the resubmission badge) should follow the same `rem` convention already established in that
file for visual consistency with the rest of the section, rather than mixing token systems mid-file.
Do not refactor the whole file's spacing system as a side effect of this phase.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (0.9rem) | 400 | 1.5 |
| Label | 12px (0.72–0.76rem) | 800 | 1.2 |
| Heading | 16px (1.05rem) | 800 | 1.25 |
| Display | 19px (1.2rem) | 800 | 1.2 |

Two weights project-wide for this phase's new copy: `400` (Body) and `800` (Label/Heading/Display).
The shipped `ReleaseVersionMediaSection.module.css` uses `700` for some pre-existing Label instances
(e.g. `.categoryKicker`) — that is pre-existing, out-of-scope debt (same treatment as the hardcoded-hex
color debt noted in the Color section below). Any **new** Label-role markup this phase adds (rejection/
resubmission hint text, replace-file helper text, category field label) MUST use `800`, matching
Heading/Display, so the contract stays at exactly two weights.

Matches the already-shipped scale in `ReleaseVersionMediaSection.module.css`
(`.helper`/`.mediaName` ≈ Body, `.categoryKicker`/`.contextLine` ≈ Label uppercase,
`.detailTitle`/`.categoryTitle` ≈ Heading, `.headline` ≈ Display). New copy introduced by this phase
uses these same four roles — do not introduce a fifth size.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--bg-primary` (#f9f9f9) | Page/app background behind the drawer overlay |
| Secondary (30%) | `--bg-card` / `--bg-secondary` (white / near-white) | Drawer surface, `Card`, form field backgrounds |
| Accent (10%) | `--accent-primary` (#5f84dd) | Primary CTA button ("Überarbeitung einreichen"), active segmented-control tab, drop-zone/replace-zone border and hover state, focus ring |
| Destructive | `--color-error` (#dc3545) via `Button variant="danger"` / `Badge variant="danger"` | "Medium löschen" action only — never used for the replace-file or resubmit actions |

Accent reserved for: the resubmit/replace primary action button, the active category tab in the
segmented control, and the file-replace drop-zone's active/hover border — nothing else in this
phase's new markup gets accent color.

**Locked constraint (UAT-04, Phase 143):** no hardcoded hex color fallbacks in new user-facing
markup. `ReleaseVersionMediaSection.module.css` currently hardcodes status colors directly
(`#f59e0b`, `#16a34a`, `#ef4444`, `#92400e`, `#166534`, `#991b1b`) in `.assetStatusReview` /
`.assetStatusPublic` / `.assetStatusRejected` / `.statusHint` / `.errorBox` instead of using the
`Badge` primitive's built-in variants (`success` / `warning` / `danger` / `info` / `muted`, defined
once in `frontend/src/components/ui/ui.module.css`). This is pre-existing debt, not something to fix
wholesale in this phase — but the **new** resubmission/revision indicator this phase adds MUST use
the `Badge` component with an existing variant (`warning` recommended: "Überarbeitet") rather than
adding another hardcoded hex class. Do not extend the hardcoded-hex pattern.

## Interaction Contract — File Replace (submitter side)

Location: the existing "Medium bearbeiten" `Drawer` (`variant="responsiveSheet"`) opened from a
media card in `ReleaseVersionMediaSection.tsx`. Only rendered when `selectedItem.review_state ===
'rejected'` and `canEditSelectedItem` is true.

Layout, top to bottom, inside the existing `.sheetStack`:

1. Existing `.editPreview` image (unchanged) — shows the **currently stored** file until a
   replacement is staged locally; once a replacement file is chosen, swap this preview to the local
   object-URL preview (same `buildLocalPreviewURL` helper already used for the upload drop-zone) so
   the submitter sees exactly what they are about to submit, not a second thumbnail below it.
2. Existing rejection context panel (`.statusHint`, unchanged) — stays visible above the fold the
   whole time so the fix is made with the reason in view.
3. **New**: `FormField label="Kategorie"` wrapping a `Select` populated from the existing
   `CATEGORY_OPTIONS` constant (`ReleaseVersionMediaSection.helpers.tsx`) — same options already
   used for the top-level segmented control, reused here, not redefined.
4. **New**: `FormField label="Datei ersetzen" hint="Ersetzt die aktuell abgelehnte Datei durch eine neue Fassung."`
   wrapping a drop-zone control that visually mirrors the existing upload drop-zone
   (`.dropZone`/`.dropZoneActive`/`.dropZoneDisabled` classes, single-file mode — `multiple` is not
   set here, only one file replaces one row). Reuse the class names; do not create a second visual
   drop-zone style.
5. Existing `FormField label="Beschreibung"` with `Textarea` (unchanged).
6. Existing preview-candidate checkbox row (unchanged, when category allows it).

Footer (existing `Drawer` `footer` prop):
- Left: "Löschen" (`Button variant="ghost" className={styles.dangerGhost}`, unchanged).
- Right: primary action button — label switches per the Copywriting Contract table above, `disabled`
  until at least one of {new file staged, category changed, caption changed} is true for a rejected
  item (prevents a no-op "Erneut einreichen" click that resubmits nothing).

## Interaction Contract — Resubmission Indicator (reviewer side)

Location: `frontend/src/app/admin/fansubs/[id]/reviews/[reviewId]/page.tsx`, in the existing
`.contentPanel` section, directly above the media preview — and mirrored as a compact `Badge` in
whatever list view already renders pending review rows (reuse `releaseReviewPresentation.ts`'s
existing status-badge helper pattern rather than adding a second status-formatting module).

- Detail page: a `Badge variant="warning"` reading "Überarbeitet" next to the existing status
  `Badge`, plus one line of context copy (see Copywriting Contract) showing who rejected the prior
  revision and why. This uses data already available once the backend lifecycle change lands
  (source_revision + prior rejection record) — no new fetch pattern, extend the existing
  `getReleaseReview` DTO consumption.
- List/queue rows: the same `Badge variant="warning"` "Überarbeitet" as a compact inline chip next
  to the item's existing status badge — do not add a second row or a new card layout for this.
