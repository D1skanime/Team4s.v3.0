<objective>
Implement CONTEXT.md D-05 (targeted, trigger-respecting reseed) and D-06 (protected asset hash
guard) together, since D-06 exists specifically to prove D-05's reset never touches tracked media.
This is the ONLY point in Phase 134 (per D-03) where the shared `team4s_v2` database is actually
reset — it runs after the green gate (Plan 134-04) has already proven the fixture, migration, and
matrix all work, so this reset is a low-risk confirmation step, not a leap of faith.

The reset is deliberately narrow: `TRUNCATE members CASCADE` structurally reaches ~50 tables via
`media_assets.owner_member_id -> anime.cover_asset_id/banner_asset_id` and is blocked anyway by the
`reject_truncate` append-only triggers (RESEARCH.md Anti-Patterns). The reset instead DELETEs only
rows carrying this fixture's own identifying prefixes (`seed129-` group slugs, `Seed129 Anime %`
titles) in FK-safe child-to-parent order, then re-runs the Plan-134-01 seed to recreate a clean
`sheppert`/`csubs-leader` state — proving PMQA-01's "idempotent, reproducible from a clean state"
claim is genuinely real, not just a re-run-without-deleting no-op.

Purpose: prove the reset/reseed cycle is safe and leaves canonical ownership + tracked badge assets
untouched (PMQA-06), immediately before the live UAT (Plan 134-06) inspects the resulting live data.
Output: a hash-guard script, a triple-guarded targeted reset script, and captured before/after
evidence.

  <name>Task 1: Protected-asset hash guard (snapshot + verify modes)</name>
  <files>scripts/verify-protected-assets.mjs</files>
  <read_first>frontend/scripts/verify-profile-image-delivery.mjs</read_first>
  <action>
Create `scripts/verify-protected-assets.mjs` (Node 18+, no external dependencies, matching the
seed/evidence scripts' zero-npm-dependency convention). Support two modes via `--mode
snapshot|verify` (parse args the same minimal way `collect-member-profile-evidence.mjs`'s
`parseArgs` does — `--key value` pairs).

`snapshot` mode: recursively walk (`node:fs` `readdirSync(..., { recursive: true, withFileTypes:
true })`, Node 18+ supports the `recursive` option) exactly these three directories relative to repo
root: `frontend/public/history-event-badges`, `frontend/public/history-event-badges-transparent`,
`frontend/public/member-achievement-badges`. For every regular file, compute `sha256(readFileSync(path))`
and record `{ path (relative, POSIX-separated), sha256, bytes }`. Write the sorted-by-path array as
JSON (via `--out <file>`) with a top-level `{ captured_at, file_count, files: [...] }` shape.

`verify` mode: takes `--against <snapshot-file>` (a file produced by a prior `snapshot` run),
re-walks the same three directories, and compares: (a) `file_count` matches exactly, (b) every path
in the snapshot still exists with an IDENTICAL sha256, (c) no path exists now that wasn't in the
snapshot. On ANY mismatch, `fail()` with a message naming the specific path(s) and hash values that
differ (never a generic "assets changed" message) and exit 1. On full match, print
`"protected assets verified bit-identical: <file_count> files"` and exit 0.

Both modes must fail loudly (throw, non-zero exit) if any of the three target directories does not
exist at all — a missing directory is itself a protected-asset integrity failure, never treated as
"zero files, pass."
  </action>
  <acceptance_criteria>
    - `node scripts/verify-protected-assets.mjs --mode snapshot --out /tmp/test-snapshot.json` produces valid JSON with `file_count` matching `find frontend/public/history-event-badges frontend/public/history-event-badges-transparent frontend/public/member-achievement-badges -type f | wc -l`.
    - Running `--mode verify --against /tmp/test-snapshot.json` immediately after the snapshot (no changes made) exits 0.
    - Manually touching one byte of one tracked file, then re-running verify, exits 1 and names the specific changed file path in its error output.
  </acceptance_criteria>
  <verify>
    <automated>node scripts/verify-protected-assets.mjs --mode snapshot --out /tmp/phase134-protected-assets-test.json && node scripts/verify-protected-assets.mjs --mode verify --against /tmp/phase134-protected-assets-test.json</automated>
  </verify>
  <done>Snapshot/verify round-trip passes with zero drift on an unmodified tree, and fails loudly with a specific path on a deliberately modified tree.</done>
</task>
