<objective>
Build the migration fresh/up/down proof tooling RESEARCH.md confirms does not exist anywhere in
this codebase today (`grep -rl "DROP DATABASE\|CREATE DATABASE" backend/ scripts/` returns zero
results). PMQA-03 requires migrations to be proven on a fresh/empty database plus a full up/down
round-trip, with existing synthetic rows reset rather than migrated — this is new, purpose-built
infrastructure driven directly from the existing `migrations.Runner` primitives (`Up`/`Down`/
`Status`), never touching the live `team4s_v2` database.

Purpose: prove the 145-pair migration chain (`database/migrations/0001...0145`) is a clean,
reversible unit before Phase 134's later rollout reset (Plan 134-05) touches the shared database.
Output: a guarded ephemeral-database helper + one hard-failing (never skipping) Go integration test
that DROPs, CREATEs, applies every migration, rolls every migration back, and asserts zero residual
application tables.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Go test process -> PostgreSQL `postgres` maintenance database | This test issues DROP DATABASE / CREATE DATABASE — the single most destructive SQL statement class in this phase. |
| Ephemeral fresh DB -> migration files on disk | The test executes every `.up.sql`/`.down.sql` file verbatim via `Runner`; a malicious or corrupted migration file would execute with full DB owner privileges (same risk profile as normal migration application, not a new one introduced by this plan). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-134-04 | Tampering | DropAndCreatePhase134FreshDatabase | mitigate | Exact-match regex on the target database name (`^team4s_phase134_migration_fresh$`, no wildcard), `pgx.Identifier{}.Sanitize()` on every DROP/CREATE, and a mandatory (never-skip) DSN whose database must literally be `postgres` before any DROP/CREATE runs — directly closes RESEARCH.md's "destructive reset script accidentally run against the wrong database/environment" threat pattern for this specific tool. |
| T-134-05 | Elevation of Privilege / Tampering | TEAM4S_PHASE134_MIGRATION_DSN reuse | mitigate | Dedicated env var, never falls back to `DATABASE_URL`; the live `team4s_v2` database is never named or connected to by this test at any point. |
| T-134-06 | Denial of Service (self-inflicted) | Full 145-pair Down chain | accept | A genuinely broken historical down-migration surfacing here is the intended, desired outcome of this test (Pitfall 3) — it only affects the throwaway ephemeral database, never production data. |
</threat_model>
