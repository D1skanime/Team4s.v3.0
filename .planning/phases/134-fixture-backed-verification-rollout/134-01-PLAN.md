manifest-vs-seed drift).

Media upload (backend/internal/handlers/app_profile_story_image.go, `UploadOwnProfileStoryImage`,
wired at `v1.POST("/me/profile/story-images", authMiddleware, appAuthHandler.UploadOwnProfileStoryImage)`
in backend/cmd/server/main.go:354):
- Request: multipart/form-data, field name "image", one of image/jpeg|image/png|image/webp, <=10MB,
  <=40MP pixel count.
- Success response: 201, body `{"data":{"media_asset_id": <int64>, "public_url": "<string>"}}`.
- Failure statuses: 400 (bad/missing file), 401 (no auth), 403 (disabled account), 500.

Reference/attach the uploaded image (backend/internal/handlers/app_profile.go:98 `UpdateOwnProfile`,
wired at `v1.PUT("/me/profile", ...)`):
- Request body field `member_story_json` (raw JSON, TipTap document). An image node has the exact
  shape `{"type":"image","attrs":{"media_asset_id": <int64 from upload>,"width_percent":60,"alignment":"center"}}`
  nested inside the document's `content` array (see backend/internal/handlers/app_profile_story_image_test.go:282
  and :347 for the exact wire shape already exercised by existing tests).
- The handler auto-derives `member_story_editor_type="tiptap"` and
  `member_story_content_schema_version=1` server-side when `member_story_json` is set
  (backend/internal/handlers/app_profile.go:306-307, :336-337) — the seed must NOT set these fields
  itself.
- `applyStoryImageLifecycle` (backend/internal/handlers/app_profile_story_image.go:322) performs an
  IDOR check (rejects an `media_asset_id` the caller doesn't own, `ErrIDORViolation`) AND
  cleanup-on-save (deletes any PREVIOUSLY-referenced-but-now-dropped image). This means: if the
  seed's PUT omits a previously-uploaded image's id from the new `member_story_json`, that image is
  DELETED. The idempotent re-run path must therefore always include the SAME already-uploaded
  `media_asset_id` in every subsequent PUT, never a fresh upload, once one exists.

Read the uploaded image back / resolve it publicly (backend/internal/handlers/app_profile_story_image.go:216
`ResolveStoryImageByID`, wired at `v1.GET("/media/story-images/:id", appAuthHandler.ResolveStoryImageByID)`
in backend/cmd/server/main.go:437):
- Public (no auth), 200 with the image bytes, or 404.

Public profile read-back (existing, unmodified): `GET /api/v1/members/{slug}` returns
`{"data": {..., "member_story_html": "<p>...<img src=\"/media/story-images/{id}\" .../>...</p>"}}`
once the story image is referenced and the profile re-fetched — `member_story_html` is the server-
rendered HTML the public DTO exposes (backend/internal/models/member_profile.go:319); this is the
field the seed's new media assertion and later plans' live-UAT screenshot check must inspect.

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Seed script -> backend API | The seed authenticates via real Keycloak direct-grant tokens and calls the real, already-hardened creation/admin/upload API — no new trust boundary, but the new multipart upload call is a new request shape on an existing boundary. |
| Uploaded fixture image -> media_assets / disk storage | The story-image handler already enforces MIME allow-list, size cap, pixel-bomb guard, and EXIF strip (D-16/D-17/D-19 per existing code comments) — this plan does not touch that handler, only calls it. |
| Manifest JSON -> seed/matrix/reset scripts | A malformed or incomplete manifest could silently produce false-green fixture verification across three downstream consumers (134-01 itself, 134-03's matrix, 134-05's reset). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-134-01 | Tampering | scripts/seed-member-profile-fixtures.mjs media step | mitigate | Only ever uploads the one checked-in `scripts/fixtures/seed134-story.jpg`; never accepts an externally-supplied path or URL, so the seed cannot be tricked into uploading arbitrary attacker-controlled bytes. |
