<objective>
Build the dedicated verification matrix (CONTEXT.md D-07): a Postgres-backed integration suite that
seeds the versioned Phase-134 fixture ONCE against a full-schema throwaway database and asserts
every one of the nine required cases (anonymous public, hidden, owner, refresh-only, missing,
sparse, dense, error, pagination) against `scripts/member-profile-fixture.manifest.json` — the SAME
manifest Plan 134-01 made the seed itself read from, so the matrix cannot silently drift from what
the fixture actually guarantees.

This diverges deliberately from the Phase-129 precedent (which builds its throwaway database via
`pg_dump --schema-only` and hand-writes each test's own reference-table rows): migrations
`0085_role_definitions_seed.up.sql`, `0097_v12_status_foundation.up.sql`,
`0100_role_definitions_fansub_lead.up.sql`, and `0112_role_model_cleanup.up.sql` embed the
`role_definitions`/`visibilities`/`review_statuses` reference-data INSERTs directly in migration
files — a `pg_dump --schema-only` copy would NOT carry that data (schema-only excludes all rows
regardless of origin), but replaying the real migration chain via `migrations.Runner.Up` (the same
primitive Plan 134-02 already drives) does. Building `team4s_phase134_test` via a full migration
replay is therefore both simpler and more complete than a schema-only dump for this specific case.

Purpose: prove PMQA-04's nine-case matrix against realistic, manifest-declared, API-seeded data (not
ad hoc inline SQL fixtures), so the matrix result is trustworthy evidence for milestone closure.
Output: a provisioning script, an extended testsupport helper, and two new Go test files covering
all nine matrix cases.
</objective>
