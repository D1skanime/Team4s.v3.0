<objective>
Close GAP-06 from 137-UAT.md: determine whether `CanForReleaseVersion`'s separate
contribution-role fallback (Step 3) is permitted to grant access after the central group-rights
resolver (Step 2, `canForReleaseVersionGroupRole`) has already produced a decisive `user_deny` for
the same actor/action — a reachable path today, per `137-PATTERNS.md`'s pattern analysis — and
either fix it, lock it as an intentional exception, or flag it for a human decision, strictly
following the investigate-first Fall A/B/C protocol `137-UAT.md` mandates. This is NOT a blind fix;
the plan's own execution must perform the investigation, not assume an outcome in advance.

Purpose: `137-CONTEXT.md`'s D01 precedence list states a User DENY override "overrides normal
group-scoped grant sources" and "also overrides a specialized Review Delegation grant" but never
mentions "contribution role" as a resolver source category at all — Contribution Roles are a
`CanForReleaseVersion`-local Step-3 concept, not one of `GroupRightsResolution`'s batch-loaded
source categories. The current "override-blind by design" framing for Step 3 traces only to
`137-05-SUMMARY.md` (an executor's own implementation note), not to any `137-CONTEXT.md`-authored
decision — `137-PATTERNS.md` already flags this as inconclusive/Fall-C-leaning unless stronger
evidence is found during this plan's own re-investigation.

Output: `permissions.go` with either a corrected `CanForReleaseVersion`/`canForReleaseVersionGroupRole`
(Fall A) or an unchanged runtime plus an explicit locking regression test and documentation (Fall
B/C), and `effective_rights_integration_test.go` with a new test that actually exercises the
conflict (unlike the existing test, whose fake resolver leaves `contributionRoles` empty and
therefore never proves what happens when Step 3 would grant).
</objective>

backend/internal/permissions/permissions.go's CanForReleaseVersion (lines 568-641, full text
reproduced in 137-PATTERNS.md's GAP-06 section) has three steps: Step 0 base checks
(platform-admin/disabled-user short-circuits), Step 1 resolve the release version's fansub group
IDs, Step 2 canForReleaseVersionGroupRole (the shared, override-aware group-context path — already
routes through ResolveGroupRights and already honors a stored user_deny for the group-role
question), Step 3 an independent contribution-role loop over
s.resolver.ListActorContributionRolesForVersion(ctx, actor.AppUserID, releaseVersionID) that grants
immediately if any returned role code satisfies roleAllows(code, action) — this loop runs
unconditionally regardless of what Step 2 returned. Only after Step 3 fails to grant does the
existing code check "if groupRoleResult.ReasonCode == ReasonCodeUserDeny { return groupRoleResult,
nil }" (lines 533-535) to surface the more specific denial reason.

canForReleaseVersionGroupRole (lines 643-678) returns (Result, hasGroupMembership bool, error); its
Result carries ReasonCode == ReasonCodeUserDeny (permissions.go's package-level constant) exactly
when a stored user_deny was the decisive source for that group, distinguishable from a zero-value
Result (never granted, never explicitly denied by override) by this ReasonCode field.

backend/internal/permissions/effective_rights_integration_test.go's integrationFakeResolver (lines
29-64, reproduced in 137-PATTERNS.md) already has a contributionRoles []string field and
ListActorContributionRolesForVersion method wired to return it — the existing
TestIntegrationCanForReleaseVersionGroupRoleStepUserDenyOverridesRoleGrant test (lines 622-644)
leaves contributionRoles nil/empty, so it proves Step 2's own override-awareness but never actually
exercises Step 3 granting after Step 2 denied. This plan's new test must populate contributionRoles
with a role that satisfies roleAllows(role, action) for the same action Step 2's stored user_deny
targets, to actually reach the conflict.

137-CONTEXT.md D01 (Section 3) is reproduced in full in this plan's @context reference above; the
directly relevant line is item 4's "User DENY override ... Overrides normal group-scoped grant
sources. Also overrides a specialized Review Delegation grant." and Section 2 rule 9's "Review
delegation remains a specialized membership seam and is not migrated into generic user overrides."
Neither passage names "contribution role" anywhere in the document.
