<objective>
Close GAP-01 and GAP-02 from 137-UAT.md: fix `AdminEffectiveRightsHandler.MutateOverride` so a
post-commit-only failure (target actor re-resolution or `ResolveGroupRights` re-resolution) can
never make an already-committed, successful override write look like a failed HTTP request to the
caller, and make the generic admin/security audit log consistent — written unconditionally for
every successful mutation and for the reject branches that currently write nothing at all
(target-not-active-member, unknown action, non-overridable action, missing reason, and the
request-level body/path-mismatch guard).

Purpose: `MutateOverride` currently commits the override + immutable history transactionally, then
performs two more reads (`resolveTargetActor`, `ResolveGroupRights`) purely to build the response
and only THEN writes the generic audit entry. If either post-commit read fails, the handler returns
404/500 for an operation that already succeeded and permanently changed state, and the generic
audit log entry for that successful mutation is silently lost (137-REVIEW.md WR-02). Four of five
mapped rejection branches plus the separate body/path-mismatch guard also write no audit entry at
all today, leaving BOLA-style probing attempts (foreign/inactive target, unknown action code, or a
manipulated body group_id/target_user_id) untraceable in the generic admin audit trail that
CLAUDE.md calls out as a project-level observability requirement.

Output: `admin_effective_rights_handler.go` where the HTTP response for a successful mutation is
built entirely from data the mutation service already returned (best-effort enrichment only adds
the computed `effective_right` snapshot, never gates the 200), the generic audit write for success
happens immediately after commit, and all reject branches UAT names — including the BOLA/IDOR body/
path-mismatch guard — are audited too. Because this plan makes `CapabilityActivationStatusPending`
genuinely reachable in production for the first time, it also brings the three locked documentation
sites that currently claim "Phase 137 mutations only ever emit active" back in line with real
behavior (see the Revision Note below).

**Revision note (checker round):** Two blocking findings were raised against this plan. (1) GAP-02's
audit coverage did not include the body/path-mismatch guard at admin_effective_rights_handler.go:227,
the one reject path that returns via `c.JSON` directly instead of through `writeMutationError` — Task
2 now adds an explicit `auditMutationRejected` call there plus a named regression test. (2) GAP-01's
fix makes `CapabilityActivationStatusPending` reachable by real traffic, contradicting three locked
"pending is unused in Phase 137" documentation sites. Of the two suggested fix shapes, this revision
chose **option (a): update the documentation to match the new true behavior**, not option (b)
(introducing a new response field/flag). Reason: `CapabilityOverrideMutationResult`'s schema
`required` field list (`status, changed, before, after, effective_right, activation_status`) is
itself locked as byte-for-byte unchanged by `TestCapabilityOverrideSchemasUnchangedContract`; a new
field would touch that schema, its root mirror, and frontend consumers for no additional safety,
since `activation_status` already exists specifically to carry this kind of degraded-response signal
and `Pending` was declared exactly for this purpose. A three-site description-text edit plus one
updated test assertion is the smaller, cleaner change consistent with 137-UAT.md's "kleinstmöglichste
saubere Korrektur" instruction for GAP-01.
</objective>
