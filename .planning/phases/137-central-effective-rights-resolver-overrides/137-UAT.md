# Zu behebende Gaps

## GAP-01 — Erfolgreicher Commit darf nicht als HTTP-Fehler erscheinen

### Ist-Zustand

Im aktuellen `AdminEffectiveRightsHandler.MutateOverride()`-Ablauf wird die eigentliche Override-Mutation inklusive immutable History bereits committed.

Danach erfolgen im Handler nochmals Reads/Resolutionen, u. a.:

- Target Actor erneut auflösen
- `ResolveGroupRights()`
- generisches Audit
- Response-Aufbereitung

Dadurch kann aktuell folgender Zustand entstehen:

1. Override erfolgreich gespeichert.
2. Override-History erfolgreich gespeichert.
3. DB-Transaktion erfolgreich committed.
4. Nachgelagerter Read/Resolve schlägt fehl.
5. Client erhält `404` oder `500`.
6. Mutation ist trotzdem dauerhaft aktiv.

Damit meldet die API einen fehlgeschlagenen Write, obwohl der Write erfolgreich war.

### Ziel

Nach erfolgreichem Commit darf ein rein nachgelagerter Response-/Enrichment-Fehler **nicht den Persistenzerfolg falsch darstellen**.

### Anforderungen

- Bestehende Handler-/Service-Grenze analysieren.
- Kleinstmögliche saubere Korrektur wählen.
- Persistenzfehler vor Commit weiterhin korrekt zurückgeben.
- Keine Catch-all-Lösung, die echte Write-Fehler verdeckt.
- Immutable Override-History weiterhin atomar mit der Mutation speichern.
- Authorization, BOLA/IDOR und Gruppen-Scope nicht abschwächen.

### Pflichttests

Mindestens:

- erfolgreicher Override-Write → Erfolgsresponse
- Fehler vor Commit → kein persistierter Override
- History-Fehler → kein persistierter Override
- Post-Commit-Response/Resolve-Problem kann erfolgreichen Write nicht mehr als fehlgeschlagen darstellen
- Retry-Verhalten bleibt konsistent

## GAP-02 — Generisches Audit konsistent machen

### Ist-Zustand

Die fachliche Override-History ist transaktional.

Das allgemeine Admin-/Security-Audit ist jedoch auf mehreren Fehler-/Reject-Pfaden unvollständig bzw. kann nach erfolgreichem Commit ausbleiben.

Zu prüfen sind insbesondere:

- Target ist kein aktives Gruppenmitglied
- unbekannte Action
- Action nicht `user_overridable`
- erforderlicher Reason fehlt
- Permission denied
- BOLA/IDOR-relevante Rejects
- Fehler-/Success-Pfade im Zusammenhang mit GAP-01

### Ziel

Security-relevante Mutationsversuche und erfolgreiche Admin-Mutationen sollen nachvollziehbar auditiert werden.

### Anforderungen

- Keine sensiblen Daten unnötig protokollieren.
- Keine widersprüchlichen Doppel-Audits.
- Immutable Override-History bleibt Source of Truth der fachlichen Änderung.
- Sekundäres Audit darf einen bereits committed erfolgreichen Write nicht nachträglich als fehlgeschlagen darstellen.
- Wenn das generische Audit technisch `best effort` bleiben muss, dies klar implementieren, dokumentieren und testen.

## GAP-06 — Contribution-Role-Fallback gegen D01/Phase-137-Semantik prüfen

### Hintergrund

In `CanForReleaseVersion()` existiert nach dem zentralen Group-Rights-Resolver weiterhin ein separater Contribution-Role-Fallback.

Der bestehende Code behandelt Contribution Roles offenbar bewusst als eigene bzw. `override-blind` Domain.

Dadurch ist potentiell möglich:

```text
user_deny
→ Group Resolver DENY
→ Contribution Role Fallback
→ ALLOW
```

### Verbindliches Vorgehen

Dieser Punkt darf **nicht blind geändert** werden.

Claude muss zuerst:

1. `137-CONTEXT.md` lesen.
2. D01 und die dokumentierte Precedence prüfen.
3. vorhandene Contribution-Role-Tests lesen.
4. bestehende `CanForReleaseVersion()`-Semantik nachvollziehen.

Danach:

### Fall A — Context ist eindeutig

Wenn Phase 137 eindeutig festlegt, dass `user_deny` auch Contribution Roles schlagen muss:

- Enforcement korrigieren,
- Regressionstest ergänzen,
- relevante Release-Version-Pfade prüfen.

### Fall B — Contribution Roles sind ausdrücklich override-blind

Wenn Phase-137-Unterlagen diese Ausnahme eindeutig bestätigen:

- Runtime-Semantik nicht ändern,
- expliziten Regressionstest sicherstellen,
- Ausnahme dokumentieren.

### Fall C — Unterlagen widersprechen sich

Dann:

- keine eigenmächtige fachliche Änderung,
- bisherigen Runtime-Stand beibehalten,
- im Abschlussbericht klar ausweisen:

```text
DECISION REQUIRED — Contribution Role vs User Deny
```

Dieser Punkt darf **nicht** zu einem allgemeinen Permission-Redesign führen.
