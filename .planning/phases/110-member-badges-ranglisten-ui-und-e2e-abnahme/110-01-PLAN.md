## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser (anonymous or authenticated) -> `/members/ranking` SSR page | Untrusted `page` query param crosses here |
| `/members/ranking` SSR page -> `GET /api/v1/member-point-ranking` | Already-existing Phase 109 public read endpoint; no new trust boundary introduced |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-110-01 | Tampering | `page` query param on `/members/ranking` | accept (pre-existing mitigation) | Authoritative clamp (`<1->1`, `>1000->1000`, non-numeric->1) already lives server-side in `MemberPointRankingHandler.GetMemberPointRanking` (Phase 109); this plan's client-side `Math.max(1, ...)` is a UI default only, never the security boundary — do not reimplement clamping as a client-side source of truth |
| T-110-02 | Information Disclosure | Ranking row rendering | accept (pre-existing mitigation) | `member_point_totals` join in `ListRanking` already filters `profile_visibility='public'` server-side (Phase 109, unchanged by this plan); this plan adds no client-side "show all" bypass and consumes the response as-is |
| T-110-03 | Tampering | Nav entry visibility (AppShell) | mitigate | Static, non-conditional nav item added identically to both `publicItems` arrays — no user input controls whether it renders, so there is no injection/bypass surface |
| T-110-SC | Tampering | npm/pip/cargo installs | accept (not applicable) | Zero new package installs in this plan (Package Legitimacy Audit in 110-RESEARCH.md confirms no new dependencies for the whole phase) |

Note: the ROADMAP SC6 abuse guards (self-confirmation, double-booking, scope escalation) are
explicitly out of scope for Phase 110 per `110-CONTEXT.md`'s divergence note — already built and
tested in Phases 106/107/107.1/108. This plan adds only a read-only ranking page and nav entry;
no new abuse surface is introduced.
</threat_model>
