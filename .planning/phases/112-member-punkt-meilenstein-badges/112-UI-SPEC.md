# Phase 112 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope reminder:** Phase 112 adds **zero new pages, zero new sections, zero new components**. It
only adds new *data* (badge catalog entries + one small row-markup addition) inside the existing
category-grouped „Auszeichnungen"-Sektion (`MemberBadgeChain`) that Phase 110 built. Everything in
this document is a delta on top of `110-UI-SPEC.md`, which remains authoritative for the section
frame, the ranking page, and the hero point count — none of that is touched here.

### Badge-Palette-Erweiterung (Bronze / Silber / Gold / Platin)

`MemberBadgePalette` (currently `'gold' | 'indigo' | 'orange' | 'mint' | 'red'`) gains **three**
new values: `'bronze' | 'silver' | 'platinum'`. `'gold'` is **reused as-is** for the Gold tier — no
fourth new value needed there. All four tier colors are derived from existing tokens only, no new
hex literals:

| Tier | `data-palette` value | CSS `--badge-accent` (new rule in `MemberBadgeChain.module.css`) | Rationale |
|------|----------------------|--------------------------------------------------------------------|-----------|
| Bronze | `bronze` (new) | `color-mix(in srgb, var(--color-warning) 55%, var(--text-secondary) 45%)` | Muted warm tone below Gold, derived from the same warning token Gold already uses, mixed toward neutral text-secondary — reads as "duller than gold," matching bronze's real-world rank |
| Silber | `silver` (new) | `var(--text-secondary)` | Grey **is** silver — the existing neutral text token needs no mixing at all, the most literal token-reuse possible |
| Gold | `gold` (existing, unchanged) | `var(--color-warning)` (already defined) | Reuses the exact existing `[data-palette="gold"]` rule — zero new CSS |
| Platin | `platinum` (new) | `color-mix(in srgb, var(--color-primary) 45%, var(--text-secondary) 55%)` | Cool steel-blue-grey mix (primary blue + neutral grey) reads as "above gold" / rarer without inventing a new hue — visually distinct from Silber's flat grey and from Gold's warm amber |

Add these two new CSS rule pairs (`.badgeStep[data-palette="bronze"], .badgeStepLocked[data-palette="bronze"] { --badge-accent: ...; }` and the same for `silver`/`platinum`) directly beneath the
existing `gold`/`indigo`/`orange`/`mint`/`red` rules in `MemberBadgeChain.module.css`, following the
exact existing rule shape. No other CSS file changes.

**Accent reserved for:** unchanged from Phase 110 (nav active state, ranking-row links, active
pagination button) — the new bronze/silver/gold/platinum colors are **badge-family palette values**,
not the page's 10% UI accent color, and must not be reused for any interactive/navigational element.

### Typ 2 — Punkt-Meilenstein-Badges (Gruppe „Fortschritt")

Fixed, statically catalog-able set of 6 (thresholds are locked by D-01) — added to
`MEMBER_BADGE_PRESENTATIONS` only, **not** to `PUBLIC_MEMBER_BADGE_CATALOG`
(see "Kein Locked-Zustand" note below):

| Punkte | `badge_code` | Label | Icon (`lucide-react`) | `variant` | `palette` | `group` |
|---|---|---|---|---|---|---|
| 1 | `point_milestone_first` | Erster Beitrag | `Flag` | `muted` | `mint` | `progress` |
| 50 | `point_milestone_active` | Aktiver Mitwirkender | `Flame` | `neutral` | `mint` | `progress` |
| 200 | `point_milestone_experienced` | Erfahrener Mitwirkender | `Award` | `success` | `orange` | `progress` |
| 500 | `point_milestone_engaged` | Engagierter Mitwirkender | `Medal` | `success` | `orange` | `progress` |
| 1 000 | `point_milestone_veteran` | Veteran | `Trophy` | `warning` | `gold` | `progress` |
| 2 500 | `point_milestone_legend` | Archiv-Legende | `Gem` | `warning` | `gold` | `progress` |

Palette ramps mint → orange → gold in pairs, mirroring the exact ascending-rarity convention
already established by `productive_bronze/silver/gold` (mint → mint → gold) in the same
"Fortschritt" group — no new visual language invented, just extended.

**Kein Locked-Zustand für Typ 2 (wichtige Abweichung vom Rollen-Muster):** D-03 verlangt „nur der
höchste erreichte Meilenstein … keine Kette aller erreichten Stufen." Anders als die Rollen-Gruppe
(die alle 8 Typ-1-Rollen-Badges auch im gesperrten Zustand als Katalogeinträge zeigt) dürfen die 6
Meilensteine **nicht** in `PUBLIC_MEMBER_BADGE_CATALOG` stehen — sonst erschienen bis zu 5 gesperrte
Meilenstein-Chips gleichzeitig neben dem einen erreichten, was D-03 explizit ausschließt. Nur der
aktuell höchste erreichte Meilenstein wird zur Laufzeit als **eine** synthetische, nicht
persistierte `PublicMemberBadge`-Zeile erzeugt (Details siehe `112-RESEARCH.md`, Architecture
Patterns) und fließt über den bereits existierenden „earned-but-not-in-catalog"-Fallback in
`catalogWithEarnedBadges` automatisch in die Fortschritt-Gruppe ein — als ein einzelner, für sich
stehender Zeilen-Eintrag (kein Merge mit `first_contribution`/`productive_*`, die bleiben eigene
Zeilen). Bei 0 Punkten erscheint gar keine Meilenstein-Zeile.

### Typ 3 — Rollen-Volumen-Badges (Gruppe „Rollen", zusammengeführt mit Typ 1)

Tier-Presentation ist **dynamisch** (kein hartcodierter Katalogeintrag pro Rolle — D-04 verbietet
eine hartcodierte Rollenliste). Ein Parsing-Resolver für `badge_code`s der Form
`role_volume_<roleCode>_<tier>` liefert:

| Tier-Token (intern, englisch) | Deutsches Tier-Label | Schwelle | `palette` | `variant` | Icon |
|---|---|---|---|---|---|
| `bronze` | Bronze | 12 | `bronze` | `muted` | `Medal` |
| `silver` | Silber | 108 | `silver` | `neutral` | `Medal` |
| `gold` | Gold | 320 | `gold` | `warning` | `Medal` |
| `platinum` | Platin | 510 | `platinum` | `info` | `Gem` |

`Gem` markiert bewusst konsistent über beide Badge-Familien hinweg die jeweils höchste erreichbare
Stufe (Typ 2 „Archiv-Legende" nutzt ebenfalls `Gem`) — ein absichtliches wiederkehrendes visuelles
Signal für „Spitzen-Rang", keine zufällige Doppelverwendung.

**Chip-Label-Formel (nur der Tier-Anteil, Rollenname steht bereits im Zeilen-Präfix — siehe
unten):** `"{TierLabel} · {Schwelle}+"`, z. B. `"Gold · 320+"`, `"Bronze · 12+"`, `"Silber · 108+"`,
`"Platin · 510+"`. Der `·` (Mittelpunkt, U+00B7) ist der bereits im Katalog etablierte Trenner
(vgl. `"Produktiv · 10+ Anime"`), keine neue Konvention.

**Kein Locked-Zustand für Typ 3:** wie Typ 1's Grundsatz „kein Punkt, kein Badge" gilt hier „unter
12 Credits, kein Volumen-Chip" — es gibt keinen gesperrten Platzhalter-Chip pro Tier. Nur die
aktuell höchste erreichte Stufe wird gerendert (identische „highest-reached"-Logik wie Typ 2, siehe
`112-RESEARCH.md`, Don't-Hand-Roll-Tabelle).

### Zeilen-Komposition — Rollenname-Präfix (löst CONTEXT-Beispiel „Übersetzung: Erste Übersetzung · Gold · 320+" auf)

Jede Zeile der Rollen-Gruppe (ob nur Typ 1 oder Typ 1 + Typ 3 zusammengeführt) erhält **einen**
kleinen Rollenname-Präfix vor dem/den Chip(s), gerendert als eigenes `<span>` (Klasse `.roleLabel`,
12px/700/1.2 — identisch zur bestehenden `.groupTitle`-Typografie, keine neue Größe) am Anfang von
`.badgeRow` (`display:inline-flex; gap:8px`, aus Plan 110-04 unverändert übernommen — der Präfix
wird einfach das erste Flex-Kind):

- Rollenname-Quelle: `FANSUB_GROUP_ROLE_OPTIONS` (`frontend/src/types/fansub.ts`), per `roleCode`
  nachgeschlagen; Fallback auf den rohen `role_code`-String, falls kein Treffer (defensiv, gleiches
  Muster wie `getMemberBadgePresentation`s bestehender Fallback).
- Format: `"{Rollenname}:"`, z. B. `"Übersetzung:"`.
- Gilt **einheitlich für jede Zeile der Rollen-Gruppe**, auch wenn nur ein Typ-1-Chip vorhanden ist
  (kein Sonderfall „nur bei Merge") — das hält die Zeilenform über die ganze Gruppe konsistent und
  skaliert sauber, wenn künftig weitere Badge-Familien (Phase 113) in dieselbe Zeile joinen.

Resultat für eine vollständig zusammengeführte Zeile:
`Übersetzung:` `[Erste Übersetzung]` `[Gold · 320+]` — exakt die vom Nutzer in CONTEXT.md
illustrierte Komposition, aus drei unabhängigen, wiederverwendbaren Teilen zusammengesetzt (Präfix
+ unveränderter Typ-1-Chip + neuer Typ-3-Chip), keine neue String-Konkatenation quer durch Labels.

Fälle:
- **Nur Typ 1, unter 12 Credits:** `Übersetzung:` `[Erste Übersetzung]` — ein Chip, kein
  Volumen-Anteil, keine Lücke/Platzhalter.
- **Mehrere Rollen:** eine eigene Zeile pro `roleCode`, jede unabhängig nach obigem Muster
  zusammengesetzt; das bestehende horizontale Scroll-Verhalten der Gruppe (`.chain{overflow-x:auto}`)
  bleibt unverändert, keine neue Wrap-/Grid-Logik nötig.

**Visueller Fokus der Zeile (löst Checker-FLAG Dim. 2):** Innerhalb der zusammengeführten Rollen-Zeile
trägt der **Typ-3-Tier-Chip** (die aktuell höchste erreichte Volumenstufe, z. B. `[Gold · 320+]`) den
visuellen Fokus — er nutzt die metallische Tier-Palette (Bronze/Silber/Gold/Platin) und ist damit der
farbstärkste, blickführende Anteil der Zeile. Der **Rollenname-Präfix** (`Übersetzung:`) bleibt bewusst
sekundär/gedämpft (`--text-secondary`, kein Akzent), und der **Typ-1-Einstiegs-Chip** (`[Erste
Übersetzung]`) behält seine unveränderte Phase-110-Darstellung als neutraler Einstiegsmarker. Blickführung
also: Tier-Chip (primär) → Typ-1-Chip (sekundär) → Präfix (Kontext-Label). Fehlt der Typ-3-Anteil (unter
12 Credits), trägt der Typ-1-Chip den Fokus der Zeile.

## Platzhalter-Artwork (Icon-Austauschbarkeit)

Alle neuen Icons (`Flag, Flame, Award, Medal, Trophy, Gem`) sind **Lucide-Platzhalter**, exakt wie
Typ 1's bestehende Icons. Der einzige Austauschpunkt für echtes Artwork ist das `Icon: LucideIcon`
-Feld je `MemberBadgePresentation`-Eintrag (Typ 2: 6 statische Einträge; Typ 3: die
`resolveRoleVolumePresentation`-Zweig-Rückgabe). Ein späterer Wechsel auf Bild-Assets (z. B.

Gruppierung und die Zeilen-Zusammenführung bleiben unverändert. Kein Logikcode verweist auf einen
bestimmten Icon-Namen außerhalb dieser Präsentations-Map.

## Interaction / State Contract

| Surface | Kein Erfolg erreicht | Live-Rückstufung | Erfolg |
|---------|----------------------|-------------------|--------|
| Fortschritt-Gruppe — Meilenstein-Zeile (Typ 2) | Unter 1 Punkt: keine Zeile, keine Lücke, keine „nächstes Ziel"-Andeutung | Fällt die Summe durch Storno unter die aktuelle Schwelle, verschwindet die alte Meilenstein-Zeile und ggf. erscheint die nächstniedrigere beim nächsten Render — kein „einmal erreicht"-Badge, keine Verlaufskette, keine Animation/Toast | Genau eine Zeile mit dem höchsten aktuell erreichten Meilenstein-Chip (Icon + Label je Tabelle oben) |
| Rollen-Gruppe — Volumen-Anteil einer Zeile (Typ 3) | Unter 12 Credits in dieser Rolle: Zeile zeigt nur den Typ-1-Chip, kein Volumen-Chip, kein Lock-Icon-Platzhalter für den Volumen-Anteil | Fällt die Netto-Credit-Zahl durch Storno unter die aktuelle Tier-Schwelle, verschwindet der Tier-Chip sofort bzw. wechselt zur nächstniedrigeren Stufe beim nächsten Render — rein visuell, keine Downgrade-Markierung | Zusätzlicher Tier-Chip (`{Tier} · {Schwelle}+`) neben dem unveränderten Typ-1-Chip, in derselben Zeile, mit demselben Rollenname-Präfix |
| Rollen-Gruppe — Zeilen-Präfix | Rendert für jede Zeile der Rollen-Gruppe identisch, unabhängig vom Chip-Inhalt der Zeile | N/A (reiner Label-Text, keine eigene Zustandslogik) | `"{Rollenname}:"` vor dem/den Chip(s) |

Alle drei Zeilen sind rein serverseitig (bzw. laufzeit-)abgeleitet und werden bei jedem
Profil-Fetch neu berechnet — kein Caching/Memoization von „jemals erreicht"-Zustand, identisch zur
bereits etablierten Live-Projektion aus Phase 110 (T-110-09-Muster).
