<objective>
Consolidate the THREE independent client-side owner/viewer resolvers found in this phase's
research — `OwnHiddenProfilePreview.tsx`, `OwnProfileEditLink.tsx`, and (transitively, via its
parent) `CorrectionReportModal.tsx` — onto ONE central `useMemberViewer` hook built on Plan
132-02's `useCancellableSlugState`, with a fail-closed default (uncertain/loading/error ⇒ not
owner) preserved exactly as `OwnHiddenProfilePreview.tsx` already implements it today.

Purpose: PMFE-02 forbids duplicate `getOwnProfile`/`getMemberProfile` logic across owner/preview/
correction actions. `OwnHiddenProfilePreview.tsx` and `OwnProfileEditLink.tsx` each run their own
`useEffect` + `active`-flag + `getMemberProfile` call today; `CorrectionReportModal.tsx` runs a
THIRD, independent `useEffect` + `getOwnProfile()` call to decide whether to hide "Korrektur
melden" on the viewer's own profile — even though it is only ever rendered by
`OwnProfileEditLink.tsx` in the branch where `viewer.is_owner` is ALREADY known to be false. This
plan removes that redundant third call entirely (the parent already gates it) and makes the
remaining two sites consume one shared, single-request, fail-closed (PMFE-10) hook.
Output: `useMemberViewer.ts` (new shared hook + test), `OwnHiddenProfilePreview.tsx` and
`OwnProfileEditLink.tsx` refactored to consume it, `CorrectionReportModal.tsx` with its
independent `getOwnProfile` effect removed.
</objective>

      hook resolves to an `'unavailable'` status, not `'error'`; on any other failure it resolves
      to `'error'`.

      `viewer`), not just `viewer`, so a consumer that needs the whole profile (the owner-upgrade
      preview) does not need a second request.
    - Two independent hook instances called with the SAME `(slug, enabled)` inputs in the same
      render tree each still resolve correctly and consistently (this hook does not need a
      cross-instance request cache — Task 2 achieves the "one request" truth by having only ONE
      call site per page, not by de-duplicating concurrent instances).
  </behavior>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Browser client (unauthenticated timing) -> owner-only UI | The client cannot be trusted to know "am I the owner" before the server response resolves; the fail-closed default is the only thing preventing a transient owner-UI flash for a non-owner. |

| T-132-06 | Repudiation / Tampering (redundant duplicate authority) | `CorrectionReportModal`'s former independent `getOwnProfile` gate | mitigate | Removed entirely; the single authoritative owner check now lives in `OwnProfileEditLink` via `useMemberViewer`, eliminating a second, differently-shaped ("app_user"-keyed via `getOwnProfile` vs slug-keyed via `getMemberProfile`) owner-determination code path that could drift out of sync with the primary one. |
| T-132-SC | Tampering | npm/pip/cargo installs | accept | No new packages are installed by this plan. |
