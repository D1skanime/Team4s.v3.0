### D-12
Canonical Proxy-merge pattern (frontend/src/components/ui/Select.tsx:5-9):
```ts
import ownStyles from './Select.module.css'
import sharedStyles from './ui.module.css'

const styles = new Proxy({} as Record<string, string>, {
  get: (_target, prop: string) => ownStyles[prop as keyof typeof ownStyles] ?? sharedStyles[prop as keyof typeof sharedStyles],
})
```
Current broken pattern, confirmed present in exactly 16 files via
`grep -rl "{ \.\.\.sharedStyles, \.\.\.ownStyles }\|{ \.\.\.ownStyles, \.\.\.sharedStyles }\|{
\.\.\.shared" frontend/src/app/admin/fansubs/[id]/edit/*.tsx` (re-run this grep at execution time to
confirm the exact 16 files and exact variable names each uses -- they are not all named
`sharedStyles`/`ownStyles` identically, e.g. `NotesTab.tsx:20,30` uses
`import sharedStyles from '../../../admin.module.css'` +
`const styles = { ...sharedStyles, ...fansubEditStyles }`):
```ts
const styles = { ...sharedStyles, ...fansubEditStyles }  // or equivalent spread variable names per file
```
Why this matters beyond tests: per 174-23-SUMMARY.md, this bug is currently LATENT in production too
(real CSS Modules under webpack/Next bundling ARE plain objects, so the spread works correctly at
runtime in the actual app) -- it ONLY manifests under Vitest+jsdom's CSS-module mock (a Proxy). The
fix is still worth making repo-wide now: it removes a footgun where any FUTURE test asserting a
merged-only class name would silently fail to detect missing styles, and brings these 16 files in
line with the project's own established canonical pattern.

### D-11
Flaky assertion (frontend/src/app/admin/fansubs/[id]/edit/AnimeProjectNotesSection.test.tsx:116, in
`it('verwendet übergebene Anime-Props ohne zusätzlichen Admin-Anime-Load', ...)`):
```ts
render(<AnimeProjectNotesSection fansubId={5} hasAccessToken animes={[{ id: 22, title: 'Bleach' }]} />)
expect(getAdminFansubAnimeMock).not.toHaveBeenCalled()   // <-- synchronous, immediately after render
fireEvent.click(screen.getByRole('button', { name: /bleach ausklappen/i }))
...
await waitFor(() => { /* later assertions */ })
```
Confirmed via 5 consecutive isolated runs during planning: always green alone (202/195/197/200/199ms).
Per 174-FOLLOWUPS.md F-24: red specifically "im vollen Vitest-Lauf" (full suite), suggesting the
assertion races against `AnimeProjectNotesSection`'s own mount-time effect queue under heavier
concurrent suite load rather than against any real component defect (the component is NOT supposed to
call `getAdminFansubAnime` when an `animes` prop is supplied -- read the component to confirm the
exact condition). The robust fix is to stop asserting "never called" at a single synchronous instant
and instead assert it at the END of the test (after the save flow's `await waitFor(...)` has already
resolved), where any delayed/async call would have had ample time to occur if the component were
actually buggy -- this makes the assertion's correctness independent of suite-load timing while
preserving its real intent.
