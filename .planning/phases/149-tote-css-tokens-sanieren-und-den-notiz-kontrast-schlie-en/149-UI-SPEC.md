# Phase 149 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Phase framing (read first)

This phase is **token-hygiene and one contrast-number remediation, not new UI.** No new
component, layout, spacing value, typography value, or copywriting string is introduced. The
binding baseline — the 13 dead-token names, the dead→replacement mapping, the guard-test
requirement, and the PublicNoteCard band-mix change — is defined verbatim in `.planning/ROADMAP.md`
under "### Phase 149: Tote CSS-Tokens sanieren und den Notiz-Kontrast schließen"; that section
remains the authoritative source for goal/scope/success-criteria. This document translates it into
a design contract and — where this agent's own repo-verification (2026-09-05, commit `aa9256f5`)
found the ROADMAP's per-token occurrence tally does not match the live source files — **corrects
the occurrence-level scope** so the executor touches exactly the broken references and nothing
else. Sections that do not apply to a token-rename/contrast phase (Spacing, Typography, most of
Copywriting, Registry) are marked N/A with a one-line reason, matching the precedent set by
`148-UI-SPEC.md`.

**Every fix in this phase is a pure token-name substitution or a single mix-percentage change.
No hex value, no design token's stored value, and no spacing/typography value changes.**

### `--radius` resolution (mechanical lookup, resolved by source-reading, not asked to the user)

`RoleCapabilityDetail.tsx:224` sets `borderRadius: 'var(--radius)'` on a `role="alert"` inline
error box (`padding: var(--space-3)`, 1px danger border, `fontSize: '0.875rem'`). Two structurally
identical `role="alert"` danger boxes elsewhere in the codebase with the same visual weight
(`MemorialSetterAction.tsx:108`, `CorrectionReportModal.tsx:111`) both hardcode `borderRadius: 6` —
i.e. exactly `--radius-sm` (`globals.css:113`). This is the closer contextual match than
`--radius-md` (12px, used for larger cards/panels, e.g. `.hero` in `globals.css:241`). **Resolved:
`--radius-sm`.** This does not change the box's rendered geometry from what an executor would
naturally pick by matching sibling alert boxes — it only makes the existing convention explicit
via a token instead of an undefined variable.

### `--tag-` resolution (false positive, confirmed)

`app/dev/ui-system/page.tsx:217,220` builds `` `var(--tag-${item.key}-bg)` `` / `` `var(--tag-${item.key}-fg)` `` /
`` `--tag-${item.key}` `` as template strings over a static `item.key` catalog (gallery, history,
oldweb, forum, irc, event, artwork, other). Every resulting concrete property name (`--tag-gallery-bg`,
`--tag-gallery-fg`, … `--tag-other-fg`) **is already defined** in `globals.css:47-62`. The repo-wide
scan's raw-substring match on `--tag-` is a template-string artifact, not a real dead-token
reference. **Resolved: not in scope, no fix needed, no guard-test exclusion required** (the guard
test operates on literal `var(--name)` CSS syntax, which this dynamic-string pattern in a `.tsx`
file will not match in the first place — see the guard-test design below).

### `--color-text-tertiary` special case: `Breadcrumbs.module.css:41`

```css
color: var(--breadcrumb-separator-color, var(--color-text-tertiary));
```

This is a **two-level dead reference**: the outer token `--breadcrumb-separator-color` is also
undefined anywhere in the codebase (confirmed), and its fallback is itself a `var()` reference to
the also-undefined `--color-text-tertiary` with no further fallback. Per CSS `var()` substitution
rules, a fallback that is itself an unresolvable `var()` reference does not rescue the declaration
— the whole thing is still invalid-at-computed-value-time. This occurrence is genuinely broken
despite superficially "having a fallback," and is correctly counted as in-scope. **Fix: replace
only the inner dead reference**, keeping the outer customization-seam token intact:

```css
color: var(--breadcrumb-separator-color, var(--text-faint));
```

This preserves `--breadcrumb-separator-color` as a legitimate, currently-unused
component-customization seam (consistent with several other similarly-shaped, still-undefined,
always-fallback-protected tokens found elsewhere in this codebase, e.g. `--group-nav-*`,
`--breadcrumb-link-color` — none of those are in this phase's 13-token list and must not be
touched) while making the chain fully resolvable using only an already-existing token, per
Success Criterion 2.

**Accent reserved for:** not applicable in the Part-A sense — none of these renames touch the
10%-accent role-color seam (`--role-accent`, owned by Phase 148). `--accent-primary` here is used
for two unrelated pre-existing purposes (candidate-search hover/focus chrome in `FansubEdit`, and
an info badge in `VersionRow`) that already existed as "accent-ish" treatments before this phase;
this phase does not expand what counts as accent, it only fixes the token name pointing at it.

## How correctness is verified (no eyeballing — matches `roleCatalog.accessibility.test.ts`'s rigor)

### 1. Guard test — Success Criterion 3 (new/extended automated test in the regular frontend suite)

Add a new `describe` block (a sibling file, e.g. `src/lib/cssCustomProperties.guard.test.ts`, or a
new top-level `describe` in an existing lint-style test file — executor's choice, not a design
decision) that:

1. Reads every `.css`/`.module.css` file under `frontend/src` (and `.tsx`/`.ts` files, to also
   catch inline-style `var()` usage as seen in `UserOverviewTab.tsx` etc.) via `fs`/`glob`, the
   same way `roleCatalog.accessibility.test.ts` reads `globals.css` directly — **real files, no
   mocking.**
2. Extracts every **defined** custom property name via a declaration-position regex
   (`/(?<![a-zA-Z0-9_-])--[a-zA-Z0-9-]+(?=\s*:)/` at a property-declaration position, not inside a
   `var()` call) across all scanned files (not `globals.css` alone — locally-scoped definitions
   like `.role-catalog-chip { --role-chip-accent: ... }` count as defined).
3. Extracts every **usage** via `/var\(\s*(--[a-zA-Z0-9-]+)\s*(,)?/g`, capturing the token name and
   whether a second (fallback) argument follows the comma.
4. Fails the test — naming the token, file, and line — if any usage (a) references a name absent
   from the defined-set, **and** (b) has no fallback argument. This mirrors the phase's own
   distinction from the corrected table above: a fallback argument (even one that is itself a
   `var()` reference) is only "safe" if it ultimately resolves to a concrete value; the guard test
   additionally re-checks a one-level nested `var()` fallback against the same defined-set (closing
   the `Breadcrumbs.module.css` two-level-dead-reference class of bug for future occurrences, not
   just the one fixed here).
5. Explicitly asserts the known-safe list of **currently remaining** fallback-protected undefined
   tokens (the 18/12/6 = 36 protected occurrences from the corrected table above, plus any other
   pre-existing fallback'd usage not in this phase's 13-token list, e.g. `--group-nav-*`,
   `--breadcrumb-link-color`) is **not** flagged — i.e. the test has a positive case proving
   fallback'd references are treated as legitimate, not just a negative case that dead references
   fail. This directly implements Success Criterion 4 ("sie sind im Guard als zulässig dokumentiert").
6. On a clean tree after this phase's fixes, the failing-usage set must be **exactly empty** —
   this is Success Criterion 1's "Nachweis über denselben Scan."

Template-string constructions (`` `--tag-${item.key}-bg}` ``) do not match the static `var(--name)`
regex and are correctly never flagged — no special-case exclusion needed for `--tag-`.
