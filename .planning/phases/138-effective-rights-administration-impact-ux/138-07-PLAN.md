<objective>
Build CAP-09's backend engine: before a Grant/RevokeCapability role→action change, batch-compute the
effective-rights diff for EVERY current holder of that role, across every group they hold it in — using
138-01's new role-holder query to enumerate "who is affected" and the same pure precedence evaluator
Plan 138-04 already extracted (`Service.loadGroupRightsSources` + `evaluateGroupRights`) to compute
before/after per holder, with zero second engine (D-20, binding). The wire DTO
(`CapabilityOverrideImpactPreview`/`CapabilityOverrideImpactItem`) is already locked in Go/OpenAPI/TS from
Phase 136/137 — this plan is purely the producing endpoint, per 138-RESEARCH.md's explicit finding that
these types exist today with zero producers.

Purpose: closes CAP-09's backend half — "vor einer Rolle-zu-Capability-Änderung sieht der Admin betroffene
Rolleninhaber und die tatsächliche effektive Änderung, einschließlich Benutzer ohne Änderung wegen
weiterer Quellen".
Output: a new batch preview method in the permissions package + a new platform-admin-gated handler/route.
</objective>

<interfaces>
Already-locked, zero-producer DTOs (backend/internal/handlers/capability_policy_contract.go, read
directly this session — do NOT redefine, only produce):
```go
type CapabilityOverrideImpactItem struct {
    TargetUserID int64               `json:"target_user_id"`
    Before       EffectiveRightState `json:"before"`
    After        EffectiveRightState `json:"after"`
}
type CapabilityOverrideImpactPreview struct {
    AffectedUserCount int                            `json:"affected_user_count"`
    Items             []CapabilityOverrideImpactItem `json:"items"`
}
```
Note this shape carries ONE `EffectiveRightState` per side, i.e. it is scoped to exactly ONE action_code
per preview request — matches Grant/RevokeCapability's own one-action-at-a-time mutation shape exactly
(138-RESEARCH.md Open Question 3, resolved: no wrapper/batch-of-actions shape is needed).

From Plan 138-01 (already merged by this wave): `AuthzRepository.ListRoleHolders(ctx, roleCode)
([]repository.RoleHolderEntry, error)` — the enumeration source. Each `RoleHolderEntry` carries
`AppUserID` and `FansubGroupID` — the preview must be computed PER (AppUserID, FansubGroupID) PAIR (the
same user can hold the same role in multiple groups and must get an independent before/after per group,
matching D-11's "rights are structured by group first").

From Plan 138-04 (already merged by this wave): `Service.loadGroupRightsSources(ctx, actor Actor,
fansubGroupID int64) (groupRightsSources, bool, error)` — reuse this EXACT method (do not re-extract it a
second time) to load each holder's current sources, then feed `evaluateGroupRights` twice: once with the
real sources (`before`, single-action projection via
`effectiveRightStateFromCapabilityState(before.Can(permissions.Action(actionCode)))`), once with a
synthetically modified `sources.RoleCapabilities`-equivalent — IMPORTANT DIFFERENCE from Plan 138-04's
role-ASSIGNMENT preview: this preview does NOT add/remove a role from the holder's role list (they already
hold the role); it changes what THAT ROLE GRANTS. `grantingRolesFor`/`roleAllows` (unexported,
`effective_rights.go`) decide role->action grants via the package-level `loadedCache` — to compute "after"
without mutating the real cache, this plan's new file needs a small variant of `evaluateGroupRights` that
accepts one additional "hypothetical grant override" parameter: `hypotheticalRoleCode string,
hypotheticalActionCode Action, hypotheticalAdd bool` — when evaluating `grantingRolesFor` for exactly that
one `(role, action)` pair, force-include (`add=true`) or force-exclude (`add=false`) it in the granting-role
determination regardless of what `roleAllows` currently returns, leaving every other role/action pair
untouched. Implement this as a new unexported sibling function
`evaluateGroupRightsWithHypotheticalGrant(actor, fansubGroupID, sources, actions, hypotheticalRoleCode,
hypotheticalAction, hypotheticalAdd) *GroupRightsResolution` in the SAME new file
(effective_rights_capability_impact_preview.go) that wraps/calls the real `evaluateGroupRights` for every
action EXCEPT the hypothetical one, and computes the hypothetical one's `CapabilityRightState` with the
forced grant — reuse as much of the real precedence switch as possible rather than duplicating it (D-20
still holds: this is a thin, provably-equivalent wrapper, not an independent decision path — document this
equivalence in a code comment referencing effective_rights.go's precedence switch).

Exported entry point:
```go
func (s *Service) PreviewGroupRightsCapabilityChange(ctx context.Context, roleCode string, actionCode Action, add bool, holders []RoleHolderTarget) ([]CapabilityImpactResult, error)
```
where `RoleHolderTarget{AppUserID int64; FansubGroupID int64}` and `CapabilityImpactResult{TargetUserID
int64; Before CapabilityRightState; After CapabilityRightState}` are new small package-local types (the
handler projects these into the wire DTO via the existing `effectiveRightStateFromCapabilityState` helper
— reuse it, do not duplicate the Go-struct-to-wire-DTO mapping).

Handler auth: platform-admin-only (Source B) — this preview sits directly in front of
`AdminCapabilityHandler.GrantCapability`/`RevokeCapability`, which are already `requirePlatformAdminIdentity`-gated; the preview must use the identical gate, never a looser one.

Route: `GET /api/v1/admin/role-capabilities/:roleCode/:actionCode/impact-preview` (mirrors the existing
`/admin/role-capabilities/:roleCode/:actionCode` PUT/DELETE path shape, adds `add=true|false` query param
for which direction is being previewed — Grant vs Revoke).
