`Rolle zuweisen`/`Rolle entfernen` action on one user in one group (the existing, already-live
`PUT /admin/fansubs/:id/app-members/:appUserId/roles` mutation, `AppAuthHandler.SetFansubGroupMemberRole`),

not just one action_code (unlike CAP-09's role→capability preview, which is "one action, many users",

evaluator (`evaluateGroupRights`) the resolver already uses — this plan's only new logic is loading the
current sources once and feeding a synthetically modified role list through the SAME function twice
(current vs. hypothetical), never a second engine.

Purpose: closes D-22/CAP-09's role-assignment half; the mutation endpoint itself (`SetFansubGroupMemberRole`)
already exists and is untouched by this plan — only a new, read-only, no-side-effect preview endpoint is
added ahead of it.
Output: `Service.PreviewGroupRightsWithRoleChange` (new permissions-package method, reusing existing
internals via a small extraction refactor) + a new group-scoped preview handler/route + full contract chain.

}
