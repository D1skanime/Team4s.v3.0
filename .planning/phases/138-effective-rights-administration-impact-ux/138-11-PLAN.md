{total, limit, offset}}>` and `AdminChangeEntry` type (fields: `event_id, actor_app_user_id, event_type,
scope_type, scope_id, target_type, target_id, action, outcome, occurred_at, payload` — `payload` is a raw
JSON value) already exist in `frontend/src/lib/api.ts`/`frontend/src/types/admin-users.ts`.

Real, confirmed `event_type` strings seen this session across handler call sites (do not invent others;
build the translator's map from the actually-observed set and give it a generic, honest fallback for any
`event_type` not explicitly mapped — never throw, never render a blank line): `role_capability.granted`,
`role_capability.revoked`, `effective_rights.override.mutated`, `effective_rights.override.rejected`,
`effective_rights.inspect.denied`, `effective_rights.history.denied`, `effective_rights.override.denied`,
`member_claim.verified`, `member_claim.activated`, plus the generic `*.denied` permission-check pattern
(`auditPermissionDenied`) used across many other handlers.

`translateChangeEntry(entry: AdminChangeEntry): { sentence: string; before?: string; after?: string }` —
pure function. For `role_capability.granted`/`role_capability.revoked`: read `payload.role_code`/
`payload.action_code`, produce "Admin hat der Rolle {role_code} die Berechtigung {action_code}
{gewährt|entzogen}." (no before/after — a role-capability change's payload does not carry a resolved
before/after effective-rights snapshot, so per D-25/R-07 this event type HONESTLY omits Vorher/Nachher
rather than guessing). For `effective_rights.override.mutated`: read `payload.action_code`/`payload.kind`/
`payload.changed`, produce a sentence using the D-25 locked template shape ("Admin hat {Aktion} für
Benutzer {target_id} in Gruppe {scope_id} {gesetzt|entfernt}.") — this event's payload (confirmed by direct
read of the `Write()` call site in `admin_effective_rights_handler.go`) does NOT include a resolved
before/after effective-rights snapshot either (only `action_code`/`kind`/`changed`), so Vorher/Nachher must
ALSO be honestly omitted here, not fabricated from `kind` alone (knowing "a deny was set" does not
honestly tell you what the capability's PRIOR effective state was without a resolver call this pure
function must never make) — record this finding explicitly rather than silently rendering a guessed
Vorher/Nachher pair; this is the concrete, real answer to R-07's open question for these two event types.
For `member_claim.verified`/`member_claim.activated`: simple sentence, no before/after. For every
`*.denied` event_type: "Zugriff verweigert: {action} für {target_type} #{target_id}." For any unmapped
`event_type`: fall back to a generic honest sentence using the raw `event_type`/`action`/`outcome` fields
(mirrors `capabilityCategories.ts`'s `capitalizeFirst` fallback pattern per 138-RESEARCH.md's Don't-Hand-Roll
table) — never throw on an unknown type.

UI-SPEC.md empty-state copy (locked): "Keine Änderungen gefunden." / "Für die gewählten Filter liegen
keine administrativen Änderungen vor. Zeitraum oder Filter anpassen."

D-26 (binding): this page/route renders ONLY administrative changes (audit_logs), never a mixed
"Aktivität" feed — if a future plan ever adds an Aktivität view, it must be a visually and structurally
separate section/route, not interleaved rows in this table. This plan does not build an Aktivität view at
all (out of current scope), so this constraint is satisfied by simple omission — do not add one
speculatively.
