<objective>
Add the one genuinely missing backend query 138-RESEARCH.md (R-03) identifies: "who holds fansub-group
role X, in which group, with what membership status and override presence". This is the data source
for D-07's "Rollen" view ("wer besitzt diese Rolle?") and is reused by later Phase-138 plans
(the Rollen top-level page, and any role-holder enumeration a guided flow needs). Global app roles
(platform_admin/content_admin/user) are explicitly OUT of this endpoint's scope — they already have
a working "who holds this" answer via the existing `/admin/users?role=<code>` filter
(`RoleMasterList.tsx`'s `renderImpactCount`, confirmed live in 138-PATTERNS.md). This plan only closes
the gap for real `role_definitions` fansub-group-context roles (`fansub_lead`, `co_leader`, `encoder`,
etc.), which have no existing "who holds this" answer anywhere in the codebase today.

Purpose: unblock D-07 and give later impact-preview/Rollen-view plans a single, tested, non-N+1 data
source instead of each reinventing the join.
Output: a new repository query, a new platform-admin-gated handler/route, and a frontend consumption
function + type, wired end to end and covered by a real-Postgres test.
</objective>
