`onGrant`/`onRevoke` (props, ultimately `RoleCapabilityClient.tsx`'s `handleGrant`/`handleRevoke`) call
`grantRoleCapability`/`revokeRoleCapability` IMMEDIATELY — this is the exact D-18 violation to fix. Change
`RoleCapabilityDetail.tsx`'s `onCheckedChange` to instead call a NEW prop `onRequestChange(actionCode:
string, add: boolean)` that OPENS the modal (owned by `RoleCapabilityClient.tsx`, passed down) — the
Switch itself still renders `checked={action.granted}` (visual state does not change until the mutation
actually succeeds; do not optimistically flip it), but its `onCheckedChange` no longer calls
`onGrant`/`onRevoke` directly.

From Plan 138-07 (already merged by this wave), new api.ts function this plan adds (does not exist yet —
Plan 138-07 only built the backend endpoint): `export async function getRoleCapabilityImpactPreview(roleCode: string, actionCode: string, add: boolean): Promise<CapabilityOverrideImpactPreview>` — GET
`/api/v1/admin/role-capabilities/${roleCode}/${actionCode}/impact-preview?add=${add}`, `authorizedFetch`
convention (matches the other role-capabilities-section mutation-adjacent functions in this file's 9700s
block, per 138-PATTERNS.md's documented apiClientFetch-vs-authorizedFetch split).

UI-SPEC.md Section F (Impact Preview screen-by-screen, binding contract):
1. Trigger: any capability Switch toggle in the Capabilities split-view detail.
2. `Modal size="lg"`, title "Auswirkungs-Vorschau: {Capability-Label} für {Rolle}".
3. Header counts row (locked D-19 example, exhaustive, Label/Caption typography 12px/700): "{N}
   Rolleninhaber" · "{N} verlieren das Recht" · "{N} gewinnen das Recht" · "{N} behalten es über eine
   andere Rolle" · "{N} behalten es über eine persönliche Abweichung" — compute these 5 counts client-side
   from `CapabilityOverrideImpactPreview.items[]` by comparing each item's `before.allowed`/`after.allowed`
   and inspecting `after.decisive_source` (behalten-über-andere-Rolle = `after.allowed && before.allowed &&
   after.decisive_source === 'group_role'`; behalten-über-persönliche-Abweichung = `after.allowed &&
   before.allowed && (after.decisive_source === 'user_allow')`) — this is pure display arithmetic over
   already-resolved fields, not new precedence logic (D-14 still holds).
4. Expandable detail table (`Accordion` wrapping a `Table`, OR a paginated `Table` directly — this plan's
   discretion per 138-CONTEXT.md §6's open pagination question; RECOMMENDED per 138-RESEARCH.md/UI-SPEC:
   page size 25, sorted with "verliert das Recht" rows first since those are the highest-risk/most-actionable):
   columns exactly `Benutzer | Gruppe | vorher | nachher | Grund` matching the locked D-19 example table —
   "Benutzer"/"Gruppe" need display names, which `CapabilityOverrideImpactItem` does NOT carry (only
   `target_user_id`) — resolve this by also passing Plan 138-01's already-fetched `RoleHolderEntry[]` (the
   SAME holder list the backend preview iterated) into this modal as a prop so the frontend can join
   `target_user_id` -> `{display_name, fansub_group_name}` without a second backend call; `RolesClient.tsx`
   pattern from Plan 138-12 already knows how to call `listRoleHolders` — reuse that same function call
   here (do not add a redundant backend join, join client-side against already-available data).
5. Confirm ("Änderung übernehmen", primary, disabled until preview finishes) / Cancel ("Abbrechen",
   secondary) per the locked Copywriting Contract.
6. Compute failure: locked "Auswirkungs-Vorschau nicht verfügbar" error copy, confirm stays permanently
   disabled for that open (D-18/D-20, blocking).
7. On confirm: call the EXISTING `grantRoleCapability`/`revokeRoleCapability` (Plan 138-02 already extended
   their return type to `RoleCapabilityMutationResult`), then render
   `ActivationStatusIndicator({path: 'role_matrix', cacheReloadSucceeded: result.cache_reload_succeeded})`
   from Plan 138-02 IN PLACE (modal stays open, D-21) — this is the exact honest CAP-10 role-matrix path.
