# Phase 181 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Phasencharakter:** Dies ist eine Konsolidierungsphase, kein Redesign. Die beiden bestehenden
Implementierungen (`EpisodeVersionEditorPage.tsx`, 966 Zeilen / `/me/releases/[versionId]/workspace/page.tsx`,
448 Zeilen) werden zu **einer** rechtebasierten Seite unter `/releases/[versionId]/edit`
zusammengeführt. Dieses Dokument spezifiziert, welches der beiden bestehenden visuellen Muster
gewinnt, wo das bestehende Primitive-System bisher verletzt wurde (handgebaute Tabs/Buttons im
Admin-Editor) und wie das in der Zusammenführung behoben wird — **keine neuen Farben, Typografie-
oder Spacing-Werte werden eingeführt.**

## Typography

Bestehende Projekt-Styles, **keine neuen Größen/Gewichte**:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px (`1rem`) | 400 | 1.55 |
| Label (Eyebrow/Breadcrumb) | 11px | 700, uppercase, `letter-spacing: 0.12em` | 1.2 |
| Heading (Card-/Section-Titel, z. B. „Basisdaten") | 16px (`~0.98rem`) | 700 | 1.3 |
| Display (Seitentitel `h1` in `PageHeader`) | `clamp(2rem, 3vw, 2.75rem)` (32–44px) | 700 | 0.98 |

**Korrektur gegenüber vorheriger Fassung:** Die vorherige Version dieses Dokuments führte für die
Rolle „Heading (Card-/Section-Titel)" das Gewicht 600 — damit drei statt zwei Gewichte in dieser
Phase. Verifiziert gegen die tatsächliche Implementierung
(`frontend/src/components/ui/Card.tsx:28` + `Card.module.css`): `.cardTitle` rendert als `<h3>` und
setzt **kein eigenes** `font-weight` — ohne Override fällt der Browser-Standard für `<h3>` auf
`bold` (= 700). Keine Fundstelle im Projekt belegt 600 für diese konkrete Rolle (die einzigen
600-Treffer im Repo betreffen andere, hier nicht verwendete Elemente wie `Switch`, `HeroMetrics`
oder den alten handgebauten `tabActive`-Stil des Admin-Editors, der in dieser Phase ohnehin durch
die globale `Tabs`-Primitive ersetzt wird). Korrigiert auf 700 — damit führt diese Phase exakt
**zwei** Gewichte: 400 (Body) und 700 (Label/Heading/Display), konsistent mit der übrigen
Primitive-Bibliothek (`Button` 700, `Badge` 700, `Tabs` 700, `FormField`-Label 700,
`AdjacentNavigation` 700).

Fußnote — fixe Primitive-interne Typografie (nicht überschreibbar, unverändert übernehmen):
`Tabs`-Tab-Label 14.4px/700/1.1 (`Tabs.module.css`), `Badge`-Text 12px/700 — beide bereits im
2-Gewichte-Budget enthalten (700), keine zusätzliche dritte Stufe.

## Interaktionskontrakt (phasenspezifisch)

### 1. Tab-Inventar und Sichtbarkeits-Matrix

Einheitliche Tab-IDs über beide Rollen (löst die in `181-CONTEXT.md` D-01 geforderte
Vereinheitlichung der Query-Parameter-Konvention: Admin bisher
`uebersicht/dateien/informationen/segmente/media/changelog/notizen`, Workspace bisher
`metadata/media/segments/notes`):

| Tab-ID (URL `?tab=`) | Label | Sichtbar wenn | Admin-exklusiver Zusatzinhalt im selben Tab |
|---|---|---|---|
| `metadata` | „Basisdaten" | `isPlatformAdmin \|\| canEditMetadata` | Ja — Episoden-Klassifikation (`EpisodeClassificationSection`), Speicherort-Anzeige, Fansub-Gruppen-Zuweisung, Jellyfin-Anreicherungs-Hinweis (`JellyfinEnrichmentNotice`) additiv **innerhalb** derselben `Card`, nicht als eigener Tab |
| `files` | „Dateien" | `isPlatformAdmin` (ausschließlich) | Jellyfin-Ordner-Scan, Datei-Auswahl, Advanced-Mode Media-Provider-Override — heute Platzhalter-Stub, Inhalt bleibt unverändert, nur die Chrome (Tab-Mechanik, Card-Wrapper) wird vereinheitlicht |
| `segments` | „Segmente" | `isPlatformAdmin \|\| canManageSegments` | keiner — `SegmenteTab` ist bereits identisch für beide Rollen |
| `media` | „Bilder & Medien" | `isPlatformAdmin \|\| canUseMedia (can_view_media)` | keiner — `ReleaseVersionMediaSection` ist bereits identisch; Label vereinheitlicht auf die Workspace-Formulierung „Bilder & Medien" (ersetzt Admin-Label „Media / Assets") |
| `changelog` | „Änderungsverlauf" | `isPlatformAdmin` (ausschließlich) | bestehender Platzhalter-Stub bleibt inhaltlich unverändert; Label korrigiert von „Changelog" auf „Änderungsverlauf" (korrekte deutsche Umlaut-Konvention, Pflicht-Constraint) |
| `notes` | „Notizen" | `isPlatformAdmin \|\| (canUseNotes (can_edit_notes) && memberId != null)` | Für `isPlatformAdmin` wird `memberIdFilter` als `null` an `ReleaseVersionNotesTab` übergeben (zeigt alle Notizen statt nur eigene) — bestehendes Komponentenverhalten, keine neue UI nötig |

Die „Übersicht"-Tab aus dem Admin-Editor (Platzhalter, „Eine detaillierte Übersicht wird in einem
späten Plan ergänzt.") entfällt ersatzlos in der Zusammenführung — sie hat laut Inventur keinen
produktiven Inhalt und keinen Einstiegspunkt, der sie referenziert. **Annahme (nicht durch
D-01..D-05 abgedeckt) — zur Bestätigung.**

Für Nicht-Admin-Mitglieder bleiben ausschließlich `metadata`, `segments`, `media`, `notes`
sichtbar, exakt wie heute im Workspace (D-02) — keine ausgegrauten Tabs, kein Hinweis auf
`files`/`changelog`.

### 2. Primitive-Fixes (Pflicht, Teil der Zusammenführung)

Der Admin-Editor verletzt heute das Pflicht-Constraint „globale Primitives" an folgenden Stellen —
die Zusammenführung behebt dies, statt den Code 1:1 zu kopieren:

| Verletzung (Admin-Editor, alt) | Fix (neue Seite) |
|---|---|
| Handgebaute Tab-Buttons (`<button className={styles.tab/tabActive}>`) | Globale `Tabs`-Komponente (`@/components/ui`), `items`-Array aus der Matrix oben |
| Handgebauter Header-Markup (`<nav className={styles.topLinks}>`, `<header className={styles.header}>`) | `PageHeader`-Primitive mit `breadcrumbs`/`eyebrow`/`title`/`description`/`actions`-Props, analog zum heutigen Workspace-Header |
| Submit-Button als rohes `<button className={styles.primaryButton + styles.successButton}>` | `<Button type="submit" variant="success">Basisdaten speichern</Button>` |
| Löschen-Button als rohes `<button className={styles.dangerButton}>` | `<Button variant="danger" onClick={...}>Version löschen</Button>` (Label um Objekt-Nomen ergänzt gegenüber dem bisherigen reinen „Löschen", siehe Copywriting-Contract) — der bestehende `useConfirmDialog`-Fluss (`editor.confirmDialog`) bleibt unverändert, nur der Auslöser-Button wird zur Primitive |

### 3. Header-Kontrakt

Einheitlicher `PageHeader` für beide Rollen, Inhalt je Einstiegskontext:

- **Eyebrow:** „Administrator" (`isPlatformAdmin`) vs. „Release-Projektbereich" (Mitglied,
  unverändert aus Workspace). **Annahme (nicht durch D-01..D-05 abgedeckt) — zur Bestätigung:**
  Admin-Editor nutzte bisher „Admin Editor"/„Contributor Editor" als Eyebrow-Text für dieselbe
  Seite je nach Capability-Lage — das entfällt, weil die Rolle jetzt eindeutig über
  `isPlatformAdmin` vs. Mitglied bestimmt wird, nicht mehr über einen Editor-internen Modus-Namen.
- **Breadcrumbs:** kontextabhängig nach Einstiegspfad (spiegelt D-03s Navigationslogik):
  - Projekt-Kontext (`return_to` passt auf `/me/projects/\d+/group/\d+` oder kein `return_to`,
    aber `animeId`/`episodeId` fehlen): „Meine Projekte / {Anime-Titel} / Episode {N}" — exakt wie
    heutiger Workspace-Breadcrumb.
  - Episoden-/Admin-Kontext (`return_to` passt auf `/admin/fansubs/\d+/edit` oder
    `animeId`+`episodeId` sind als Query vorhanden): „Anime / {Anime-Titel} / Episode {N}" — exakt
    wie heutiger Admin-Breadcrumb.
  - Beide Breadcrumb-Varianten nutzen dieselbe `<nav aria-label="Breadcrumb">`-Struktur, kein neues
    Muster.
- **Title:** Anime-Titel (unverändert aus beiden Vorbildern).
- **Description:** `{Episode-Label} · {Gruppenname(n)} · {Release-Version-Label}` (Workspace-Muster,
  da präziser als Admins reiner `titleMeta`-Span-Anhang).
- **Actions:** „Zurück zum Projekt"/„Zurück"-Button (`Button variant="secondary" leftIcon={ArrowLeft}`)
  mit Ziel aus dem jeweiligen Rückweg (`projectReturnHref` bzw. `backHref`-Logik, unverändert aus
  den jeweiligen Vorbildern je Kontext), plus Badge-Reihe (`capabilities.can_upload_media` →
  `Badge variant="info"` „Medien hochladen", `capabilities.can_edit_notes` → `Badge variant="success"`
  „Notizen", unverändert aus Workspace). „Ungespeicherte Änderungen"-Badge (`Badge variant="warning"`
  oder neutral, aus Admin-Editor übernommen) erscheint nur, wenn die aktive Tab-Formularlogik
  tatsächlich einen Dirty-State führt (heute nur im admin-seitigen Multi-Feld-Formular relevant).

### 3a. Visueller Fokuspunkt (Hierarchie)

Damit die Umsetzung nicht raten muss, welches Element auf `/releases/[versionId]/edit` den Blick
führt:

- **Primärer Blickfang:** der aktive Tab-Inhalt — das `Card`-Panel mit Formular/Liste (z. B. die
  „Basisdaten"-Card). Hier verbringt der Admin die eigentliche Interaktionszeit; dieser Bereich,
  nicht der `PageHeader`, ist der visuelle Fokus der Seite.
- **Sekundärer Ankerpunkt innerhalb des Fokus:** der primäre Submit-Button des aktiven Tabs
  (`--accent-primary`, siehe Color-Kontrakt) — bewusst das **einzige** akzentfarbene Flächenelement
  pro Tab-Ansicht, damit der Blick gezielt zur Speichern-Aktion gezogen wird, ohne mit anderen
  Elementen zu konkurrieren.
- **Kontextrahmen, kein Fokuspunkt:** `PageHeader` (Titel, Breadcrumbs, Eyebrow) sitzt bewusst auf
  der neutralen Secondary-Fläche (`--surface-card`) ohne Akzentfarbe — er orientiert, zieht aber den
  Blick nicht vom Tab-Inhalt ab. Ebenso die `AdjacentNavigation`-Leiste darunter: reine
  Orientierungs-Chrome, keine Akzentfarbe.

### 4. Navigations-Kontrakt (D-03, unverändert in der Fachlogik, hier nur die UI-Seite)

Beide Navigationsmodi bleiben als separate Datenquellen bestehen; die UI zeigt **immer nur eine**
`AdjacentNavigation`-Leiste gemäß Einstiegskontext, kein sichtbarer Umschalter:

- Projekt-Kontext → Datenquelle `getMyProjectDetail(...).release_versions`, Linkziel-Builder
  bleibt `buildWorkspaceHref` (umbenennen auf einen rollenneutralen Namen ist Executor-Entscheidung,
  keine UI-Auswirkung), Label-Format unverändert aus `formatAdjacentReleaseLabel`.
- Episoden-Kontext → Datenquelle `getGroupedEpisodes(animeId)` + `useEpisodeNeighborNavigation`,
  bestehende `EpisodeNavigationControls`-Darstellung wird auf die globale `AdjacentNavigation`-
  Primitive umgestellt (heute nutzt der Admin-Editor eine eigene `EpisodeNavigationControls`-
  Komponente statt der globalen Primitive — **Annahme (nicht durch D-01..D-05 abgedeckt) — zur
  Bestätigung:** `EpisodeNavigationControls` wird durch `AdjacentNavigation` ersetzt, sofern
  funktional äquivalent abbildbar; falls `EpisodeNavigationControls` zusätzliche episodenspezifische
  Zustände transportiert, die `AdjacentNavigation` nicht abdeckt, bleibt die bestehende Komponente
  als begründete Ausnahme erhalten).
- Lade-/Fehlerzustand der Navigationsleiste: bestehender Workspace-Text „Release-Navigation wird
  geladen."/„Release-Navigation konnte nicht geladen werden." (als `role="status"`-Absatz,
  unverändert) gilt für beide Navigationsmodi einheitlich.

### 5. Einstiegspunkte (Linktext-Konsistenz)

Alle 11 externen Einstiegspunkte zeigen künftig direkt auf `/releases/[versionId]/edit` (D-01).
Linktexte bleiben unverändert wie heute an jeder einzelnen Stelle (z. B. „Bearbeiten",
„Release-Medien öffnen", „Release bearbeiten", „Werkzeuge", „Media verwalten", „Notizen & Medien",
„Projekt öffnen", „Arbeitsfläche öffnen") — **keine Vereinheitlichung der Linktexte ist Teil dieser
Phase**, nur das Linkziel ändert sich. Dies ist explizit aus `181-CONTEXT.md` abgeleitet (Zielbild
nennt nur „zeigen direkt auf die neue Zielroute", keine Textänderung).

### 6. Redirect-Seiten (D-01, D-04)

- `/admin/episode-versions/[versionId]/edit` → `/releases/[versionId]/edit` (dauerhaft, Query-Pass-
  through).
- `/me/releases/[versionId]/workspace` → `/releases/[versionId]/edit` (dauerhaft, kein
  Entfernungstermin, D-04).
- Beide Redirects sind serverseitig/routing-seitig ohne sichtbaren Zwischenzustand zu realisieren
  (kein Flash of unstyled/old content). Nur falls technisch ein Client-Redirect nötig wird, siehe
  Copywriting-Contract-Zeile „Redirect-Seiten".
