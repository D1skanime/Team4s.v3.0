## Scope Note (read first)

Of this phase's 8 success criteria, **only Success Criterion 2 is UI-relevant** and this document
covers nothing else, on explicit instruction:

- Criteria 1, 3, 4 (registry self-protection: server-side rejection of removing a baseline action
  from the reserved pseudo-role, the missing `NOT reserved` filter, the single source of truth for
  the 3 baseline action codes) are **backend-only**. No UI-SPEC content for them.
- Criteria 5–8 (replacing source-substring tests with real behavioral tests, the frozen exception
  list, the documented remainder) are **test remediation**, not UI. No UI-SPEC content for them.

**Success Criterion 2 (verbatim, the sole subject of this document):**

> „Die Capability-Matrix weist diese drei Rechte sichtbar als geschützt aus und zeigt bei einem
> Versuch eine sprechende deutsche Meldung mit korrekten Umlauten — kein stiller Fehlschlag und
> kein roher Serverfehler."

This is a small, additive follow-up to `145-UI-SPEC.md` on the exact same component
(`frontend/src/app/admin/roles/RoleCapabilityDetail.tsx`), not a redesign. Phase 145 shipped the 3
baseline actions (`fansub_group.members.view`, `fansub_group_media.view`,
`fansub_group_media.upload`) as ordinary, unprotected `Switch` rows for the reserved pseudo-role
(role code `group_member`, `role_kind: 'reserved_baseline'`) — its own test is explicitly named
"keine Sonderbehandlung" (no special treatment). Phase 146 criterion 1 makes the backend now
**reject removing** one of these 3 actions from that role at the mutation layer. Criterion 2 is
the frontend half of that: make the protection visible at rest, and make a rejected attempt read
as a clear, worded, German explanation — never a raw error, never a silent no-op.

Confirmed dead end, not in scope (same as 145): `/admin/role-capabilities`
(`RoleCapabilityTable.tsx`) is a redirect-only shim to `/admin/roles`. It renders no real UI and
needs no change.

**Chosen interaction shape (decision, not left open):** the 3 rows stay real, interactive
`Switch` controls — they are **not** disabled/locked-out up front. Reasoning:

1. Criterion 2's own wording is "zeigt **bei einem Versuch** eine … Meldung" — it presupposes an
   attempt happens and is then rejected with an explanation, not that the attempt is prevented
   before it can be made.
2. A disabled switch communicates nothing on its own (opacity is not a message) — turning it into
   a real explanation would require inventing a new always-visible tooltip/callout affordance this
   codebase does not have (no `Tooltip` primitive exists under `@/components/ui`, see Design
   System below). Keeping the switch live and reusing the existing
   `RoleCapabilityImpactPreviewModal.tsx` confirm-then-reject round trip needs **zero new
   interaction primitive** — only a persistent protected-state badge at rest, plus the modal's
   already-existing error-message rendering path.
3. Backend rejection is real defense in depth (criterion 1) regardless of what the frontend does
   first; the frontend does not need to duplicate that enforcement to satisfy criterion 2, only to
   make its outcome legible.

So: two things change, both additive on top of Phase 145's exact row layout:

- **At rest:** the 3 rows for the reserved pseudo-role gain a persistent, non-color-only
  "protected" badge next to the (still fully interactive) `Switch`.
- **On a rejected attempt:** the existing `RoleCapabilityImpactPreviewModal.tsx` confirm flow
  (unchanged code path) surfaces the backend's speaking German rejection text through its
  already-existing `mutationError` paragraph — no new UI needed there, only a copy contract for
  the string the backend (criterion 1, out of this document's scope) must return.

**Accessibility (non-color-only) requirement — how this contract satisfies it:** the protected
state is never conveyed by color alone. Each of the 3 rows carries (a) a `Lock` icon shape, (b)
the literal visible text "Geschützt", and (c) a screen-reader-only expanded description wired via
`aria-describedby` on the `Switch` itself (see Copywriting Contract and Interaction Contract
below). Removing all color from the page (e.g. forced-colors mode) still leaves the icon + text
fully legible.

Accent reserved for: role-row selection state and existing primary buttons only, unchanged from
Phase 145 — this phase does not extend accent usage. The protected badge deliberately uses the
existing `info` (not `accent`) semantic slot, keeping the 10% accent budget exactly as Phase 145
locked it.

## Interaction Contract (executor must implement exactly this — not a generic "handle it")

Touches exactly one file: `frontend/src/app/admin/roles/RoleCapabilityDetail.tsx`. No other file
in this UI-SPEC's scope changes.

1. **New imports.** Add `import { Badge } from '@/components/ui/Badge'` and
   `import { Lock } from 'lucide-react'` to `RoleCapabilityDetail.tsx` (both already project
   dependencies, see Design System table — this is the file's first use of either, but neither is
   new to the codebase).

2. **Row rendering — protected badge placement.** Inside the existing action-row `map` (currently:
   label `span` with `flex: 1`, then either the `"Systemaktion"` span for `standalone` actions or
   the `Switch`), when **both** `isReservedBaseline === true` **and**
   `membershipBaselineCodes.has(action.code) === true` for that specific row, render a `Badge`
   between the label span and the `Switch` (the row already has `gap: var(--space-3)` from its
   existing flex container — no new gap value needed):

   ```tsx
   {isReservedBaseline && membershipBaselineCodes.has(action.code) && (
     <Badge variant="info" id={`baseline-protected-${action.code}`}>
       <Lock size={16} aria-hidden="true" />
       {' '}Geschützt
       <span className="visually-hidden">
         {' '}– Teil der Mitgliedschafts-Grundausstattung. Entziehen wird serverseitig abgelehnt,
         da jedes aktive Mitglied dieses Recht automatisch benötigt.
       </span>
     </Badge>
   )}
   ```

   Note: `membershipBaselineCodes` already exists at the top of this file (Phase 145's own
   constant) — reused unchanged, not duplicated. `className="visually-hidden"` is the existing
   global utility class already defined in `frontend/src/styles/globals.css` (confirmed present,
   used bare/unimported project-wide) — not a new CSS module import, not a new class.

3. **`Switch` — `aria-describedby` wiring.** For the same 3 rows, add
   `aria-describedby={`baseline-protected-${action.code}`}` to the existing `Switch` element (its
   `aria-label={action.label_de}` stays unchanged — label names *what* the control is, the new
   `aria-describedby` adds *why it's protected* as an accessible description, read together by
   assistive tech). This is a plain prop addition; `Switch`'s existing `SwitchProps` type already
   accepts arbitrary `ButtonHTMLAttributes` via its `...rest` spread, so no type change to
   `Switch.tsx` is needed.

4. **No change to switch interactivity.** `disabled={!isEditable}` stays exactly as today — the 3
   baseline rows on the reserved pseudo-role remain `isEditable === true` (unchanged from Phase
   145) and therefore remain clickable. Do **not** add a new `disabled` condition tied to
   `isReservedBaseline` or to `membershipBaselineCodes` — see the "Chosen interaction shape"
   decision above.

5. **No change to `onRequestChange`, the accordion, categories, the top caution paragraph
   (lines 163–169 in the current file), or the "other roles" deep-link sentence** (lines
   171–191). All of Phase 145's copy and structure there stays byte-identical — this phase is
   additive only at the per-row level described in steps 2–3.

6. **No change to `RoleCapabilityImpactPreviewModal.tsx`.** Its existing
   `catch (err) { setMutationError(err instanceof ApiError ? err.message : '…') }` block and its
   existing `{mutationError && <p role="alert" style={{ color: 'var(--color-error)' }}>…</p>}`
   render already do exactly what criterion 2 needs, *provided* the backend (criterion 1, out of
   this document's scope) returns the exact rejection copy from the Copywriting Contract above as
   the error body's `message` field for the blocked mutation. This UI-SPEC's job ends at
   documenting that copy contract; wiring the backend response is criterion 1's responsibility.

7. **Test evolution note (informational, not this document's job to write the test):** Phase
   145's `RoleCapabilityDetail.test.tsx` test named *"145-03: rendert für die reservierte
   Pseudo-Rolle alle 3 Grundausstattungs-Aktionen als normale Switch-Zeilen (keine
   Sonderbehandlung) …"* asserted the 3 switches render with **no** special treatment. This phase
   deliberately adds a real, visible special treatment (the protected badge) to those same 3
   rows — that test's title and body will need to change to assert the new badge is present
   (`screen.getAllByRole` for 3 switches, each `aria-checked="true"`, still holds; a new
   assertion for `screen.getAllByText('Geschützt')` having length 3, or equivalent, must be
   added). This is expected and correct per this UI-SPEC, not a conflict — the planner/executor
   should update or replace that test rather than treat its old assertion as a locked contract.
