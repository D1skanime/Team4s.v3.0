# Phase 153 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This UI-SPEC covers only Workstream C (RCA-03, requirements P153-08/09/10) of
153-USER-REQUEST.md — the SSR-visibility and skeleton-timing contract for the public member
profile. Workstreams A (`sizes` attribute fix) and B (import-graph/barrel split) are backend/
technical corrections with no new visual surface and are out of scope for this document. No new
screens, no new visual design, no restyle — this is a **timing and mount contract** for UI that
already exists and is visually approved from prior phases (132/133/150/151).

## Interaction & Visibility Contract (Workstream C) — the actual design contract of this phase

This is the binding contract for `gsd-planner` and `gsd-executor`. It translates
153-USER-REQUEST.md's C1–C6 into concrete, checkable UI states.

### 1. Confirmed defect pattern (do not misdiagnose as a new one)

Three components share one identical, already-identified anti-pattern — verified in source during
this research pass:

| Component | Skeleton element | Gate condition (today) |
|---|---|---|
| `MemberCurrentProjectsSection.tsx:125-127` | `.projectSkeleton[data-visible]` overlay over already-rendered `<ul>` items | `data-visible={interactionEnabled ? 'false' : 'true'}` — tied to `useNearViewportActivation`, i.e. to hydration + IntersectionObserver firing, not to real data-loading state |
| `LatestContributionsSection.tsx:167-170` | `.skeletonLayer[data-visible]` overlay over already-rendered `<ul id={listId}>` items | same pattern |
| `MemberBadgeChain.tsx:210-219` + `.module.css:68-69` | `.carouselSkeleton[data-badge-skeleton]` overlay, hidden via `.carouselShell:has([data-interaction-enabled="true"]) > .carouselSkeleton` | same pattern, applies to every badge group AND the role-progression group |

In all three cases the real, server-rendered markup is already in the initial HTML response
(confirmed: both `.skeletonLayer`/`.projectSkeleton`/`.carouselSkeleton` and the real content
list/carousel are siblings in the same DOM subtree, stacked via CSS `opacity`/`visibility`, not
conditionally mounted). The defect is purely a **CSS-visibility gate wired to a JS-hydration
signal** instead of to a real loading signal. This is exactly what C1/C4 name as the fix target —
confirm this understanding before proposing any change; do not touch `ACTIVATION_ROOT_MARGIN` or
`useNearViewportActivation.ts`'s IntersectionObserver mechanics themselves (C4 forbids rootMargin/
timer tuning as a fix).

### 2. New visibility contract (must-have, C1)

- Content that is present in the initial server-rendered HTML response must be visible to the
  user immediately on first paint. No skeleton, overlay, `opacity: 0`, or `visibility: hidden`
  rule may gate already-rendered real content behind a hydration or IntersectionObserver signal.
- A skeleton overlay is legitimate ONLY when it represents a **genuine** loading state that has no
  content yet to show — i.e., `MemberCurrentProjectsSection`'s pagination continuation fetch
  (`attempt > 0 && state.status === 'loading'`, already exposed via the existing `Button
  loading={isLoading}` prop) or an equivalent real fetch-in-flight state. It must never duplicate
  items that are already rendered as real content on the page.
- `interactionEnabled` from `useNearViewportActivation` remains a legitimate gate for *interactive
  affordances only* — e.g. `Button disabled={!interactionEnabled}` on "Weitere Projekte laden" /
  "Weitere Beiträge anzeigen", and `FocalCarousel`'s pointer/drag/keyboard handlers. Disabling a
  button is not hiding content and stays allowed. What must end is using the same signal to hide
  or visually mask already-present content.
- Visual outcome for the end user: identical card/list/carousel layout, identical German copy,
  identical badge ladder — content simply appears at first paint instead of after a multi-second
  skeleton phase under throttling. This is a timing fix, not a redesign.

### 3. Empty-section server decision (must-have, C2/C5 — WITH the one locked exception)

- Sections with zero content today still mount their full client-side empty-state composition
  and pagination/interaction scaffolding (hooks, IntersectionObserver targets, fetchers) even
  though there is structurally nothing to paginate or activate. `MemberProfileContent` (the
  Server Component composing the page) already does this correctly for the whole
  contributions band (`hasContributions` gate, `MemberProfileContent.tsx:56,150`) — that pattern
  is the template to extend, not invent from scratch.
  - `MemberCurrentProjectsSection`: when `totalCount === 0`, the section must render a plain,
    static `EmptyState` (`"Keine aktuellen Projekte sichtbar."`) without mounting the pagination
    hook chain (`useCancellableSlugState`, `getMemberProjects` fetcher, `Button
    loading/disabled` wiring) — there is nothing to paginate for zero total items.
  - `LatestContributionsSection`: already returns `null` when `allUsableItems.length === 0`
    (`LatestContributionsSection.tsx:160`) — this early-return pattern is correct and must be
    preserved, not weakened.
- **Explicit exception — binding, do not deviate:** `MemberBadgeChain`'s full locked/gesperrte
  badge ladder is **excluded** from this server-decides-empty rule. It stays exactly as visually
  complete as it is today for an empty profile (all badge groups, all locked tiers, the full
  role-progression carousel) — this was a deliberate product decision by the Auftraggeber during
  phase planning (rationale: RCA-03 is a *timing* defect, not a *scope* defect; the locked ladder
  shows new members what is achievable and has real product purpose). Do not propose, suggest,
  or implement any reduction, lazy-mount-as-content-cut, or count-based simplification of
  `MemberBadgeChain`'s rendered badge/family/tier count as part of this phase, even though it
  would technically also reduce the C1 skeleton-overlay defect described in section 1 above. Fix
  `MemberBadgeChain`'s skeleton-visibility timing (section 2) WITHOUT reducing what it renders.
- **Non-goal, must not be treated as a regression by verification:** the report's own measurement
  shows `kara`'s 606 DOM elements only drop to 172 when the badge section is entirely removed
  (REPORT.md RCA-03 A/B test). This phase does **not** target that 172-element number. Whoever
  verifies this phase later (gsd-ui-checker, gsd-ui-auditor, or a human) must not fail Workstream
  C for `kara`'s document-element count staying materially above 172 — that would misapply an
  A/B diagnostic number as a success target the phase never adopted. The only element-count
  claim this phase makes is "fewer initial modules/elements than today's baseline where
  reasonably achievable outside the badge ladder" (P153-08/10), plus faster skeleton clearance
  under identical throttling, per `audit-public-member-visibility.mjs`.

### 4. Interactive islands with real loading boundaries (must-have, C3)

- Replace "one continuous client-side composition, gated by one shared hydration signal" with
  smaller, independently-mounted interactive islands per section
  (`MemberCurrentProjectsSection`, `LatestContributionsSection`, `MemberBadgeChain`'s carousel
  groups) so that a failure or slow load in one section does not visually block another (C6:
  isolate failures per-section).
  - `LoadingState` (`@/components/ui/LoadingState.tsx`) is the only sanctioned genuine-loading
    visual — spinner icon + title + description, `--surface-card`/`--surface-sunken` background,
    already token-compliant. Reuse it for any newly-introduced real Suspense/loading boundary;
    do not build a new spinner component.
  - `ErrorState` (`@/components/ui/ErrorState.tsx`) is the only sanctioned per-section error
    visual — already used by `MemberCurrentProjectsSection`'s pagination failure path. Reuse the
    same primitive for any new per-section error boundary introduced for isolation.
- No new visual component is needed for this requirement — the existing `LoadingState`/
  `ErrorState`/`EmptyState` trio already covers every state this phase can produce. Do not design
  new skeleton shapes; the existing `skeletonCard`/`skeletonCover`/`skeletonTitle` placeholder
  markup in the three CSS modules stays visually as-is and is only reused for the narrowed,
  genuinely-loading case from section 2.

### 5. Explicitly forbidden "fixes" (C4 — do not implement, do not propose)

- Do not change `ACTIVATION_ROOT_MARGIN` (`useNearViewportActivation.ts:3`, currently `'600px
  0px'`) as a way to make skeletons clear "sooner." The report explicitly names this class of
  change a Scheinlösung (fake fix).
  - Do not tune any skeleton animation/transition duration, delay, or debounce value as a
    substitute for the actual visibility-gate rewire in section 2.
  - Do not disable or gate features behind `typeof window === 'undefined'`/no-JS fallbacks as a
    way to make SSR "arrive earlier" — the report explicitly proves this does not work (skeletons
    then never clear at all without JS).
- Any executor deviation from this must be flagged in the plan's `SUMMARY.md`, not silently
  substituted.

### 6. Data, SEO, accessibility invariants (C6, must remain byte-identical)

- `generateMetadata`, structured data, and all `aria-label`/`aria-live`/heading-level contracts in
  the four scoped components stay unchanged. `aria-hidden="true"` on skeleton overlays stays
  correct once those overlays are narrowed to genuine-loading-only use.
- `PreviousContributionsSection` and `FocalCarousel` share the same `useNearViewportActivation`
  hook and the same skeleton-overlay pattern (confirmed via grep during this research pass:
  `PreviousContributionsSection.tsx:64-66`, `FocalCarousel.tsx` gates interaction only, no content
  overlay of its own). Apply the identical section-2 visibility fix there for consistency, even
  though `PreviousContributionsSection` was not named explicitly in the phase's component list —
  leaving it on the old pattern while its sibling `LatestContributionsSection` moves to the new
  one would create the exact "second variant" divergence CLAUDE.md's modularity/no-parallel-
  architecture principle warns against.
- Public group page (`/fansubs/[slug]`): confirmed via grep that no group-page component
  currently imports `useNearViewportActivation` — the skeleton-over-real-content defect pattern in
  section 1 does not exist there today. No group-page component requires this specific fix; do
  not invent group-page changes to "match" this contract. (RCA-03's own measurement already shows
  the group page has no such visibility-switch problem: "Die Gruppenseite zeigt diese
  Sichtbarkeitswechsel bei 26,63 s Load gar nicht.")
