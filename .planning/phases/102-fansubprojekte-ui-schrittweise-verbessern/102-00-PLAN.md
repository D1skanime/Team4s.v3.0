<execution_protocol>
## Required Loop

For each UI slice:

1. **Discuss** - define what feels wrong and what the target should be.
2. **Document** - update this plan/context if the decision becomes durable.
3. **Implement** - change only the selected UI slice.
4. **Test** - run focused tests/typecheck and live-check `http://127.0.0.1:3000`.
5. **Review visually** - use screenshot/browser verification for desktop, tablet, and mobile where relevant.
6. **Proceed** - start the next slice only after user acceptance.
</execution_protocol>

<ui_todos>
## Discussion / Implementation Todos

### 1. Fansub project detail hero on `/anime/[id]/group/[groupId]`
- [ ] Discuss how closely it should match the public Fansub hero.
- [ ] Decide banner placement, panel proportions, stats labels, and mobile stacking.
- [ ] Implement only the hero after discussion.
- [ ] Test desktop/tablet/mobile on `/anime/13/group/1`.

### 2. Public Fansub project URL and navigation
- [x] Discuss public URL direction. Decision: primary public route should be `/fansubs/[fansubSlug]/fansubprojekt/[animeSlug]`, e.g. `/fansubs/c-subs/fansubprojekt/vipers-creed`.
- [x] Discuss current edge navigation mismatch. Decision: `Weitere Projekte von [Fansub]` must navigate to other projects of the same Fansub group, not other groups for the same Anime.
- [x] Discuss control placement. Decision: previous/next controls should dock to the glass project hero card, close to the banner/project name, not to the far page edges.
- [ ] Decide whether no further same-Fansub project hides the edge navigation or shows a return link to the Fansub project overview.
- [ ] Implement route/link/navigation behavior after discussion.
- [ ] Test that `/fansubs/c-subs` jumps to the pretty project URL and that project edge navigation never sends C-Subs users to Honto's same-Anime page as "next project".

### 3. Fansub project story title and reading behavior
- [x] Discuss shape. Decision: this is one project outlook/story text block, not a multi-story archive.
- [x] Discuss behavior. Decision: use the same collapsed/expanded reading pattern as the public Fansub story section when the text is long.
- [x] Discuss scope. Decision: no archive/modal/multiple pages for this section, because a Fansub project has only one outlook/story text.
- [x] Decide final public title. Decision: `Geschichte des Fansub-Projekts`; current `Anime-Ausblicke` wording is rejected.
- [ ] Implement story/outlook section after title decision.
- [ ] Test long text with `alles anzeigen` / `weniger anzeigen` behavior.

### 4. Fansub project members
- [x] Discuss shape. Decision: show members involved in this project after the project text, visually aligned with the public Fansub member section.
- [x] Discuss link target. Decision: do not lock normal member-profile links yet; future target may be a member contribution page with all texts/images by that member.
- [ ] Decide whether links are hidden/disabled in this phase or keep existing profile links as temporary fallback.
- [ ] Implement only after the project text slice is accepted.

### 5. Remove detail navigation/tabs
- [x] Discuss need. Decision: remove the `Geschichte` / `Beteiligte` / `Releases` / `OP/ED/Middle` / `Medien` list because the Fansub project page should follow the public Fansub page's flowing section structure.
- [ ] Remove the section nav during implementation.
- [ ] Test that the page still reads naturally without the jump list.

### 6. Release versions section
- [x] Discuss newest release block. Decision: remove the standalone `Neuestes Release` highlight; it is not needed in the new public Fansub project structure.
- [x] Discuss section title. Decision: title the section `Releases zum Fansub`; `Weitere Releases` is wrong once the newest-release block is removed.
- [x] Discuss public release naming. Decision: public release cards/lists must never show raw Jellyfin/file/import names such as `Vipers Creed. S01E02-CSubs.mkv`; only an explicitly curated release name may appear as the public title.
- [x] Discuss admin field separation. Decision: the edit mask should distinguish episode title, editable curated `Release-Name`, and read-only physical/import release name. The editable `Release-Name` should normally remain empty until intentionally set.
- [x] Discuss reduced member basis data editing. Decision: Fansub members should get a reduced `Basisdaten` area where they can edit only `Release-Name`, `Version`, `Release-Datum`, `Untertitel-Typ`, and `CRC32`; the episode title is visible read-only, all other full admin/technical fields are hidden.
- [x] Discuss rights model. Decision: use the existing global rights/permission system for this reduced Basisdaten access; do not hardcode roles, group IDs, or ad-hoc permission checks.
- [x] Decide the exact neutral public fallback label when no curated release name exists. Decision: use episode title + group label + real mapper/version field, e.g. `Kanonenschuss (Honto) Version 1` / `Kanonenschuss (Honto) Version 2`.
- [x] Discuss version uniqueness. Decision: `Version` must be unique per episode and Fansub group; if episode 1 by group X already has `Version 1`, another release for episode 1 by group X cannot also be `Version 1`. Coop releases apply the uniqueness check to every participating group.
- [ ] Plan API/permission enforcement for reduced member basis data updates so hidden technical fields cannot be changed by crafted requests.
- [ ] Plan backend validation and next-version suggestion/calculation for version uniqueness; UI-only checks are not enough.
- [ ] Discuss release-version display, cooperation visibility, and release cards.
- [ ] Implement only release section changes.
- [ ] Test that cooperation display does not imply wrong ownership.

### 10. Global empty-area summary
- [x] Discuss need. Decision: remove the global message `Weitere Bereiche sind noch nicht öffentlich befüllt: ...`.
- [ ] Remove the empty-area summary during implementation.
- [ ] Test that missing sections are simply absent unless a local section-specific empty state is intentionally kept.

### 7. OP/ED/Middle section
- [ ] Discuss segment grouping and media preview treatment.
- [ ] Implement only segment section changes.
- [ ] Test global and group/member segment examples.

### 8. Medien section
- [ ] Discuss gallery density and lightbox entry points after the recent media modal polish.
- [ ] Implement only media section changes.
- [ ] Test desktop/tablet/mobile lightbox behavior.

### 9. Entry link check from `/fansubs/[slug]`
- [ ] Verify that the project card/link still opens the improved project detail page.
- [ ] Only touch profile project cards if the entry into the project detail page is broken or visually misleading.
