Per CLAUDE.md's Frontend-UI rule, the clickable hero metric renders through the global `Button`
component from `@/components/ui`, not a native `<button>`. `157-PATTERNS.md:355` is explicit: "No
native `<button>`/`<select>`/`<input>` is acceptable per CLAUDE.md's Frontend-UI rule — the existing
`ProjectMemberStickyNav.tsx:27` native `<button>` is grandfathered (predates the rule …) but any NEW
interactive element must go through `Button`." The hero-metric jump button is unambiguously a NEW
interactive element (it does not exist before this plan), so that carve-out excludes it, not includes
it — it must go through `Button`. (The "predates the rule" premise about `ProjectMemberStickyNav.tsx`
also does not hold up historically; moot here regardless, since that file is deleted by this plan.)

`Button`'s existing 6 variants (`primary`/`secondary`/`ghost`/`subtle`/`danger`/`success`) all compose
the same base `.button` chrome in `ui.module.css` (fixed `min-height`, `padding: 0 16px`,
`border-radius`, `border`, `background`, `font-size: 14px; font-weight: 700`), which is genuinely
incompatible with the plain inline `dt`/`dd` metric typography this plan must otherwise leave untouched
on the other 6 `HeroMetrics` call sites. CLAUDE.md forbids using that incompatibility ("the shape
doesn't fit") to justify bypassing the primitive — the correct fix is to extend the primitive
additively, the same discipline this plan already uses for `HeroMetrics` itself: add a 7th `Button`
variant, `variant="text"`, that keeps every one of `Button`'s existing semantics (native `<button>`
element, full props passthrough, keyboard/click handling, the anchor form for `href`) while resetting
only the *visible* chrome to nothing beyond focus/hover. The 6 existing variants keep their exact
current CSS and are provably unaffected — see Task 2's acceptance criteria.

  if (!el) return

  el.scrollIntoView({ behavior: prefersReduced ? 'auto' : 'smooth', block: 'start' })
