<objective>
Close V3 and V4 from `157-UAT.md`'s GAP-02: the contribution timeline's dot is too small, and its line
is a single thin, neutral-gray, always-continuous bar shared by the whole list — independent of role.
Per the operator-approved "Entscheid 2026-09-14 zu V4" (pre-approved, not open for further discussion):
each timeline entry must own its OWN line segment, colored with ITS OWN role, running from that entry
down to the next entry, using the exact same `data-color-key -> --role-accent` seam the dot already
uses. With a single-role member this reads as one continuous colored line; with a multi-role member the
color changes exactly at the entries whose role changes.

Purpose: this is a pure CSS-geometry and color-source change on top of the already-closed GAP-01
structure (plan 157-10) — no markup restructuring, no new attributes, no new color-mapping.
Output: a larger dot, a thicker per-entry-colored line segment, and test coverage proving the DOM
wiring (each entry's own distinct data-color-key) that the CSS depends on, since jsdom does not apply
real stylesheet rules or resolve `::before` computed style — the actual rendered pixel-color
distinctness is proven live via the screenshot script, not fabricated in the unit test.
</objective>

The gap between consecutive entries is fixed at 14px (`.entry + .entry { margin-top: 14px; }`),
unaffected by the `data-compact` padding variant. `--role-accent` already cascades onto BOTH `.entry`
(which carries `data-color-key={colorKey}`, set in ProjectMemberNoteEntry.tsx) and its `::before`
pseudo-element and its `.dot` child — no new attribute or prop is needed to color the line; it is the
exact same custom-property inheritance the dot already relies on (globals.css:271-293).

Geometry design for this plan (derived, not arbitrary — do not deviate from this derivation without
re-deriving it): set the dot's `top` and the line's `top` to the SAME value (so the line starts exactly
at the dot). Then, for every entry except the last, `height: calc(100% + 14px)` makes the line's bottom
edge land exactly at the NEXT entry's own dot position, regardless of `top`'s value (the algebra:
target = ownHeight + gap + nextDotTop; height = target - top = ownHeight + gap + nextDotTop - dotTop =
ownHeight + gap, since dotTop is identical on every entry). For `:last-child`, there is no next entry,
so its line must not reach past its own bottom edge: `height: calc(100% - <dotTop>px)`. No `bottom`
property is set on the new rule at all (this replaces the old top/bottom-pair approach). The
`:first-child::before { top: 50% }` override is removed entirely — it is not needed under this
approach (a line that only extends downward from its own dot naturally does not reach above the first
entry).

jsdom does not process real stylesheet rules and cannot resolve pseudo-element (`::before`) computed
style — confirmed by an empty repo-wide search for `getComputedStyle` in any `*.test.tsx` file. The
existing `P157-13 Nachtrag 2` test (`ProjectMemberNotesSection.test.tsx` lines ~141-179) therefore
already proves role-color distinctness the only way this codebase's Teststil allows in jsdom: by
asserting on the `data-color-key` DOM attribute, not on rendered color. This plan follows the same
discipline for the line.
