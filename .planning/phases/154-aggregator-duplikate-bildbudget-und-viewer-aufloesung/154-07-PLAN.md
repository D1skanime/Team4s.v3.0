    Plan 154-04 changed viewer/owner resolution for the members/[slug] surface: a new slim
    `GET /api/v1/members/:slug/viewer` endpoint (reusing the existing `ResolvePublicMemberAccess`
    resolver) now backs the "Profil bearbeiten" edit link via a new `useMemberViewerAccess` hook,
    while `OwnHiddenProfilePreview.tsx`'s full-profile owner-preview path (`useMemberViewer`, built in
    Phase 128/132) is unchanged. Plan 154-06 confirmed the full regression suite and
    `docker compose build` are green against this change. What has never been confirmed, in this or
    the prior phase, is that a REAL logged-in owner session correctly sees their own hidden
    (private-visibility) profile end-to-end in a browser.
  </what-built>
  <how-to-verify>
    1. Open `http://127.0.0.1:3300` in a browser on the Windows side (the tunnel to the Linux frontend)
       — this is required because `crypto.subtle` needs a Secure Context.
    2. Log in as the app-user who owns a member profile currently set to private/hidden visibility.
    3. Navigate to that member's own public profile URL (`/members/<their-slug>`).
    4. Confirm: (a) the owner sees their OWN full profile content rendered (not a neutral 404/"Profil
       nicht verfügbar" denial that an anonymous viewer would see for a hidden profile), (b) the
       "Profil bearbeiten" edit link is visible (proves `is_owner` resolved `true` via the new slim
       endpoint), (c) no unrelated/incorrect data or login-state is shown.
    5. Optional cross-check: open the SAME profile URL in a private/incognito window with no session —
       confirm it shows the neutral "not available" state, not the owner's content.
  </how-to-verify>
