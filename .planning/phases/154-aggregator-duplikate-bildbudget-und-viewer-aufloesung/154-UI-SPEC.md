### 1. P154-05 — Locked hero-artwork gate for `AnimeProjectAchievementStage`

**Confirmed defect (verified in source during this research pass):** `AnimeProjectAchievementStage.tsx:24-27`
computes `currentCode = family.currentStage?.badge_code ?? null` but never uses it to gate the hero
artwork — it falls straight through to `heroStage = selectedStage ?? family.heroStage`, which
resolves to the first **unearned** stage (`first_contribution`) when a profile has zero projects
(e.g. `kara`). The result: an ungated `AchievementArtwork` renders the not-yet-earned
`first_contribution` motif/frame pair at full 1254×1254 source resolution as the hero.

**Required fix — apply the existing 3-sibling pattern verbatim, do not invent a fourth variant:**

```tsx
// Exact pattern already used by ContributionAchievementStage.tsx:65-81,
// PointsAchievementStage.tsx:50-67, and MembershipStage.tsx:44-58.
// AnimeProjectAchievementStage.tsx's hero span must become:
<span data-anime-project-art={heroStage.badge_code}>
  {currentCode ? (
    descriptor ? (
      <AchievementArtwork
        descriptor={descriptor}
        badgeCode={heroStage.badge_code}
        alt={heroStage.label}
        size="hero"
        className={`${animeProjectStageStyles.animeProjectArtwork} ${chainStyles.animeProjectArtwork}`}
      />
    ) : (
      <presentation.Icon size={96} aria-label={heroStage.label} />
    )
  ) : (
    <LockedStageArtwork hero />
  )}
</span>
```

**Visual outcome at zero-project state (`kara`-equivalent, must-have):**
- The `Card` titled "Anime-Projekte" still renders — the section itself is NOT removed or hidden.
  This is a **hero-slot content swap**, not a section-level empty state.
- Inside the hero slot (`.animeProjectHero`, fixed 192×192px via `AchievementArtwork.module.css`'s
  `.hero` class), the ungated `first_contribution` artwork is replaced by `LockedStageArtwork hero`'s
  existing rendering: a grey circular medal (`--surface-card-muted` fill, `--border-strong` outline,
  `--shadow-sm`), a large low-opacity "?" glyph, a small `Lock` icon badge in the bottom-right corner,
  and the copy "Noch nicht freigeschaltet" beneath it — pixel-identical to what
  `ContributionAchievementStage`/`PointsAchievementStage`/`MembershipStage` already show for their
  own zero-progress states.
- The count ("0 Projekte"), progress bar (0%), and "Noch N Anime-Projekte bis …" copy beneath the
  hero remain exactly as today — only the artwork slot changes, not the surrounding info column.
- The milestone list (`<ol>` beneath the hero) is unaffected: it already correctly renders
  `LockedStageArtwork` (non-hero, small marker variant) for every unearned stage
  (`AnimeProjectAchievementStage.tsx:129`) — this was never the bug; only the single hero slot was
  ungated.
- **Do not** invent a badge/label change for the `Badge variant={presentation.variant}` chip shown
  next to the hero (currently shows the rank derived from `heroStage`) — CONTEXT.md scopes this fix
  to the artwork gate only; a `presentation`/`rank` value change for the zero-project state is out of
  scope unless a plan explicitly finds the current chip also misrepresents "0 earned" (verify against
  sibling components' chip behavior at plan time if this comes up; do not silently change it here).

**Non-goal (do not attempt):** Do not remove, collapse, or lazily-not-mount the "Anime-Projekte"
card itself when a profile has zero projects. Per the phase's own scope fence (P154-05) and the
Phase 153 precedent this UI-SPEC's sibling document already locked for `MemberBadgeChain`'s full
badge ladder, the card and its full milestone track stay visually complete — only the hero
**artwork** is gated, exactly mirroring what the other three families already do for the same
zero-progress case. This is not a reopening of Phase 153's "keep full locked ladder" decision — it is
the same decision now correctly applied to the one family that was missing it.

### 2. P154-06 — Bounded original-image fallback, no layout shift

**Confirmed current behavior (`ResponsiveImage.tsx`, unmodified):**
```tsx
<Image {...props} src={src} alt={alt}
  unoptimized={usingDisplayOriginal}   // on ANY optimizer error, bypasses ALL resizing
  onError={...} />
```
On an optimizer error, `unoptimized` becomes `true` and Next.js serves the literal original file at
full byte size (up to 2.92MB combined for the `kara` `first_contribution` motif+frame pair) with no
resize, no format conversion, no `srcset`.

**"Same geometry" — the exact, binding definition for this phase (do not weaken):**
- Every `ResponsiveImage` consumer already passes fixed numeric `width`/`height` props
  (`AchievementArtwork.tsx`: `width={1254} height={1254}` for every descriptor variant;
  `MemberProfileHero.tsx`: `width={140} height={140}` for the avatar). These numeric props are the
  intrinsic-size contract `next/image` uses to reserve layout space and are **never conditional on
  optimizer success/failure** in the current code.
- The CSS slot wrapping every `ResponsiveImage`/`Image` instance (`.hero { inline-size: 192px;
  block-size: 192px }`, `.stage { inline-size: 64px; block-size: 64px }` in
  `AchievementArtwork.module.css`; `.heroAvatar`'s fixed dimensions in `MemberProfileHero.module.css`)
  is a **separate, CSS-only constraint** that already clips/contains (`object-fit: contain`,
  `overflow: hidden` on `.slot`) whatever pixel dimensions the underlying `<img>` reports, regardless
  of `unoptimized` state.
- **"Same geometry" means:** the bounded fallback must keep both of these unchanged —
  1. `width`/`height` (or `fill`) props passed to `<Image>`/`ResponsiveImage` must stay identical
     between the optimized and the bounded-fallback render paths (no conditional width/height swap
     based on `usingDisplayOriginal`).
  2. The CSS slot class (`.hero`/`.stage`/`.heroAvatar` or equivalent) must stay applied identically
     regardless of fallback state — no new/removed wrapper, no conditional class.
  - What is explicitly ALLOWED to change on fallback: the **requested/served asset itself** (e.g.
    routing through a smaller `/_next/image` derivative width instead of the raw original) — this
    changes byte size and possibly the *decoded pixel dimensions* of the underlying image resource,
    but never the *rendered box* the browser reserves, since `object-fit: contain` inside a
    fixed-size slot already normalizes any source-resolution mismatch without reflow. This is exactly
    how the CURRENT (pre-fix) fallback already avoids layout shift — the fix must preserve, not
    reinvent, this mechanism.
- **Forbidden:** any fallback design that removes or defers setting `width`/`height`/`fill`, that
  swaps the slot's CSS class, that introduces a two-step "load small then relayout to natural size"
  interaction, or that retries indefinitely (no retry loop — B2 requirement, one bounded fallback
  attempt only).

**Byte budget — open question, see below.** This UI-SPEC does not lock a specific KB ceiling (that
crosses into mechanism/infra territory 154-RESEARCH.md flags as MEDIUM confidence and CONTEXT.md
leaves undecided). The VISUAL contract that must hold regardless of the chosen mechanism:

- Whatever bounded derivative/size-limit mechanism is chosen, the rendered result must remain
  visually acceptable inside its fixed slot: no visible pixelation *worse than* what the same-source
  image already shows at its normal optimized size today (i.e., the bound should be at or above the
  size class the image would normally receive at that slot's rendered dimensions — e.g. do not
  serve a 64px derivative into a 192px hero slot when the normal optimized path would have served a
  192-class derivative).
- The fallback must never enlarge the effective transferred payload beyond what today's *normal*
  (non-error) optimized path already transfers for that same slot — i.e., "bounded" means capped at
  roughly the existing normal-case byte budget for that image role, not merely "smaller than the
  unbounded original."

### 3. P154-07 — Animated-avatar budget

**Confirmed root cause:** Next.js's built-in image loader auto-detects animated GIF/APNG/WebP and
bypasses optimization entirely regardless of the requested `w=` — documented, intentional Next.js
behavior, not a bug in this codebase. `MemberProfileHero.tsx:107,175-184` already has a working
"animated avatar gets special handling" branch, but its `isAnimatedAvatar` detection is
extension-based (`.gif` only) and does not catch animated `.webp`.

**Existing precedent, current code (unchanged unless the chosen mechanism edits it):**
```tsx
const isAnimatedAvatar = /\.gif(?:$|\?)/i.test(avatarURL)
...
{avatarURL && isAnimatedAvatar ? (
  <Image src={avatarURL} alt={...} width={140} height={140}
    sizes="(max-width: 760px) 100px, (max-width: 1099px) 120px, 140px"
    loading="eager" unoptimized />
) : avatarURL ? (
  <ResponsiveImage src={avatarURL} alt={...} width={140} height={140}
    sizes="..." loading="eager" />
) : ( ... )}
```

**Visual contract that must hold regardless of the chosen mechanism (mechanism is Claude's
Discretion per CONTEXT.md, open question below):**
- The avatar slot's rendered box stays exactly `140×140` (desktop) / responsive down to `100×120px`
  per the existing `sizes` breakpoints — no geometry change for ANY avatar type (animated or static).
- Whatever budget is chosen (broadened animated-format detection, byte-size cap, frame-reduction/
  poster-frame policy — see Open Questions), the avatar must visually remain recognizable as the
  member's chosen avatar; a policy that silently substitutes a generic placeholder for an animated
  avatar without any visual/copy acknowledgement would be a product regression, not a performance fix
  — if a poster-frame/static-substitute approach is chosen, the static frame must be a real frame
  from the member's own animated source, not a generic placeholder icon.
- The existing GIF branch's user-visible behavior (an eagerly-loaded, unoptimized `<Image>` at fixed
  140×140) must not regress for GIF avatars while WebP animated avatars gain equivalent protection —
  whether via the same branch (broadened detection) or a parallel one, there must be exactly ONE
  animated-avatar code path after the fix, not two divergent ones (mirrors CLAUDE.md's
  no-parallel-architecture principle).

### 4. Explicitly forbidden "fixes" (do not implement, do not propose)

- Do not invent a fourth "achievement stage" locked-artwork variant for P154-05 — reuse
  `LockedStageArtwork` exactly as the three siblings already do.
- Do not attribute the fallback fix to a general PNG-crash narrative (B4) — the report explicitly
  found no crash and no oversized-original-PNG loading in the baseline profiles; frame the fallback
  fix purely as a byte-budget/defense-in-depth improvement for the already-identified optimizer-error
  path.
- Do not build a new backend thumbnail/derivative-generation service for B2 — no such service exists
  for this asset class today (`backend/internal/services/media_service.go` has no resize call), and
  building one is explicitly flagged in 154-RESEARCH.md as a disproportionate new subsystem risking
  the "neue Parallelarchitektur" CLAUDE.md forbids.
- Do not implement a retry loop of any kind for the fallback path (B2 requirement).
- Do not change `AchievementArtwork.module.css`'s `.hero`/`.stage` fixed dimensions or
  `MemberProfileHero.module.css`'s avatar slot dimensions as part of any B2/B3 fix — these are the
  mechanism that already prevents layout shift; changing them would be exactly the "Geometriesprung"
  this phase forbids.

## Open Questions (surfaced, not silently decided — per orchestrator instruction)

These are visual-contract-adjacent but cross into mechanism/infrastructure decisions that
154-RESEARCH.md flags as genuinely undecided (MEDIUM confidence) and 154-CONTEXT.md explicitly
leaves to the planner/executor with a "must be justified" requirement, not a locked choice. The
VISUAL contract above (sections 2 and 3) holds regardless of which mechanism is picked; only the
implementation mechanism is open.

1. **B2 mechanism — what exact bounded-derivative/size-limiting approach replaces the current
   unconditional `unoptimized={true}` fallback?** 154-RESEARCH.md's strongest-evidenced reading is
   routing the fallback through Next.js's own configured `deviceSizes`/`imageSizes` ladder
   (`next.config.mjs`: `[640, 1080, 1480, 1920]` / `[64, 96, 128, 160, 192, 256, 512]`) via the
   same-origin `/_next/image` endpoint at a small fixed width, instead of disabling optimization
   entirely — but this is presented as the strongest available reading, not a locked fact. **This
   UI-SPEC does not decide this for the planner.** Whichever mechanism is chosen must satisfy section
   2's "same geometry" and byte-budget contract above and must be justified in the plan (per B2/B4
   framing: defense-in-depth, not a claimed crash fix).

2. **B3 mechanism — how is the animated-avatar budget technically enforced?** 154-RESEARCH.md lists
   three plausible, un-locked directions: (a) broaden `isAnimatedAvatar` detection beyond file
   extension (requires either a server-reported flag or a client-side WebP RIFF/ANIM-chunk probe),
   (b) a byte-size cap at upload/serving time regardless of animation status, (c) a format/
   frame-reduction policy at upload time (static poster frame plus a separate animated opt-in). Each
   has different backend/upload-pipeline implications beyond pure frontend presentation. **This
   UI-SPEC does not decide this for the planner** — CONTEXT.md explicitly makes this Claude's
   Discretion, requiring only that the chosen path be justified. Whichever mechanism is chosen must
   satisfy section 3's visual contract above (fixed 140×140 slot, no silent placeholder substitution,
   exactly one animated-avatar code path after the fix).

If the planner's chosen mechanism for either open question introduces any NEW user-visible copy,
color, or spacing value not already covered by this document, this UI-SPEC must be updated before
that plan is executed — do not let a mechanism decision silently expand the design contract.
